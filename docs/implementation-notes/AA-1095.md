# AA-1095: Bedrock chat models served from acc1 while acc3 is blocked (Infra side)

Lane l22 of S278. Tech lead decision S278 (12/11/2026): "if acc1 can use every model of the system, use acc1
instead of acc3". acc1 answered a Converse call on all 13 chat models of the gateway through their `global.`
profiles the same day; AWS refuses 7 of them on acc3 at account level (open AWS cases). Root ADR 0001a, Note S278.

## Decisions

- **New minimal root `accounts/acc1-bedrock/`**, modelled on `accounts/acc3-bedrock/` but narrowed: the role
  `AA1-Bedrock-Invoker` and its inline policy only. No Batch role, no Cost Explorer reader, no budget or anomaly
  subscription (see Tradeoffs). The role name is new (`AA1-`, the acc3 pattern), not the retired `AA-Bedrock-Invoker`
  of AA-296, so nothing that guards the retired name has to change.
- **Trust**: the CIS ECS task role `aa-cis-dev-ecs-task-role` (api and worker share it), ExternalId
  `aa1095-satellite-bedrock-acc1` (the value CIS migration 406 writes on the connection row `acc1`). The principal is a
  literal ARN, as on acc3, because `tools/terraform/iam_trust_inventory.py` reads trusts statically; the trust is
  acknowledged in `tools/terraform/iam_trust_allowlist.json`. TripPlanner is not trusted (its gateway calls only the
  `BEDROCK_ACCT_PRIMARY` satellite).
- **Permissions**: `bedrock:InvokeModel` + `bedrock:InvokeModelWithResponseStream` (Converse / ConverseStream authorize
  as these) on the 13 chat models, three ARN forms each (us-west-1 `global.` profile, foundation model in any region,
  region-empty foundation model: the AA-296 IAM note and acc3's `InvokeAvailabilityCandidates` shape), built from one
  `local.chat_models` list. Plus `bedrock:ListFoundationModels` (read only, free) for the CIS lifecycle sync, which
  lists every Bedrock connection.
- **State**: own bucket `aa-cis-tfstate-acc1-bedrock-<acc1 ID>` on acc1, created by three one-line CLI commands in
  `versions.tf` (root ADR 0018 decision 5: one state bucket per account, nothing crossing accounts on the state path;
  acc3 does the same). `allowed_account_ids` from `var.account_id` (ADR 0018 decision 5) refuses a plan against
  any other account. `use_lockfile` (S3 native lock), so `required_version >= 1.10`.
- **Caller side (aa365, CI apply)**: statement `AssumeSatelliteBedrockInvokerAcc1` in
  `accounts/aa365/bedrock_satellite_assume.tf` (in-place update of the inline policy) and env `BEDROCK_ACCT_PAYER`
  (acc1's ID, `local.bedrock_acct_payer`) on the CIS api and worker task definitions (`modules/ecs`
  `bedrock_satellite_env`). The env reaches the tasks on the next CIS Deploy Dev (the deploy copies the latest
  task-definition revision).

- **No acc1 ID or profile name in this repo (review fix pass).** acc1 is a personal account; CONTEXT.md says no new
  account ID goes into this public repo, and root `docs/security/baseline.md` keeps acc1's ID in the public-repo
  pattern. So, the `MGMT_ACCOUNT_ID` pattern: aa365 reads `var.bedrock_acct_payer_id` from the repo secret
  `BEDROCK_ACCT_PAYER_ID` (`TF_VAR_bedrock_acct_payer_id` in terraform-plan / -apply / -drift); unset, the assume
  statement is left out and the task env is empty (the policy is exactly as before). `accounts/acc1-bedrock` takes the
  state bucket and the profile through `-backend-config` at init and `account_id` / `aws_profile` from an untracked
  `terraform.tfvars`; the one-line commands in `versions.tf` read the ID with `aws sts get-caller-identity`.
  Guarded by `tools/terraform/tests/test_aa1095_acc1_no_id.py`.

## Changed

- No guard in this repo refused acc1's ID or the `acc1-bedrock` root (grep of `.github`, `tools`, `scripts`): nothing
  to remove. The tag guard test (`test_tag_guard.py` ROOT_DEFAULTS and the old-spelling scan) and the guard workflow's
  paths now include the new root.
- `CONTEXT.md` / `README.md`: acc1 row and the Bedrock routing paragraph.

## Tradeoffs

- **No spend guard on acc1 in Terraform.** acc3 has a monthly budget and two anomaly subscriptions (cost 0 per its
  file). The issue says paid services on acc1 (budgets, anomaly monitors) need an explicit yes first, and acc1 keeps
  its owner's hand-made budget. The gateway's own cap (connection `acc1` monthly budget, hard stop, alert 80 %) holds
  the spend from the CIS side. Ready to add after a yes: a copy of `accounts/acc3-bedrock/cost_guard.tf` with an
  `aa1-` name.
- **Literal acc2 role ARN in the trust** instead of a variable: the static trust inventory cannot resolve an
  expression and would flag it as a possible cross-account trust.
