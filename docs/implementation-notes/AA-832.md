# AA-832 — Infra: missing RDS alarms, per-role connection metric schedule

CIS side (job kind `ops_rds_role_connections`, `POST /admin/job-runner/rds-role-connections/schedule`)
lives in AA-CIS-App `docs/implementation-notes/AA-832.md`. This file covers the AA-CIS-Infra change only.

## Decisions
- **Worker task role = the shared CIS task role.** `modules/ecs` gives the api and the worker task
  definitions the same `aws_iam_role.ecs_task` (`aa-cis-dev-ecs-task-role`); there is no separate
  worker role. The grant is a new root-level inline policy on `module.ecs.task_role_name` (same
  shape as `ses.tf` / `cost_explorer_satellite_assume.tf`), not an edit of the module's
  `ecs_task_policy`, so the module and its existing `acp` PutMetricData statement stay untouched.
  Condition `StringEquals cloudwatch:namespace = AA/RDS`; Resource `*` (PutMetricData has no ARN).
  The api process gets the same right as a side effect of the shared role.
- **One place for max_connections.** `local.rds_max_connections = 181` (measured `SHOW
  max_connections`, 16/10/2026) in `observability_ecosys.tf`; `rds-connections-high` uses
  `floor(0.6 * 181) = 108`, 5 minutes, per data standard C4.1 "after a resize, 60 % of
  max_connections". A local, not a variable: nothing overrides it per environment, and C4.1b wants
  it changed in the resize PR, next to the alarm.
- **Per-role alarms from a local map** `rds_role_connection_limits = {tripplanner=30, booking=15,
  aa_app_user=15}` (measured `pg_roles.rolconnlimit`). The CIS job discovers roles dynamically, so
  the map only decides which roles get an alarm. Statistic Maximum, period 300,
  `evaluation_periods = 1`: the job samples once per 5 minutes, so one sample above 80 % alarms.
- **Schedule on the existing ops-probe Lambda** (`aws_scheduler_schedule.rds_role_connections`,
  group `aa-cis-dev-acp`, same invoke role), event `{paths: [rds-role-connections/schedule],
  secret_id}`, the AA-825 shape. The path is added to the handler's `_ALLOWED_PATHS` only, not to
  the 06:15 default `_PATHS`.
- **Flexible window OFF, no retries** (`maximum_retry_attempts = 0`, event age 240 s): a flexible
  window would shift samples and leave some 5-minute alarm periods empty; a retry would land on top
  of the next tick. A missed tick is covered 5 minutes later.
- **Alarm actions** are alarm + OK on `aws_sns_topic.alerts`, like the neighbouring RDS alarms;
  every new alarm has `treat_missing_data = "notBreaching"` (C4.1a).

## Tradeoffs
- Missing data is not breaching, so if the schedule, the Lambda or the job stops, the per-role
  alarms sit at OK instead of paging. Accepted to keep the Dev "stopped on purpose" case quiet
  (C4.1a); the job's health is visible on `/admin/job-runner/summary`. A "no data" alarm on the
  custom metric would cost another $0.10 and page every time Dev is scaled to 0.
- 288 invocations/day of the ops-probe Lambda instead of 2. Each one reads the admin secret
  (~$0.04/month) and passes API GW + WAF; cheaper than a new Lambda/role and keeps one pattern.
- Read/Write latency use Average over 15 minutes (C4.1 wording "> 20 ms for 15 min"); p99 would
  need extended statistics and catch single slow bursts that Dev does not need to page on.

## Should know
- Cost: 7 new alarms $0.70 + 6 custom metrics $1.80 + ~8,640 PutMetricData $0.09 + Lambda,
  Secrets Manager, API GW/WAF for ~8,640 invocations ~$0.10 ≈ **$2.70/month**.
- Apply order: the CIS PR (job kind + endpoint) must be deployed before the schedule is applied,
  otherwise the Lambda gets 404 every 5 minutes (logged, not raised). The IAM grant can go first.
- **Deploy guard interaction (CIS side to confirm):** a job enqueued every 5 minutes means
  `shared.job` is rarely empty for long. If the kind is `background=True` and a long background job
  holds `BACKGROUND_MAX_RUNNING = 1`, the sample sits `queued` (no stacking, the endpoint returns
  `already_pending`) and the Deploy Dev guard sees a queued job. The CIS PR should either exclude
  this ops kind from the guard or keep it out of the background lane; otherwise every deploy may
  need a short wait.
- Before the first sample there is no AA/RDS data, so the per-role alarms start in
  INSUFFICIENT_DATA and move to OK with the first datapoint.
- Data standard 03-scaling.md C4.1 "Status" column is stale after this PR (rows say "To build" /
  "Exists as > 70"); that file is in the root repo, not here — update it in the root PR.
- No unit test exists for the handler's `_select_paths` in this repo (nothing under `db/tests`
  covers `lambda_src`); checked by hand with a local import (new path accepted, default list
  unchanged, unknown path refused).
