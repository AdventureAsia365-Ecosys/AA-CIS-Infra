# AA-1171 — Alerts catalogue P0 (Infra part)

Lane l12 of S287. Decisions D1–D11 of the tech lead (S287 decision page, root
`docs/audits/2026-11-21-S287-alerting-inventory/README.md` section 8).

## Decisions

- **Severity rule** (D5): `page` = security, identity, the NAT instance, the database down (RDS instance event rule)
  and the alert path itself (the delivery-failed watchdog); everything else `ticket`, including service down /
  no-healthy-task on Dev (no real users yet). Each tagged block carries a one-line reason next to its tags.
- **Tag sets, not literals**: `local.alert_tags.{page,page_locked,ticket,ticket_locked}` (root) and
  `var.alert_tags` (module). `Mutable = false` for security / identity / break-glass / KMS anomaly, the NAT recover
  alarm (a mute would also stop its recover action), the watchdog and every EventBridge rule.
- **Component**: the existing mandatory key, set per alarm to the component watched (allowed values of the tagging
  standard only). Alarms that had `Component = observability` from `local.ecosys_tags` now say api / db / network /
  worker / web / admin.
- **Page topic** `aa-ecosys-<env>-page-alerts`, no Terraform subscription (D6). Page alarms use
  `local.alert_actions.page` (both topics). Page rules get a second target through one `for_each` resource
  (`aws_cloudwatch_event_target.page`) that copies the input transformer of the rule's alerts target, so the e-mail
  text cannot drift; the module's two CRM KMS rules have `crm_kms_page`.
- **Recipients** (AA-913 flow extended, not duplicated): the CIS task role's subscription grant covers both topics;
  the app chooses the topic per recipient (CIS PR). Publish stays on the alerts topic (in-app checks are ticket).
- **Worker liveness**: CIS worker = AWS/ECS CPUUtilization SampleCount of the worker service, missing data breaching
  (free AWS metric). Booking has no worker service (the worker runs in the API task), so its liveness is a log metric
  filter on the job checks sampler line `ops_metrics_sampled` (started with the worker, every 300 s), missing data
  breaching, 3 windows.
- **API 5xx rate**: the AA-Partner SLO shape (ALB target group 5XX / RequestCount, min requests per window) for CIS and
  Booking, thresholds in `var.api_5xx_rate` (5 %, 20 requests, 2 of 3) — looser than the CRM SLO's 2 % because these
  APIs have no written SLO yet.
- **Catalogue read grant**: `tag:GetResources` and `events:ListRules` on `*` (no resource-level support),
  `cloudwatch:ListTagsForResource` / `events:ListTargetsByRule` / `events:ListTagsForResource` scoped to the account's
  alarms and rules. No Budgets read: budgets come from the Terraform docs output (D7).
- **Management account ID** for the catalogue's static budget rows: env `AWS_MGMT_ACCOUNT_ID` from the existing
  `var.org_management_account_id` (repo secret MGMT_ACCOUNT_ID, already mapped in the three Terraform workflows);
  no new secret, nothing committed.
- **Docs generator**: a Severity column and per-severity totals on `alarms.md`; `aws_mask` masks load balancer /
  target group (and listener) ID suffixes on every generated page; `check-source` also fails an alarm or SNS rule
  without a severity tag set, a page alarm without both topics and a ticket alarm on the page topic.

## Changed

- `tools/terraform/tag_policy.json`: optional keys `Severity` (page|ticket) and `Mutable` (true|false). The root
  tagging standard page is updated in the root PR of this lane.
- Three existing tests asserted `alarm_actions = [aws_sns_topic.alerts.arn]` on page alarms; they now assert
  `local.alert_actions.page`.

## Tradeoffs

- Severity in tags (read live by the CIS catalogue) rather than a registry file: one source, visible in the console,
  re-rated with a one-line PR. The price is a static guard instead of a type check.
- The Booking worker liveness alarm watches the sampler, not the worker loop itself; a hung loop is the in-app
  `jobs_stuck` check. Adding a dedicated heartbeat log line in Booking would be more direct but changes app code for
  a signal the sampler already gives.
- Cost 0.70 USD/month (the Linear estimate said ~0.50: the two rate alarms are metric math over 2 metrics, 0.20 each).

## Should know

  recipients page shows the page topic only once `PAGE_TOPIC_ARN` reaches the task on the next CIS Deploy Dev).
- After apply: `aws sns list-topics` shows the page topic; `aws cloudwatch describe-alarms --alarm-names
  aa-ecosys-dev-alerts-delivery-failed` OK; the CIS worker alarm goes OK within ~5 minutes of the first sample; the
  Booking worker alarm starts INSUFFICIENT_DATA → OK after the first sampler line (or ALARM if the Booking worker is
  off: that is the finding).
- Re-tagging alarms and rules is an in-place update; the plan shows `tags` / `tags_all` changes on ~45 resources,
  `alarm_actions` changes on the page alarms and 13 + 2 new event targets.
