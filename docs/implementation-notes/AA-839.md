# AA-839 — data erasure flags on the CIS task definitions (Infra side)

The CIS `data_erasure` job (AA-CIS-App #946) reads two env vars: `ERASURE_APPLY_ENABLED` (apply runs only for the
string `true`) and `ERASURE_TENANT_RETENTION_DAYS` (days a tenant stays offboarded before an apply; code default
30). Neither was set anywhere. This puts both in Terraform so the Dev erasure drill (root
`docs/legal/dsar-erasure-runbook.md` section 5) can turn the apply on and off with a reviewed change.

## Decisions
- **Same pattern as AA-847 `place_shapes_env`**: module variables `erasure_apply_enabled` (bool, default false) and
  `erasure_tenant_retention_days` (number, default 30, `nullable = false`, whole number >= 0) → `local.erasure_env`
  in `modules/ecs/main.tf`, appended to the `environment` of BOTH the api and the worker container. The api checks
  the flag before it enqueues an apply (403) and the job re-checks flag and retention on the worker, so the two
  must carry the same values.
- **Both vars always emitted** (`"false"`, `"30"`): the values equal the code's behaviour when unset, so the first
  PR changes nothing at runtime, and the admin page shows the real values from the task definition.
- **One drill switch**: `local.erasure_drill` in `accounts/aa365/main.tf` drives both module inputs
  (`false` → `false` / module default 30; `true` → `true` / 0 days). The drill PR and the PR that turns it off are
  each a one-word diff. A workflow input or tfvars toggle was not used: `terraform-apply.yml` applies `main` only,
  so any toggle must be a merged change anyway, and adding an input would change a CI workflow.

## Changed
- `modules/ecs/variables.tf`, `modules/ecs/main.tf` (local + api and worker env), `accounts/aa365/main.tf` (local
  and module inputs).

## Tradeoffs
- Retention 0 during the drill applies to every offboarded tenant on Dev, not only the synthetic one. The apply
  still needs a DRY RUN of that exact tenant, its fingerprint, an approver, a snapshot id and a Cognito admin
  session; the drill window is kept short and the off PR follows the same session.

## Should know
- **How a flag change reaches the running tasks**: the CIS services have `ignore_changes = [task_definition]`.
  Terraform Apply registers a new revision of the `aa-cis-dev-api` and `aa-cis-dev-worker` families (image
  `:latest`, a placeholder the immutable ECR repo does not have) and does not move the services. Nothing changes
  at runtime until **CIS Deploy Dev** runs (`workflow_dispatch` in AA-CIS-App, or the next code merge): it reads
  the family's latest ACTIVE revision (the Terraform one), swaps `containerDefinitions[0].image` for `dev-<sha>`,
  registers that and points each service at it. Never `update-service` onto the Terraform revision itself.
- Expected plan for each of the three changes: `module.ecs.aws_ecs_task_definition.api` and `.worker` replaced
  (2 to add, 2 to destroy), the only difference inside `container_definitions` being the erasure env lines (first
  PR: two added; drill PRs: the two values). No `aws_ecs_service`, image or secret change. Cost 0.
- Check after the deploy: `GET /admin/job-runner/erasure` returns `apply_enabled` and `tenant_retention_days`.
