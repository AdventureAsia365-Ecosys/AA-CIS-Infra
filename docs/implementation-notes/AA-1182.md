# AA-1182 — Terraform state lock and CIS task role least privilege (S296 part)

Scope of this PR: part (2) of the issue (restrict Terraform state access) plus the CIS task role narrowing. The RDS
managed master password (part 4) and the key ceremony (part 5) are later sessions. The rotation of values that the
state held (part 3) is a runbook for the orchestrator, kept outside this public repo (Linear AA-1182).

## Decisions

- **State bucket stays hand-made.** The backend bucket holds this root's own state, so it is never an `aws_s3_bucket`
  here. `accounts/aa365/tfstate_protection.tf` manages what sits on it: versioning and bucket Block Public Access by
  `import` blocks (both were already on, checked live 27/11/2026: versioning Enabled, all four BPA flags, ownership
  BucketOwnerEnforced, SSE-S3, no bucket policy), and a new bucket policy.
- **Lock = same bucket.** The backend uses only the S3 native lockfile (`use_lockfile`, AA-846), so the bucket policy
  covers the lock. The old DynamoDB lock table is unused; deleting it stays a separate clean-up.
- **Who may touch state objects:** the CI plan role, the CI apply role and the MFA admin role, plus the company
  Identity Center permission sets in `var.tfstate_admin_sso_permission_sets` (default `AA-Admin`, for after acc2 joins
  the company organization) and, once `org_access_role_enabled` is true, the organization break-glass role
  `OrganizationAccountAccessRole` (review fix: after the move the company admin arrives through that role, not an
  `AWSReservedSSO_*` role in acc2). Gated on the flag so a reseller-owned role of that name is never trusted early;
  the management README §6 step 2 local apply now also targets `aws_s3_bucket_policy.tfstate`, because a CI apply may
  not write that policy. The TripPlanner artifacts bucket does not list the org role: deploying Lambda code is not its
  job, and that bucket's policy has no deny on policy edits, so an administrator can still repair it. Everyone else gets every S3 action denied except bucket configuration reads
  (`s3:GetBucket*` and the other `Get*Configuration` reads), so Access Analyzer, the compliance collector and
  inventories keep working.
- **Plan role writes only `*.tflock`.** It is assumed from any PR branch; reads stay (plan needs the state).
- **Version deletes and bucket configuration changes: MFA admin only.** The CI apply role can create the policy on the
  first apply (none exists), but any later change to it is a local MFA admin apply, like the other bootstrap objects.
- **No MFA condition key in the policy.** The admin role can only be assumed with MFA (admin_role.tf trust), so naming
  the role is the MFA check; adding `aws:MultiFactorAuthPresent` would add a lock-out path for no gain.
- **TripPlanner artifacts bucket:** TLS only, and writes/deletes/re-tags of objects only by the TripPlanner app deploy
  role, the CI apply role and the MFA admin role. Reads stay open inside the account: the zips are built from the
  public TripPlanner repo, and Terraform refresh, Lambda code updates and the TripPlanner post-deploy verify read them.
- **CIS task role:** the first statement (S3, `GetSecretValue`, SQS, Logs writes, Bedrock invoke on `*`) is replaced by
  named grants (inventory below). The S18/S19 Deny statement and every existing prefix Deny/Allow are unchanged.
- **Named grants are a customer managed policy (review fix).** All inline policies of a role share one 10,240-character
  limit (no whitespace counted). An offline render of the task role's eleven inline policies (live-length placeholders,
  27/11/2026) gave about 10.1k on main and about 12.0k with the named grants inline: the apply would have failed with
  `LimitExceeded` at `PutRolePolicy`, which a plan does not check. The grants moved to `aa-cis-<env>-ecs-task-data-access`
  (`aws_iam_policy` + attachment, about 2.4k of its own 6,144), and the inline policy shrinks by the old `*` statement
  (about 0.3k, to about 9.8k). The apply role has no `iam:CreatePolicy`, so the policy is a bootstrap object (local MFA
  apply, `-target=module.ecs.aws_iam_policy.ecs_task_data_access`); the inline narrowing `depends_on` the attachment,
  so a CI apply that runs first fails on the create and leaves the old grants in place. Guard: the role keeps exactly
  its eleven inline policies, and the managed policy's render stays under a 4,500 budget.
- **Gold bucket: tenant backup prefix only (review fix).** Get/Put on `exports/tenants/*` only; published-tour and
  webhook objects are out of reach. `ListBucket` on gold has no `s3:prefix` condition: S3 answers a GET/HEAD of a
  missing key with 404 only when the caller may list the bucket, and that check carries no prefix, so a condition would
  turn the restore drill's `object_missing` into AccessDenied. A listing returns key names only.
- **Secret allow-list keeps `admin-secret-preview`.** The secret is deleted; the API still asks for it on staff-path
  requests (5-minute failure cache). Keeping the grant keeps the answer ResourceNotFound; an AccessDenied would fire
  the denied-secret-access alarm on every cache miss. Dropping the code path in CIS is a follow-up.
- **Bedrock:** grant per provider (`amazon`, `anthropic`, `cohere`, `meta`, `moonshotai`), foundation models in any
  region (cross-region profiles serve from member regions; global profiles use the region-less ARN) and this
  account's inference profiles `*.<provider>.*`. Not per model: an acc2 model added by a CIS catalog migration of a
  listed provider needs no Infra change; a new provider does.

- **`tripplanner` joins `set-password`.** Rotating the TripPlanner login had no tool (the secret-rotation runbook
  listed it as "plan later"). The runner, the workflow regex and the registry test move together; the role gets the
  `x1:password-set` comment like the others. Booking and `aa_app_user` stay out (their DSNs never sat in state).

## Tradeoffs

- **Customer managed KMS key on the state bucket: not in this PR.** About 1 USD per month (a paid new item needs the
  tech lead's explicit yes) and both CI roles would need `kms:Decrypt` / `kms:GenerateDataKey` on it (lockfile writes
  included); the agent session role denies `kms:Decrypt` everywhere anyway. Follow-up with cost stated.
- **No workload boundary deny on the state bucket.** The bucket policy already denies every principal outside the
  Terraform roles, bounded or not; a boundary edit would add a local bootstrap apply for no extra coverage.
- **Allow-list over prefix for `aa-cis/<env>/`.** A forgotten runtime read fails with AccessDenied (and the
  denied-secret alarm) instead of silently working; the list was built from a code search and the secrets register.
- **Provider-level Bedrock scope.** Narrower per-model ARNs would make every catalog migration an Infra change.

## Should know

- **Apply order:** (1) local MFA admin apply from an up-to-date main checkout of `accounts/aa365`:
  `-target=module.ecs.aws_iam_policy.ecs_task_data_access` (1 to add); (2) the CI apply (dispatch, root aa365): 2
  imports, 1 state bucket policy create, 1 artifacts bucket policy create, 1 policy attachment create and 1 in-place
  update of the CIS task role policy. After that, any edit of `tfstate_protection.tf` or of `ecs_task_data_access`
  must be applied locally with the MFA admin profile (CI gets AccessDenied).
- **Lock-out recovery:** the account root user can always replace or delete a bucket policy. After acc2 joins the
  company organization, centralized root access from the management account does the same (task policy
  `S3UnlockBucketPolicy`).
- **IAM eventual consistency:** verify the task role a few minutes after the apply, several times (lessons, AA-860).
- **Watch after apply:** CloudTrail `AccessDenied` events by the CIS task role (S3, Secrets Manager, Bedrock) for a day;
  any hit is a missing inventory line, fixed by adding it to `modules/ecs`.
