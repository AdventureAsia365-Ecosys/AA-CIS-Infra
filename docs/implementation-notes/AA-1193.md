# AA-1193 — Auto-rollback of the API deploys: the alert grant (AA-CIS-Infra part)

Whole picture: root `docs/implementation-notes/AA-1193.md` (S297, lane l5-rollback; S295 Well-Architected review OPS06).

## Decisions

- `accounts/aa365/cicd_deploy_alerts.tf`: one inline policy per API deploy role (`aa-cis-dev-app-deploy`,
  `aa-booking-dev-app-deploy`, `aa-crm-dev-app-deploy`), `sns:Publish` on `aws_sns_topic.alerts` only. The app
  workflows publish one message per red post-deploy verify (after the rollback attempt).
- Alerts topic, not the page topic: a red Dev deploy is ticket severity (`alert_severity.tf`, D5).
- The topic ARN reaches the workflows from the task definitions' `ALERTS_TOPIC_ARN` (already set by Terraform on the
  three API tasks): no new output, no GitHub variable.
- The rollback itself needs no new grant (describe, list/describe tasks, ECR describe-images, update-service to an
  own-family revision are already granted; the web rollback of AA-1119 uses the same calls).
- One root file instead of three edits: the CIS role is bootstrap (local MFA apply), the other two are module roles;
  keeping them together shows the one purpose and leaves the module untouched. The Booking/CRM role names come from
  the module's role ARN outputs (dependency kept).

## Should know

- Apply: Terraform Apply (CI) applies the Booking and CRM policies; the CIS policy needs the local MFA admin apply
  with `-target=aws_iam_role_policy.cis_app_deploy_publish_alerts` from `accounts/aa365/` (bootstrap role).
- Until applied the app workflows log "alert not sent" as a warning; the deploy-smoke-red issue still opens.
- Cost 0 USD.
