# AA-998 — Remove the acc1 grants from accounts/aa365

acc1 (867490540162, a personal account) leaves the AA ecosystem (S255). LLM runs on acc3 only, acc2
native models stay on acc2, infrastructure is on acc2. Nghiệp accepted losing the cross-account LLM
fallback. Audit: AA-Ecosys `.tmp-session/S255/aa998/audit-code.md` (+ `audit.json`, `deletion-dry-run.md`).

## Decisions

- **This branch removes every acc2-side reference to acc1 that Terraform applies**, and nothing on acc1:
  - `accounts/aa365/bedrock_satellite_assume.tf`: statement `AssumeSatelliteBedrockInvoker` (acc1
    `AA-Bedrock-Invoker`) and `local.bedrock_acct_fallback`. Policy name and address unchanged.
  - `accounts/aa365/cost_explorer_satellite_assume.tf`: statement `AssumeSatelliteCostExplorerReaderAcc1`.
  - `accounts/aa365/tripplanner.tf`: acc1 ARN in `tp_satellite_invoker_arns`; Lambda env
    `BEDROCK_ACCT_FALLBACK` (browse + assembly), `BEDROCK_ROLE_NAME_FALLBACK`, `BEDROCK_EXTERNAL_ID_FALLBACK`
    (assembly).
  - `accounts/aa365/main.tf` + `modules/ecs`: env `BEDROCK_ACCT_FALLBACK` on the CIS api and worker task
    definitions and the `bedrock_acct_fallback` variable.
  - `modules/s3/main.tf`: bronze bucket-policy statements `AllowBedrockBatchCrossAccountAccess` and
    `AllowBedrockBatchListBucket` (principal acc1 `aa-bedrock-batch-inference-role`).
  - `modules/api_gateway/variables.tf`: the default of `acm_cert_arn_us_east1`.
- **ACM default — verified before removing.** The default was `arn:aws:acm:us-west-1:<acc1>:certificate/260ab2f0-…`.
  The only caller (`accounts/aa365/main.tf` `module "api_gateway"`) passes `var.acm_certificate_arn`, which
  `terraform.tfvars` sets to the acc2 certificate; the acc1 inventory (S255) lists **0** ACM certificates on
  acc1. So it was a dead default, not an acc2 dependency: the variable is now required, no plan diff.
- **`accounts/acc1-bedrock/` is NOT deleted here.** Its destroy is a separate human step (MFA, profile
  `pqnghiep-admin`) that must come after this apply (S3 rejects a later `PutBucketPolicy` naming a deleted
  principal, so the bucket-policy statements go first). The root gets a `README.md` "scheduled for destroy".
- `scripts/pre-push.sh`: the "two roots" self-test fixture used `accounts/acc1-bedrock`; it now uses
  `accounts/aa365` + `accounts/acc3-bedrock`, so deleting the acc1 root later does not break the hook test.
- `AWS_ACCOUNT_ALIASES`: only the documented examples change (`docs-gen.yml` comment, `aws_mask.py`
  docstrings). The repo secret value is a human step; recommended to **keep** the acc1 entry until the acc1
  root and every generated page that names it are gone, so old pages stay masked (the parser is generic).

## Changed

- vs. the audit's "Infra PR #2": also removed the `BEDROCK_EXTERNAL_ID_FALLBACK` Lambda env (audit extra),
  and fixed comment-only history in `observability.tf` and `cicd_split.tf`. `tools/docs/gen_docs.py` text
  ("satellite roles in acc1 / acc3") is left for the follow-up PR that deletes the root: changing it here

- Living docs: `README.md`, `CONTEXT.md`, `.claude/CLAUDE.md`, `.github/pull_request_template.md`.

## Tradeoffs

- Removing the env var instead of setting it to `""`: the CIS and TripPlanner code on `main` read it with a
  `""` default, so a missing var behaves exactly like an empty one (acc1 skipped). Either app PR can ship
  before or after this apply.

## Should know

- **Expected `terraform plan` (accounts/aa365): 2 to add, 6 to change, 2 to destroy.**
  In place (6):
  1. `aws_iam_role_policy.ecs_assume_bedrock_invoker` (acc1 statement removed)
  2. `aws_iam_role_policy.ecs_assume_cost_explorer_reader` (acc1 statement removed)
  3. `aws_iam_role_policy.tripplanner_lambda_permissions` (`AssumeSatelliteBedrockInvokers` loses the acc1 ARN)
  4. `aws_lambda_function.tripplanner_browse` (env `BEDROCK_ACCT_FALLBACK` removed)
  5. `aws_lambda_function.tripplanner_assembly` (env: 3 `*_FALLBACK` removed)
  6. `module.s3.aws_s3_bucket_policy.bronze` (2 acc1 statements removed)
  Replaced (2 add + 2 destroy): `module.ecs.aws_ecs_task_definition.api` and `.worker` (env
  `BEDROCK_ACCT_FALLBACK` removed; a task-definition change is a new revision, `-/+`). The services ignore
  `task_definition`, so nothing is redeployed by the apply; the old revisions are deregistered (INACTIVE), the
  running tasks keep running. The `modules/api_gateway` default removal gives no diff. Anything else in the
  plan is drift and must be explained before apply.
- Lesson (S250, AA-835): a Terraform apply that touches the ECS task definitions registers a new ACTIVE
  revision from the template, and CIS deploy-dev copies the latest ACTIVE revision. After the apply, compare
  the env names of the new api/worker revisions with the running ones (runtime-only flags such as
  `S1_WRITER_V2`), and do not apply while `shared.job` has queued/running jobs (DM-11.4).
- Lambda env updates do not change code (`ignore_changes` covers the code attributes).
