# AA-286 — CloudTrail (S102 Phase 3a)

Repo/file: `accounts/aa365/observability.tf`

## Decisions

- Single-region trail (`us-west-1`, `is_multi_region_trail = false`) —
  matches account footprint (everything for account 2 lives in us-west-1).
  This is called out explicitly as an **assumption, not a locked decision**
  per the task — Nghiep should confirm single-region is really sufficient
  before/at apply time.
- `include_global_service_events = true` — kept on even though the trail is
  single-region, so IAM/STS/other global-service events are still captured
  (this account has no other trail, so if this flag were off those events
  would go completely unlogged).
- New dedicated S3 bucket `aa-cis-dev-cloudtrail-logs-005097885195` —
  separate from the medallion (bronze/silver/gold) buckets, matches how
  `modules/s3` already keeps CIS vs. ACP buckets separate by purpose.
- Bucket policy built with `data.aws_iam_policy_document` (2 statements:
  `AWSCloudTrailAclCheck` + `AWSCloudTrailWrite`), scoped via
  `aws:SourceArn` to this specific trail — standard AWS-documented pattern.
- Trail ARN used in the bucket-policy condition is built from `var.aws_region`
  / `var.account_id` / the trail name as a `local`, not
  `aws_cloudtrail.main.arn` — avoids a real dependency cycle (AWS validates
  the bucket policy exists *before* allowing `CreateTrail` to succeed, so the
  bucket policy resource must apply first; if the policy's condition
  referenced the trail resource's own output attribute, Terraform would need
  the trail to exist to compute the policy that must exist before the trail).
  Same pattern the root module already uses in `main.tf` locals to break the
  ECS ↔ Step Functions module cycle.

## Changed vs. original ask

- Lifecycle: Standard → Glacier Deep Archive at 30 days, no expiration — as
  specified. No separate short-term "hot" tier or CloudWatch Logs integration
  was added (task only asked for S3 delivery).

## Tradeoffs

- No CloudWatch Logs group wired to the trail — CloudTrail writes to S3 only.
  If Nghiep wants log-based alerting/metric filters on CloudTrail events
  later (e.g. root login, IAM policy changes), that's separate follow-up
  work (a `cloudwatch_logs_group_arn` + delivery role on the trail).
- `enable_log_file_validation = true` — adds tamper-evidence (digest files)
  at effectively no cost; not explicitly requested but standard practice for
  an audit trail, not scope creep on the resource being created.

## Should know

- Bucket has public access block + SSE (AES256) + lifecycle only — no
  versioning enabled (not requested; CloudTrail always writes new,
  uniquely-named objects rather than overwriting, so versioning wouldn't add
  meaningful protection here).
- `force_destroy` intentionally left at default (`false`, unlike the diagnostic
  buckets in `diagnostics.tf`) — this bucket should not be trivially
  destroyable given it holds the audit trail.
