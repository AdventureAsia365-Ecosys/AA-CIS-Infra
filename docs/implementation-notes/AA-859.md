# AA-859 — Infra notes (tenant pool wave 2)

## Decisions
- **API autoscaling max 10 -> 7** (S240, Nghiệp chose sizing option A). The CIS tenant pool goes to 2 connections per api task; 2 x 7 = 14 <= `aa_app_user` CONNECTION LIMIT 15. Cost: $0.

## Changed
- `modules/ecs/main.tf` `aws_appautoscaling_target.api.max_capacity` = 7.

## Tradeoffs
- Fewer api tasks at the autoscale ceiling (7 x 10 main-pool connections = 70 instead of 100) also lowers the instance worst case (C2.2) from ~201 to ~175 against `max_connections` 181. Throughput ceiling under real load is lower; Dev runs 1 task.
- Alternatives weighed: raise the role limit to 30 + 3/task (needs a bigger RDS instance), RDS Proxy (~$22/month), keep 1/task (503 risk from head-of-line blocking). Plan: root `docs/audits/2026-10-16-S240-aa859/aa859_plan.md` §2.

## Should know
- Apply this BEFORE the CIS PR that raises `TENANT_POOL_MAX_SIZE` to 2 is deployed.

# AA-859 — Infra notes (wave 4: isolation probe after CIS 265 / 266, S247)

## Decisions
- **Tenant column per table, not only `tenant_id`.** `RLS_TABLES_SQL` now returns `tenant_col`: `tenant_id`, else
  `owner_scope` (`TENANT_SCOPE_COLUMNS`, first match wins). `acp_contract.tour_atoms` (266) is judged by
  `owner_scope`: a platform atom is shared only because a pool policy names `'platform'`, a tenant atom must be the
  GUC tenant's.
- **`PARENT_SCOPED` for `acp_shared.quarter_plan_version`** (no tenant column; 265 policy through its plan): a
  visible version is cross-tenant unless the session can see its `quarter_plan` with `tenant_id` = the GUC tenant (or
  a shared constant). The parent read runs as `aa_app_user`, through the plan's own policy, so a leaked foreign
  version has an invisible parent and counts. Before, such a table only had its unset/empty/forged rows checked;
  under a real tenant its `cross` was `None` (not judged).
- **Shared constants restricted to `SHARED_SCOPE_CONSTANTS` = {AA master tenant, `'platform'`}**, `::uuid` or
  `::text` literal (`SCOPE_CONST_RE`). Accepting `::text` alone would have widened the hole the old check already
  had (any uuid constant in a pool policy was accepted as shared); now a policy that names another tenant's id shares
  nothing and its rows stay cross-tenant.

## Changed
- `db/isolation_probe.py`: `TENANT_SCOPE_COLUMNS`, `PARENT_SCOPED`, `SHARED_SCOPE_CONSTANTS`, `PLATFORM_SCOPE`,
  `SCOPE_CONST_RE` (was `UUID_CONST_RE`), pure `matrix_count_sql()` (the count `tenant_matrix` runs), `RLS_TABLES_SQL`
  takes `$2` = the scope columns. No new cell, no new state key: the always-expected cell
  `tenant.aa_app_user_isolation` covers the new tables.
- `db/tests/test_isolation_probe.py`: constants (`::text` master, `owner_scope` platform, another tenant's id
  rejected), `matrix_count_sql`, and `TenantMatrixWave4Test` (a fake pool session with the 265 / 266 row filters):
  live shape passes; the `::text` false positive reproduced with the old regex; t2's rows shared by a `::text`
  constant, a tour_atoms / quarter_plan / quarter_plan_version `USING (true)` leak and platform atoms without
  `atoms_platform_read` all FAIL.

## Tradeoffs
- `angle_gate_option` (241, same parent pattern) is left as it was (unset/empty/forged only) to keep this change to
  the wave-4 tables; adding it is one `PARENT_SCOPED` entry.
- Without the fix the live probe would also have flagged `tour_atoms` (no `tenant_id`: every visible platform atom
  counted as foreign under unset/empty/forged) — a second false positive, not only a gap.

## Should know
- Verified the SQL against a throwaway local PostgreSQL 16.2 (pgserver, scratch only, never Dev) with the exact 265 /
  266 policies: live shape 0 cross rows in every mode; each leak variant above caught. The deparsed quals there match
  `docs/architecture/db-schema-reference.md` (dump after 268) character for character.
- `tour_atoms` (~32k rows) is counted once per mode (3 + number of tenants), each a seq scan inside the 30 s
  statement timeout; the read takes ACCESS SHARE in a rolled-back savepoint like every other matrix read.
