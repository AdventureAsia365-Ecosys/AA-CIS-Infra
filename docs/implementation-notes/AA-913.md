## Decisions

- **One recipient list (D2).** Every alert path already published to `aws_sns_topic.alerts`
  (`aa-cis-dev-acp-alerts`) except AWS Budgets. The CIS api manages the topic's e-mail
  subscriptions; Budgets move onto the topic, so the admin page list covers alarms, security rules,
  cost anomaly and budgets.
- **Budgets: SNS only (D3).** All 4 `notification` blocks (`total_monthly` x2, `per_app_monthly`
  x2 over 4 apps = 10 live notifications) now use `subscriber_sns_topic_arns = [topic]` and drop
  `subscriber_email_addresses`. Keeping both would mail the bootstrap twice and still miss the
  admin-added people. Both budget resources `depends_on` `aws_sns_topic_policy.alerts` (Budgets
  checks the publish right when the SNS subscriber is set).
- **Topic policy statement `AllowBudgets`** (`identity_alerts.tf`): `budgets.amazonaws.com`,
  `SNS:Publish` on the topic, `aws:SourceAccount = account` + `aws:SourceArn ArnLike
  arn:aws:budgets::<account>:*` (AWS guide "Creating an Amazon SNS topic for budget
  notifications"). `__default_statement_ID` untouched (CloudWatch alarms rely on it).
- **Bootstrap stays in Terraform (D4).** `aws_sns_topic_subscription.alerts_email`
  (`var.alert_email`) is the only subscription Terraform manages; the page shows it locked.
  App-created subscriptions are not in state by design: no drift, no plan/page fight.
- **Env, not code (D5).** `ALERTS_TOPIC_ARN` and `ALERT_BOOTSTRAP_EMAIL` are appended to
  `modules/ecs` `local.ops_alert_mail_env`, so the api AND the worker get them (the worker's
  `ops_alert_email` does a best-effort reconcile). Root wiring: `alerts_topic_arn =
  aws_sns_topic.alerts.arn`, `alert_bootstrap_email = var.alert_email` on `module "ecs"`. No cycle:
  the topic does not depend on `module.ecs`. Module defaults are `""` (= page not configured).
- **`ALERT_EMAIL_TO` / `var.cis_ops_alert_email` kept** as the ops-mail fallback; per D6 the CIS job
  always includes it next to the confirmed table rows (deviation from the Linear wording "falls back
  when the table is empty", recorded in the CIS notes too).
- **IAM grant** (`alert_recipients.tf`, inline `aa-cis-dev-ecs-alert-recipients` on the CIS task
  role, attached like `ses.tf` `cis_ecs_task_ses_send`): exactly the 4 Linear actions on this one
  topic. `sns:Subscribe` only with `sns:Protocol = email`. No `sns:Publish`, no
  `SetSubscriptionAttributes`, no account-wide `ListSubscriptions`.

## Changed

- Linear says "falls back to `ALERT_EMAIL_TO` when the table is empty"; the Infra side keeps the
  env exactly as before and adds two vars; the always-include rule (D6) is app behaviour.
- File header comments that said alarms are "e-mailed to var.alert_email" now say "the topic's
  recipients: bootstrap + CIS admin page" (`cost_anomaly.tf`, `alarm_runbooks.tf`,
  `observability_ecosys.tf`). The AA-287 "e-mail chosen over SNS" comment and the AA-828
  "same e-mail" line are rewritten; `var.alert_email` description now says "bootstrap recipient".

## Tradeoffs

- **IAM resource form for Unsubscribe / GetSubscriptionAttributes.** Service Authorization
  Reference (Amazon SNS, read S245): `Subscribe` and `ListSubscriptionsByTopic` require the `topic`
  resource type; `Unsubscribe` and `GetSubscriptionAttributes` list `topic` as **optional**, and the
  API is called with a subscription ARN (`<topic ARN>:<uuid>`), which is not a declared resource
  type. Because the reference does not say the topic is the only authorized form, both
  `<topic ARN>` and `<topic ARN>:*` are kept (spec: drop `:*` only if the topic is the only form).
  Topic names cannot contain `:`, so `:*` matches only subscriptions of this topic. The live check
  (remove a test recipient from the page after apply) settles it; if Unsubscribe works with the
  topic ARN alone, the `:*` form can be dropped in a follow-up.
- **Default topic statement left wide.** `__default_statement_ID` lets any same-account principal
  `SNS:Subscribe` / `ListSubscriptionsByTopic` on the topic. Tightening it is a separate change (risk:
  CloudWatch alarms publish through it); out of scope here, noted in the PR.
- **Budget mail cannot be triggered on demand.** Verify structurally after apply
  (`describe-subscribers-for-notification` shows the SNS subscriber), not with a real crossing.

## Should know

- **Cost: $0/month.** IAM inline policy and a topic policy statement are free; SNS e-mail is free up
  to 1,000 notifications/month ($2 per 100,000 after); Budgets -> SNS adds nothing. No new resource
  with a monthly price.
- **Expected plan:** in-place update of 5 `aws_budgets_budget` (`total_monthly` +
  `per_app_monthly` x4), in-place update of `aws_sns_topic_policy.alerts`, 1 new
  `aws_iam_role_policy.cis_ecs_task_alert_recipients`, 2 new task-definition revisions (api,
  worker; `aws_ecs_task_definition` replace = new revision, services untouched because they ignore
  `task_definition`). Nothing destroyed.
- **CI apply is enough** (no bootstrap / MFA apply): the apply role may `iam:PutRolePolicy` on
  `aa-*-dev-*` roles (`cicd_split.tf` `IAMRoleManageStack`, `local.tf_managed_role_arns` matches
  `aa-cis-dev-ecs-task-role`), has `budgets:ModifyBudget` (`cicd.tf` `BudgetsManage`) and already
  manages the topic policy (AA-854 / AA-896).
- **Env reaches running tasks on the next CIS deploy**, not at apply: `deploy-dev.yml` registers each
  revision from the family's latest (= Terraform's new revision with the two vars).
- **Migration copy** `db/migrations/cis/251_alert_recipient.sql` is NOT in this PR: per the S237 D8
  flow (and spec §6 step 3) it is a separate Infra copy PR, opened after the CIS migration-only PR
  merges, byte-identical to `api/migrations/251_alert_recipient.sql` on CIS `main` (Migration Copy
  Guard fails a copy opened before the owner PR merges).
- **Rollback:** revert this PR -> budgets back to e-mail, `AllowBudgets` and the role policy removed,
  the two env vars gone on the next CIS deploy. Subscriptions the app created stay on the topic until
  removed in the admin page or the console (`aws sns list-subscriptions-by-topic`, then
  `aws sns unsubscribe`).
- **Verify after apply** (orchestrator): `aws budgets describe-notifications-for-budget` +
  `describe-subscribers-for-notification` show the SNS subscriber; `aws iam get-role-policy` on the
  CIS task role; latest api and worker task-def revisions carry `ALERTS_TOPIC_ARN` and
  `ALERT_BOOTSTRAP_EMAIL`; after the CIS deploy, add + remove a test recipient from the page (lesson
  "role applied != role usable").
