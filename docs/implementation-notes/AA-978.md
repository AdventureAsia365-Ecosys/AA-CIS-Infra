# AA-978 (CRM-P1) — M2M scope cis.tenant/read, the /tenant/membership route and the CRM task wiring

Infra slice S1 of AA-978: CIS publishes `tenant.membership.v1` (root contract, ADR 0006b / 0010) and the partner CRM
(AA-Partner) pulls its event feed with an aa-m2m client-credentials token. The CIS producer (migration 276, the
`/tenant/membership/v1` routes) and the CRM consumer (`crm_membership_pull`, migration crm-013) are separate app PRs;
the idle-check exemption of `crm_membership_pull` is a separate registry branch (`db/owners.yaml`, see below). Session
S250, agent Claude Code.

## Decisions

- **Resource server `cis.tenant` with one scope `read`** in `identity_m2m.tf`, the same shape as AA-976's `cis.catalog`:
  identifier and scope description in locals, a `dynamic "scope"` block, output `identity_m2m_tenant_scopes`.
- **The existing CRM client `aa-m2m-dev-crm` gets `cis.tenant/read`** next to its booking.b2b and cis.catalog scopes. No
  new client: one app client per calling service (ADR 0006b decision 7), and each receiver checks only its own scope
  per route, so the new scope grants nothing on Booking or on `/catalog`.
- **API Gateway route `/tenant/membership/{membership_proxy+}`** (`modules/api_gateway/main.tf`). The CIS REST API is
  not a greedy proxy: every top-level prefix is its own resource (the live API has `/admin`, `/auth`, `/catalog`,
  `/content`, `/docs`, `/health`, `/v1` and no `/tenant`, checked read-only on 24/10). Without this route the CRM's
  calls to `https://api-cis.lumiguides.it.com/tenant/membership/v1/...` would get API Gateway's 403 "Missing
  Authentication Token". Only the `membership` subtree is routed, not `/tenant/*`, so no other future `/tenant` path
  of CIS reaches the public edge by accident. NONE at the gateway, HTTP_PROXY over the VPC link (the ALB default
  action forwards to the CIS api target group; no ALB rule matches `/tenant`). The integration, its URI and the
  method's authorization are in the deployment `depends_on` and the redeploy trigger (AA-432 / AA-583 trap).
- **`CIS_API_URL` from a variable** `crm_cis_api_url` (default `https://api-cis.lumiguides.it.com`, the live custom
  domain), like `dfs_balance_api_base_url`. `var.domain_name` is the account's other hostname
  (`api-cis-aa365.`), which is why it is not reused. A validation keeps it an https origin with no path or trailing
  slash (the app appends `/tenant/membership/v1`).
- **`M2M_CLIENT` = the whole secret JSON** (`{client_id, client_secret, token_url, scopes}`), not one JSON key per env
  var: the plan's S5 parses that JSON in `app/cis/m2m.py`, and one `valueFrom` keeps the execution-role grant to one
  ARN. Wired unconditionally (no `crm_*_enabled` flag like Sentry): the secret already holds a value on Dev since
  AA-972 (`describe-secret` shows an AWSCURRENT version), and the app treats an empty value as not configured.
- **Execution role grant on exactly that secret ARN** (`ReadCrmSecrets`), no `aa-crm/*` wildcard. The workload
  boundary allows it (`AllowWithinIdentityPolicy`); the secret has no resource policy.

## Changed (vs. the plan)

- **Added the API Gateway route.** The plan assumed the CIS REST API was a greedy proxy "as /catalog/v1 already
  proves"; `/catalog` is its own resource (AA-976 added it), so `/tenant/membership` needs one too.
- **`db/owners.yaml` is not in this branch.** The plan put the `crm_membership_pull` idle exemption here. The schedule
  says one Infra registry PR at a time and round 1's `chore/aa-835-copy-bk023` (which waits for the Booking bk-023
  PR) also edits `owners.yaml`. Stacking this Terraform PR on that copy branch would hold the M2M scope behind an
  unrelated Booking merge, so the registry change is its own branch `chore/aa-978-membership-pull-exempt`, stacked
  on `chore/aa-835-copy-bk023`.
- **No migration copies here.** CIS 276 and crm-013 (renumbered from 275 / crm-012 by the S250 schedule) get their own
  copy PRs after the app PRs merge (Copy Guard compares with app main).

## Tradeoffs

- **Narrow route vs. `/tenant/{tenant_proxy+}`.** The narrow one costs two extra resources and a later Infra PR if CIS
  adds another public `/tenant/...` contract; in exchange the edge exposes only what a contract serves.
- **Unconditional secret wiring vs. a flag.** A future environment whose `aa-crm/<env>/m2m-booking-client` has no
  value yet would fail to start the CRM task. Accepted for Dev (the value exists); a staging/prod stack must write
  the value before the first CRM deploy, as it must for the DSN secret.

## Follow-up S251: feed alarms (`accounts/aa365/crm_membership_alarms.tf`)

- **Decisions.** Two log metric filters on the CRM log group (`aws_cloudwatch_log_group.crm_api`, api + crm.job
  worker in one task) and two alarms, the `tenant_pool_alarms.tf` shape (Sum > 0 over 5 min, missing data = OK, SNS
  `alerts` on ALARM and OK): `crm_membership_feed_stuck` (runbook `queue_stuck`) and
  `crm_membership_event_apply_refused` (runbook `incident`). Namespace `AA/Crm/Membership` (the `AA/Crm/*` family of
  the KMS decrypt filter). The pattern is a quoted term: the CRM logs JSON lines whose `event` is the formatted message
  (`crm_membership_feed_stuck error=<class> failures=<n>`), so a term match is enough and survives field changes.
- **Tradeoffs.** No alarm on a feed that is merely `stale` (worker not running): the CRM's own health alarms
  (`crm_no_healthy_task`) and the job summary cover a stopped worker; `stale` shows on `/crm/health/ready` and, from
  crm.ops.v1 1.2, on the L1 agency summary (`membership_feed_state`, `membership_feed_lag_s`).
- **Should know.** Cost: 2 alarms x $0.10 = **$0.20/month**; the filters are free, the custom metrics bill only in
  hours with a matching line. Renaming either log line in AA-Partner (`app/cis/membership_feed.py`) disables its
  alarm silently. Validated locally with `terraform validate` (providers from the main checkout's cache) and
  `tools/docs/gen_docs.py check-source accounts modules`; needs a plan + apply by the orchestrator.
