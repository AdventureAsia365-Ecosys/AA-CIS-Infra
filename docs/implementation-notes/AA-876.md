# AA-876 — API edge hardening (AA-CIS-Infra part)

Scope here: throttling on the CIS REST API stage (WAF deferred per S241). The login throttle per IP / per user,
CORS and headers are in the app repos; the Booking stage already had `booking_throttle` 20/40.

## Decisions

- **Measured first** (Logs Insights on the CIS execution log group, 14 days to 21/10/2026, one line per request =
  `HTTP Method: ..., Resource Path: ...`; the plan's `Method request path: {auth_proxy=...}` marker matches
  nothing in this log format):
  - whole stage, busiest second: 101 (09/10 14:28, almost all `/content/photos/*`); next 42
  - `/content/*`: 100, then 42, 36
  - `/auth/*` all routes: 20 (verify routes)
  - `/auth/admin-login` + `/auth/tenant-login`: 6 per second (several seconds on 13/10), 13 per minute max;
    1,047 logins in 14 days
- **Stage default `*/*` 50 rps / burst 100**, applied per method. Fits every method's peak except `/content`.
- **Login override 20 / 40** on the two explicit login methods: the plan's rule is max(10, 3 x peak) = 18, rounded
  to 20, burst 2x. The real brute-force defence is the app's per-IP failure limit and per-(user, IP) backoff; this
  is the global ceiling.
- **`/content` override 300 / 600** (3x its 100/s peak): TripPlanner list pages load cover images from
  `/content/photos/...` with plain `<img>`, so the stage default could 429 images for a few concurrent visitors.
- **Explicit `/auth/admin-login` and `/auth/tenant-login` resources (POST, HTTP_PROXY over the VPC link)** instead
  of throttling `auth/{auth_proxy+}/ANY`: a method bucket is shared by every caller, so a tight cap on the proxy
  would also cover verify-admin / verify-tenant / booking-token, which the BFFs call on navigation — one client at
  ~10 rps could cut every session off, and with no WAF there is no per-IP rule to stop it.
- **Deployment trigger + depends_on** include the new integrations and methods (the AA-432/AA-465/AA-583 trap).
- **`diagnostic_logging` (count) → `stage_defaults` (always)** with a `moved` block from `[0]`; logging stays
  `INFO` + metrics on when `enable_execution_logging` (true on aa365), `OFF` otherwise.
- **Detailed metrics off on the login overrides** (would be ~5 new custom metrics per method, ~3 USD/month). The
  `/content` override keeps the same metrics flag as the stage default (that method already has them, no new cost).
- Overrides `depends_on` the stage default and each other: method settings are patches on one stage document.

## Changed

- `modules/api_gateway/main.tf`: `aws_api_gateway_resource|method|integration.login` (for_each over
  `admin-login`, `tenant-login`), deployment `depends_on` + `triggers`, `stage_defaults` + `moved`,
  `login_throttle` (for_each), `content_throttle` (count, only when `content_throttle_rate_limit` is set).
- `modules/api_gateway/variables.tf`: 6 variables. `accounts/aa365/main.tf`: values passed explicitly.
- `accounts/aa365/variables.tf`: WAF deferral comment. `CONTEXT.md`: CIS REST API throttling bullet.

## Tradeoffs

- The login cap is global (all callers share it): an attacker at ~20 rps can delay legacy password / API-key logins
  for everyone, but not session verification, `/content`, `/v1` or Cognito sign-in.
- Any non-POST method on the two login paths now gets API Gateway's 403 instead of FastAPI's 405. Nothing sends
  one (no CORS preflight: the API has no CORS on Dev since AA-876).
- WAF stays off (S241). Reusing the existing ALB web ACL on the stages would cost ~0.60 USD per million requests
  inspected (no new ACL or rule fee), not the ~7 USD quoted in S241. Blockers found on main today: the CI role
  already has `apigateway:SetWebACL`, and the WAF log already redacts `authorization`, `x-admin-secret`,
  `x-api-key`, `cookie` (AA-806); only the Booking geo allow-list decision remains.
