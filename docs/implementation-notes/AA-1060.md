# AA-1060: permanent WordPress test site as a sidecar of an existing ECS task (S274)

Linear AA-1060. Tech lead approved the design and the $0 cost on 09/11/2026 (S274). Design and cost:
`modules/environment/test_wp.tf` header; edge: `accounts/aa365/test_wp_edge.tf`.

## Decisions

- **Host task: the Booking admin (`aa-booking-dev-admin`), not the TripPlanner web.** Both task definitions are owned
  by Terraform and both app deploys copy the family's latest revision and swap only the image of the container they
  name. The Booking admin sits behind the ALB's HTTPS listener with the `*.<zone>` wildcard certificate, so the test
  host needs one host rule, one target group and one CNAME. The TripPlanner web is reached only through its own
  CloudFront distribution and origin-secret host rules on :80 (a new host there means a distribution or alias, a
  us-east-1 certificate and web ACL work). Headroom: Booking admin 512 MB, max ~14 % used over 3 days.
- **Secret: the whole existing test secret `aa-cis/<env>/e2e-wordpress-test`** (JSON `site_url`, `app_user`,
  `app_password`, the shape the agent E2E checks already read), not a new secret (0.40 USD/month) and not an SSM
  parameter (the CI apply role has no `ssm:PutParameter`; adding it is a bootstrap change). Referenced without a
  JSON key: a missing key never stops the Booking admin task from starting (the script logs it and leaves the REST
  sign-in off). Only the secret's metadata is read by Terraform (data source).
- **Health check on a static file (`/license.txt`)**, present in the fallback root and in WordPress. ECS replaces a
  task whose target is unhealthy in ANY of its target groups; a `/wp-json/` check would restart the Booking admin on
  a WordPress fault. The site itself is checked by the live steps.
- **Apache first, set-up in the background, WordPress switched in last.** The document root is a symlink
  (`/var/www/site`) that points at a static fallback until the set-up has installed the site and set the users. The
  health file answers within seconds of the container start (no network on the critical path), and the WordPress
  installer is never served. A failed set-up (download, checksum, wp-cli) keeps the fallback and logs the reason.
- **Two switches, two applies.** `test_wp_enabled` (container, target group, rules, DNS, SG port) and
  `test_wp_service_attached` (the service's second `load_balancer` block). ECS rejects a load balancer that names a
  container the service's current task definition lacks; the service ignores `task_definition`, so the container
  reaches the service only through a Booking admin deploy. Step 2 is a one-line follow-up PR (prepared on branch
  `feat/aa-1060-test-wp-attach`).
- **Publishing user is an editor** (posts, trash, restore; the CIS publisher uses `/wp/v2/posts`, `/users/me`). The
  install admin `site-admin` and the publishing user get random passwords at every start that nobody keeps.
- **Application password hash** = `WP_Application_Passwords::hash_password()` (WordPress 6.8+, `wp_fast_hash`), else
  `wp_hash_password()`; checked by the image's WordPress 7.1.4 source (`check_password()` reads both). The helper
  self-checks through `wp_authenticate_application_password()` and the script calls `/wp-json/wp/v2/users/me` through
  apache with the password on stdin.
- **No restart policy on the sidecar.** The provider compares container definitions after a read; an
  `ignoredExitCodes: []` read back would give a new revision on every plan. A stopped sidecar fails its target group
  and ECS replaces the task, which re-creates the site.

## Changed (vs the Linear scope)

- "Start script re-installs the site and sets a fixed Application Password from Secrets Manager": the fixed value is
  the `app_password` of the existing test secret; the orchestrator rewrites that secret for the new site
  (`site_url` = `https://test-wp.lumiguides.it.com`, a new 24-character `app_password`) before the first deploy.
- Extra hardening not in the issue: ALB 403 on `/wp-login.php`, `/wp-admin`, `/wp-admin/*`, `/xmlrpc.php`
  (rule `test_wp_block`, above the forward rule), mu-plugin refusing `login_init` and XML-RPC, `X-Robots-Tag`,
  `DISABLE_WP_CRON`, `AUTOMATIC_UPDATER_DISABLED`, the secret unset before apache starts.

## Tradeoffs

- **Downloads at every start** (SQLite plugin from downloads.wordpress.org, wp-cli from GitHub releases, via the
  NAT instance) instead of a custom image: no new ECR repository or build pipeline, $0. If wordpress.org rebuilds the
  zip of a published version the checksum fails and the site stays on the fallback until the pin is bumped.
- **Ephemeral data**: every new Booking admin task (deploy, Spot interruption) re-creates an empty site. The CIS
  retire -> restore check creates its own post each run, so it does not depend on old posts.
- **Shared fate both ways, bounded**: the sidecar cannot take the admin down through memory (hard cap 256 MB) or a
  setup failure (static health), but an apache crash in the sidecar makes ECS replace the whole task (a short
  Booking admin restart on Dev).
- **Reusing the test-only secret instead of a new one** keeps the cost at $0; the access trade-off is recorded in
  Linear AA-1060, and the root secrets register row lists the new consumer.

## Should know

- The script is not executed locally (no PHP or Docker on the agent host; the auto-mode classifier refused running a
  downloaded static PHP). It was checked against the WordPress 7.1.4 sources, the docker-library entrypoint and
  wp-config template, and the plugin's `db.copy`; `bash -n` and the offline guards run in CI
  (`tools/terraform/tests/test_aa1060_test_wp.py`). The live steps are the real test.
- The Booking admin deploy (`AA-Booking` `deploy-admin-dev.yml`) refused any task definition with more than one
  container; the same wave relaxes that guard to "the named container is present". Merge it before the first
  Booking admin deploy after this apply.
- The CIS admin task, the CIS and TripPlanner deploys are untouched.
