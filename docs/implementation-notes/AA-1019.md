# AA-1019 — CRM staff console: crm-staff client, web task values, Dev E2E staff user

The AA-Partner staff console (S-02 ops releases, S-04 support / break-glass sessions) lives at `/staff` of the CRM
web on the agency host and signs in with the WORKFORCE `crm-staff` client (root ADR 0006b decision 6). App side:
AA-Partner `docs/implementation-notes/AA-1019.md`. Identity exception: root ADR 0006a A10c.

## Decisions

- **crm-staff URLs on `portal.`** (`identity_variables.tf`): `/staff/auth/callback` and `/staff/signed-out`. The old
  `partner-dev.` URLs could never work since AA-979 (that host answers 301 to `portal.`, and the sign-in attempt
  cookie is host-only). localhost:3005 kept for local development.
- **Web task values** (`crm_web.tf`): `STAFF_COGNITO_DOMAIN` (the WORKFORCE managed login, same expression as the
  `identity_managed_login_base_urls.workforce` output) and `STAFF_COGNITO_CLIENT_ID`; two more keys of the existing
  secret `crm/dev/web`: `staff_cognito_client_secret`, `staff_session_secret`. No new secret, no new paid service.
- **A separate staff cookie key** rather than reusing `session_secret`: the agency key is also mapped into the Content
  studio (AA-979), so a staff cookie sealed with it could be opened there. The portal's execution role can still read
  the whole JSON (IAM cannot scope a key, see the secrets register), but its task only receives `session_secret`.
- **A10c E2E staff user**: one more entry in the Dev-only trigger map (`workforce.py E2E_DEV_ONLY_TEST_STAFF`), groups
  exactly `crm-ops` + `crm-support`; its codes go to the A10b rule / prefix (`inbound-admin/`, MFA admin only), never to
  the CI-readable `inbound/`. Created by `crm_dev_identity.py e2e-staff` (SUPPRESS, no password), not the CIS directory
  (same as A10a's Booking user).

## Changed

- `crm_dev_identity.py web-secret` now keeps every key it does not own (before, it rewrote the JSON with its two keys,
  which would have dropped the staff keys).

## Tradeoffs

- The new keys are mapped unconditionally (no feature flag): the running service ignores task definition changes, so
  the apply alone is harmless; the next web deploy needs the keys. The runbook writes them first.

## Should know

- Order: merge → `staff-web-secret --apply` → Terraform Apply → `e2e-staff --apply` → AA-Partner PR (its web verify
  requires `staff_auth_configured`). Runbook: `tools/identity/README.md` "Runbook: the Dev E2E staff user". The
  README command table, the `crm_web.tf` comment and the tool's help say the same: write the keys BEFORE the apply
  (writing them after the apply and before the next web deploy also works; one order is documented).
- **Known exposure, accepted for Dev (review finding B2): the Content studio's execution role can read the staff keys.**
  `crm_portal.tf` grants `aa-crm-dev-portal-ecs-execution-role` `secretsmanager:GetSecretValue` on the whole
  `crm/dev/web` secret, because the portal task maps its `session_secret` key (`WEB_SESSION_SECRET`: the studio reads
  the agency session on the same host, read only). IAM cannot scope a grant to one JSON key, so that role can also read
  `staff_cognito_client_secret` and `staff_session_secret`. What limits it: only the ECS agent uses an execution role;
  the portal container gets `session_secret` alone, and its task role has no AWS API (ECS Exec channel only), so code
  running in the studio cannot fetch the staff keys. Someone able to use the execution role's credentials directly
  (an admin) could.
  - Checked: the portal really needs that one key from this secret (it must be the very value the web seals with), and
    no other existing secret holds it, so there is no pure IAM narrowing without a new resource. No IAM change here.
  - Recommended split (needs the tech lead's yes, it is paid): a new secret `crm/dev/web-staff` (~$0.40/month) holding
    the two staff keys, read only by the web execution role; `staff-web-secret` writes it, `crm_web.tf` maps the two
    `STAFF_*` values from it, and the portal grant stays on `crm/dev/web`. Do it before the first prod / paying tenant
    at the latest. Follow-up for the root repo: the `crm/dev/web` row of `docs/security/secrets-register.md` still
    lists only the agency keys; it should name the two staff keys and this exposure.
- The Lambda zip changes (trigger code), so the apply publishes a new version and moves the `live` alias.
- Cost: $0 (no new resource; one more secret key, one more mailbox recipient).
