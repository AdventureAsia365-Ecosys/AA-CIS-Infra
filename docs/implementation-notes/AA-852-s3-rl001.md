## Decisions
- **Create if missing, then restate.** `CREATE ROLE` runs inside a guarded `DO` block (idempotent);
  `ALTER ROLE bk_owner/tp_owner NOLOGIN` and `ALTER ROLE cis_app LOGIN CONNECTION LIMIT 90` restate the
  attributes so a role that already existed with another shape is corrected, and the guard checks the rest.
- **No `ALTER ROLE … NOSUPERUSER / NOBYPASSRLS / NOREPLICATION`.** On PostgreSQL 15 (RDS 15.17) a
  non-superuser CREATEROLE role errors on any of those keywords in `ALTER ROLE` ("must be superuser to
  change …"), even in the NO form; `CREATE ROLE` accepts the NO forms. So the guard asserts
  `NOT (rolsuper OR rolbypassrls OR rolcreaterole OR rolcreatedb OR rolreplication)` instead.
- **Session guard first:** the file raises unless `session_user = 'aa_cis_admin'` (belt and braces: the
  S1 runner already refuses `roles/` under another login, exit 8).
- **Guard set** (all RAISE): owner roles NOLOGIN with no elevated attribute; `cis_app` LOGIN, limit 90,
  no elevated attribute; the three new roles are members of **nothing**; `aa_cis_admin` is a member of
  all three; `aa_cis_admin` is **not** a member of `aa_app_user` or `catalog_owner` (§1.4, S236 lesson:
  policies `TO r` reach members); N3 limits are 30/15/15.
- **N3 limits restated with 234's values** (`tripplanner 30`, `booking 15`, `aa_app_user 15`): no
  behaviour change; the bootstrap is now their home (MIG-6). Cross-owner roles are not wrapped in
  `IF EXISTS` (schema-ownership rule 5).
- **Static test `db/tests/test_roles_files.py`** (runs in Migration Copy Guard and DB Schema Dump unit
  tests): every `roles/` file has no `PASSWORD`, no `SUPERUSER`/`BYPASSRLS`/`REPLICATION` (only NO forms),
  memberships scoped by **grantee** (review fix, below); rl-001 creates exactly `bk_owner`,
  `tp_owner`, `cis_app` (not `cis_owner`/`db_migrator`, those are rl-002), grants exactly the two
  memberships, its limits equal CIS 234's, and it registers `rl-001` with `ON CONFLICT DO NOTHING`.
  Uses the runner's lexer view (`_role_view`) so comments and string literals do not count.

- **Review round (S241), catalog.* view freeze (choice (a) of the review).** Since 225:426 the master is
  not a member of `catalog_owner` and must never become one (master-read policies on FORCE tables would
  reach the CIS runtime); the S1 lint refuses the old 225/235 `GRANT catalog_owner TO CURRENT_USER` dance
  in files ≥ 243; the S22 catalog recipe needs `db_migrator` as the login. So **no catalog.* view change
  from the S1 merge until S22** (≈ 2.5–3 weeks, Dev only, no customer). Chosen over (b) an Infra-native
  `roles/` catalog file — the view SQL would leave AA-CIS-App, its CI replay (`api/migrations`) would test
  a stale view and Copy Guard would not cover it — and over (c) moving `db_migrator` before Wave 2, which
  needs the S11/S12 migrator task definition, a secret and `set-password` first. Enforced, not just
  written down: (1) lint: DDL on a `catalog.` view in an owner file ≥ `role_lint_from` must come after
  `SET LOCAL ROLE catalog_owner` (the recipe), and the membership-grant error for `catalog_owner` names
  the freeze; (2) runner: before a linted owner-dir file runs (`check` and `apply`), every `SET LOCAL ROLE`
  target must be reachable from the login role (`pg_has_role(session_user, r, 'MEMBER')`, the check
  PostgreSQL makes), else exit 8 "would fail at apply with 42501" + the freeze text. While the master is
  the login this refuses every catalog-recipe file at `check`; from S22 (`db_migrator` in
  `catalog_owner`) it passes with no change. Escape if a catalog change cannot wait: Nghiệp decides
  (b) or (c) then.
- **Grantee-scoped membership rule (review fix).** The old test refused any `GRANT catalog_owner …` in
  `roles/`, which would turn the planned rl-002 (`GRANT bk_owner, tp_owner, cis_owner, catalog_owner TO
  db_migrator`, S20) red. Now: `aa_app_user` is granted to nobody (so `db_migrator` never joins it);
  `catalog_owner` only `TO db_migrator`; every other grantee (master, `CURRENT_USER`, `cis_owner`,
  `cis_app`, `booking`, `tripplanner`, any `*_owner`) fails. Cases: the planned rl-002 lines pass; eight
  forbidden shapes fail (incl. `WITH ADMIN OPTION`, `GRANTED BY`, a grant inside a `DO` block); object
  grants (`GRANT SELECT ON …`) are not memberships.
- **`db_migrator` must reach every switch target (review fix).** `SET ROLE` checks the session user's
  memberships, so after S22 a `SET LOCAL ROLE cis_app` (244-style guard block) fails unless rl-002 also
  grants `cis_app` to `db_migrator` (harmless: its only policies are `USING (true)` on ENABLE-only tables,
  where `db_migrator` is already exempt through `cis_owner`; `db_migrator` results are never tenant
  evidence). `db/owners.yaml` gains `migrator_role: db_migrator` + `migrator_member_of: [bk_owner,
  catalog_owner, cis_app, cis_owner, pg_read_all_stats, tp_owner]`; tests: the list covers every
  `owner_role` and `set_local_roles` entry and excludes `aa_app_user`/master/bypass roles, the plan's
  rl-002 line grants exactly that list, and once a `roles/` file creates `db_migrator` its grants equal
  the list. The runner pre-check above also catches a missing membership at `check` time.
- **Rollback text was wrong (review fix).** `DROP ROLE IF EXISTS cis_app, tp_owner, bk_owner` fails as soon
  as CIS 243 (right after rl-001 in the S8 train) or 244 reference the roles. The undo is now a prepared
  `roles/` file (AA-Ecosys `docs/audits/2026-10-17-S241-x1/s3-undo/0NN_x1_rl001_undo.sql`, not merged):
  guard (master, member of the three; no owner dependency in `pg_shdepend` — `DROP OWNED` would drop
  owned objects —, none in another database, no `cis_app` session), drop 243's key guard trigger +
  function, `DROP OWNED BY cis_app, tp_owner, bk_owner`, `DROP ROLE`, guard, register `rl-0NN`.

## Tradeoffs
- The file restates `CONNECTION LIMIT 90` for `cis_app`; the XD6 measurement (S15) changes it with a
  later `roles/` file, never by editing this one (applied files never re-run).
- `GRANT cis_app TO aa_cis_admin` (plan) makes the master subject to future `TO cis_app` policies; they
  exist only on ENABLE-without-FORCE tables where the master is owner-exempt (244), so no read changes.
