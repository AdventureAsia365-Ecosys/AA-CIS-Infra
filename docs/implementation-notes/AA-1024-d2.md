# AA-1024 D2 — IAM for the model lifecycle sync (Infra part, lane l4 of S265)

The code part (job `llm_model_lifecycle_sync`, migration CIS 350, digest and bell) is in AA-CIS-App
`docs/implementation-notes/AA-1024-d2.md`.

## Decisions

- **Two read-only statements, nothing else.** `bedrock:ListFoundationModels` on the CIS task role (acc2, task-role
  connection) and on `AA3-Bedrock-Invoker` (acc3, the assume-role connection the job reaches through the existing
  satellite session). No `GetFoundationModel` (the list already carries `modelLifecycle` with `status`,
  `legacyTime`, `endOfLifeTime`, `publicExtendedAccessTime` in botocore 1.43) and no Marketplace/agreement reads.
- **Resource "*"**: ListFoundationModels has no resource-level permission.
- **Separate Sids**, so the existing invoke statements stay untouched (the inline policy names are kept: renaming
  one would destroy and create it).

## Changed

- The plan names "acc3 and aa365"; the acc2 grant lives in `modules/ecs` (the CIS task role's inline policy), not in a
  file of `accounts/aa365`.

## Tradeoffs

- The TripPlanner Lambda can also assume `AA3-Bedrock-Invoker`; it gains the same read. Harmless (a public catalog
  list, no data, no cost), not worth a second role.

## Should know

- acc2: `module.ecs.aws_iam_role_policy.ecs_task_policy` is an `aa-*-dev-*` role policy, so CI Terraform Apply can
  apply it (no bootstrap). It changes no task definition.
- acc3: the `acc3-bedrock` root is applied only locally with MFA (`nghiep_aa365`),
  `-target=aws_iam_role_policy.bedrock_invoker_policy`. While acc3 has its account-level Bedrock hold, the call may
  still be refused after the apply; the CIS job records `access: refused` for acc3 and does not fail.
- Cost: 0 USD (control-plane read, no new resource).
