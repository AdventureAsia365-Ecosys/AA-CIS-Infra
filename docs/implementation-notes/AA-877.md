# AA-877 (Infra part): dump and render DM-6.1 column tags

AA-877 tags the Booking and TripPlanner PII columns (`bk-018`, `tp-016`, owner repos) and needs the
live dump to show the tags (Done when 1). Before this PR the dump read no column comment at all, so
the tags would have been invisible. This PR ships first, with no DB change.

## Decisions

- `schema_dump.py` reads `col_description()` in the `columns` query and keeps it raw as `comment` in
  `schema.json`. No parsing in the ECS task (revised in S246 after the plan critique): the dump stays a read-only
  catalog copy, and `gen_schema_reference.py` (runner, no DB, unit-tested) derives `tag` (the leading
  `pii:<class>` / `conf:<class>`) and `also` (every other tag named later, in order, without repeats) with
  `parse_tag`. `TAG_CLASSES` moved to the generator too; it no longer imports `schema_dump`.
- Accepted forms: `'<tag>; text'` (DM-6.1), `'<tag> — text'` / `' – '` / `' - '` (the tp-011 form),
  and a bare `'<tag>'`. `'pii:contact (x)'` is not a leading tag, so it is reported as a misplaced
  tag. The bk-012 form `'pii:contact; also pii:name and pii:free_text (…)'` gives
  `also = [pii:name, pii:free_text]`.
- Fingerprint: `structural_view` replaces `comment` with the parsed `tag` / `also`, each only when non-empty. So the
  free text of a comment never moves the fingerprint, and an untagged column has exactly its
  pre-AA-877 shape. The candidate outcome (`pii_state`: candidates, allowlist in use, stale entries,
  findings) is hashed next to the RLS guard state, so an allowlist edit reaches the file on the next
  run.
- Tokens: `email phone name address note notes message payload snapshot title summary label sub iss data
  itinerary`. The allowlist is enumerated by name from the 2026-10-20 reference (every booking / tripplanner column
  that matches a token and stays untagged after bk-018 / tp-016), one reason each; `trip_case_versions.title` is
  tagged (`pii:free_text`, staff-written title sent to the customer), not allowlisted.
- Untagged candidates are checked only in `booking` and `tripplanner`. A candidate is a column name
  with a whole snake_case token from `PII_CANDIDATE_TOKENS`: `mission` does not match `iss`, and
  `subject_id` does not match `sub`. Columns on `PII_ALLOWLIST` (one reason each) are excluded. The
  constant is the seed of the X2+ lint.
- Rendering: tagged columns get ` · <tag> (also …)` inside the existing code block. Untagged lines
  are unchanged. The "Column format" convention line explains the suffix. The new section sits before
  the RLS guard section, and the totals line gets a "DM-6.1 tags" count.

## Changed

- `db/schema_dump.py` (raw comment only), `db/gen_schema_reference.py` (parse, render, candidates),
  `db/tests/test_schema_reference.py` (new `PiiTagTest`, 11 tests: forms, raw dump, structural view, old dump
  without `comment`, inline render, section counts, unknown class / misplaced tag, candidates + allowlist + stale,
  fingerprint moves on a tag change and not on untagged text), `db/README.md`.
- No workflow change. `FORMAT` stays 2, because the change only adds fields and the renderer reads
  them with `.get`.

## Tradeoffs

- The allowlist lives in Infra (one place for the rendered check), and the owner repos keep their
  own candidate test with the same reasons. That duplicates the list, but every owner's CI catches a
  missing tag before the dump runs. Moving it to one shared file would need a new copy guard.
- No `::warning::` annotation for candidates yet: that would need a workflow edit. The section and the
  totals line show them. A warning step can come with the X2+ lint.
