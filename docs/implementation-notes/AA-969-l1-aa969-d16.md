# AA-969 part 2 (lane l1-aa969-d16): DB Migrate run-script never reads row-level personal data

Item (2) of the S265 re-scope comment on AA-969 (root ADR 0019 d16): a guard in DB Migrate `mode=run-script` refuses
reads of the pilot tenant's personal data (counts and aggregates only), because this repo's Actions logs are public.
The agent-side half is the root repo hook `.claude/hooks/pilot-pii-guard.sh`.

## Decisions

- **Enforced at run time, in the runner, on the live catalogue.** `db/run_migration.py` is the only file the
  migrator task downloads, so the guard lives there (no new module). Before `main(conn)` it reads the protected columns
  (`PII_COLUMNS_SQL`: DM-6.1 `pii:` comments in `crm`, `booking`, `tripplanner` and in the `shared` tables with
  `tenant_id`, plus their partitions) and hands the script `PiiGuardedConnection`.
- **The planner decides, not a regex on SQL text.** Every row-returning call is first planned with
  `EXPLAIN (VERBOSE, FORMAT JSON)` (in a savepoint, so a refusal aborts nothing). `pii_plan_reads()` reads the plan's
  top output (aliases resolved to relations, views and subqueries already expanded or flattened by the planner, bare
  names for single-table queries, whole rows `t.*`, CTE / Subquery scans and Init/SubPlans followed). This sees
  through aliases, views and `SELECT *` that a text check would miss.
- **Allowed forms are narrow:** `count(...)` (with `FILTER`) and `IS [NOT] NULL`. Every other function of the value
  is a read (`min()` and `string_agg()` print values; `length()` leaks little but the rule stays simple).
- **Always on, not only while a pilot exists.** No run-script needs a person's row values (the scripts README already
  said "aggregate counts only"); an always-on guard is tested before the pilot starts and does not depend on a marker
  being read right. The rule is per column, not per tenant: a script cannot read the pilot's rows by mistake through a
  query that "should" only hit synthetic tenants.
- **Fail closed:** a statement the planner cannot explain is refused (except `SHOW` / `SET` / `RESET`, and for
  `execute()` the utility list below); a catalogue read failure runs nothing (exit 13).
- **Review fix pass (S269):** the first version checked only row-returning calls and only nodes that print `Output`.
  Reviewers showed six bypasses; each is now closed and pinned by a test:
  1. `Append`, `Merge Append` and `Recursive Union` print no `Output` (PostgreSQL `explain.c`): their result is now
     the union of their members (UNION ALL, 2+ partitions, recursive CTEs, a Subquery Scan over them). A node above a
     partitioned table names the parent alias, which has no scan node: `<alias>` resolves to the `<alias>_N`
     partition scans.
  2. `execute` / `executemany` are planned too. A write (`ModifyTable`, also inside a CTE) of a protected value into
     a table without protected columns is refused; so are `CREATE TABLE AS`, `SELECT INTO` and `CREATE MATERIALIZED
     VIEW` of one (their plan is the query). `set_config()` in a statement that reads a protected table, and any
     `*_to_xml` / `ts_stat` / `dblink` call (SQL text the planner never sees) are refused.
  3. Statements that cannot be planned are classified by their first keyword: `DO`, `CALL`, `COPY`, `IMPORT`, `LOAD`
     and `CREATE FUNCTION / PROCEDURE / TRIGGER / RULE / EXTENSION …` are refused; transaction control, `SET`, `LOCK`,
     `ANALYZE`, `PREPARE` (its `EXECUTE` is planned) and query-less DDL pass; anything else must plan. A multi-statement
     `execute()` string is split (a small tokenizer that knows quotes, `E''`, dollar quotes and comments) and runs one
     checked statement at a time inside one transaction, so `SET search_path …; CREATE TABLE … AS SELECT` is caught.
  4. The wrapped connection is a private slot; any `_`-prefixed attribute (and `add_listener`, `add_query_logger`)
     raises `PiiReadRefused`.
  5. A failed statement's error text is withheld from the log (class, SQLSTATE, and the schema / table / column /
     constraint names PostgreSQL attaches): `WHERE email::int > 0` used to print the value in a cast error.

## Changed

- `db/run_migration.py`: `PII_COLUMNS_SQL`, `load_pii_columns()`, `pii_plan_reads()`, `_strip_allowed()`,
  `PiiGuardedConnection`, `PiiReadRefused`; `run_script()` loads the catalogue, logs
  `run-script: PII guard on: N personal-data columns in M tenant tables`, and runs `main()` on the guarded connection.
- `db/tests/test_aa969_pii_guard.py` (CI, no database: canned plans of the real planner, the wrapper, run_script);
  `db/tests/test_aa969_pii_guard_pg.py` (local only, `AA969_TEST_PG_DSN`: the real planner, 24 refused and 11 allowed
  reads, 13 refused and 9 allowed `execute()` statements in a rolled-back read-write transaction, every call kind, two
  partitions, a view, a savepoint after a refusal, the cast-error text); `test_run_migration.FakeConn` answers
  the catalogue read.
- `db/scripts/README.md` "Personal data", `CONTEXT.md` one paragraph.

## Tradeoffs

- One extra EXPLAIN per row-returning statement of a script (milliseconds; scripts send few statements).
- Older reviewed scripts that read a tagged column now fail if run again (static scan of `db/scripts/` at this
  commit: the AA-682 live checks read `booking.trip_cases` dates / pax, `aa990_*` read TripPlanner itineraries and
  event payloads, `dm65_consent_capture` reads inbox payloads). They are history; a new run would be a new reviewed
  file (a backfill that rewrites a tagged JSON column should do it in SQL, `UPDATE … SET col = jsonb_set(…)`, so no
  value comes back to Python).
- **The AA staff directory `booking.staff_users` is out of scope**: staff identities, not a tenant's or a traveller's
  data, and the re-runnable B2B / price-chain / incident seeds (`aa973`, `aa1029`, `aa961`) link `created_by` through
  `cis_user_id`. `shared.admin_users` is out already (no `tenant_id`).
- Not a sandbox: a script runs as the master, and Python can still reach the wrapped connection on purpose
  (`object.__getattribute__`). A value moved into an untagged column of the same tagged table
  (`UPDATE crm.x SET note = email`) is not tracked: the guard knows the target table of a write, not its target
  columns (EXPLAIN does not print them for UPDATE). The guard stops mistakes in reviewed files; the review stays the
  control.
- `execute()` of DDL now goes through the keyword list: a new script that needs a statement kind outside it gets a
  clear refusal, not a silent pass; widen the list in the runner when such a need is reviewed.
- A set-returning function over a tagged column in `FROM` (`jsonb_array_elements(d.itinerary) e`) is not followed:
  its rows (`e.value`) pass. Following it would refuse the nightly DB Tour Liveness Gate probe, which reads only the
  `source_tour_id` key of TripPlanner itinerary entries that way. Review covers that form.
- Columns without a `pii:` tag are not protected; the tag census (DM-6.1, 52 untagged candidates in the schema
  reference) is the place to close that, not this guard.
