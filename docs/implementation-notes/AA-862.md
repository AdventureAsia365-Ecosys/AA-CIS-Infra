# AA-862 — Cohere Embed v4 on the satellite invoker roles (S239)

Infra half of AA-862. Branch `feat/aa862-embed-satellite-iam` (this IAM change); a later
`chore/aa862-copy` PR copies CIS migration 240 for DB Migrate. App halves: AA-CIS-App
`feat/aa862-embed-acc3-fallback` (migration 240: catalog rows `cohere-embed-v4-acc3` /
`cohere-embed-v4-acc1` + `fallback_model_ids` on the embed routes), AA-TripPlanner-Web
`feat/aa862-embed-satellite-client` (cached satellite embed client).

Chain per embed call: TripPlanner query cache -> acc2 -> acc3 -> TripPlanner keyword fallback.

## Decisions

- New statement `InvokeCohereEmbedV4` (action `bedrock:InvokeModel` only; embeddings do not stream)
  on the existing inline policy of both invoker roles:
  - acc3 `AA3-Bedrock-Invoker` — `accounts/acc3-bedrock/main.tf`
  - acc1 `AA-Bedrock-Invoker` — `accounts/acc1-bedrock/bedrock_invoker_import.tf`
- Resources (same ARN set as acc2's TripPlanner `BedrockEmbedDirect`, AA-856):
  `inference-profile/global.cohere.embed-v4:0` and `inference-profile/us.cohere.embed-v4:0` in any
  region of the account, `foundation-model/cohere.embed-v4:0` in any region, and the regionless
  `foundation-model/cohere.embed-v4:0`. A cross-region profile authorizes against the member region's
  foundation-model ARN (seen live on acc2, us-east-1), hence the region wildcards.
- `us.` is granted as well although migration 240 uses `global.`: acc3 has 2,000 rpm on both, so a
  later switch to `us.` is a catalog edit, not another apply.

## Changed

- Nothing on acc2: the CIS ECS task role (`accounts/aa365/bedrock_satellite_assume.tf`) and the
  TripPlanner Lambda role (`accounts/aa365/tripplanner.tf`) already may assume both invoker roles,
  and both trust policies already trust both callers with each account's ExternalId.

## Tradeoffs

- Separate statement instead of appending to `InvokeApprovedModelsOnly`: the existing statements
  (acc1's is a byte copy of live state) stay untouched, so the plan shows one added statement only.
- Policy names kept (`InvokeApprovedClaudeModelsOnly`): renaming an inline policy is destroy+create.
