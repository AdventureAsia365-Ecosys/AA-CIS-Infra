# AA-852 — X1 step S1: owner registry, `roles/` dir, live-owner role switch, ownership post-check, role lint

Plan: `AA-Ecosys/docs/audits/2026-10-17-S241-x1/x1-plan.md` §5 S1 (revision 2, XD8). One PR, no apply.
Nothing here changes how today's migrations run: every anchor schema is owned by the login role
(`aa_cis_admin`), so the switch is a no-op until an owner transfer (bk-014 / tp-013 / 245) commits.

## Decisions
- **Registry = `db/owners.yaml`, mirrors stay as constants.** The runner reaches the ECS task as one
  presigned file (no PyYAML, no extra file, no new env var), and the guards are standard-library only.
  So `run_migration.py` (`MASTER_ROLE`, `OWNER_DIRS`, `IDLE_EXEMPT_KINDS`), `check_migration_copies.py`
  (`OWNERS`, `PATH_RE`) and `db-migrate.yml` (regex, prefix `case`, `environment` options) keep their
  copies, and `db/tests/test_owners_registry.py` (plan item 7) fails on any disagreement. Mutation-checked:
  changing `role_lint_from`, `idle_exempt_kinds`, the `roles` prefix or the workflow prefix each fails it.
- **Owner role fields:** `owner_role` is the X1 target (`cis_owner`, `bk_owner`, `tp_owner`),
  `owner_role_today` is `aa_cis_admin`; same for runtime roles (`runtime_roles` / `runtime_roles_today`).
  The runner reads neither: it reads the live schema owner (XD8). Runtime role names kept (XD1).
- **Consumer grants** (input for X2, not enforced) were taken from the live schema reference (dump 16/10):
  catalog USAGE+SELECT and `geo.name_norm` EXECUTE to `booking`/`tripplanner` (contract),
  `shared.llm_call_log` INSERT (standing exception), TripPlanner's 173/179/180/216/201/published_tours
  reads (grandfathered until X4), `tripplanner.v_inquiry_outbox` to `booking` (tp-009). `aa_app_user` is
  CIS's own tenant pool, so it is a CIS runtime role, not a consumer.
- **`tripplanner.job_table: null`** (no `tripplanner.job` yet, AA-861); the test requires the
  `IDLE_EXEMPT_KINDS` keys to be exactly the owners with a job table.
- **Switched execution path.** The post-check must run inside the file's transaction, before its COMMIT,
  but files carry their own `BEGIN; … COMMIT;`. Under a switch the runner therefore splits the file: sends
  the file's first statement (`BEGIN`, header comments included), `SET LOCAL ROLE "<owner>"`, the body as
  one simple-protocol message, `RESET ROLE`, the post-check, then the file's `COMMIT` (or `ROLLBACK` +
  exit 9). It requires exactly one `BEGIN … COMMIT` block (else exit 8, also in check mode). Unswitched
  files (today, all of them) still go out as one `conn.execute(sql)`, byte for byte as before.
- **No-transaction file under a switch:** session `SET ROLE`, statements one by one, `RESET ROLE`,
  post-check; a hit returns 9 with "already committed, fix by hand" (cannot roll back by design).
- **Post-check scope.** Plan wording: 0 objects in the owners.yaml schemas owned by `session_user`. Taken
  literally that fails every booking/ apply during Waves 2–4, because the master (login) still owns every
  CIS object. Implemented as: object owned by the login role AND (its schema is owned by someone else OR
  its catalog row was written by this transaction, `xmin = pg_current_xact_id()::xid`). After S22 (login
  `db_migrator`, owns nothing) this is the plan's full rule. Covers `pg_class`, `pg_proc`, `pg_type`
  (non-array, no relation row types: those are covered by `pg_class`).
- **New exit codes:** 8 = role refused (roles/ under a non-master login, login not a member of the live
  owner, unknown dir, switched file not one transaction block); 9 = ownership post-check failed. The
  workflow prints a specific `::error::` for both.
- **`roles/` refused in check mode too** under a non-master login, so `check` tells you before `apply`.
- **Role lint is a lexer view, not regex on raw text:** comments dropped, string literals replaced by
  placeholders, dollar-quoted bodies lexed as code (225/229/239 put their role switches inside `DO $$`
  blocks). Strings are inspected only where they are dynamic SQL (`EXECUTE '…'` / `EXECUTE format('…'`)
  and as the first argument of `set_config(`. `UPDATE … SET role = …` (a column) is skipped.
- **Role lint additions beyond the plan's literal list** (same intent, DM-8.1 / A7): role membership
  `GRANT r TO x` / `REVOKE r FROM x` (no `ON`) → `roles/`; `SET SESSION ROLE`, `SET role = …`,
  `ALTER FUNCTION … SET role` count as "SET ROLE without LOCAL"; `SET LOCAL ROLE NONE` is rejected (it
  resets to the login role, same hazard as `RESET ROLE`).
- **`environment` input:** choice `[dev]`, default `dev`, validated again in the script, shown in the job
  name and the step summary. Not passed to the task (that would be a new env var; nothing in the task
  depends on it). A second environment needs its own cluster/service/bucket values first.
- **CI needs PyYAML** only for the registry test: Migration Copy Guard's unit-test step now uses
  `actions/setup-python@v5` (3.12, the version the app repos use) + `pip install pyyaml==6.0.2`. The guard
  and lint steps stay on the runner's system Python.

## Tradeoffs
- Constants + agreement test over reading YAML at run time: one more place to edit per owner change, but
  the runner stays a single stdlib file and a drift fails CI on the PR that causes it.
- The lint's threshold (`role_lint_from`) instead of linting every file: 225/226/228/229/234/235/237/239/241
  and bk-001 use the pre-X1 patterns (catalog dance, `SET LOCAL ROLE aa_app_user` guards, CREATE ROLE /
  EXTENSION) and are applied; re-linting them would only force no-op edits of applied copies.
- Splitting the file under a switch changes how it is sent (several messages instead of one). Only
  switched files take that path; the post-check needs it.
