# AA-874 — CIS Redis with TLS, AUTH and at-rest encryption (Infra PR A: additive)

AA-874 (security): the CIS Redis (`aa-cis-dev-redis`, standalone `aws_elasticache_cluster`, Redis 7.1,
cache.t3.micro) has no AUTH, no in-transit and no at-rest encryption (checked live 24/10/2026: all three
False, no replication group). It holds the tenant-pool RLS rollback flags, the rate-limit counters, writing
progress and the SEO cache.

This PR (slice S2) is **additive only**: a new encrypted replication group next to the old node, the AUTH
secret, and the plan role's secret list. No ECS service or task definition changes, so it can apply during a
wave. Later slices: S4 key copy (live, no PR), S5 task definitions → TLS endpoint + CIS deploy in one gap,
S6 remove the old node. The tenant-pool alarms (S3) are a separate Infra PR (notes: `AA-874-alarms.md`).

## Decisions

- **Blue/green, not in place.** On a standalone cluster `transit_encryption_enabled` is ForceNew and at-rest
  encryption is not offered at all; AUTH requires TLS. In place = destroy + create: ~10–15 min with no node
  and every key lost (SEO cache → paid DataForSEO re-fetch; a tenant-pool flag set to `false` by hand →
  route silently back ON). A new replication group next to the old one costs ~$0.5 of overlap and no outage.
- **Valkey 8.2, not Redis 7.1.** Redis-wire compatible (redis-py, DUMP/RESTORE), $0.0176/h vs $0.022/h on
  cache.t3.micro in us-west-1. One variable (`cache_engine` / `cache_engine_version` in the module) switches
  back to `redis` / `7.1`; the parameter group follows the engine (`default.valkey8` / `default.redis7`).
  `describe-cache-engine-versions --engine valkey` on 24/10 lists 7.2, 8.0, 8.1, 8.2, 9.0, 9.1: 8.2 is the
  newest 8.x.
- **Id `aa-cis-dev-cache`** (the old `-redis` id stays on the old node until S6). Single node:
  `num_cache_clusters = 1`, no failover, no Multi-AZ, no snapshots (cache only, as before). Same subnet group,
  same security group (6379 ingress for the CIS api / worker groups unchanged), same maintenance window.
- **TLS `required`** from creation (no `preferred` phase: no client talks to this group before S5).
  At-rest encryption with the AWS-managed key (no CMK, no cost).
- **AUTH token never in state.** `ephemeral "random_password" "auth"` (64 alphanumerics) feeds the group's
  `auth_token_wo` and the secret version's `secret_string_wo` in the same apply; both `*_wo_version` follow
  `var.auth_token_version` (default 1), so they cannot drift apart by editing one.
- **Secret version after the group** (review round): `depends_on = [aws_elasticache_replication_group.main]`
  on the secret version. Without it the token reached Secrets Manager seconds into the apply while the group
  took 10–15 min; a failed group create would leave token A in the secret and the retry (fresh ephemeral
  token B on the new group) would not rewrite the version, because `secret_string_wo_version` did not
  change. Now a failed group create writes nothing, and the retry writes one token to both.
- **Engine / version guard** (review round): a validation on `cache_engine_version` ties the major version to
  the engine (valkey `8.x`, redis `7.x`), so a half switch fails at plan instead of at apply.
- **Secret `aa-cis/dev/redis-auth`** in the module next to the group (`recovery_window_in_days = 0` on dev,
  like the other dev secrets), tags = `cis_app_tags` + Name. The CIS ECS execution role's `aa-cis/dev/*`
  pattern already covers it for S5; the CIS task role is not denied it (`DenyMasterAndOtherAppSecrets` lists
  only rds / db-migrator / other apps), which the S4 copy script relies on.
- **Plan role secret list** (`local.tf_plan_secret_arns`, `cicd_split.tf`) gets the new secret: refresh of a
  write-only secret version still calls GetSecretValue.

## Tradeoffs

- **Valkey vs Redis:** a different engine is a small compatibility risk (RESTORE of a Redis 7.1 payload);
  the S4 copy script falls back to GET/SET and HGETALL/HSET per key. Saves ~$3.2/month.
- **Ephemeral password vs `random_password` resource:** a `random_password` resource would keep the token
  in state (readable by anyone with state access, i.e. both CI roles). The ephemeral one keeps it only in
  Secrets Manager and on the node, at the cost of a slightly unusual rotation (below).

`Plan: 3 to add, 1 to change, 0 to destroy` — create the replication group, the secret and the secret version;
in-place update of `aws_iam_role_policy.tf_plan` (ReadStackSecretValues 2 → 3 ARNs; shown as a whole-policy

task definition) means stop.

### Apply order (orchestrator)

`aws_iam_role_policy.tf_plan` is a bootstrap object: the CI apply role is denied writes on it. So:

1. Merge after the CI plan is green.
2. **Local targeted apply with MFA, from the merged `main` checkout** (lesson S240), safe credential export
   (lesson S244). The target pulls in its dependency, the empty secret container
   `module.elasticache.aws_secretsmanager_secret.redis_auth`; the module's `depends_on = [module.vpc]` also
   refreshes the VPC module (expect no change there). Expected: `1 to add, 1 to change, 0 to destroy`.
3. CI `terraform-apply.yml` with `allow_guarded=true` (the secret version is a guarded type) and a reason.
   Expected: `2 to add` (replication group + secret version), nothing else. The group takes ~10–15 min.
4. A plan on `main` afterwards shows `No changes` (it also proves the plan role can read the new version).

Both writes of the token happen in step 3 (one apply), the secret version only after the group exists.
A failed group create therefore heals on retry (nothing was written to the secret). The reverse case,
group created but the version write failed: the node holds a token no secret has. Bump
`auth_token_version` to 2 with `auth_token_update_strategy = "SET"` (no client uses the group yet) and
apply again rather than editing either by hand.

**Hard gate before S4 / S5:** live check 2 below (ECS-exec PING with the token read from
`aa-cis/dev/redis-auth`) must return True. It is the only proof that the secret and the node hold the same
token; do not copy keys or switch task definitions before it passes.

### Live checks after step 3

- `aws elasticache describe-replication-groups --replication-group-id aa-cis-dev-cache --profile aa365-admin --region us-west-1 --query 'ReplicationGroups[0].{auth:AuthTokenEnabled,tls:TransitEncryptionEnabled,mode:TransitEncryptionMode,rest:AtRestEncryptionEnabled,st:Status}'`
  → `true / true / required / true / available`.
- From the api task (ECS exec, S3-mediated): plain `redis://` PING fails; `rediss://` without password →
  NOAUTH / AuthenticationError; `rediss://` + token from `aa-cis/dev/redis-auth` → True. Use the app helper
  `shared.cache.redis_conn.redis_conn_args()` (AA-CIS-App S1) for the last one, so the production kwargs
  (certificate + host-name check) are what is proven.

### Rotation

The token exists only in Secrets Manager and on the node. Always set `auth_token_update_strategy`
explicitly: aws provider v6 gives it no default (schema checked on 6.69.1: optional, no default), so relying
on whatever the API does is not a plan. To rotate:

1. Set `auth_token_update_strategy = "ROTATE"` on the group and bump `auth_token_version`: one apply writes
   the same new token to the node and to a new secret version; the node then accepts old and new.
2. Redeploy CIS api + worker (ECS re-reads the secret at task start).
3. Set `auth_token_update_strategy = "SET"` and apply, so only the new token is valid.

No shortcut on Dev either: without step 1's ROTATE, running tasks lose Redis until the redeploy (rate limit
and SEO cache fail open, tenant flags fail closed to the tenant pool, writing progress is lost).
