## Decisions
- **Probe as a `run-script`, not the S237 parity runner.** The S237 runner cannot run since X1 S19 (the CIS task role
  is denied the master secret). DB Migrate `run-script` is the only master path; READ_ONLY, budgeted to ~20 minutes
  (the workflow waits 30), samples capped (80 tiles, 150 destinations, 8 query vectors, days 3–21, 60 tours,
  8 destinations / 8 pinned ids for the assembly readers).
- **Readers run as `tripplanner`** (`SET LOCAL ROLE` from the master, as CIS 239's guard does on RDS) so the catalog
  views read with their owner's rights exactly as for the Lambdas. Refused → `SCRIPT refuse`, return 1. The
  `tripplanner/dev/database-url` fallback (the isolation probe can read it) is not used: it would need its own
  reviewed secret read.
- **Reader SQL is generated, never hand-copied**: root `gen_probe_sql.py` reads the TripPlanner source with `ast`
  (no import), renders module constants, the f-strings built inside functions and (6c) the `Source(...)` relations
  of `vector_topk`, and writes the block between markers with the TripPlanner commit. It works on TripPlanner before
  and after 6c: optional readers are listed in `READERS_ABSENT` when the source lacks them. The block committed here
  is generated from TripPlanner main (before 6c) for the baseline run; regenerate after 6c merges (assembly twins,
  the cis top-k over `catalog.v_component_embedding`).
- **Step 18 regeneration (S246) is from the TripPlanner ship build, not TripPlanner main**: block generated from
  `feat/aa-847-places-cis` @ c701d608ad81 (6c + 6d + destination redirect) so the probe can gate the TripPlanner merge
  (HNSW in the `search cis` EXPLAIN). The root generator needed a fix first: 6d builds the cis reader SQL from
  `LINE_COLS` / `LINE_COLS_SQL` shared from `browse/tiles.py`, which the generator could not render (root branch
  `fix/aa-847-gen-probe-6d`; output for the pre-6c commit unchanged). The cis search columns now follow
  `browse.search.CIS_DEST_COLS` (6d adds the CIS 256 line columns), so the timed top-k is the SQL the Lambda sends.
- **Probe-fix regeneration (S246 gate diagnosis, section 2.2)**: block regenerated from `feat/aa-847-places-cis` @
  3b6e62d665be (the TripPlanner routes fix: `CHAIN_SQL_CIS` joins the second leg on its start place through a `hop`
  CTE, skips self-pair junctions, breaks ties on the pair key). Only `browse.routes.CHAIN_SQL_CIS` and `READERS_FROM`
  changed. TripPlanner also runs its cis single + chain reads under `SET LOCAL plan_cache_mode = force_custom_plan`;
  that is code, not reader SQL, so the probe mirrors it itself around its own calls (probe-fix PR, branch
  `feat/aa-847-probe-fixes`).
- **Route-candidates regeneration (S246, after CIS 258)**: the first post-258 probe failed one parity item,
  `assembly_route_candidates` Laos cis 886 ms vs legacy 26 (target 200; 191.7 before 258). Its plan rescanned the
  `stops` CTE per candidate pair (`CTE Scan:s2_1 loops=16544`). Better row estimates through 258's `source_key`
  flipped the join order onto the inlined next-stop subquery. Block regenerated from `feat/aa-847-places-cis` @
  ee5b0bac5652: `ROUTE_CANDIDATES_SQL_CIS` finds the next stop by an equality join + GROUP BY, and breaks ties on
  the destination id. Only that reader and `READERS_FROM` changed. No probe code changed (branch
  `feat/aa-847-probe-route-candidates`). TripPlanner notes: `docs/implementation-notes/AA-847-route-candidates.md`.
- **Probe fixes (S246 gate diagnosis, section 2.1), branch `feat/aa-847-probe-fixes`**:
  - `env_topk` moved from the master pass to pass 1, as `tripplanner`, on the generated `TOPK_SQL_CIS` with the vector
    bound as `$1` (the old `TOPK_EXPLAIN_SQL` ordered by a joined subquery's column, which PG can never serve from an
    index, and ran as the master on the base tables). Settings are TripPlanner's: `hnsw.ef_search` =
    `ef_search_for(200)` = 400 (`vector_topk.ef_search_for`: 2 × k, 40..1000) and `hnsw.iterative_scan =
    relaxed_order` on pgvector >= 0.8. Two EXPLAINs: natural and `enable_sort=off` (forced).
  - The vector is the slowest `search cis` call's (the call the timing EXPLAIN shows), else the first Laos query
    vector.
  - The liveness probe is looked for inside the `scan` CTE only (`Subplan Name = "CTE scan"`, checked on PG 16). The
    per-destination `component_count` subquery also joins `_live_tour`, and it is the `Seq Scan raw_tours loops=60`
    of the diagnosis. The loops>1 flag is plan-wide, as the revised gate wording asks.
  - Two verdicts, both printed: `verdict_pre258` (forced plan reaches `tour_place_embedding_hnsw` ordered by `<=>`,
    the TP-merge condition of memo section 3) and `verdict_full` (the full revised step-18 clause: also no raw_tours
    seq scan loops>1 in the natural plan, liveness on `raw_tours_source_key_idx`, no `Join Filter … source_id`).
  - Every probe EXPLAIN now runs in a savepoint that is **rolled back**, not released (`explain_doc`), so
    `enable_sort` / `plan_cache_mode` end with it. Checked on PG 16: a `set_config(…, true)` in a released savepoint
    survives (that is why the routes toggle restores the value explicitly).
  - The routes toggle restores the value read at the start (`current_setting('plan_cache_mode')`, normally `auto`),
    not a hard-coded `auto`.
  - `routes_single_auto` is not in the memo. It was added because, with the fix mirrored, the forced cis series cannot
    show the generic-plan jump any more. A distinct statement text (`AUTO_TAG`) makes asyncpg prepare it apart from
    the forced statement, whose custom-plan history would otherwise skew the plan-cache choice. It runs in run 1 only,
    is not scored, and is not EXPLAINed.
  - The generic proof uses a SQL-level `PREPARE aa847_single_generic(text, int, int)`, then `EXPLAIN EXECUTE` under
    `force_generic_plan` and `force_custom_plan`, then `DEALLOCATE` in a `finally`. The country literal comes from
    the `COUNTRIES` constant, quoted. `PREPARE` / `EXECUTE` / `DEALLOCATE` run in a read-only transaction (checked on
    PG 16 with `default_transaction_read_only=on`).
  - `REPEATS = 3`, a constant (run-script passes no arguments). The memo's `--repeat 3` becomes this constant.
    Parity uses the median of the per-run aggregates. The `timing` line keeps its old fields (calls and rows of run 1;
    total and per-call medians; max over all runs) and adds `repeats` and `runs`, so it stays comparable with the
    earlier single-run files. A run starts only if 1.5 × the first run + 300 s fits in the budget. The last Dev run
    took 64.5 s in all, so 3 runs is about 4 minutes against the 20-minute budget and 30-minute ceiling.
  - Review follow-ups (independent review of the probe fixes, S246): the search readers' `hnsw.ef_search` /
    `hnsw.iterative_scan` were set with `set_config(…, true)` per query and never put back, so every later reader in
    pass 1 ran with them, including `assembly_route_candidates` (a `<=>` read that TripPlanner runs outside the
    search's transaction, at the session values). They are now set once around the search block in a savepoint that
    is rolled back (`scoped_settings`), and the EXPLAIN of the slowest search call passes them explicitly. A run the
    budget cuts short mid-section has fewer calls of a reader than a full run; it is now dropped from the medians
    (`complete_runs`, `partial=<n>` on the `timing` / `parity` lines) instead of pulling a FAIL down to a PASS. HNSW
    counts only as the index named `tour_place_embedding_hnsw` (was: any index name containing "hnsw").
- **Coverage gate counts live frozen keys only**: frozen keys are a tour_id or a source_id; old tour_ids map through
  `raw_tours` (master pass, any version, AA tenant). Keys of tours no longer live (AA-731 orphans) cannot be covered
  and are counted apart.
- **Section 3 is a fingerprint per view** (count + md5 of ordered rows, as tripplanner): the binding before / after
  evidence for a catalog view migration. No master-inlined candidate bodies (the master skips catalog_owner's RLS
  quals, so its timings are not like-for-like).
- **Qual pushdown report**: for the slowest call of each reader the plan is searched for the consumer's filter
  (`lat >=`, `country =`, `destination_id =`, `= ANY`): on a base scan = pushed, on a Subquery/CTE Scan = blocked by a
  security_barrier view (the hypothesis behind turning barrier off on the graph views, CIS 255+ if needed).
- **Fill = dry run as merged** (`READ_ONLY = True`): pass 1 as `tripplanner` (live sources, catalog components),
  pass 2 as the master (frozen components, old tour ids → source ids through raw_tours, `geo.name_norm` of every
  name); rules (source, day, name_norm, activity) then (source, day, destination); smallest component_id on ties;
  orphans (`not_live`) and unknown keys (`no_source`) counted apart, never inserted. The apply is a one-line PR
  (`READ_ONLY = False`) dispatched in the flip window; it inserts as `tripplanner` (tp-017 grants SELECT + INSERT
  only), `ON CONFLICT (old_id) DO NOTHING`.
- **CIS 254 keeps 216 and acp_contract USAGE** (no TripPlanner code reads `v_active_tour_atoms` either; revoking it

## Tradeoffs
- Timings are wall-clock around each `fetch` inside the RDS VPC (not HTTP); the S237 numbers were HTTP-side. The
  post-flip HTTP parity (root `http-parity.py`) covers the Lambda path.
- One transaction per pass keeps one snapshot for minutes on Dev (read-only; fine on Dev).
- The fill matches in Python after two reads (≈ 1k frozen + ≈ 1–10k catalog rows): simpler to review than one SQL
  statement across the master-only raw_tours map and the tripplanner-only views.

- 3 runs triple the timing load on Dev, about 4 minutes in all, to buy a verdict that one noisy run cannot flip.
  Between runs, legacy alone moved 83.9 → 87.1 → 49.4 ms (tiles) and 36 → 102 → 34.9 ms (search).
- The forced top-k plan is a structural check, not a timing. At Dev size (~1k places) an exact top-N sort is
  cheaper and correct, so `uses_hnsw_natural=f` is expected and reported only.
- The unforced `routes_single_auto` diagnostic adds about 19 calls per country on run 1, up to ~15 s if the generic
  plan is as slow as the after-migrations run suggests. It is the only direct evidence of the generic-plan cause.
