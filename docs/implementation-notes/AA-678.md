# AA-678 — Booking bootstrap: Infra phase 1 (OIDC trust narrowing + Booking IAM prep)

S235 (14/10/2026), branch `feat/s235-oidc-trust-booking-prep`. Phase 2 (`accounts/aa365/booking.tf`)
is a separate PR that is applied only after this one.

## Decisions

- **Trust by exact immutable subject, not name wildcards.** `GET /repos/{owner}/{repo}/actions/oidc/customization/sub`
  returned `use_immutable_subject: true` for AA-CIS-App, AA-CIS-Infra and AA-TripPlanner-Web, with
  prefixes `repo:AdventureAsia365-Ecosys@276539096/AA-CIS-App@1212291079` and
  `repo:AdventureAsia365-Ecosys@276539096/AA-CIS-Infra@1212290412`. Pinning the numeric ids is
  stricter than `repo:AdventureAsia365-Ecosys*/AA-CIS-App*:*` (that would also match a repo
  named `AA-CIS-App-x`, or an org named `AdventureAsia365-Ecosys-x`). The org has no org-level
  sub template (404), so the `@id` form comes from the repo-level setting.
- **Context stays `*`.** Callers use `environment:dev` (AA-CIS-App deploy-dev, eval-regression),
  `pull_request` (Infra terraform-plan) and `environment:prod` (Infra terraform-apply, db-migrate).
  Scoping by context would add little, because the `dev` environments have no deployment-branch
  policy (any writer could use `environment: dev` from a branch), and it would add breakage risk.
- **Booking IAM prep = three scoped statements**, not just TagRole:
  - `BookingRoleTagging`: `iam:TagRole/UntagRole` on `role/aa-booking-<env>-*` (same precedent as
    TripPlannerRoleTagging).
  - `BookingEcrRepoManage`: ECR create/delete/lifecycle/tag on `repository/aa-booking-<env>-*`.
    The role's ECRPushPull statement has no `ecr:CreateRepository`, so `aws_ecr_repository` in
    booking.tf would be AccessDenied.
  - `BookingAlbListenerRuleManage`: `elasticloadbalancing:Create/Delete/ModifyRule` and
    `SetRulePriorities` on listeners and rules of `aa-cis-<env>-alb`. No inline statement grants
    them; whether `AmazonECS_FullAccess` does could not be checked from this lane (IAM reads are
    blocked for subagents), so the grant is explicit.
- `modules/alb/outputs.tf`: only a new `http_listener_arn` output (no resource change).

## Changed

- Stale comments fixed: `modules/alb/main.tf` (the Lambda authorizer was removed in AA-750) and the
  `accounts/aa365/main.tf` header (Lambdas/Step Functions/brand_brief_parser retired in AA-750).
- The `STEP_FUNCTIONS_ARN` env in `modules/ecs/main.tf` is NOT removed. AA-750 kept it on purpose,
  because removing it changes both task definitions. That is a separate change.
- `terraform fmt` alignment fixes in `accounts/aa365/main.tf` and `terraform.tfvars` (whitespace
  only, pre-existing drift) are in a separate commit.
- The CIS migration 223 copy (`db/migrations/cis/223_*.sql`, AA-798) is NOT on this branch. The
  orchestrator adds it.

## Tradeoffs

- Fail-closed: if a repo turns off the immutable subject, or is renamed or re-created, CI loses
  the role until the list is updated. This is accepted because the recovery path (local MFA apply
  with `aa365-admin`) does not depend on the role.
- `iam:CreateRole/PassRole` on `*` (IAMRoleManage) is unchanged. Narrowing it is out of scope.
  The trust narrowing is what stops a new repo from inheriting it.

## Should know

- Expected plan: `aws_iam_role.cicd` trust update in place, `aws_iam_role_policy.cicd_inline`
  update in place, `time_sleep.wait_for_iam_propagation` replaced (its trigger is the policy
  hash), and an in-place `_iam_gate` tag update on the 3 eventbridge resources (bus, scheduler
  role, schedule group), which is the normal side effect of any `cicd_inline` change. Nothing
  else may change.
- Apply this BEFORE booking.tf is planned or applied (IAM propagation trap).

# AA-678 — Booking bootstrap: Infra phase 2 (`accounts/aa365/booking.tf`)

S235 (14/10/2026), branch `feat/s235-booking-service`, stacked on phase 1
(`feat/s235-oidc-trust-booking-prep`). Apply phase 1 first.

## Decisions

- **Names follow phase 1's IAM scopes**: ECR repo, roles and target group all use the
  `aa-booking-dev-*` prefix (`aa-booking-dev-api`, `aa-booking-dev-ecs-execution-role`,
  `aa-booking-dev-ecs-task-role`, `aa-booking-dev-app-deploy`, `aa-booking-dev-api-tg`). The brief
  said ECR repo "aa-booking"; that name is outside `BookingEcrRepoManage`
  (`repository/aa-booking-<env>-*`) and would be AccessDenied, so the repo is `aa-booking-dev-api`
  (the name ADR 0004 and the Booking review also use).
- **Routing = separate REST API on the existing VPC link**, Dev on the execute-api URL. Checked
  read-only on 14/10: both CIS custom domains (`api-cis.lumiguides.it.com`,
  `api-cis-aa365.lumiguides.it.com`) have a single EMPTY base path mapping to `4ylo382khg/dev`, so
  a `booking` base path cannot be added; the CIS REST API has no catch-all proxy, and adding
  `/booking` there means editing `modules/api_gateway` (out of scope) plus a CIS redeploy. The ACM
  cert `257ca800…` covers only `api-cis-aa365.lumiguides.it.com`, so no `api-booking.*` domain yet.
- **ALB rule** on the HTTP listener (the NLB → ALB hop is :80), priority 100, paths `/booking` and
  `/booking/*`. Read-only check on 14/10: both ALB listeners have only the default rule, and the
  only target groups are `aa-cis-dev-api-tg` and `aa-cis-dev-nlb-tg`, so no clash.
- **Secret container only** (no `aws_secretsmanager_secret_version`): Terraform never holds the
  DSN, not even `REPLACE_ME`. Until Nghiệp puts the value, a task cannot start — fail closed, and
  the service is at 0 anyway.
- **Least-privilege roles, no AWS managed policies**:
  - execution role: ECR pull on the Booking repo, logs on `/ecs/aa-booking-dev`, GetSecretValue on
    `booking/dev/database-url` only (not `AmazonECSTaskExecutionRolePolicy`, which is `*`);
  - task role: only the four `ssmmessages:*` actions for ECS Exec;
  - deploy role: ECR push on the Booking repo, `ecs:RegisterTaskDefinition` scoped to
    `task-definition/aa-booking-dev-api:*` (the Service Authorization Reference lists
    `task-definition*` as the resource for this action), `UpdateService`/`DescribeServices` on the
    Booking service ARN only (UpdateService also conditioned on a Booking task definition,
    `StringLikeIfExists`), `ListTasks`/`DescribeTasks` in the cluster for the image-SHA check,
    `PassRole` on the two Booking roles with `iam:PassedToService = ecs-tasks.amazonaws.com`.
    Why the family scope matters: CIS deploy-dev copies the LATEST revision of `aa-cis-dev-api`
    (`describe-task-definition --task-definition "$FAMILY"`), so a role that could register into
    that family could change what CIS deploys next.
- **OIDC trust**: contexts `environment:dev` and `ref:refs/heads/main` only. The repo does not
  exist yet, so its id is unknown: `var.booking_github_repo_id` (default empty) accepts the
  immutable form with any id plus the plain form, both pinned to the exact name `AA-Booking` and
  (immutable form) to org id 276539096. Setting the id narrows the trust to the exact immutable
  subject.
- **ECR tags immutable**: ADR 0004 decision 4 (one image per git SHA). This is NOT the CIS
  `:latest` convention in this repo's `.claude/CLAUDE.md`, which applies to `aa-cis-dev-api` only.
- **Service**: `desired_count = 0`, `ignore_changes = [desired_count, task_definition]`, FARGATE
  base 1 + FARGATE_SPOT weight 3 (same as CIS), min healthy 100 % (single task), circuit breaker
  with rollback, grace 60 s, ECS Exec on, app SG `sg_app_id` (ALB → app all ports, app → RDS 5432).
  0.25 vCPU / 0.5 GB.
- **Container contract** (matches `AA-Booking/backend`): container `api`, port 8000, env
  `ENVIRONMENT=dev`, `DB_SSL=require`, secret `DATABASE_URL`; health probe in Python (no curl in
  `python:3.12-slim`). Placeholder image tag `bootstrap` is never pushed.
- **Throttling** on the Booking stage (20 rps, burst 40): the edge is unauthenticated and the ALB,
  NLB and RDS are shared with CIS.

## Tradeoffs

- No custom domain for Dev: clients use the execute-api URL until a cert and hostname are decided.
- The ALB is internet-facing, so `/booking/*` is also reachable on the ALB DNS name over HTTP (as
  CIS paths are). The app must authenticate every non-health route itself.
- The deploy role can change the service's desired count (UpdateService). Accepted: it is scoped to
  the Booking service, and the CIS services are not reachable with it.
- `ecs:task-definition` condition semantics are not fully documented (ARN vs family:revision); both
  forms are listed. If the first deploy is denied on UpdateService, check this condition first.
