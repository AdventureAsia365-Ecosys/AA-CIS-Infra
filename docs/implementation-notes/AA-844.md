# AA-844 (S246) part 2: photos CDN and the daily photo_sync schedule

CloudFront `img.lumiguides.it.com` in front of the bronze bucket's `photos/` prefix, and a third
ops-probe schedule that calls `POST /admin/photos/sync/schedule` once a day. The CI apply grant is
the separate branch `chore/aa-844-cloudfront-apply-grant` (notes `AA-844-grant.md`) and must be
applied locally first. The app side (302 target, schedule endpoint, admin card) is AA-CIS-App
branch `feat/aa-844-photo-cdn-schedule`.

## Decisions

- **Host resolved in the CIS app, not in the catalog views.** `/content/photos/{id}` keeps being the
  public path (views, TripPlanner, Booking admin unchanged); only its 302 target moves from a
  presigned S3 URL to this distribution. Every image view still goes through API GW, WAF, ECS and
  one DB lookup; CloudFront serves the bytes.
- **`origin_path = "/photos"`** plus a bucket-policy statement scoped to `photos/*`: two independent
  fences keep `scripts/`, `batch-*/` and `raw-*/` of the same bucket out of reach. Viewer URLs are
  therefore `https://img.../<country slug>/<file>`; the app strips the `photos/` prefix.
- **No ListBucket** for the CloudFront principal: a missing key is a 403, never a listing.
- **Cache key = path + `v` only.** The app appends `?v=<sha256[:12]>` of the source bytes, so a
  Drive edit that overwrites the same S3 key gets a new cache entry without an invalidation.
- **TTLs** min 1 day, default and max 1 year. Objects already carry
  `CacheControl: public, max-age=31536000` from `put_object` (photo_sync), so the viewer sees the
  long header from the origin.
- **Response headers policy: nosniff + HSTS (1 year, no includeSubdomains/preload), no
  Cache-Control override.** A headers policy also applies to error responses, so an override would
  make browsers keep a 403 for a key that is not synced yet for a year; and `immutable` would be
  wrong because keys get overwritten.
- **`custom_error_response` for 403 and 404 with `error_caching_min_ttl = 60`** (no custom page):
  a miss on a key photo_sync has not uploaded yet is cached at the edge for one minute only.
- **`allowed_methods` and `cached_methods` = GET, HEAD**: the Done-when check is two HEAD requests,
  the second one a Hit.
- **Gating like `custom_domains.tf`:** cert + validation CNAME always; validation wait,
  distribution and A/AAAA aliases only with `photos_cdn_enabled && custom_domains_enabled`. The OAC
  and the two policies are free and always present.
- **Separate validation-record resource** (`aws_route53_record.photos_cdn_acm_validation`): the
  existing `acm_validation` for_each over the api/auth certs is not touched, so no record of those
  certs is re-addressed.
- **`photos_cdn_subdomain` (default `img`)** instead of a `photos_cdn_host` variable: a variable
  default cannot reference `var.dns_zone_name`.
- **Schedule 21:00 UTC (04:00 ICT)**, after retention at 20:30, 30-minute flexible window, retry 2:
  the run ends before 00:00 UTC, so the UTC day the API keys its idempotency on is the intended
  day. The path is in `_ALLOWED_PATHS` only, never in the default 06:15 probe run.
- **No logging, no WAF** on the distribution (static public images; WAF would add ~$5+/month).

## Tradeoffs

- **PriceClass_100** has no Asian edges, and most viewers are in Asia. It is the cheapest class;
  PriceClass_200 is a one-line variable change if latency matters.
- **302 through the API vs direct CDN URLs in the views:** keeps the read contract, TripPlanner and
  Booking unchanged, at the cost of one API hop per image view (the CIS side caches the 302 for
  1 day in the browser, `max-age=86400`; see the AA-CIS-App note).
- **Exact `AWS:SourceArn`** instead of `arn:aws:cloudfront::<account>:distribution/*`: tighter, but
  the policy JSON depends on an ARN unknown before the first apply (see Should know).

## Should know

- **Plan display of the bronze policy:** on the first apply the distribution ARN is unknown, so the
  plan shows `aws_s3_bucket_policy.bronze` as an in-place update with `policy = (known after
  apply)` rather than a statement diff. The code keeps the 5 existing statements byte-for-byte;
  after apply confirm with `aws s3api get-bucket-policy` (one line) that there are 6 statements and
  the 6th is `AllowPhotosCdnRead`.
- **Expected plan:** create cert, validation record, cert validation, OAC, cache policy, headers
  policy, distribution, A and AAAA records, schedule (10); update bronze bucket policy and the
  ops-probe Lambda code hash (2); 0 destroy. The Lambda update means the manual idle gate applies
  (CONTEXT.md: an apply touching `aws_lambda_function` has no job guard).
- **Rejected photos stay reachable at a leaked CDN URL.** `photo_image` hides `status='rejected'`,
  but the S3 objects remain; before, a leaked presigned URL died within 1 hour. The key holds an
  unguessable Drive file id and there is no ListBucket, but a URL leaked before the reject keeps
  working. Decision for Nghiệp; not fixed here (options: delete/move rejected objects in photo_sync,
  or an invalidation on reject).
- **Versioned bucket:** a Drive edit overwrites the same key and the old version is kept (small
  storage growth; lifecycle rules only touch `raw-archive/` and `archive/`).
- **Cost:** CloudFront always-free tier (1 TB, 10M requests a month) means ~$0 on Dev, but acc2 is
  billed through the TrueIDC reseller payer and the free tier is per payer, so it may be used up.
  Worst case pay-as-you-go on Dev (~10 GB ~ $0.85 + ~$0.01 per 10k requests): under $2/month. ACM,
  alias queries and S3-to-CloudFront transfer are $0; S3 GETs on misses ~$0.0004 per 1k; Scheduler
  and Lambda within the free tier.
- **If the schedule fires before the CIS endpoint is deployed**, the Lambda logs a 404 and returns
  (no raise, no retry storm). Harmless.
- **`?v=` through OAC:** the `v` query string is forwarded to S3, which ignores unknown query
  parameters on GetObject. If it were rejected, drop `v` from the cache policy and invalidate on
  change instead (1,000 paths a month free).
- Not run locally: `terraform init/validate/plan` (by instruction; CI plan is the check).
  `terraform fmt -check` passed on every touched file; ops-probe unit tests pass (16).
