# AA-286/AA-287 — aa-cis-dev-role IAM fix for Budgets + CloudTrail (S102 Phase 3d)

Repo/file: `accounts/aa365/cicd.tf` (`aws_iam_role_policy.cicd_inline`, Sid pattern)

## Decisions

- Root cause: run #59 (post PR #13 merge) failed applying `aws_budgets_budget.total_monthly`
  and `aws_cloudtrail.main` — `aa-cis-dev-role` (the GitHub Actions OIDC role
  `terraform-apply.yml` assumes) had never needed Budgets or CloudTrail
  permissions before this account's first use of either service.
- Followed the exact existing pattern in `cicd_inline` (one `Sid` block per
  service/feature added over time — `ELBManageVpcLinkNLB`, `WAFv2Manage`,
  `DynamoDBStateLock`, etc.) rather than a new standalone policy/role — two
  new Sids added: `BudgetsManage`, `CloudTrailManage`.
- **Budgets**: `budgets:ViewBudget` + `budgets:ModifyBudget` only — not the
  older granular `CreateBudget`/`DescribeBudget`/`UpdateBudget`/`DeleteBudget`.
  Confirmed via AWS's own Cost Management IAM reference
  (docs.aws.amazon.com/cost-management/.../billing-permissions-ref.html):
  any account or AWS Organization created on/after 2023-03-06 already runs
  on the fine-grained model where `ViewBudget`/`ModifyBudget` gate all
  Budgets read/write API calls — the granular actions are superseded, not
  additive.
- **CloudTrail**: 15 actions, cross-checked against the actual
  `terraform-provider-aws` source
  (`internal/service/cloudtrail/trail.go`) rather than guessing from docs —
  `CreateTrail`, `UpdateTrail`, `DeleteTrail`, `DescribeTrails`, `ListTrails`,
  `GetTrailStatus`, `StartLogging`, `StopLogging`, `GetEventSelectors`,
  `PutEventSelectors`, `GetInsightSelectors`, `PutInsightSelectors`, plus
  CloudTrail's own tagging API (`AddTags`/`RemoveTags`/`ListTags` — not the
  generic `TagResource`/`UntagResource` some newer services use). Included
  the Insight/EventSelector actions even though `aws_cloudtrail.main` doesn't
  set those blocks, since the provider's Update path calls them
  unconditionally — omitting them would just be the "5th round-trip" failure
  pattern already documented three times over in `AA-272.md` (ELB, DynamoDB,
  WAFv2).
- Both Sids use `Resource = "*"` — not a wildcard *action* (no `budgets:*`/
  `cloudtrail:*`), but the correct scoping for these specific actions. AWS's
  own CloudTrail IAM policy examples state the Resource element is always
  `*` for these actions; Budgets' consolidated `ViewBudget`/`ModifyBudget`
  are account/console-level virtual actions with the same characteristic.
  This matches the existing file's own convention (11 of the pre-existing
  12 Sids already use `Resource = "*"`; only `DynamoDBStateLock` is ARN-scoped,
  specifically because DynamoDB unambiguously supports resource-level ARNs).
