# AA-1164 — Scan the images that actually run, nightly (Infra part)

Lane l8-aa1164-image-scan, S287. The Node base-image pins are separate PRs in AA-CIS-App, AA-Booking, AA-Partner and
AA-TripPlanner-Web (their own `docs/implementation-notes/AA-1164.md`).

## Decisions

- **Workflow in AA-CIS-Infra, not the root repo:** the read-only plan role `aa-cis-infra-tf-plan` already trusts this
  repo's `ref:refs/heads/main` (docs-gen.yml uses it the same way) and its ReadOnlyAccess covers `ecs:List*` /
  `Describe*` and the ECR pull reads. No new read permission.
- **What runs, not what is deployed:** `ecs list-services` -> `list-tasks --desired-status RUNNING` ->
  `describe-tasks`, tasks whose `lastStatus` is RUNNING only, one entry per `imageDigest` + platform (the api and the
  worker share one digest, scanned once). Platform from the task attribute `ecs.cpu-architecture`.
- **Pull by digest, SBOM once, scan every night:** Trivy writes a CycloneDX SBOM from the image read by digest
  (`--image-src remote`), the SBOM is cached per digest (Actions cache, saved on main only, pruned to the running set),
  and every night `trivy sbom` scans it with that day's DB. An unchanged digest is never pulled again, which keeps ECR
  data transfer out inside the free tier (the issue's 0 USD Done-when).
- **Syft not used:** the issue names Syft for the SBOM. Trivy's own CycloneDX SBOM is the one `trivy sbom` reads back
  reliably, so one tool gives the SBOM and the scan from a single pull. Syft stays pinned in release-bin if a second
  SBOM format is ever wanted.
- **One rule, one register:** the triage is the root `tools/security/vuln_triage.py` (AA-1163) run per image with the
  image's OWNER repo as `--input <repo>=<trivy.json>`, against root `docs/security/vuln-exceptions.toml`, both read
  from root master at run time (sparse checkout). Nothing is forked into this repo. A register row accepts a finding
  when repo = owner, source = trivy, id = the CVE/GHSA, not expired.
- **Gate (all in `tools/security/image_scan.toml`):** fails when a finding is not accepted, has a fixed version
  (`require_fix`), and its class is in `classes` (P0, P1) or its Trivy severity in `severities` (CRITICAL, HIGH); an
  image that could not be scanned fails too (`fail_on_scan_error`). Unfixable findings are counted, not paged: they are
  the monthly triage's job.
- **Where the details go:** the run summary (counts by level, fixable C/H, P0/P1, accepted, gate per digest, the gate
  failures), the run artifact (masked Trivy JSON, triage JSON, SBOMs; 14 days), and the masked `summary.json` in the
  private `docs-reader/security/image-scan/` prefix of the bronze bucket (new upload role, below). SARIF to code
  scanning was not used: the ci-bot App has no Code scanning permission for the owner repos, and Infra's own code
  scanning would hold every image finding a second time as "AA-CIS-Infra code scanning #n" in the monthly triage,
  accepted through a different key.
- **Upload role** `aa-cis-dev-image-scan-upload` (`accounts/aa365/image_scan.tf`): this repo's main only, PutObject on
  one key, workload boundary, listed in the Access Analyzer archive rule. The plan role is assumable from pull
  requests, so it never gets a write. The bucket name comes from the account id at run time (`upload-uri`).
- **Masking:** every file the tool writes outside `running.json` goes through `tools/docs/aws_mask.py` and is checked
  with `find_leaks` (exit 2 on a leak; a masked bare number that would break JSON is refused). `running.json` keeps the
  pull references (the registry host names the account) and stays in RUNNER_TEMP. The workflow masks the account id
  before any AWS output.
- **WordPress sidecar pin bumped** (`modules/environment/test_wp.tf`, 7.1.4 -> 7.1.5 digest of 21/11): the first local
  run of the tool found 45 fixable CRITICAL / HIGH findings in the 7.1.4 digest (apache2, zlib1g, linux-libc-dev), none
  fixable in the new one. Owner of third-party images = this repo (`[[owners]]` last row).

## Tradeoffs

- A new digest is pulled from a GitHub runner (data transfer out); caching SBOMs by digest bounds that to the images
  deployed since the night before.
- `trivy sbom` on a cached SBOM finds what the SBOM lists; anything Trivy would only find by reading the image again
  (a newly supported language analyser) appears when the digest changes. Bump the cache key prefix (`image-sbom-v1-`)
  after a Trivy upgrade to re-read every running digest once.
- Nightly gate on HIGH fixable findings can go red on a Monday CVE before anyone redeploys: that is the alert the issue
  asks for; the way out is a rebuild (the Node images now pin their base by digest with Dependabot bumps) or a register
  row with its `.trivyignore` entry.

## Should know

- Settings: the gate values are in `image_scan.toml` because no admin settings mechanism exists for CI policy yet
  (same as AA-1163's `vuln_triage.toml`). Follow-up for the compliance settings issue: seed them from this file.
- Merge order: root PR #924 (AA-1163: the triage tool and the register) must be on root master before the first run,
  else the triage step stops with "root checkout has no tools/security/vuln_triage.py".
- After merge: Terraform apply (the role, the WordPress pin), set secret `IMAGE_SCAN_UPLOAD_ROLE_ARN` from the output
  `image_scan_upload_role_arn`, dispatch the workflow once (cron of a new workflow is not trusted until it ran once).
- The test-wp sidecar takes the new pin only at the next Booking admin deploy (the Booking Node-pin PR does that).
- Checked against root master after #924 merged (21/11): the root triage tool's JSON (`findings[].cls`, `fixed_in`,
  `status` "accepted until ...", `severity` lower case) is what `evaluate()` reads; an invented fixable HIGH gates, an
  invented unfixed CRITICAL does not. The unit test of `triage` mocks the root tool, so a change of that JSON shape in
  the root repo shows up only in the nightly run (the report step then fails with "no triage output" or wrong counts).
