# AA-993 Phase E, slice M2b — expand runtime post-check (exit 14) and `--classify`

Design: root `docs/audits/2026-10-26-S252-aa993-delivery-pipeline/design.md` §1 D2.3, §2 M2b; critic points 3, 6, 19;
root ADR 0017 decision 3 (Proposed). Builds on M2a (#478: header, lint, lock risk, CIC validity, apply lock). Nothing
applies expand files automatically after this slice: `migration-apply.yml` is M3.

## Decisions

- **The post-check lives in `db/run_migration.py`, not in `db/expand_check.py`.** DB Migrate ships exactly one file to
  the task (`RUNNER_URL`, `exec` of `run_migration.py`), so a second module would not exist at apply time.
  `db/expand_check.py` is the `--classify` CLI; it imports the runner and the replay.
- **One catalog query, every non-system schema** (`EXPAND_SNAPSHOT_SQL`), not only the owner's schemas: an expand file
  of one owner that touches another owner's object is also caught. Rows: schemas, relations (owner, grants, RLS
  enabled / forced, relfilenode, options, persistence, partition flag, sequence parameters, view definition), columns,
  indexes, constraints (tables and domains), policies, non-internal triggers, rules, functions per identity signature,
  non-array types (enum labels, domain definition), `pg_default_acl`, and `pg_stat_xact_user_tables` counters. No
  owner filter, so objects owned by the owner role are included (critic 3; `OBJECTS_SQL` drops them).
- **Definitions are md5'd and read with a pinned `search_path`** (`expand_snapshot` sets `pg_catalog, pg_temp` with
  `set_config` around the query and puts the caller's value back): `pg_get_viewdef` / `pg_get_functiondef` /
  `pg_get_expr` qualify names by `search_path`, and the switched path pins it between the two snapshots.
- **Fields are joined with `array_to_string(ARRAY[…], '|', '')`**, not `concat_ws` (which drops NULLs and shifts the
  positions), so a finding names the field that changed (`EXPAND_FIELDS`), e.g. "relation booking.trip: storage
  (relfilenode: a table rewrite) changed".
- **A volatile default is caught as a table rewrite** (relfilenode changes), not by parsing the default; the same
  signal catches a domain-with-constraints column, TRUNCATE and anything else that rewrites.
- **RLS rule:** a new base table in an `owners.yaml` `expand_rls_schemas` schema (`crm` today, mirrored by
  `EXPAND_RLS_SCHEMAS`) or with a `tenant_id` column (any schema, RLS catalogue rule a) must be ENABLE **and** FORCE.
  No schema has RLS on every table (live dump, S256: crm 70 of 79 forced, the CIS schemas mixed, booking none), so
  "a schema whose tables require RLS" became a registry list plus the tenant_id rule.
- **Partitions:** a new partition / child of an existing table is contract (it routes rows of a live table).
- **Rows:** any insert / update / delete counted on an existing table is contract except `shared.schema_versions`
  (the file's own registration). Tables the file creates may be seeded.
- **Shape:** a transactional expand file must be one `BEGIN … COMMIT` block (new lint rule), so the plain path can run
  `BEGIN`, snapshot, body, snapshot, then `COMMIT` or `ROLLBACK` + exit 14 (`run_expand_transaction`). The switched path
  (`run_switched`) takes the expand snapshot right after the ownership snapshot and checks after the ownership
  post-check, inside the same transaction. A CIC file is diffed before its registration (not registered on a finding).
- **Check mode rehearses** a transactional expand file: the body and the post-check run, then `ROLLBACK`. This is what
  the design's live proof asks for ("DB Migrate `check` … exit 0; the contract variant → exit 14"). Because it runs
  statements, it takes the apply lock (M2a's "check takes no lock" still holds for every other file). A CIC file is
  not rehearsed (it cannot run in a transaction); its apply checks it.
- **`--classify`** replays every applied file with `db/replay_migrations.py` in the live dump's order (the DB Schema
  Dump artifact `schema.json`; critic 19), then for every pending file in owner / number order: lint, rehearsal with
  the post-check (a header-less file is rehearsed as if expand, which gives the `eligible` evidence), then the real
  apply through `run_item` so the next file sees it. Without an artifact it falls back to number order (`--files`
  required; roles and extensions that only exist live are missing, said in the result as `order: number`). Exit 14
  only for target files with the expand header; a header-less file is contract by definition and never fails the job.
- **CI job "Expand classify"** (migration-copy-guard.yml, same `scope` gating, fail closed): runs the PostgreSQL tests
  on one pgvector pg15 container, then `--classify` on a fresh one for the owner-dir copies the PR adds or changes
  (schedule / manual: every pending file). Added to `tools/github/infra-main-ruleset.json` as a required check.

- **Independent review (S256) tightened two rules and one robustness gap** (own commit):
  - The registry (`shared.schema_versions`) takes at most one inserted row and no update or delete. The expand lint
    skips the registration statement, so `WITH d AS (DELETE FROM shared.schema_versions …) INSERT …` in that
    statement unregistered another key with exit 0 (reproduced on PostgreSQL 16; the ownership lint catches it only
    for non-CIS dirs, CIS owns `shared`).
  - A new `SECURITY DEFINER` function is contract: it runs with the owner role's rights (its own RLS policy) and
    EXECUTE is PUBLIC by default, so an auto-applied expand file could add an RLS bypass.
  - `expand_check.classify_one` records a per-file exception as that file's error instead of crashing the run (a
    crash would fail the required "Expand classify" check for unrelated copy PRs; a target still exits 1).

## Changed vs the design

- `db/expand_check.py` holds only `--classify`; the post-check is in the runner (single-file shipping, above).
- The "classify sets the PR label from evidence" part is not done: this slice reports the class in the job summary
  and the JSON artifact; labelling the copy PR belongs to M3's `migration-sync`, which opens those PRs.
- M2a said "M2b may relax" the lint's refusal of DO blocks / SELECT calls. Not relaxed: the static lint stays strict
  and the runtime check is a second layer, not a replacement.
- The design's 7 exit-14 cases and 3 pass cases run as PostgreSQL tests (`test_aa993_expand_check_pg.py`), plus
  extras (update / delete rows, tenant table without RLS, overload, default privileges, volatile default rewrite, type
  change, drop, plain path, rehearsal both ways, a unique CIC). They need a server; the new CI job provides one.

## Tradeoffs

- Snapshotting every schema costs one larger catalog query per expand file (thousands of rows on Dev, md5 of every
  function definition): seconds, accepted by ADR 0017 ("a catalog scan per expand file").
- A concurrent DDL by another session between the two snapshots (a job's TRUNCATE of a staging table, say) shows as a
  change and rolls the file back. Fails safe; the file is re-run. The apply lock keeps other migrations out.
- Not snapshotted (allowed silently): `COMMENT ON`, column statistics targets, extended statistics, security labels,
  operators / casts / collations. None changes how existing rows are read or written.
- New-object grants are not re-checked at runtime (the M2a lint limits grantees to the owner's runtime / nologin
  roles).

## Should know

- **A `check` of an expand file now takes real locks** for the length of the rehearsal (an `ADD COLUMN` holds ACCESS
  EXCLUSIVE on its table until the ROLLBACK, under `lock_timeout` 5 s and `statement_timeout` 30 s, after the exit-15
  size check). That is the same lock the apply takes; a check is no longer read-only for expand files.
- **Exit 14** = rolled back, not registered, every object named in the `MIGRATE ERROR` line (`db-migrate.yml` maps it).
- **Local PostgreSQL tests:** `AA993_TEST_PG_DSN=postgresql://postgres@127.0.0.1:<port>/postgres python3 -m unittest
  db.tests.test_aa993_expand_check_pg` (19 tests; ran green on a local PostgreSQL 16, S256). The classify end-to-end
  test patches the replay's PostgreSQL-15 check only inside the test (its sources create no role). A full classify
  on the live dump needs PostgreSQL 15 (on 16 the X1 ownership files fail by design); that run is the CI job's.
- **Live proof (orchestrator, after merge; needs DB Migrate dispatch):** DB Migrate `check` of an expand probe copy
  (`booking.aa993_probe` with ENABLE + FORCE RLS) → exit 0 with "expand rehearsal: post-check ok … rolled back"; the
  contract variant (e.g. `CREATE POLICY … ON booking.trip_plans USING (true)`) → exit 14 naming the policy. The probe
  copy needs the owner-repo migration-only PR first (Copy Guard). After this PR merges, re-run
  `tools/github/db_auto_apply_gate.sh ruleset` with the tech lead's login so "Expand classify" becomes required.
- **Rollback (exact):** revert this PR, then re-run the gate script `ruleset` (drops the required context). The runner
  is uploaded from `main` on every DB Migrate run; no copy carries the header yet; nothing in the DB or AWS to undo.
