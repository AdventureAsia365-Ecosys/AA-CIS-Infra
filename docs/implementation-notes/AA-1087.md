# AA-1087 — Dev-only write-capable E2E staff identities (AA-CIS-Infra half)

Root ADR 0006a A10e. The S278 system audit (gap B2) found no test identity that can write on the staff side; the tech
lead chose to build write identities before the synthetic pilot rehearsal. AA-Booking holds each identity to its own
writes on synthetic agencies (`app/auth/e2e_staff.py`); CIS gives the A10b admin one more synthetic-only write
(A10b-3, no Infra change); CIS 401 gives Booking the synthetic flag (`catalog.v_tenant_account_v1.is_synthetic`; the
Infra copy of the migration comes from the migration-sync bot, not this PR).

## Decisions
- Three addresses in the Dev-only trigger map `E2E_DEV_ONLY_TEST_STAFF` (behind `E2E_DEV_ONLY_STAFF_ENABLED`, dev
  only): `e2e-booking-staff@` exactly `booking-sales`; `e2e-booking-maker@` and `e2e-booking-checker@` exactly
  `booking-finance`. The maker and checker share a group tuple on purpose (both need finance permissions); the guard
  test "every address maps to its own group set" now allows exactly that one pair.
- Codes go to `inbound-admin/` (rule `e2e-cognito-admin`, MFA admin reads only), never to the CI-readable `inbound/`:
  these sessions write.
- Users are created by `tools/identity/crm_dev_identity.py e2e-booking-writers` (AdminCreateUser SUPPRESS, no
  password, exact groups), not by Terraform: ADR 0006 section 3 keeps WORKFORCE users out of Terraform state (A10a /
  A10c were created the same way). The `e2e-staff` code was factored into one helper used by both commands.

## Changed
- `accounts/aa365/lambda_src/identity_triggers/workforce.py` (three constants + map entries + docstring) and its tests.
- `accounts/aa365/e2e_mailbox.tf`: `local.e2e_mail_booking_writer_recipients`, appended to the `e2e-cognito-admin`
  rule's recipients (dev only, count).
- `tools/identity/crm_dev_identity.py` `e2e-booking-writers` + tests; `tools/identity/README.md` row and runbook.
- `CONTEXT.md` (the mailbox line).

## Tradeoffs
- No new group: the identities use the existing `booking-sales` / `booking-finance` groups; Booking's allow-list, not
  a new group, keeps them narrow.

## Threat note
- A leaked code (MFA admin role, or control of the E2E mail domain) yields a Dev Booking session of that role, capped
  by Booking to its allow-listed writes on synthetic agencies. Outside dev the trigger never issues the token
  (flag + precondition) and Booking refuses the identity (exact `ENVIRONMENT=dev`).
- Look-alike addresses (non-ASCII, extra sub-domain, other local part) are denied by the ASCII-only exact lookup
  (tests).
