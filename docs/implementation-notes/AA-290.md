## The deployment_id / triggers problem (the hard part — flagged for review, not resolved unilaterally)

`aws_api_gateway_deployment.this`'s `triggers` block is
`sha1(join(",", [8 integration URIs, authorizer id]))`. This value is
**not stored anywhere in the AWS API** — it's a Terraform-only bookkeeping
value used purely to decide when to force a new deployment. The AWS
provider has no `Update` for this resource (API Gateway deployments are
immutable snapshots), so **any** diff on `triggers` — for any reason —
always forces `create_before_destroy` replace, never an in-place update.
(Confirmed against community precedent, not assumed:
[registry.terraform.io/.../api_gateway_deployment](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/api_gateway_deployment),
[hashicorp/terraform-provider-aws#17341](https://github.com/hashicorp/terraform-provider-aws/issues/17341),
[aws-samples/apigateway-deployment-lifecycle-management-terraform](https://github.com/aws-samples/apigateway-deployment-lifecycle-management-terraform).)

Current state: Terraform still tracks deployment `zjas9n` (the pre-cutover,
ALB-based deployment). Live/actual: stage `dev` points at `62rsje` (created
out-of-band via `aws apigateway create-deployment` during cutover attempt
#4, 2026-07-10T09:52:52Z). These are two different deployment IDs with two
different (but now, post-fix, equivalent-in-effect) URI sets baked in.

Fixing the 8 integrations' code changes what `triggers` computes to
(verified locally, no AWS calls: `sha1(join(",", [...]))` over the 8 live
NLB URIs + authorizer id `22qdq8` = `5592f7e905d488ad153d2cc8451246ca3be14b86`).
State's stored trigger value (from when `zjas9n` was created) reflects the
old ALB URIs, so it will never match — meaning **the code fix alone does
not produce a "no changes" plan for `aws_api_gateway_deployment.this` /
`aws_api_gateway_stage.dev`**, regardless of how correct the integration
code now is.

Two ways to actually reach zero-diff, with different risk profiles:

1. **Let Terraform replace the deployment on apply.** Standard,
   AWS-sample-documented mechanism working exactly as designed — a fresh
   deployment gets created whose content matches the (now-correct) live
   VPC_LINK/NLB config, and the stage points at it. Functionally safe (same
   routing as what's live today), but is a real replace — a new deployment
   activates, not zero-effect — and this system has already had two live
   incidents (WAF geo-block, NLB SG) from cutover-adjacent changes. Doesn't
   meet the task's literal "plan → no changes" bar.
2. **`terraform import` deployment `62rsje` + hand-patch state's `triggers`
   attribute** to the computed hash above (`terraform state pull` → edit →
   `terraform state push`), so plan is byte-for-byte clean with zero
   deployment/stage diff. Reaches the literal "no changes" bar, but is
   direct state-file surgery on a production-critical resource — no
   `terraform import` flag sets `triggers` directly, so this requires manual
   JSON editing of pulled state, which itself carries a state-corruption
   risk if done imprecisely.

**Decision (Nghiep, post-CI-plan review): accept replace-on-apply (option
1).** CI's plan on this PR confirmed the 8 integration fixes are byte-for-byte
correct — the computed trigger hash matched the local pre-push calculation
exactly (`5592f7e905d488ad153d2cc8451246ca3be14b86`), and all 8
`aws_api_gateway_integration` resources show zero diff. Only
`aws_api_gateway_deployment.this` (replace) and `aws_api_gateway_stage.dev`
(`deployment_id` update) remain in the plan — expected and accepted. State
surgery (option 2) was explicitly not pursued, given the risk of hand-editing
state on a production resource for a cosmetic "no changes" plan when the
functional outcome (fresh deployment matching live routing) is identical
either way.
