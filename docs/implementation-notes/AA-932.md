# AA-932 — CRM-04 Infra + DB owner `crm` (lane aa932-crm-infra, S248)

Source: root `docs/audits/2026-10-21-S246-crm-design-v3/design-v3.md` §3.1 (placement, roles), §4.1 (keys), §6.3
card CRM-04; ADR 0008a decisions 1–2, ADR 0010 decisions 2–3, ADR 0003a; data standards v1.3 (DM-6.8, DM-7 CRM rows,
C2.2 `crm_app` 6 / pool 3); Linear AA-932 comment of 22/10/2026 (connection budget).

Scope of this lane: the DB owner (roles, registry, first migration, probe, budget), the runtime DSN secret shell and
the three KMS keys with their policies and alarms. The rest of the CRM-04 checklist (ECR, task definitions, service,
SGs, ALB/CloudFront host rules, OIDC deploy role, budget, the four buckets, nightly key-policy diff, Decrypt-rate
anomaly alarm) is listed under "Not done here" below.

## Decisions

- **Owner `crm` through the ADR 0008 playbook, unchanged tooling.** `owners.yaml` entry + every mirror the registry test
  names (`run_migration.py` `OWNER_DIRS` / `IDLE_EXEMPT_KINDS` / `PASSWORD_ROLES`, `check_migration_copies.py`
  `OWNERS` / `PATH_RE`, `db-migrate.yml`, `isolation_probe.py`, the CIS `rls_catalogue_rules.py` copy). Repo
  `AA-Partner`, path `api/migrations` (ADR 0010: `api/` holds the FastAPI app), key prefix `crm-` (ADR 0008a, DM-1),
  job table `crm.job`, kind prefix `crm_`.
- **Born under its owner role; no transfer.** rl-003 is the template render (byte-identical to
  `render_new_owner_roles.py` output, pinned by a test): `crm_owner` NOLOGIN, `crm_app` LOGIN limit 6, empty schema
  `crm` owned by `crm_owner`. So DB Migrate runs `crm-001` as `crm_owner` from the start (XD8). `owner_transfer_key`
  is `crm-001` (the probe's ownership / grant cells are expected once the first file is in).
- **NOLOGIN reader roles now (rl-004), not later.** `crm_ai_reader`, `crm_insights`, `crm_support_reader`,
  `crm_eraser` (design §3.1) are role DDL, which only a `roles/` file may do, so they come with the bootstrap; their
  object grants come table by table in later `crm-NNN` files. **`crm_app` is NOINHERIT**: it reaches the readers only
  by `SET LOCAL ROLE`, never holds their rights, and a policy `TO <reader>` does not apply to its own session (PG
  checks policy roles with `has_privs_of_role`). Registry key `nologin_roles` (optional) carries them; the CIS rules
  map and the probe mirror it.
- **CIS migration 269** (AA-CIS-App) is needed: the 243 key guard refuses every role but `bk_owner` / `tp_owner` /
  registry-owner members, and the runner refuses a switched file whose owner cannot register (exit 8). The ADR 0008
  playbook in `db/README.md` did not list this step; it is now in the "Owner `crm`" section.
- **`crm-001` content:** privilege model first (no `PUBLIC` on the schema, `USAGE` to `crm_app` + readers, default
  privileges `FOR ROLE crm_owner`: DML on tables and `USAGE, SELECT` on sequences to `crm_app`; **no PUBLIC `EXECUTE`
  on functions and no schema-wide `EXECUTE` for `crm_app`**, so `crm.erase_subject()` can be `crm_eraser`-only), then
  `crm.job` rendered from the ADR 0003a template (kind `^crm_[a-z0-9_]+$`, 5 attempts as Booking). No tenant table:
  `crm.tenant` and the RLS base template are AA-933 (`crm-002`). The registry row for `crm.job` already exists in
  data standards §7, so the retention-row check passes.
- **Idle exemption `crm_heartbeat`** (exact kind, like `bk_inquiry_pull`), not every `crm_*` kind: a real CRM job still
  blocks a migration, only the always-queued liveness kind does not (card E check). AA-933 must use this kind name.
- **Connection budget:** `crm_app` limit 6, pool 3 x 2 processes (1 task + deploy overlap, `fixed` until AA-933 adds
  the service) = 6, as C2.2. The checked total moves 162 → 168; the existing accepted overage (cause: cis-api pool 10
  instead of 5) is raised by exactly 6 with the reason rewritten. See "Should know".
- **KMS key policy model** (`accounts/aa365/crm_data.tf`): account root for administrative verbs only (no crypto, no
  `CreateGrant`) so IAM decides who administers (CI apply: create / tag / alias / rotation only; MFA admin: policy
  edits) and the CreateKey lockout check passes; crypto only for `aa-crm-dev-ecs-task-role` through
  `aws:PrincipalArn` (the role may be created later by AA-933 with no key-policy change), with the KeyProvider
  context `{tenant_id, purpose}` (exact keys, known purposes) or S3 SSE-KMS on `aa-crm-dev-*` buckets; ingest also lets
  SES receipt rules `aa-crm-dev-*` encrypt raw mail; seal = Sign / Verify / GetPublicKey; explicit Deny of every crypto
  verb to any non-service principal but the task role and `aa-crm-dev-breakglass`; `CreateGrant` only for AWS
  resources. Statements that later cards need (S3 buckets, SES rule, break-glass) are in now, because every key-policy
  change after this is a local MFA apply that fires the alarm.
- **Seal key RSA_3072 SIGN_VERIFY** (PAdES-compatible with every PDF reader; ECC P-256 is smaller but older readers
  reject it). Symmetric keys rotate yearly.
- **Alarms as EventBridge rules on CloudTrail** (same pattern as `identity_alerts.tf`): `aa-crm-dev-kms-key-admin`
  (write events, state ENABLED) and `aa-crm-dev-kms-foreign-use` (read-only crypto events: state
  ENABLED_WITH_ALL_CLOUDTRAIL_MANAGEMENT_EVENTS); one rule covers all three keys (`resources[].ARN` or
  `requestParameters.keyId`/alias). Break-glass use alerts too, on purpose. Runbook key `crm_keys` → root
  `docs/ops/runbooks/crm-keys.md`. `aws_sns_topic_policy.alerts` gets `AllowCrmEventBridgeRules`.
- **CIS task role denied `crm/*`** in `DenyMasterAndOtherAppSecrets` (same as booking/*, tripplanner/*). The migrator
  task role may read `crm/dev/database-url` (set-password, probe login).

## Tradeoffs

- Budget overage raised instead of shrinking the CRM pool to fit: the target model (C2.2) already has room (133/135 at
  cis-api 5); a CRM pool of 2 would only hide the CIS decision that is the real cause, and 3 is the standards value.
- One alarm rule per kind for all three keys instead of one per key: same coverage, half the rules; the live check
  proves each key matches.
- Reader roles created before anything grants them: harmless (they own nothing, open no connection) and avoids a
  second roles/ file and master run later.

## Should know

- **Order (no shortcut):** Infra PR without `crm-001` → rl-003 → rl-004 → CIS 269 (CIS PR + Infra copy) → AA-Partner
  `api/migrations/001_crm_schema_job.sql` on AA-Partner `main` (AA-933) → Infra copy PR with `crm/001` → `crm-001`.
  The Copy Guard fails the `crm/001` copy until the file is on AA-Partner `main` (the repo does not exist yet).
- **Verified locally** on a throwaway PostgreSQL 16 (RDS-like roles; master stand-in): the real `run_migration.py`
  applied rl-003, rl-004, 269 (as db_migrator → cis_owner) and crm-001 (db_migrator → crm_owner, ownership post-check
  clean); `crm_app` (NOINHERIT) DML on `crm.job` ok, 42501 on `booking`, `tripplanner`, `shared`; `SET LOCAL ROLE
  crm_ai_reader` → 42501 on `crm.job`; `cis_app` / `booking` / `tripplanner` / `aa_app_user` → 42501 on `crm.job`; the
  idle check reports `crm.job` busy for a queued `crm_intake_process` and idle (exempt) for `crm_heartbeat`; the
  isolation probe (dsn_file mode) passed all 23 crm cells.
- **Budget figure mismatch:** the Linear comment (and C2.2) speak of 132/135; the checker's worst case is 162 → 168
  because cis-api is 10 x 7 tasks. The overage expires 2026-12-15 and needs a decision (shrink cis-api, cut
  `max_capacity`, or measured ceiling).
- **CreateKey through CI:** the key policies pass the lockout check through the root statement; if CI apply is refused
  (MalformedPolicyDocumentException or AccessDenied on CreateKey), apply the KMS targets locally with MFA.
- Name contract for AA-933: task role `aa-crm-dev-ecs-task-role` (workload boundary), execution role reads only
  `crm/dev/*`, buckets `aa-crm-dev-*`, SES receipt rules `aa-crm-dev-*`, worker heartbeat kind `crm_heartbeat`.
