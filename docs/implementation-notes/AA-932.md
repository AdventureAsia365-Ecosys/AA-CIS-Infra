# AA-932 — CRM-04 Infra + DB owner `crm` (lane aa932-crm-infra, S248)

Source: root `docs/audits/2026-10-21-S246-crm-design-v3/design-v3.md` §3.1 (placement, roles), §4.1 (keys), §6.3
card CRM-04; ADR 0008a decisions 1–2, ADR 0010 decisions 2–3, ADR 0003a; data standards v1.3 (DM-6.8, DM-7 CRM rows,
C2.2 `crm_app` 6 / pool 3); Linear AA-932 comment of 22/10/2026 (connection budget).

Scope of this lane: the DB owner (roles, registry, first migration, probe, budget), the runtime DSN secret shell and
the three KMS keys with their policies and alarms. The rest of the CRM-04 checklist (ECR, task definitions, service,
SGs, ALB/CloudFront host rules, OIDC deploy role, budget, the four buckets, nightly key-policy diff, Decrypt-rate
anomaly alarm) is listed under "Not done here" below.

## Decisions

- **Owner `crm` through the ADR 0008 playbook, unchanged tooling.** `owners.yaml` entry + every mirror the registry test
  names (`run_migration.py` `OWNER_DIRS` / `IDLE_EXEMPT_KINDS` / `PASSWORD_ROLES`, `check_migration_copies.py`
  `OWNERS` / `PATH_RE`, `db-migrate.yml`, `isolation_probe.py`, the CIS `rls_catalogue_rules.py` copy). Repo
  `AA-Partner`, path `api/migrations` (ADR 0010: `api/` holds the FastAPI app), key prefix `crm-` (ADR 0008a, DM-1),
  job table `crm.job`, kind prefix `crm_`.
- **Born under its owner role; no transfer.** rl-003 is the template render (byte-identical to
  `render_new_owner_roles.py` output, pinned by a test): `crm_owner` NOLOGIN, `crm_app` LOGIN limit 6, empty schema
  `crm` owned by `crm_owner`. So DB Migrate runs `crm-001` as `crm_owner` from the start (XD8). `owner_transfer_key`
  is `crm-001` (the probe's ownership / grant cells are expected once the first file is in).
- **NOLOGIN reader roles now (rl-004), not later.** `crm_ai_reader`, `crm_insights`, `crm_support_reader`,
  `crm_eraser` (design §3.1) are role DDL, which only a `roles/` file may do, so they come with the bootstrap; their
  object grants come table by table in later `crm-NNN` files. **`crm_app` is NOINHERIT**: it reaches the readers only
  by `SET LOCAL ROLE`, never holds their rights, and a policy `TO <reader>` does not apply to its own session (PG
  checks policy roles with `has_privs_of_role`). Registry key `nologin_roles` (optional) carries them; the CIS rules
  map and the probe mirror it.
- **CIS migration 269** (AA-CIS-App) is needed: the 243 key guard refuses every role but `bk_owner` / `tp_owner` /
  registry-owner members, and the runner refuses a switched file whose owner cannot register (exit 8). The ADR 0008
  playbook in `db/README.md` did not list this step; it is now in the "Owner `crm`" section.
- **`crm-001` content:** privilege model first (no `PUBLIC` on the schema, `USAGE` to `crm_app` + readers, default
  privileges `FOR ROLE crm_owner`: DML on tables and `USAGE, SELECT` on sequences to `crm_app`; **no PUBLIC `EXECUTE`
  on functions and no schema-wide `EXECUTE` for `crm_app`**, so `crm.erase_subject()` can be `crm_eraser`-only), then
  `crm.job` rendered from the ADR 0003a template (kind `^crm_[a-z0-9_]+$`, 5 attempts as Booking). No tenant table:
  `crm.tenant` and the RLS base template are AA-933 (`crm-002`). The registry row for `crm.job` already exists in
  data standards §7, so the retention-row check passes.
- **Idle exemption `crm_heartbeat`** (exact kind, like `bk_inquiry_pull`), not every `crm_*` kind: a real CRM job still
  blocks a migration, only the always-queued liveness kind does not (card E check). AA-933 must use this kind name.
- **Connection budget:** `crm_app` limit 6, pool 3 x 2 processes (1 task + deploy overlap, `fixed` until AA-933 adds
  the service) = 6, as C2.2. The checked total moves 162 → 168; the existing accepted overage (cause: cis-api pool 10
  instead of 5) is raised by exactly 6 with the reason rewritten. See "Should know".
- **KMS key policy model** (`accounts/aa365/crm_data.tf`): account root for administrative verbs only (no crypto, no
  `CreateGrant`) so IAM decides who administers (CI apply: create / tag / alias / rotation only; MFA admin: policy
  edits) and the CreateKey lockout check passes; crypto only for `aa-crm-dev-ecs-task-role` through
  `aws:PrincipalArn` (the role may be created later by AA-933 with no key-policy change), with the KeyProvider
  context `{tenant_id, purpose}` (exact keys, known purposes) or S3 SSE-KMS on `aa-crm-dev-*` buckets; ingest also lets
  SES receipt rules `aa-crm-dev-*` encrypt raw mail; seal = Sign / Verify / GetPublicKey; explicit Deny of every crypto
  verb to any non-service principal but the task role and `aa-crm-dev-breakglass`; `CreateGrant` only for AWS
  resources. Statements that later cards need (S3 buckets, SES rule, break-glass) are in now, because every key-policy
  change after this is a local MFA apply that fires the alarm.
- **Seal key RSA_3072 SIGN_VERIFY** (PAdES-compatible with every PDF reader; ECC P-256 is smaller but older readers
  reject it). Symmetric keys rotate yearly.
- **Alarms as EventBridge rules on CloudTrail** (same pattern as `identity_alerts.tf`): `aa-crm-dev-kms-key-admin`
  (write events, state ENABLED) and `aa-crm-dev-kms-foreign-use` (read-only crypto events: state
  ENABLED_WITH_ALL_CLOUDTRAIL_MANAGEMENT_EVENTS); one rule covers all three keys (`resources[].ARN` or
  `requestParameters.keyId`/alias). Break-glass use alerts too, on purpose. Runbook key `crm_keys` → root
  `docs/ops/runbooks/crm-keys.md`. `aws_sns_topic_policy.alerts` gets `AllowCrmEventBridgeRules`.
- **CIS task role denied `crm/*`** in `DenyMasterAndOtherAppSecrets` (same as booking/*, tripplanner/*). The migrator
  task role may read `crm/dev/database-url` (set-password, probe login).

## Tradeoffs

- Budget overage raised instead of shrinking the CRM pool to fit: the target model (C2.2) already has room (133/135 at
  cis-api 5); a CRM pool of 2 would only hide the CIS decision that is the real cause, and 3 is the standards value.
- One alarm rule per kind for all three keys instead of one per key: same coverage, half the rules; the live check
  proves each key matches.
- Reader roles created before anything grants them: harmless (they own nothing, open no connection) and avoids a
  second roles/ file and master run later.

- **crm-001 copy split off.** The PR branch is `ea27236` + `3c7456d` + the review commits; the crm-001 copy is on the
  local branch `feat/aa932-crm001-copy` (`42e41c0`), cherry-picked after AA-Partner `main` holds the file.
- **PostgreSQL 15 re-verification.** rl-001, rl-002, 243 (setup), rl-003, rl-004, 269 and crm-001 applied with the
  real `run_migration.py` on PostgreSQL 15.19 (PGDG build, throwaway cluster), master stand-in `aa_cis_admin` =
  NOSUPERUSER CREATEROLE CREATEDB (RDS-like; PG15 gives it implicit admin over every non-superuser role and records no
  ADMIN membership row). 269 ran as `cis_owner` and crm-001 as `crm_owner` through the `db_migrator` switch; re-apply
  skips. Role catalog on 15: `crm_app` rolinherit = false, connlimit 6; each reader's only member is `crm_app`;

- **rl-003 is not re-runnable after rl-004** (its "new roles are members of nothing" guard then sees `crm_app` in the

  the guard comes from the shared new-owner template.
- **S3 Bucket Keys.** `CrmRuntimeS3Objects` (data, ingest) accept `aws:s3:arn` = bucket ARN or object ARN
  (`local.crm_bucket_s3_arns`), so CRM-12 / AA-933 may enable Bucket Keys. Contract line in `cicd_crm.tf`.
- **Tag changes alarm.** `aa-crm-<env>-kms-key-admin` also matches `TagResource` / `UntagResource`: the CI boundary
  deny keys on `App = crm`. A tag change made by a planned apply alarms too (expected; the runbook says so).
- **Break-glass gets a real, narrow Allow** (`CrmBreakGlassOneAgency`, data key only): `kms:Decrypt` when
  `kms:EncryptionContext:tenant_id = ${aws:PrincipalTag/tenant_id}` (session tag required), keys exactly
  `{tenant_id, purpose}`, a known purpose, `BoolIfExists aws:MultiFactorAuthPresent = true`. Design v3 §5.5 L3.

  say whether a chained session carries the MFA key; MFA is enforced in the break-glass trust policy (CRM-13b, contract
  in `cicd_crm.tf`). CRM-13b E check: a break-glass Decrypt for tenant A works, for tenant B is AccessDenied.
- **Not verified here:** a targeted plan / Access Analyzer `validate-policy` of the changed key policies (the MFA

## Rest of the card (S248, lane infra-docs): budget, buckets, key-policy diff, Decrypt-rate alarm

Source: design v3 §3.6, §4.1, §4.9, §7; data standards DM-7 rows `crm.audit_event` (archive), raw inbound mail, export
files; master plan risk note "keep Dev governance-only and guard it in tests".

### Decisions

- **Budget `crm` = 25 USD/month** in `var.per_app_monthly_budgets` (same mechanism as the AA-896 rebalance, #298:
  TagKeyValue `user:App$crm`, 80 % actual / 100 % forecast to the alerts topic). Design §7 puts Dev at $13–22 (worst
  $26–33). To keep the per-App sum at the 250 USD account budget, **tripplanner 25 → 10** (run-rate ~1 USD/month).
- **Bucket names** `aa-crm-<env>-{audit-c,audit-g,documents,ingest}-<account>` (naming contract in `cicd_crm.tf`;
  `-c` / `-g` are the design's tier names). `audit-c` = the 12-month tier: GOVERNANCE on Dev, COMPLIANCE only through
  `var.crm_audit_compliance_enabled`, which a precondition refuses on Dev; `audit-g` = GOVERNANCE, 7 years.
- **Keys:** audit tiers and ingest use the ingest key (design: "ingest for raw mail and the audit export"), documents
  the data key; Bucket Keys on every bucket (the key policies already accept the bucket ARN as `aws:s3:arn`).
- **Lifecycle:** audit versions expire one day after their retention (366 / 2558 days; lifecycle never removes a locked
  version), noncurrent versions 1 day after that; documents keep replaced versions 7 days (erased data ≤ 30 days) and
  expire `exports/` after 7 days (DM-7 export files); ingest expires everything after 1 day, not versioned.
- **Bucket policies:** TLS only; a PutObject that *names* another SSE algorithm or another KMS key is denied (each deny
  is `Null = false` AND `StringNotEquals`, so a request without the header, i.e. the bucket default, passes);
  ingest lets SES PutObject only from receipt rules `aa-crm-<env>-*` of this account.
- **No task-role object grants** here: CRM-09 (documents), CRM-12 (audit export) and CRM-17 (SES ingest) add theirs.
- **Plan guard Object Lock rule** (`tools/terraform/plan_guard.py`): refuses a COMPLIANCE create and any update /
  delete / replace / forget / import of `aws_s3_bucket_object_lock_configuration`, and deleting an
  `object_lock_enabled` bucket; a GOVERNANCE create passes. Plus a static test that the Terraform source can only put
  `audit-c` in COMPLIANCE, behind the false-by-default variable and the Dev precondition.
- **Nightly key-policy diff** = live `GetKeyPolicy` vs the policy in the Terraform state (not the code: a merged but
  unapplied PR is not drift), normalised (statement and list order, string vs one-element list). Read-only plan role,
  sub `ref:refs/heads/main`, like `docs-gen.yml`; output names keys and Sids only (public logs). A red run is the
  alert (GitHub failure e-mail).
- **Decrypt-rate anomaly alarm** via EventBridge → CloudWatch Logs → metric filter → anomaly-detection alarm. KMS has
  no per-key Decrypt metric and CloudTrail has no CloudWatch Logs delivery here; `AWS/Usage CallCount` is account-wide
  (CIS and every service would drown the CRM signal). Log group 365 days (security/audit class).

### Tradeoffs

- One anomaly alarm on the sum over the three keys, not one per key: Decrypt is rare by design (cached DEKs, Bucket
  Keys), so the sum already shows a storm; 3 alarms would triple the cost for no new signal.
- Anomaly detection on a sparse Dev metric is noisy until there is real traffic; missing data = not breaching. A
  fixed ceiling cannot be combined with `ANOMALY_DETECTION_BAND` in one alarm. Revisit at Go-real.
- No Glacier transition on `audit-g`: hourly manifests are a few KB, below the 128 KB minimum where a transition pays.

### Should know

- The four buckets are created empty: ≈ $0. Alarm ≈ $0.30 + metric $0.30 = **≈ $0.60/month**.
- SES writing to an SSE-KMS (customer key) bucket relies on the ingest key statement `SesReceiptEncrypt`
  (`aws:SourceArn` = the CRM receipt rule). CRM-17's E check proves a real delivery; the fallback is SSE-S3 on the
  bucket with SES client-side encryption under the ingest key.
- Destroying an audit bucket with locked versions is impossible before retention ends (governance: only with
  `s3:BypassGovernanceRetention`, denied to CI by the boundary).
