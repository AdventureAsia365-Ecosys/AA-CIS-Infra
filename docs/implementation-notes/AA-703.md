# AA-703 — Ecosystem identity on Cognito (Phase 0 draft)

Source of truth: root ADR 0006 "Ecosystem identity" (Proposed, S236). Files:
`accounts/aa365/identity.tf`, `identity_variables.tf`, `lambda_src/identity_triggers/`,
tests in `lambda_src/identity_triggers_tests/` (`python3 -m pytest -p no:cacheprovider lambda_src/identity_triggers_tests` from `accounts/aa365`).

## Decisions
- Allow-list for WORKFORCE Google sign-in = the WORKFORCE pool itself (exactly one enabled native
  user with that email, pre-created by the staff directory), per ADR decision 5. No DynamoDB/SSM:
  triggers are outside the VPC with a 5 s limit.
- Google `hd` is enforced by default (`identity_workforce_require_hd = true`), reading `custom:hd`.
  `custom:hd` is created only when `identity_workforce_map_google_hd = true` (after the spike).
  Until one of the two is changed, Google staff sign-in is refused (fail closed).
- EXTERNAL pre sign-up identifies the app client by NAME via `DescribeUserPoolClient` (client ids in
  the Lambda env would be a Terraform cycle).
- Four functions (pre sign-up + pre token V2_0 per pool), published versions behind alias `live`.
- One shared REGIONAL WAF web ACL for both pools.

## Changed (vs ADR text)
- `PASSWORD` stays in `allowed_first_auth_factors` (Cognito requires it). `EMAIL_OTP` only once the
  SES identity variable is set (AA-811). Before that, EXTERNAL native sign-up is refused by the
  trigger (`NATIVE_SIGNUP_ENABLED=false`).
- Clients that offer a social IdP can write `email`, `email_verified`, `name` (+ `custom:hd`):
  Cognito requires write access to mapped attributes. No client has the
  `aws.cognito.signin.user.admin` scope, and native SignUp setting `email_verified`/`custom:*` is
  refused by the trigger.
- WORKFORCE link targets may be `CONFIRMED` or `FORCE_CHANGE_PASSWORD` (AdminCreateUser without a
  usable password); `UNCONFIRMED` is never accepted. EXTERNAL link targets must be `CONFIRMED`.

## Tradeoffs
- Break-glass is not technically pinned to the `breakglass` client (pure pre token trigger cannot
  know client ids); every break-glass token raises an alarm instead.
- Lambda `Errors` counts refusals too, so the Errors alarm uses a burst threshold (20 / 5 min) and
  unexpected exceptions get their own log-metric alarm.

## Should know
- Not applied, not planned against real state. Offline empty-state plan (fake credentials, all
  optional pieces off): 63 resources to add.
- The CI role has no `cognito-idp:*` / `wafv2:CreateWebACL`: apply from an admin session or grant
  first (Infra #103 is splitting the CI role).
- Managed login v2 needs a branding style per client before its pages render: output
  `identity_branding_commands` (provider 6.12+ needed to do it in Terraform).

# S237 rework — align the draft with the ACCEPTED ADR 0006 (14/10/2026)

Branch `feat/cognito-user-pools-s237`, based on the PR #105 head (`5333639`) with `origin/main`
merged in (the draft predated #103 / the CI role split; merge was clean). Supersedes the "Proposed"
statements above where they differ.

## Decisions
- **Staff = email one-time code only.** ADR 0006 was accepted with the S236 amendment: adventure.asia
  mail is on DreamHost, not Google Workspace, so there is no `hd` claim and no Internal consent screen.
  The WORKFORCE Google IdP, its secret data source, the `custom:hd` schema attribute and the four
  variables `identity_workforce_google_client_id`, `identity_workforce_google_client_secret_arn`,
  `identity_workforce_map_google_hd`, `identity_workforce_require_hd` are **removed**, not just
  `count = 0`: a staff Google path that can be switched on by one variable is exactly what the ADR
  rejected. Re-adding Google later starts from commit `5333639`.
- **WORKFORCE pre sign-up is now a pure function**: only `PreSignUp_AdminCreateUser` with an
  `@adventure.asia` email passes; every `PreSignUp_ExternalProvider` (any provider), `PreSignUp_SignUp`
  and unknown source is refused. No Cognito call, so its role has no Cognito permission at all.
- **Trigger roles 3 → 2**: `pure` (logs only: WORKFORCE pre sign-up and both pre token triggers) and
  `external-signup` (logs + ListUsers / AdminLinkProviderForUser / DescribeUserPoolClient on the
  EXTERNAL pool). Both carry `permissions_boundary = aws_iam_policy.workload_boundary.arn` — mandatory,
  the apply role's boundary denies CreateRole without it (`DenyCreateRoleWithoutWorkloadBoundary`).
- **SES gate = explicit bool** `identity_ses_enabled` (default false) + `identity_ses_identity_arn`
  (the AA-811 identity) + `identity_ses_from_address` (default `Adventure Asia <no-reply@lumiguides.it.com>`,
  S237 D5) + the two configuration-set names. A precondition refuses `enabled = true` without an ARN.
  Kept as variables (not a reference to the AA-811 `ses.tf` resource) so this PR does not depend on
  the SES PR merging first.
- **Custom domains gate = explicit bool** `identity_custom_domains_enabled` (default false) +
  `identity_custom_domain_certificate_arn` (AA-818 us-east-1 cert). Precondition refuses enabled
  without a cert. Prefix domains stay always on.
- **Callback URLs**: `tripplanner` gains `https://tripplanner.lumiguides.it.com/auth/callback` (S237
  hostname list). CIS admin / portal stay on `aa-cis.lumiguides.it.com`. Booking staff and Booking
  customer stay on localhost until their frontend hosts are decided (not in the S237 list).
- **CI**: new workflow `.github/workflows/identity-triggers-test.yml` (pytest on Python 3.12, no AWS),
  path-filtered to the trigger code and tests, on PR and push to main.

## Changed
- `identity.tf`: header rewritten (accepted ADR, prerequisites); locals; trigger roles + boundary;
  WORKFORCE IdP / data source / schema removed; WORKFORCE clients `COGNITO` only, write `name` only;
  preconditions for the two gates; output `identity_idp_redirect_uris` is now a list (EXTERNAL only).
- `identity_variables.tf`: as above.
- `workforce.py` + `test_workforce.py` + `conftest.py`: Google linking path removed; tests rewritten
  for admin-create-only. Test count 78 → 62 (the 16 removed tests covered the dropped Google path).
- `CONTEXT.md`: layout lists `identity.tf`.

## Tradeoffs
- `PASSWORD` cannot be removed from `allowed_first_auth_factors` (AWS: "The Password option is always
  available"; first factors are pool-wide, not per client). ADR decision 2 ("EXTERNAL EMAIL_OTP only",
  "PASSWORD only for break-glass") is met by procedure: nobody but break-glass has a known password,
  recovery is admin_only, no client enables ALLOW_USER_PASSWORD_AUTH / ALLOW_USER_SRP_AUTH. Residual:
  a traveller could `SignUp` on a public EXTERNAL client with a password of their own choosing and
  later sign in with it; the pre sign-up event does not expose whether a password was given.
- With `identity_ses_enabled = false` the WORKFORCE pool has no working staff sign-in (only
  break-glass). Accepted: applying early still fixes pool ids / issuers for the app verifier config.

## Should know
- Plan (local, read-only, `-target` = every resource in identity.tf, `-lock=false`, real state):
  **60 to add, 0 to change, 0 to destroy** (was 63: one role and two role policies fewer). The CI plan is
  untargeted and also shows any unrelated drift on main.
- Apply prerequisites (none can be done by this PR):
  1. AA-811 bootstrap grant live on `aa-cis-infra-tf-apply`: `cognito-idp:*`,
     `wafv2:CreateWebACL/DeleteWebACL/CheckCapacity`.
  2. Before `identity_ses_enabled = true`: `iam:CreateServiceLinkedRole` for
     `email.cognito-idp.amazonaws.com` on the apply role, **or** the role
     `AWSServiceRoleForAmazonCognitoIdpEmailService` already exists in acc2 (Cognito creates it with
     the caller's credentials when the pool switches to DEVELOPER email). Not in the AA-811 lane plan yet.
  3. Before setting EXTERNAL Google/Facebook variables: add their secret ARNs to
     `local.tf_plan_secret_arns` (bootstrap, local apply), or CI plan fails on refresh.
- Spike still open (ADR Open item 3c): a user created by `AdminCreateUser` without a password and
  with `MessageAction=SUPPRESS` is `FORCE_CHANGE_PASSWORD`; confirm it can sign in with `EMAIL_OTP`
  before AA-816 builds the directory on that assumption.

# S237 adversarial review (14/10/2026)

## Changed
- Corrected a false assumption carried from the draft (and from ADR 0006 decision 2): "no client
  grants `aws.cognito.signin.user.admin`" only holds for tokens from the OAuth `/token` endpoint.
  AWS (access token page): "A token from Amazon Cognito API sign-in only contains the scope
  `aws.cognito.signin.user.admin`". Every client enables `ALLOW_USER_AUTH`, and the traveller
  clients are public, so any traveller can sign in through the API and call
  `UpdateUserAttributes` / `AssociateSoftwareToken` / `SetUserMFAPreference` with their own token,
  limited only by the client's `write_attributes`.
- `email_verified` is now client-writable only while the EXTERNAL Google IdP exists (Facebook does
  not map it), instead of whenever any social IdP exists.
- Header comment, the Google variable description and the custom-domain output description
  (DNS records go to the Route 53 zone per S237 D5, not Namecheap) updated.

## Should know
- **Blocker before setting any EXTERNAL Google variable:** with Google on, `email_verified` is
  writable by the EXTERNAL clients. If Cognito accepts `email_verified=true` from a user's own
  `UpdateUserAttributes`, a traveller could mark an address they do not own as verified, which
  decision 6 trusts (Google linking in the EXTERNAL pre sign-up, Booking lead merge). Spike it on Dev
  first; if it is accepted, move Google/Facebook to dedicated clients without `ALLOW_USER_AUTH`
  (OAuth tokens there carry only `openid email profile`), so no client that issues API tokens can
  write `email_verified`. Not an issue for this PR's default apply (no social IdP, clients write
  `name` only).
- WORKFORCE is not affected in practice: its clients are confidential, so API sign-in needs the
  client secret held by the BFF. A staff member with an API token could still enrol TOTP on their
  own account (MFA OPTIONAL) and lock themselves out of email-code sign-in; recovery is
  `AdminSetUserMFAPreference` by an admin.
- ADR 0006 decision 2 states the admin scope is "not allowed"; that wording should be amended in the
  root repo to say it is excluded from OAuth tokens only.
- The CI "Terraform Apply" workflow is `workflow_dispatch`, not on push: merging does not apply.
