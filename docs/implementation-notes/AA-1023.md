# AA-1023 — job-idle gate in terraform-apply (Infra part)

Lane l14 of S264. The root repo part (parameterised ECS rollback runbook, game-day plan, `tools/ops/ecs_rollback.sh`)
has its own notes in the root repo `docs/implementation-notes/AA-1023.md`.

## Decisions

- **Reuse the DB Migrate idle check, not the app deploy gates.** The app gates (`/admin/job-runner/deploy-gate`,
  `/booking/ops/deploy-gate`, `/crm/ci/deploy-gate`) accept only their own repo's admin secret or OIDC token, and since
  AA-993 G5 they block only on deploy-blocking kinds. DM-11.4 for an Infra apply means "all job tables idle", which is
  exactly DB Migrate's check (`job_tables_busy` + `wait_until_idle` in `db/run_migration.py`). A new runner mode
  `idle-gate` calls those two functions and nothing else: same SQL, same exempt kinds (`IDLE_EXEMPT_KINDS`), same
  horizon and 3 x 20 s re-check, same `MIGRATION_IDLE_OVERRIDE` name. No new environment variable reaches the task.
- **Read-only session as the task login (`db_migrator`), no apply lock.** The gate writes nothing, so it must not queue
  behind a DB Migrate run holding the advisory lock.
- **Scope: only plans that can restart a task or the DB.** `aws_ecs_service`, `aws_ecs_cluster`,
  `aws_ecs_cluster_capacity_providers`, `aws_db_instance`, `aws_db_parameter_group` with any action other than
  no-op/read. A task-definition revision alone is listed but not gated: every service has
  `ignore_changes = [task_definition]`. Alarms, IAM, SQS etc. never wait for jobs.
- **Gate placement:** scope right after "Export plan JSON" (the plan guard deletes the JSON), gate immediately before
  "Terraform Apply" so the check-then-apply window is as small as possible.
- **Override:** `override_busy_jobs` (same name and rules as DB Migrate). With an override the gate still runs and
  logs, but no answer refuses (also the way through when the DB or the migrator task is what the apply fixes).
- **`idle_gate_check` input:** a job that runs only the gate (no Terraform). This is the $0 proof the issue asks for
  ("refuses on a seeded busy job table, passes when idle") without needing a plan that touches ECS.

## Changed (vs. the issue text)

- The issue's fourth bullet (rename `environment: prod` to `dev` in db-freshness-probe, terraform-apply,
  db-tour-liveness-gate) is **not** in this PR. The environment name is part of the OIDC subject the apply role trusts
  (`environment:prod`, `cicd_split.tf`, a bootstrap object applied locally with MFA), and the environment holds the
  secrets. A rename needs: a `dev` environment with the same secrets and branch policy, a local bootstrap apply of the
  trust change (both subjects for one cut-over), then the workflow change. Returned as a follow-up.

## Tradeoffs

- Running a Fargate task costs a few cents of compute per gated apply (well under 0.01 USD, inside the existing
  cluster); no new AWS resource.
- The gate adds about 1-2 minutes (task start + up to 60 s re-check) to gated applies only.
- Fail closed: an unreadable job table, a missing pass line, or a task that does not stop refuses the apply.
