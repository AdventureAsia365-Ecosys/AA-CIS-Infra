# AA-1027 E4 + E5 — DB Migrate scripts (lane l3-e4e5-tp, S265)

## Decisions
- One read-only script covers both destructive-ish steps of root plan row E5: the tp-025 drop of
  `tripplanner.llm_spend_daily` (DRY RUN + independent verify) and the CIS 351 REVOKE preview (grantor check, as the
  CIS 270 preview in `aa712_frozen_tables_dry_run.py`).
- The ledger comparison reads `shared.llm_call_log` for the counter's own day range (app `tripplanner`, the online
  stages): it shows the counter was a copy of the billing truth, so the drop loses nothing that cannot be recomputed.

- E4 live step without a lasting params row: `aa1027_e4_stage_params_probe.py` inserts the probe row and reads the
  view in one transaction that is always rolled back, so no TripPlanner Lambda can pick the row up and no paid model
  call is made. The view row carries the effort, but TripPlanner sends none on Bedrock (only temperature goes in the
  body). The request-body half of E4 (temperature in the body, effort not sent, the precedence) is proven by the
  TripPlanner unit tests with a stub client that logs every body (`backend/tests/test_llm_gateway_stage_params.py`):
  a live narrate cannot reach a model while the LLM account is blocked, and it would be a paid call.

- `aa805_ai_guards_read.py` (closed AA-805 evidence) still names the table and the tables tp-018 dropped; it is not
  run any more and is left as history.
- `db/owners.yaml` consumer_grants and `db/rls_catalogue_rules.py` still list the CIS 173 SELECT as grandfathered;
  the entries go stale (reported, not fatal) after 351 and are cleaned up with the next CIS rules sync.

## Should know
- The SQL ran on a local PostgreSQL 16 stand-in in a `default_transaction_read_only` session (S265): clean ->
  `drop_ready=true revoke_ready=true`; a fresh write plus a dependent view -> `drop_ready=false` with both reasons;
  after drop + revoke -> `exists=f`, `cis_grant none=t`. The probe ran on a stand-in with the 350 view shape:
  `view_carries_params=true clean=true`, 0 rows left.
- If the RDS master cannot `SET ROLE tripplanner` and has no SELECT on the tripplanner-only view, the probe prints
  `view … error=…` and exits 1 (still rolled back); the CIS integration test `test_aa1027_migration_350.py` then
  stays the proof of the view part.
