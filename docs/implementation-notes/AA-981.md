# AA-981 — Full-history secret scan and credential-key rule (AA-CIS-Infra part)

Linear: AA-981 (S248). Root repo part: AA-Ecosys `docs/implementation-notes/AA-981.md`.

## Decisions

- **One workflow, two jobs.** `secret-scan.yml` keeps the PR job `gitleaks` (same name, so the PR check
  name does not change) and adds `history` ("gitleaks full history"): nightly 19:23 UTC, every push to
  `main`, and `workflow_dispatch`. On dispatch both jobs run (working tree + full history), so a dispatch on a
  test branch proves the history job goes red.
- **Full history = every branch, every tag and every PR head.** `actions/checkout` with `fetch-depth: 0`
  fetches branches and tags; a second step fetches `refs/pull/*/head` into `refs/remotes/origin/pr/*`.
  GitHub keeps those refs for every PR, closed ones included, after the branch is deleted, and anyone can
  fetch them, so a secret pushed on a deleted PR branch is still public. gitleaks `git` mode without
  `--log-opts` runs `git log -p --all`, which covers all three.
- **Baseline = commit fingerprints in `.gitleaksignore`** (`<commit>:<file>:<rule>:<line>`), not a gitleaks
  JSON baseline report: no value, not even redacted, lands in the repo, and the same file/line in a later
  commit is still reported. The comment above the pins says only "historical findings"; which credential
  sits where and its status stay in the private record (Linear AA-981), because this repo is public.
- **PR scan reads the rules from the base commit.** The PR job copies `.gitleaks.toml` and `.gitleaksignore`
  from `BASE_SHA` (`git show`) into `$RUNNER_TEMP` and mounts them read-only, so a PR that adds a secret plus
  an ignore line or allowlist entry still fails. A PR that touches either file fails on its own (guard) until
  the label `secret-scan-baseline-reviewed` is on the PR; with the label, the PR's own copies are used (the
  only way to land a legitimate rule or baseline change). `pull_request` also triggers on `labeled` /
  `unlabeled` so adding the label reruns the check. Both files added to CODEOWNERS. If a file does not exist
  at the base (first PR that adds it), the PR's copy is used with a warning.
- **New rule `credential-key-literal`** for config data files (`*.tfvars`, `*.tfvars.json`, `.env*`, `*.json`,
  `*.yaml`/`*.yml`). Key must end in password / passwd / pwd / secret / api key / secret|access|private key /
  `*_token`. Key position: quoted anywhere, or unquoted at the start of a line (after indentation, `- `,
  `export `) or right after `{`, `,` or `;` (inline maps: `rds = { username = "admin", password = "..." }`).
  Value: a quoted value is read up to its closing quote (spaces and commas kept), an unquoted one up to the
  first space, quote, backtick, comma, `}` or `]`. No `secretGroup`: gitleaks takes the first non-empty of the
  three value groups. The line / delimiter anchor keeps prose out ("the main secret: rotate it", `$PWD:/repo`,
  ARNs with `:secret:`).
- **Entropy floor 2.5** on that rule: drops plain words (`id-token: write`, `set-password: role`) and keeps
  password-like values ("admin123" is 3.0, "Summer 2024!" 3.25).
- **Secret-name allowlist narrowed** to `<app>/<env>/<name>` with an environment word in the middle
  (`aa-cis/dev/rds`, `aa-ecosys/ops/linear-api-key`), so a password that merely contains slashes
  (`aa/bb/cc123`) is still reported.
- **tfvars stay in `terraform-plaintext-secret` too** (path `.tf` / `.tfvars` / `.hcl`, as on `main` before
  this change). The two rules overlap on tfvars on purpose: the Terraform rule has no entropy floor and
  matches the key anywhere on the line; the new rule reads quoted values with spaces. A tfvars password can
  therefore produce two findings, one per rule. (Review round, S248: the first draft moved tfvars out of the
  Terraform rule on the claim that the new rule was a superset; it was not — inline maps, commas and spaces
  inside quotes were missed.)
- **AWS network resource IDs allowlisted globally** (`sg-`, `vpce-`, `subnet-`, ...): an old CLAUDE.md line
  with a `vpce-` ID was the only non-tfvars finding in history.
- **Dispatch working-tree scan runs `dir .`**, not `dir /repo`: with an absolute path the reported file paths
  start with `/repo/`, and path allowlists anchored at `^` (the `db/tests/test_runner_modes.py` fake DSNs)
  stop matching, so a dispatch on `main` would go red on 11 known fake DSNs.

## Changed

- `.gitleaks.toml`: new rule + allowlists, Terraform rule path keeps tfvars, global resource-ID allowlist,
  header.
- `.gitleaksignore`: 7 pinned historical findings (4 commits) under a neutral comment.
- `.github/workflows/secret-scan.yml`: triggers (incl. `labeled` / `unlabeled`), PR job reads config from the
  base commit + baseline-change guard, `history` job with the PR-head fetch, concurrency per event.
- `.github/CODEOWNERS`: `/.gitleaks.toml`, `/.gitleaksignore`.
- `README.md` "Secret scan" and the `docs-lint.yml` header comment.

## Tradeoffs

- A quoted value with spaces is now read whole: a JSON/YAML description string under a credential-named key
  (`"password": "The admin password"`) would be reported. None exists in this repo's history today; fix one
  with a narrow allowlist entry if it appears.
- Unquoted values still stop at whitespace, `,`, `}` and `]`; values under 4 characters or with entropy
  <= 2.5 are not reported by the new rule (the Terraform rule still sees tfvars ones).
- The test-directory path allowlist (`tests/`, `__tests__/`, `fixtures/`) applies to the new rule only; the
  default rules and the Terraform rule still scan test files.
- The baseline-change guard trusts a label, which any writer can add; it makes the change explicit and
  reviewable (and CODEOWNERS-tagged), it does not stop a determined writer. Same trust level as merge itself
  in the dev phase.
- No history rewrite: rotation is the fix, not a rewrite (forks, caches and PR refs keep old commits).

## Review round (S248, independent review of the app-repo port)

Four should-fix findings, applied to the app repos and, as a follow-up PR, to the root repo and AA-CIS-Infra:

- **Inline allow comments need the label.** An added line with an inline `gitleaks:allow` comment was hidden from
  both jobs with no label. The PR job now lists the files where the PR's commits add such a line (each commit's
  patch, merge commits as a dense combined diff; file names only) and treats it like a baseline change. Existing
  inline allows on the base branch are not affected. Chosen over `--ignore-gitleaks-allow` on the PR job: an
  approved inline allow survives the squash merge, a commit fingerprint does not.
- **The label goes stale.** The label was read from the PR on every event, so a push after the review could add
  a new ignore line and still pass. Now, when the PR has a baseline change and the label: on `synchronize` the job
  compares the previous head with the new one (blob of each file + new inline allows outside the base); on a
  change, an unknown previous head (force push), or `opened` / `reopened` with the label already on, it removes
  the label (job permission `pull-requests: write`, used only for that call) and fails. The reviewer reads the
  new change and adds the label again. Removing it (rather than only failing) keeps later runs honest: a run
  started by another label event would otherwise trust the old label.
- **Fingerprint formats documented.** gitleaks 8.28 git mode honours the global `<file>:<rule>:<line>` format
  for every commit (verified locally: a global entry suppressed a base..head finding). The `.gitleaksignore`
  header now says so, recommends commit pins, and explains that a commit pin does not survive the squash merge:
  prefer a narrow `.gitleaks.toml` allowlist, otherwise pin the PR commit in the PR and the squash commit in a
  follow-up PR.
- **Required check pinned to GitHub Actions.** The post-merge step uses `PATCH .../required_status_checks` with
  the full `checks` array plus `{"context": "gitleaks", "app_id": 15368}` (not the legacy `contexts` POST, which
  any status source could satisfy), run after the PR's own `gitleaks` check is green and before the merge, so
  there is no window without a required secret gate.

Tradeoffs: an update-branch merge that brings a baseline change from the base branch also drops the label (the
blob differs); rare, and the cost is one more review. A fork PR cannot remove the label (read-only token): the
run fails with an error asking a maintainer to remove it.

Known gap, not changed here (also in the root repo and Infra): gitleaks does not scan the content of merge
commits in `base..head` (verified: an evil merge adding a secret passes the PR job). The squash commit on the
default branch is scanned by the full-history job. Closing it in the PR job (`--diff-merges=first-parent`)
would also rescan the base-branch lines an update-branch merge brings in, and those are pinned by other commits.

## Review round 2 (S248, second independent review)

One blocker and three should-fix findings, applied in the four app repos, the root repo and AA-CIS-Infra (the
`jobs:` block of `secret-scan.yml` stays byte-identical in the app repos and the root repo; Infra keeps its own
layout with the same logic).

- **The label counts only on the run that adding it starts (blocker).** Round 1 judged a stale label by comparing
  the previous head with the new one on `synchronize`, and read the label from the event payload. Runs of one PR
  cancel each other, so two quick pushes kept the label: B adds a secret and a pin of it, C is unrelated, B's run
  is cancelled before its DELETE call, and C's run compares B with C, sees nothing new and scans with the PR's own
  copies (green). An unrelated label added right after B did the same, because round 1 skipped the check on
  `labeled`. Now the job trusts the label only when the run was started by `labeled` for
  `secret-scan-baseline-reviewed`. On any other event (push, open, reopen, another label added or removed) with the
  label on and a baseline change in the PR, it removes the label and fails. `BEFORE_SHA` and the per-push
  comparison are gone. Not chosen: reading the PR timeline (a `committed` event carries the commit date, which the
  author sets), and `cancel-in-progress: false` (a queued run is still replaced by a newer one). Cost: every push to
  a PR with a baseline change needs the label again; such PRs are rare.
- **Merge commits are scanned.** gitleaks 8.28 does not scan what a merge commit adds: a merge that adds a tfvars
  password passed the PR job (base..head) and the full-history job. Both jobs now pass `--diff-merges=remerge` in
  `--log-opts`. In the PR job that is `--diff-merges=remerge BASE..HEAD`. In the history job it is
  `--all --full-history --diff-filter=tuxdb --diff-merges=remerge`, which is gitleaks' own default plus remerge.
  A remerge diff shows only what the merge adds beyond git's automatic merge of its parents, so an update-branch
  merge does not rescan the base-branch lines it brings in. A conflicted merge shows its resolution as added lines.
  The inline-allow detector reads the same patches (it used `--cc`; the round-1 comment saying gitleaks reads a
  merge as a combined diff was wrong). The pinned image's git is 2.43.7 (apk database of the amd64 image);
  remerge needs 2.36.
- **The workflow file is guarded too.** `.github/workflows/secret-scan.yml` is now one of the paths that need the
  label, so an accidental or careless change to the scan gets a review. The workflow header now says the gate is
  advisory: a `pull_request` run uses the PR's own copy of the workflow, and the default branch does not require
  code-owner review in the dev phase, so a hostile edit can still remove the check. When the merge rule tightens
  (first prod or first paying tenant), turn on "Require review from Code Owners" (`/.github/`, `/.gitleaks.toml`,
  `/.gitleaksignore` are in CODEOWNERS). A Dependabot bump of the checkout pin in this file now needs the label
  as well.
- **One procedure for the required check.** The lane handoff now gives the same procedure as round 1 above.

Verified locally (gitleaks 8.28.0; the PR job's `run:` block with the local binary in place of docker and a stub in
place of `gh`). The same 18 scenarios ran in each of the six repos and every result was as expected:

- The label guard on the feature PR: fails without the label, passes with it, and a reopen removes the label.
- The canary fails with 2 findings.
- Inline allow: fails without the label, passes with it.
- A push that changes `.gitleaksignore`, and an unrelated push, each remove the label and fail.
- Two quick pushes (the run for C alone) removes the label and fails with the 2 canary findings.
- An unrelated label added or removed removes the label and fails.
- When the reviewer adds the label again at C, the run trusts it.
- A change to the workflow only: fails without the label, passes with it.
- An evil merge that adds a secret fails with 2 findings.
- An evil merge that adds an inline allow trips the guard.
- An update-branch merge that brings in base lines pinned by commit passes with 0 findings and no guard.

The history job's `run:` block on a repo with an evil merge reports the merge commit; the round-1 block did not.
The full-history baseline was rerun with remerge over mirror clones (branches, tags, PR heads) and found 0 new
findings in all six repos. In CIS, the merges with a conflict add 29 lines, and none matches a rule.

## Review round 3 (S248, third independent review)

Two blockers, four should-fix findings, one gitleaks upgrade and three nits, applied the same way in the four app
repos, the root repo and AA-CIS-Infra. The `jobs:` blocks of `secret-scan.yml` and `secret-scan-history.yml` are
byte-identical in the five non-Infra repos; Infra now uses the same PR job and history job too, plus a
dispatch-only working-tree job.

- **`.gitattributes` could hide lines from both jobs (blocker).** A `binary` or `-diff` attribute (in the PR or
  already on the base branch) makes `git log -p` print "Binary files differ", so gitleaks never saw the lines.
  Both jobs now write `* !diff` to `.git/info/attributes` before scanning; that file wins over every
  `.gitattributes`, and git falls back to its own binary detection (a NUL byte), so real binaries stay binary.
  Any `.gitattributes`, in any directory, is now a guarded path (it can also move a file to Git LFS, where only the
  pointer is in git).
- **A manual run on a PR branch left a skipped `gitleaks` check (blocker).** The PR job had `if: pull_request`;
  a `workflow_dispatch` on the PR branch created a skipped `gitleaks` check on the PR head, and a skipped check
  satisfies a required check. Split into `secret-scan.yml` (`pull_request` only, no job-level `if`) and
  `secret-scan-history.yml` (push to the default branch, schedule, dispatch; no job named `gitleaks`). The new file
  is a guarded path. The required check name stays `gitleaks`.
- **Octopus merges were not scanned.** `--diff-merges=remerge` covers two-parent merges only. The PR job fails when
  `git rev-list --min-parents=3 BASE..HEAD` is not empty; the history job fails when
  `git rev-list --all --min-parents=3` is not empty (none in any of the six repos today).
- **Renames hid values.** With rename detection, a file moved out of an allowlisted path (or a file whose value is
  pinned by commit) shows no added lines. `--no-renames` is now in both `--log-opts` and in the inline-allow
  detector, so a renamed file is read as a new file.
- **Type changes were skipped by the history job.** `--diff-filter=tuxdb` (gitleaks' default) drops `T`, so a
  symlink turned into a file with a secret was not scanned. Now `--diff-filter=uxdb`. The PR job has no filter.
- **A git failure passed as "no leaks".** gitleaks logs the git error and exits 0. Both jobs now fail when the log
  has `stderr is not empty` or `[git] fatal`, and the PR job checks `git cat-file -e <sha>^{commit}` for the base
  and head first.
- **Docs: a red result means the value is public.** The job summaries, the workflow headers and the docs say to
  rotate a real value even if it was force-pushed away (GitHub keeps PR heads and pushed commits).
- **gitleaks v8.30.1** by digest (`sha256:c00b6bd0...`, the OCI index; resolved from the ghcr.io registry API and
  checked against the sha256 of the index body). The amd64 image ships git 2.49.1 (apk database), so remerge
  works. Local tests ran the `gitleaks` binary extracted from that image's amd64 layer (layer digests checked).
- Nits: `.github/CODEOWNERS` is a guarded path; `persist-credentials: false` on every checkout (the checkout is
  mounted into the gitleaks container; the PR-head fetch needs no token because the repo is public); Infra's
  checkout is SHA-pinned (`v7.0.1`) at both uses; Infra's `.gitleaks.toml` rules are byte-identical to the root
  repo's, with its two own allowlist entries (the X1 S12 runner-test DSNs, now a global allowlist with
  `targetRules = ["uri-embedded-credentials"]`, and the built Lambda zips) in a marked block at the end.

Not changed: an octopus merge reachable from any ref keeps the history job red until a reviewer has read it by hand
(there is no allowlist for that; none exists today). gitleaks 8.30 also has `--ignore-gitleaks-allow`, which would
make the inline-allow guard unnecessary; not adopted here (it would surface the reviewed inline allows in history).

Verified locally (gitleaks 8.30.1 from the image; the jobs' `run:` blocks with the local binary in place of docker
and a stub in place of `gh`):

- PR job: the 18 round-2 scenarios plus 14 new ones, all as expected: a `.gitattributes` binary in the PR (guard,
  2 findings) or already on the base (2 findings, no guard), a nested `.gitattributes`, an LFS attribute,
  `secret-scan-history.yml` and CODEOWNERS changes (guard; label trusted on its own run), an octopus merge (error),
  a rename of a commit-pinned value (2 findings), a symlink turned into a tfvars file (2 findings), a base commit
  missing from the checkout (error before any scan), and a git error inside gitleaks (error; the same PR passes
  when git works).
- History job on the review's five test repos: `.gitattributes` binary, octopus, type change, rename out of an
  allowlisted path and a two-parent evil merge all go red, and so does a git error. The round-2 block caught only
  the evil merge.
- Full history over mirror clones (branches, tags, PR heads) with the new options, `* !diff` and gitleaks 8.30.1:
  0 findings with each branch's baseline in all six repos; without the baseline the raw counts are the same as
  with the round-2 options, so nothing new was found and nothing new is pinned.

## Review round 4 (S248, fourth independent review)

One blocker and five should-fix findings, applied the same way in the four app repos, the root repo and
AA-CIS-Infra. The `jobs:` block of `secret-scan.yml` is byte-identical in all six repos again.

- **`* !diff` only unset the attribute (blocker).** git then fell back to its own binary check, so a text file
  with a NUL byte in its first 8000 bytes printed "Binary files differ" and gitleaks never saw its lines (a
  token in a `.txt`, a password in `.env.prod`, each followed by one NUL byte: green). Both jobs and every local
  command now write `* diff`, which makes git show the lines of every file. Known gap: a UTF-16 file still escapes,
  because the rules do not match NUL-interleaved text.
- **`[extend] useDefault = true` also loaded gitleaks' global path allowlist.** That list skipped TEXT files in
  every rule: `.svg`, `.bin`, `node_modules/`, `go.sum`, `bootstrap*.js` / `jquery*.js`, `venv/lib/`,
  `lib/python3.x/`, `*.dist-info/`, `Pipfile.lock` / `poetry.lock`, `.gem`, any path containing `gitleaks.toml`.
  Decision (option A of the review): the 222 default rules of gitleaks v8.30.1 (the `config/gitleaks.toml` embedded
  in the pinned image's binary) are copied verbatim into `.gitleaks.toml`, with no `[extend]`. The global
  allowlists keep only binary formats (images other than svg, fonts, Office documents, pdf, exe, dll; anchored at
  the end), gitleaks' placeholder-value regexes (its `(?i)^true|false|null$`, an unanchored alternation that
  allowlisted any value containing "false", is anchored here) and its two stopwords. The shared lock-file entry
  (package-lock / pnpm-lock / yarn / .terraform.lock.hcl) stays. One copied rule
  (`aws-amazon-bedrock-api-key-short-lived`) is a literal and matches its own line in `.gitleaks.toml`, so that rule
  is allowlisted on that one path. The PR check needs the label when a file with a binary-format extension is text
  to git (git's own NUL check, counted per commit), so a `.env` renamed to `.png` cannot pass silently.
  When the pinned image changes, copy the new version's rules over the marked block.
- **A value split across commits passed.** gitleaks reads each commit's patch alone, so a private key whose END line
  came in a second commit was never whole. The PR job now also scans a squash preview: `git commit-tree` of the PR
  head's tree on the merge base, scanned with the same rules (`--no-renames -1 <sq>`). It shows what the history
  job will see in the squash commit on the default branch, including a finding that only a pin of a PR commit
  covers. Consequence: a false positive that a PR adds needs a `.gitleaks.toml` allowlist entry (or an inline allow);
  a commit pin no longer makes the PR green (the `.gitleaksignore` headers say so).
- **The PR check ran the PR's own copy of the workflow.** It now runs on `pull_request_target`: GitHub always runs
  the base branch's copy, the PR head is checked out by SHA as data only (git objects for gitleaks; no script,
  action or config from the PR runs), `persist-credentials: false`. The baseline files are read with `git show`
  (a symlink is never followed) and the PR's `.gitleaks.toml` / `.gitleaksignore` are removed before the job's
  copies go into the checkout; logs are written to the runner's temp folder. The concurrency group is the PR
  number (on `pull_request_target`, `github.ref` is the base branch). The check fails when a workflow other than
  this file's `pull_request_target` job has a job id or name `gitleaks` (case-insensitive; a name built by an
  expression counts), read with `yq` from the PR's merge with the base (what GitHub runs for `pull_request`;
  the PR head when they conflict); a workflow `yq` cannot read fails the check too. A workflow change that grants
  `checks: write` or `statuses: write` needs the label (such a workflow could report a check through the API).
  A change to `secret-scan.yml` takes effect only after its merge, so the feature PR that switches to
  `pull_request_target` gets no `gitleaks` run of its own; the local harness is its evidence.
- Fork PRs: on `pull_request_target` the token can remove the label for forks too.

Verified locally (gitleaks 8.30.1 from the image, yq v4.44.3 with its release checksum; the job's `run:` block with
the local binary in place of docker and a stub in place of `gh`):

  token or a password (red, also under a base-branch `binary` attribute), nine text files on gitleaks' old default
  path allowlist (9 findings), a text `.png` (label needed; a real binary `.png` passes), a `.pdf` that is text in one
  commit and binary in the next (label needed), an RSA key split across two commits (only the squash preview

  with a `pull_request` trigger added (red even with the label), an ordinary new workflow (green), a workflow that
  is not valid YAML (red), a workflow granting `checks: write` (label), a `.gitleaksignore` symlink to a file
  outside the checkout (the outside file is untouched), and a PR branched before the switch (green: its merge has

- History job: the review's five test repos plus NUL bytes, the old default path allowlist and a split key: all
  red as expected; the split key only once its squash commit exists. The round-3 block and config missed the NUL

- Full history over refreshed mirror clones (branches, tags, PR heads) with `* diff` and the copied rules: the

## Review round 5 (S248, fifth independent review)

Two blockers and five should-fix findings of the review of round 4, applied the same way in the four app repos, the
root repo and AA-CIS-Infra. The `jobs:` blocks of both workflows are byte-identical in all six repos again (Infra's
history file adds its `worktree` job), and so is `.gitleaks.toml` below `title` (Infra adds one entry of its own).

- **Name-based path allowlists removed (blocker).** A text file under an allowlisted name passed with no label: a
  `.png` whose first byte is NUL (git's own NUL check hid it from the round-4 label guard for text under a
  binary-format name), any `package-lock.json` / `yarn.lock` / `pnpm-lock.yaml` / `.terraform.lock.hcl` (a lock file
  can hold a registry credential in a URL), and, in Infra, a text file at `dist/lambdas/*.zip`. Decision: no path
  allowlist at all. The binary-format, lock-file and Lambda-zip entries are deleted, and so is the label guard for
  text under a binary-format name (it only protected that allowlist). Measured on mirror clones refreshed 23/10 13:42
  (branches, tags, PR heads) with each branch's `.gitleaksignore`: 0 findings in all six. Without a baseline the
  findings are the same with and without the entries (CIS 52, TP 2, Booking 7, Partner 0, root 196, Infra 8), so
  nothing new is pinned. A false positive later gets a narrow entry keyed on the rule and the value or line, never a
  file name alone.
- **UTF-16 (blocker).** The rules match bytes, so a UTF-16 file (Windows PowerShell 5.1 writes one by default)
  passed both jobs. Both jobs now run a UTF-16 pass: each blob that starts with a BOM (FF FE / FE FF), or that is
  ASCII with every other byte NUL (3 of 4 byte pairs in its first 512 bytes), is transcoded to UTF-8 with `iconv -c`
  and scanned with `gitleaks dir` in the same pinned image and config, as a file at `<blob id>/<path>`. PR job: every
  blob the PR's commits add (`git rev-list --objects base..head`, so also a file that a later commit removes again).
  History job: every blob reachable from any ref. Decision: `dir`, not `stdin`, so the path-scoped repo rules
  (tfvars, `.env`) and the path allowlists apply; inline allows are ignored in this pass (`--ignore-gitleaks-allow`),
  because the inline-allow label guard cannot read a UTF-16 comment. A finding can be pinned as
  `<blob id>/<path>:<rule>:<line>` (that file content only; format listed in `.gitleaksignore`). Today's history has

## Follow-up S251: GitHub secret scanning alerts on the sample keys

GitHub secret scanning opened 16 "Google API Key" alerts (marked publicly leaked) in each of the six repos, all on
`.gitleaks.toml`. The 16 values are the sample keys in the `[[rules.allowlists]]` of the copied `gcp-api-key` rule:
gitleaks' own upstream list (the same 16 strings are in the gitleaks 8.30.1 binary), not keys of ours.

### Decisions

- **Same match, no literal key.** Each of the 16 regexes now has its fifth character in a non-capturing group,
  `AIza(?:S)y...` (one sample is `AIza(?:y)...`). RE2 matches exactly the same string, and the file no longer holds
  a token of the shape GitHub looks for (`AIza` plus 35 key characters). Nothing else in the rule changes.
- **A comment above the list** says why, and that a re-copy of a new gitleaks version's default rules must redo it.
- **Alerts are closed as false positive** by the orchestrator after the merge; history keeps the old blobs, so the
  alerts would not close by themselves.

### Changed

- `.gitleaks.toml` only: the 16 regex lines and the two comment lines. The shared block below `title` is still
  byte-identical in the root repo and the four app repos, and in AA-CIS-Infra above its own marked block.
- The copied rule set is no longer a verbatim copy of gitleaks' `config/gitleaks.toml` in these 16 lines.

### Tradeoffs

- Rewriting the regexes rather than deleting the allowlist: without it, 15 of the 16 sample keys become findings
  again (one is below the rule's entropy). Rather than a `.gitleaksignore` pin: the samples appear in many commits.
