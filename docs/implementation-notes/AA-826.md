# AA-826 — New-app playbook: owner dry run, role bootstrap template, consumer contract hash guard

Shipped before this branch: Infra #163 (`db/owners.yaml`, `roles/` dir, `db/tests/test_owners_registry.py`). This
branch (`chore/owner-registry-dry-run`, S245) covers what the Linear comments list as remaining. Two evidence
branches are never merged: `test/add-owner-dry-run` and `test/contract-hash-red`.

## Decisions
- **Add-owner = owners.yaml + guarded mirrors** (Done-when as reworded on 19/10). The registry test no longer pins the
  exact owner set (`{"cis","booking","tripplanner","roles"}` would have forced a test edit for every new owner); it
  requires those four, lower-case dir names and exactly one native owner.
- **"DB Migrate validation picks it up" is executed, not only regex-compared.** DB Migrate refuses any ref but
  `main` (`if: github.ref == 'refs/heads/main'`), so it cannot run on an evidence branch. New test
  `DbMigrateValidateStepTest` runs the workflow's own "Validate input" bash block (no AWS) for a throwaway
  `<owner>/999_*.sql` per owner and checks the computed `version` output carries the owner's key prefix; an unknown
  dir is refused. Mutation-checked (prefix `bk-` → `bx-` turns it red).
- **Role bootstrap template** (`db/templates/new_owner_roles.sql.tmpl` + `render_new_owner_roles.py`) was built in
  this lane because a real dry run needs a roles/ file: the owner role must be in `migrator_member_of`, and the
  roles test requires a roles/ file that grants it to db_migrator.
- **The template also creates the empty anchor schema owned by the owner role.** The runner switches to the live
  owner of the anchor schema (XD8); with no schema it runs the first owner file as db_migrator, which would then own
  the objects. This differs from ADR 0008 step 4 ("first migration `<prefix>-001`: CREATE SCHEMA … AUTHORIZATION
  <app>_owner") — see Should know.
- **Contract hash guard lives in Infra with pinned hashes.** The canonical contracts are in the private root repo
  (`docs/contracts/`), which Infra CI cannot read with `GITHUB_TOKEN`. `tools/contracts/contract_copies.json` pins
  each canonical file's sha256 and lists the app-repo copies; the guard fetches copies from the public app repos
  (GitHub API, like the Migration Copy Guard). `--workspace` (local) also proves pins == canonical files and that
  every canonical file is pinned; a unit test does the same when it runs inside the AA-Ecosys workspace.
- **Unregistered copies are found, not only registered ones checked.** The guard lists each consumer repo's tree
  (git trees API) and fails on a file named like a pinned contract that the manifest does not list; a file that
  only looks like a contract (`<name>.v<major>[.<minor>].json`) is a warning.
- **Evidence ref override** via `CONTRACT_COPY_REFS` (env) / `--ref` / dispatch input `refs`: a new workflow cannot
  be dispatched before it is on `main`, so the red evidence branch sets the env in the workflow file.

## Changed
- `db/tests/test_owners_registry.py`: owner set no longer exact; validate-step test; probe `KEY_TEXT` must cover
  every probe state key (found by the dry run: a new transfer key without text crashed the probe's records).
- `db/check_migration_copies.py`: the path error lists `OWNERS` instead of a hand-written dir list (its test pinned
  the old text, found by the dry run).
- `db/tests/test_roles_files.py`: planned rl-002 grants must be a subset of `migrator_member_of` (was equality, which
  made any new owner impossible without editing rl-002's planned text; the union-of-roles-files test stays exact).
- New: `db/templates/`, `db/tests/test_new_owner_roles_template.py`, `tools/contracts/` (guard, manifest, tests),
  `.github/workflows/contract-copy-guard.yml` (PR on its own paths + nightly 02:29 UTC + dispatch).
- `migration-copy-guard.yml` paths include `db/templates/**`. `db/README.md` "Adding an owner"; `CONTEXT.md` tools.

## Tradeoffs
- Pins in Infra vs. a guard in the root repo: the root repo has the canonical files but no required CI and cannot
  be read from Infra CI. Pins keep the check in a repo with required CI and a nightly; the cost is one extra step
  (pin the new hash here) per new contract version, proven locally with `--workspace`.
- Consumer PRs are not blocked by this guard: an in-place edit of a copy on an app repo's `main` turns the Infra
  nightly red within a day. A per-app CI step would block earlier but needs a change in each public app repo
  (follow-up if wanted; the app repos already parse samples per contracts rule 7).
- The template refuses existing role/schema names and connection limits outside 1..100; anything else (job table,
  grants, default privileges) stays in the owner's own migrations.

## Should know
- Dry-run evidence (`test/add-owner-dry-run`, fake owner `dryrun`, prefix `dr-`, roles file rl-003): step 1 (registry
  entry only) → 8 red tests naming every mirror (validate step, copy guard OWNERS/PATH_RE, db-migrate regex/prefix,
  IDLE_EXEMPT_KINDS, isolation probe, rls_catalogue_rules owner maps, run_migration OWNER_DIRS, migrator
  membership). Step 2 (mirrors + rendered roles file) → 307 tests green, lint clean. On a PR the Migration Copy
  Guard's **compare** step stays red on `db/rls_catalogue_rules.py`: it is a byte copy of AA-CIS-App's
  `tests/integration/rls_catalogue_rules.py`, so a real new owner needs a CIS PR first. That is the guard working.
- The rendered template was run twice (idempotent) on a throwaway local PostgreSQL 16 with an RDS-like
  non-superuser CREATEROLE master: roles, memberships, schema owner and the rl key are as intended; the guards fire
  when the runtime role is granted to another role or the session user is not the master. PostgreSQL 16 records the
  creating CREATEROLE role as a member of each role it creates (15 does not), so the runtime-role guard tolerates
  exactly that row.
- ADR 0008 step 4 and data standards (01-engineering CON-4/TST-6 "to build X7", 02-data-management X7 row) live in the
  root repo and still say "to build" / "first migration creates the schema": update them in the root PR.
- `db/__pycache__/run_migration.cpython-313.pyc` is tracked on `main` (pre-existing); left as is.
