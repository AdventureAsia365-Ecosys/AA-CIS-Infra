# AA-1139 — M2M scope tripplanner.leads/manage (the agency app's TripPlanner module)

## Decisions

- One more scope on the existing `tripplanner.leads` resource server (`accounts/aa365/identity_m2m.tf`), not a new
  resource server: the routes are TripPlanner's `/trip/m2m/v1/tenants/{id}/planner/*` (lead delivery status, usage,
  webhook signing key rotation; root contract `lead.submitted.v1` 1.1). The CRM client (`aa-m2m-<env>-crm`) gets it
  through `scope_identifiers`, an in-place update (client id and secret unchanged).
- A separate scope from `deliver`, so the lead pull's token cannot rotate an agency's key.

## Changed

- `local.idm2m_tripplanner_scopes` gains `manage`.

## Tradeoffs

- No new API Gateway route: `/trip/m2m/v1/...` already reaches the assembly Lambda.

## Should know

- Apply before (or with) the TripPlanner and AA-Partner deploys of AA-1139: until then TripPlanner answers the CRM 403
  and the agency app shows the module's TripPlanner parts as unavailable. Cost: none (scopes are free).
- The CRM asks each receiver's scope by name, so the `scopes` value of the `aa-crm/<env>/m2m-booking-client` JSON is
  informational; add `tripplanner.leads/manage` to it with the next credential write, no restart needed.
