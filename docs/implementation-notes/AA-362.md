## Decisions

- 3 alarms added to `accounts/aa365/observability.tf`, right after `ecs_task_count_low`
  (AA-284 section), before the AA-287 Budgets section:
  - `acp_piece_held_rate_high` — CloudWatch **metric math** (`aws_cloudwatch_metric_alarm` with 3
    `metric_query` blocks: `held_sum`, `passed_sum`, and a `held_rate` expression
    `(held_sum / (held_sum + passed_sum)) * 100`). `held_rate` is not a value AA-CIS-App computes
    in Python — the app only emits raw `piece_held`/`piece_passed` counts (see AA-CIS-App-side
    notes); the ratio is computed entirely by the alarm's own metric math over a 1h window, per
    standard CloudWatch practice.
  - `acp_grounding_score_floor` — `LessThanThreshold` @ `threshold = 1.0`, `statistic = "Minimum"`,
    `period = 300`, `evaluation_periods = 1`. Since the real F1 gate is binary (mapped to
    1.0/0.0 by AA-CIS-App, not a real score — see AA-CIS-App-side notes), `Minimum` over any
    5-minute window in which even 1 piece failed F1 is `0.0`, so this fires on the very next
    period after a single failure — matches the issue's explicit "HARD FLOOR = 1.0, not a soft
    threshold" instruction exactly (no smoothing/averaging that could hide one bad piece inside a
    window of otherwise-good ones).
  - `acp_repair_count_high` — `GreaterThanThreshold` @ `threshold = 1.0` (Average), 3 consecutive
    1h periods. Threshold/window are **unverified placeholders**, called out explicitly in the
    resource's own comment — no real N7 traffic exists yet to tune against, same acknowledged gap
    pattern as AA-298's `SWEEPER_SLA_HOURS`.
- `week_run` — comment-only `TODO(AA-364)` block, no resource. Per issue instruction: do not invent
  placeholder logic for a concept that doesn't exist yet.
- Bedrock cost — not implemented, findings above left in the PR description + this note for Nghiep
  to decide (build now as a one-off, or fold into AA-360's design).
