# AA-811 — SES on acc2 + Route 53 zone for lumiguides.it.com + bootstrap grants (S237, infra lane item 1)

## Decisions

- **Sender (S237 D5, ADR 0006 item 5):** domain identity = the apex `lumiguides.it.com`, From
  `no-reply@lumiguides.it.com`, custom MAIL FROM `bounce.lumiguides.it.com`. The Linear scope said a
  sub-domain identity; D5 chose the apex. Reputation separation is done with configuration sets instead
  (see Tradeoffs).
- **DNS moves to Route 53 (S236 decision, D5):** `dns.tf` creates the public zone and copies every record
  found at Namecheap, so the NS switch changes nothing. SES DKIM / MAIL FROM / DMARC records go straight
  into the zone. Discovery + gaps: root `docs/audits/2026-10-14-S237-lane-backlog/dns-parity.md`.
- **Three configuration sets** `aa-email-dev-{workforce,external,transactional}`: ADR 0006 asks for
  separate WORKFORCE / EXTERNAL streams (Cognito, PR #105 `identity_ses_configuration_set_*`); app mail
  (Booking, TripPlanner notify, CIS) uses `transactional`, which is also the identity's default set.
- **Send grants:** one shared policy document, three standalone `aws_iam_role_policy` resources in
  `ses.tf` (CIS ECS task role — api + worker, Booking task role, TripPlanner Lambda exec role).
  `ses:SendEmail` + `ses:SendRawEmail` on the identity + the transactional set only, with
  `ses:FromAddress = var.ses_from_address`. Not in `modules/ecs` (avoids the AA-806 step 4 conflict).
- **Feedback:** BOUNCE / COMPLAINT / REJECT events of all three sets → new SNS topic
  `aa-email-dev-feedback` (topic policy: `ses.amazonaws.com`, own account only). No subscriber yet: it is
  the hook for app-side suppression (AA-811 scope 3). Alerting = two account-level alarms
  (`Reputation.BounceRate` > 2.5 %, `Reputation.ComplaintRate` > 0.05 %, half the AWS review
  thresholds) on the existing `aa-cis-dev-acp-alerts` topic, about $0.20/month.
- **DMARC `p=none; adkim=r; aspf=r`**, no `rua` by default (no agreed report mailbox; a mailbox outside
  the domain also needs an authorization record). Variable `ses_dmarc_rua_email`.
- **Bootstrap grants on `aa-cis-infra-tf-apply`** (inline, one local MFA apply for items 1, 3, 4):
  `SESIdentityManage` (identity + configuration-set ARNs, no `Send*`), `Route53ZoneManage` (no
  `DeleteHostedZone`), `ACMCertManage` (us-west-1 + us-east-1 via `aws:RequestedRegion`),
  `CognitoUserPoolManage` (`cognito-idp:*`, us-west-1), `WAFv2WebACLCreate`
  (Create/DeleteWebACL + CheckCapacity for #105), `CognitoEmailServiceLinkedRole`
  (`iam:CreateServiceLinkedRole` only for `email.cognito-idp.amazonaws.com` — Cognito DEVELOPER email
  mode creates that SLR on first use, and the apply boundary does not deny it).

## Tradeoffs

- **Apex identity vs a sub-domain identity:** apex keeps one identity for Cognito + apps and matches the
  ADR; the cost is that SES reputation and Zoho's human mail share the apex. Configuration sets + the
  reputation alarms give the separation that matters (OTP abuse visible per stream). Production can move
  to `adventure.asia` (ADR 0006 item 5) later.
- **Account-level reputation alarms vs per-set CloudWatch event metrics:** account metrics are free and
  are what AWS acts on; per-set event metrics would add custom-metric cost. Per-set reputation metrics
  are enabled anyway (`reputation_metrics_enabled`) for later.
- **`cognito-idp:*` on `*` (region-scoped):** Cognito has several actions without a resource ARN
  (CreateUserPool, DescribeUserPoolDomain, ...). Splitting by ARN saves little (only our pools exist in
  the account) and risks an AccessDenied mid-apply. Same reasoning for `wafv2:*WebACL` on `*` (CreateWebACL
  also needs the managed rule-group ARNs) — the existing `WAFv2Manage` is on `*` too.
- **Inline size:** `tf_apply` inline policy goes 6,291 → 7,785 non-whitespace characters (limit 10,240 for
  all inline policies of the role; measured from the plan JSON). ~2.4k left for later grants.
- **Legacy `www` / `api` CNAMEs** to the dead Quanskill ALB are copied (parity) rather than dropped.

## Should know

- **Apply order (bootstrap):** `aa-cis-infra-tf-apply` cannot edit its own policy (name outside
  `aa-*-dev-*`, boundary). After merge, Nghiep runs locally with MFA
  `terraform -chdir=accounts/aa365 apply -target=aws_iam_role_policy.tf_apply`, waits ~1 min (IAM
  propagation, lesson S225 AA-750), then dispatches Terraform Apply (CI) for the rest. A CI apply before
  the local one fails with AccessDenied on `PutRolePolicy`.
- **AA-806 step 4 shares the roles and the apply queue:** merge/apply serially with a re-plan in between.
  Once the phase-3 flag is on, `PutRolePolicy` on these roles needs their workload boundary (step 4 first).
- **Nothing verifies until the NS switch.** Zone NS output: `lumiguides_zone_name_servers`. Do the parity
  check in `dns-parity.md` before switching (Zoho mail depends on it).
- **Sandbox:** 200 mails/day, 1/s, only to verified addresses until the production-access request is
  granted (console, us-west-1). Cognito email OTP (AA-703) needs the identity SUCCESS and, in the sandbox,
  a verified test inbox.
- App helpers must send From exactly `no-reply@lumiguides.it.com` and either no
  configuration set or `aa-email-dev-transactional`; anything else is AccessDenied by design.
- Plan (local, aa365-admin, `-lock=false`, placeholder `TF_VAR_db_password` — password is
  `ignore_changes`): **31 to add, 2 to change, 0 to destroy**. The second change is pre-existing drift
  (`aws_lambda_function.dfs_balance_check` source_code_hash from the local zip build), not from this PR.
- Possible later gap for AA-703 custom domains: if Cognito asks for extra permissions when attaching the
  us-east-1 cert (e.g. CloudFront), add them then; not granted speculatively.
