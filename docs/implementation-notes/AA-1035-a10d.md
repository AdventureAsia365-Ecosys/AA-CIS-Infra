# AA-1035 A10d (S270, lane aa1035-a10d-cs-e2e-identity) — AA-CIS-Infra half

Root ADR 0006a A10d: a fifth Dev-only WORKFORCE E2E identity, `e2e-cis-cs@e2e-mail.lumiguides.it.com`, staff groups
exactly `cis-customer_success`, read-only in CIS with no write allow-list. CIS half: AA-CIS-App
`docs/implementation-notes/AA-1035-a10d.md`; AA-Partner half: AA-Partner `docs/implementation-notes/AA-1035-a10d.md`.

## Decisions
- One more entry in the Dev-only map `workforce.E2E_DEV_ONLY_TEST_STAFF` (behind `E2E_DEV_ONLY_STAFF_ENABLED`, exactly
  `"true"` on dev only). Not in the always-on `E2E_TEST_STAFF` map.
- Mailbox: a third recipient of the A10b rule `e2e-cognito-admin` (prefix `inbound-admin/`, MFA admin reads only). Never
  a recipient of `e2e-cognito` (the CI-readable `inbound/`). The `e2e_mailbox` output is unchanged (optional in the
  scope; leaving it keeps the plan to resources only).
- No change to `identity.tf`: `cis-customer_success` is already a staff group (`local.id_staff_groups`, precedence 16).

## Changed
- `accounts/aa365/lambda_src/identity_triggers/workforce.py` (constants, map entry, docstring).
- `accounts/aa365/e2e_mailbox.tf` (local `e2e_mail_cis_cs_recipient`, the admin rule's recipients).
- `accounts/aa365/lambda_src/identity_triggers_tests/test_workforce.py` (A10d tests, the map and rule guards).

## Tradeoffs
- The account is created through the CIS staff directory (ECS exec, `create_staff`), like A10b, not by a
  `tools/identity` command: it has a `shared.admin_users` row (needed for the tenant book), so the directory is its writer.

## Should know
- Expected plan (aa365): the WORKFORCE trigger Lambda code update(s) and one in-place update of
  `aws_ses_receipt_rule.e2e_cognito_admin[0]` (recipients). Nothing else.
- After the apply, an A10b sign-in (Playwright `admin-evidence`) proves normal staff tokens still issue.
- Apply this before the CIS directory creates the user: the pre sign-up trigger refuses the address until then.
