## STEP 0 finding (before this fix)

- `modules/ecs/main.tf::aws_iam_role_policy.ecs_task_policy` — the ECS task role for
  `aa-cis-dev-api` — had `s3:GetObject/PutObject/ListBucket`, `secretsmanager:GetSecretValue`,
  `sqs:SendMessage/ReceiveMessage/DeleteMessage`, `logs:CreateLogGroup/CreateLogStream/
  PutLogEvents`, `bedrock:InvokeModel/InvokeModelWithResponseStream`. No `cloudwatch:*` action at
  all. Confirmed by reading the resource directly, not by inference from the AccessDenied error
  alone.
- Confirmed the emitting code's namespace exactly (`AA-CIS-App:services/acp_produce/metrics.py:58`,
  `NAMESPACE = "acp"`, lowercase, no slash — same convention `api/routers/acp_health.py`/AA-141
  already uses) before writing the IAM scope, so the fix isn't broader than the one real namespace
  in use.

## Decision

`cloudwatch:PutMetricData` has no ARN-scoped `Resource` in IAM — it is always `Resource: "*"` by
AWS's own API design, regardless of policy authoring choices. The only way to restrict *which*
namespace a role can write metrics into is the `cloudwatch:namespace` condition key. Added as a
**second statement** inside the *existing* `aws_iam_role_policy.ecs_task_policy` resource (not a
new `aws_iam_role_policy`/`aws_iam_role` resource — same role, same policy document, matching the
issue's own instruction to not create new roles):

```hcl
{
  Effect   = "Allow"
  Action   = ["cloudwatch:PutMetricData"]
  Resource = "*"
  Condition = {
    StringEquals = {
      "cloudwatch:namespace" = "acp"
    }
  }
}
```

Scoped to `"acp"` only — not a wildcard `cloudwatch:PutMetricData` grant — so this role still
cannot write to any other CloudWatch namespace.
