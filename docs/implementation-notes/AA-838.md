## Decisions

- **`crm_app = 6` joins `local.rds_role_connection_limits`** (observability_ecosys.tf), so the existing for_each
  creates `aa-cis-dev-rds-role-connections-crm_app` with the same shape as the other roles (Maximum of
  `AA/RDS RoleConnectionLimitPct{Role=crm_app}`, > 80 %, 1 of 2 x 5 min, notBreaching, ALARM + OK to the alerts
  topic, database runbook). The sampler already publishes the metric (the report read 5/6 = 83 % on 24/10).
- **Threshold not tuned for CRM.** Pool 3 x 2 tasks = the limit 6, so a rolling CRM deploy can alarm. The alarm then
  says the truth (the next connect would be refused); the fix is the pool budget (report D-list), not a higher
  threshold.
- **Probe scripts copied for DB Migrate `mode=run-script`** (master login, full statement text):
  `db/scripts/aa838_capacity_probe.py` (byte-identical to the lane file) and `db/scripts/aa850_dead_table_dry_run.py`
  (one line changed, below). Both `READ_ONLY = True`; `python3 db/run_migration.py --inspect-script` passes for both.
- **aa850: one-line change for the shape check.** Its ECS-exec fallback ran `SET default_transaction_read_only = on`,
  which the runner's check refuses in a READ_ONLY script (any literal naming `transaction_read_only`). Replaced by
  `SET SESSION CHARACTERISTICS AS TRANSACTION READ ONLY` (same effect: sets the session default), the form the
  capacity probe already uses. The lane's source in the root `.tmp-session/S255/aa850/` still has the old line.

## Changed

## Tradeoffs

# AA-838 (S256) — capacity review decisions D1–D13 (Infra part)

Session S256 (28/10/2026), Claude Code Infra lane. Branch `feat/aa-838-capacity-decisions`. Source: root
`docs/audits/2026-10-28-S255-aa838-capacity/README.md` §4 (the decision list, approved by the tech lead in S256).

## Decisions

- **D13 — `pg_stat_statements.max` 5,000 → 10,000** in `aws_db_parameter_group.main` with
  `apply_method = "pending-reboot"`. Checked live before the change (`describe-db-parameters`): the parameter is
  `static`, `engine-default`, modifiable, allowed 100–2147483647; the instance is `in-sync`. After apply the group
  shows the value and the instance shows `ParameterApplyStatus = pending-reboot`; `pg_settings` keeps 5000 until the
  reboot. The reboot is NOT in Terraform: an orchestrator step in a quiet window (every job table idle, C5.5a).
- **D2 — the C2.2 lever is the api task count, not the main pool.** The review proposed main pool 10 → 5 "from the
  `aa859_main_pool_gauge` baseline". The baseline (CloudWatch Logs `/ecs/aa-cis-dev`, api streams, 16–28/10/2026,
  18,873 gauge lines + 1,549 `aa859_main_pool_wait` lines, read in S256) says no:
  - The 60 s gauge almost always reads `in_use=0` (short requests), so it under-reports (lesson: size from the wait
    signal, not the sampled gauge).
  - The wait lines (acquire >= 50 ms) carry `in_use` at the wait: outside the AA-859 burst (22/10 13:xx, 589 waits
    at in_use >= 6, max wait 3.9 s, pool full 267 times), ordinary admin traffic still put one task's pool at
    5–7 in use 55 times and 8–10 in use 8 times in 23–28/10 (p50 wait 419 / 478 ms).
  - A pool of 5 would queue every one of those and turn an AA-859-style burst into 5 s acquire timeouts (503).
  - Autoscaling history (`describe-scaling-activities`): the api never went above **3** tasks since 29/09.
  So `aws_appautoscaling_target.api.max_capacity` 7 → 3: cis-api 10 × 3 = 30, cis-tenant 2 × 3 = 6, total
  **120 / 135**, `cis_app` **60 / 90**, `aa_app_user` 6 / 15. Both `accepted_overages` (role:cis_app, total; until
  15/12/2026) are removed; `check_connection_budget.py --verify-sources` passes with no warning.
- **D6 — probe synced to the reviewed version** (decision_log 180-day window, `shared.job` aged on `finished_at`,
  `[retention]` section) and `PROBE_TOP` defaults to **50**: run-script passes no environment, so each monthly run
  now saves the C4.3a top-50 snapshot (D7) without a flag.
- **D8 — `db/scripts/aa838_booking_queue_age_check.py`** (read-only). The Booking task log already narrows the
  cause: the 38,746 s sample came from a NEW task's sampler 0.5 s after a rolling deploy started it (git sha
  4fb0eaf, 24/10 03:14:46 UTC; the old task sent 0 at 03:11:23, the next sample was 0). The script names the row
  (kind, run_after vs created_at, when it was claimed) so the fix can be chosen (likely: a kind the old worker did
  not handle, or a job enqueued with a past `run_after`; the metric itself behaved as designed).
- **D4 — already done in S255** (#461, `aa-cis-dev-rds-role-connections-crm_app`, state OK, read in S256). No change.

- `modules/ecs/main.tf`: api `max_capacity` 7 → 3 + comment with the evidence.
- `db/connection_budget.json`: `accepted_overages` emptied.

## Tradeoffs

- Capping api tasks at 3 instead of shrinking the pool keeps today's per-task behaviour (zero new waits) and costs
  nothing; the price is less scale-out headroom (3 × 0.5 vCPU). Dev has never used more than 3. A real prod sizing
  revisits this together with the instance class (C3, C9.1), and any raise must update C2.2 + this manifest.
- The pool-5 option stays available if the tech lead prefers it: revert `max_capacity`, set `api/main.py`
  max_size=5 in CIS, and `max_size` 5 here.

## Should know

- **Expected CI plan:** 0 add, 2 change, 0 destroy — `module.rds.aws_db_parameter_group.main` (one parameter
  added) and `module.ecs.aws_appautoscaling_target.api` (max_capacity). No task definition change, so the
  lesson about TF re-registering task defs does not apply. Cost: 0 (a few MB of RDS shared memory after reboot).
- **Orchestrator after merge:** (1) Terraform Apply; (2) check `describe-db-instances` → `pending-reboot` and
  `describe-scalable-targets` → max 3; (3) at a quiet moment (shared.job / booking.job / crm.job idle, no wave):
  `aws rds reboot-db-instance --db-instance-identifier aa-cis-dev-db` (~1–2 min outage for every app), then
  `SHOW pg_stat_statements.max` = 10000 via run-script `session_info.py`-style read or the probe `[setting]`
  lines; (4) DB Migrate `mode=run-script script=db/scripts/aa838_capacity_probe.py` (full text, D12 input);
  (5) `script=db/scripts/aa838_booking_queue_age_check.py` (D8).
- The statistics should survive the reboot (`pg_stat_statements.save` is on by default: the extension writes its
  file at a clean shutdown and reloads it, and a larger `max` only adds room), but a crash or failover loses them,
  so run the probe (step 4) BEFORE the reboot to capture the three-week history with full text first.
