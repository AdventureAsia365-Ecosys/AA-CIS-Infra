# AA-807 — Data phase 1 foundation

## Slice 1 (S237): Migration Copy Guard

CI check that every DB Migrate copy in `db/migrations/<owner>/` is byte-identical to the same file
on the owner repo's `main`. The other AA-807 slices (per-app owner roles, nightly schema-drift
job, Dead Table Registry, `shared.countries`) are not in this slice.

### Decisions
- **Stdlib-only Python script** (`db/check_migration_copies.py`) plus a thin workflow
  (`.github/workflows/migration-copy-guard.yml`). No install step, no AWS, no secret. The logic
  lives in the script so it can be unit-tested and run locally.
- **GitHub contents API** (`Accept: application/vnd.github.raw`), not `raw.githubusercontent.com`.
  The raw CDN caches for about 5 minutes, so a copy PR opened right after the owner merge could
  fail on stale content. The API reads `main` directly.
- **Auth:** `GITHUB_TOKEN` (the workflow's `github.token`) is sent when set, only to lift the rate
  limit. If GitHub answers 401/403 for that token, the call retries anonymously, because the app
  repos (AA-CIS-App, AA-TripPlanner-Web, AA-Booking) are public. A 404 means "not on main".
- **GitHub errors are a per-file FAIL, not a crash** (review fix). Rate limits (401/403/429 after
  the anonymous retry), 5xx and network errors are retried 3 rounds with a short backoff, then the
  file is reported as `cannot compare with … : could not read … from GitHub` and the run goes on to
  the next file. Locally, `GH_TOKEN=$(gh auth token)` lifts the 60/hour anonymous limit.
- **Owner map** in the script mirrors `docs/database/schema-ownership.md` rule 4:
  `cis` → AA-CIS-App `api/migrations/`, key `NNN`; `tripplanner` → AA-TripPlanner-Web
  `migrations/`, key `tp-NNN`; `booking` → AA-Booking `migrations/`, key `bk-NNN`.
- **Prefix check** reads the version keys inside the file's `INSERT INTO shared.schema_versions`
  statements (the first value of each VALUES row), not any quoted number in the file. The file's
  own key (prefix + the filename's NNN) must be among them, and every key must have the owner's
  prefix. TripPlanner `007` registers `tp-001`…`tp-007`, which is allowed.
- **Path rule** = the regex `db-migrate.yml` already uses at dispatch
  (`<cis|tripplanner|booking>/NNN_lowercase_name.sql`), so a file DB Migrate would refuse fails
  at PR time instead.
- **Which files:** on `pull_request`, the files the PR adds/changes/renames under
  `db/migrations/` (`git diff --diff-filter=ACMR base...HEAD`). Deleted files are skipped. On the
  nightly schedule, on manual dispatch, and on a PR that only touches the guard itself, every copy
  is checked, so an owner editing an already-copied file on its main also shows up.

### Changed
- Spec said "fetch with raw.githubusercontent or gh api": used the REST contents API through
  `urllib` (same endpoint `gh api` uses), for the cache reason above.
- Added `__pycache__/` to `.gitignore` (test runs create it next to `db/`). The already-tracked
  `db/__pycache__/run_migration.cpython-313.pyc` is left alone.
- README, `db/README.md` and `CONTEXT.md` describe the D8 order: migration-only PR on the owner's
  main, then the Infra copy, then DB Migrate check/apply, then the code PR.

### Tradeoffs
- **Compare against owner `main`, not the owner PR head.** This forces the owner's
  migration-only PR to merge first (S237 D8). The alternative (compare with an open PR head)
  would let a copy land for a file that might still change in review.
- **Nightly `--all` makes ~23 API calls a night.** That is well under the token limit. A
  scheduled failure emails whoever last changed the cron line. Nothing posts to Slack.
- The version-key parser is a regex, not an SQL parser. Unusual shapes (a key built with `format()`
  or a `SELECT` instead of `VALUES`) would read as "does not register its version". Every current
  copy (23 files) passes, and the fix for an odd file is to use the standard `VALUES ('key', …)`.

### Should know
- **Branch protection is human-only.** To make the check required, add "Copies match owner main"
  to the AA-CIS-Infra `main` protection. The workflow has a `paths:` filter, so a required
  check would wait forever on PRs that touch no migration. If it becomes required, drop the
  filter first: a PR with no copies then checks every copy, which takes seconds.
- **Prove it live** (Done-when): the workflow runs only once it is on a PR branch / main
  (lesson: a CI workflow must run for real once before Done). Record two run URLs on AA-807: a
  green run on a correct copy (CIS 228 from AA-712, or this PR's own `--all` run) and a red run
  on a throwaway commit with one changed byte.
- Local results (14/10/2026): `python3 db/check_migration_copies.py --all` → 23 files, 0 failed
  against GitHub main. With a trailing space appended to `cis/226`, the run fails with
  `differs … sha256 copy=b0f2fd965a4d owner=a8dd5b95f89a`. A fake `booking/099` fails with
  "not found on … AA-Booking@main … merge the migration-only PR in the owner repo first". Unit
  tests: 16 passed.
- **Edits to a copy already on main** (review fix 2). The guard cannot see whether a version is
  applied, and DB Migrate never re-runs a registered version, so re-syncing an applied copy after
  an owner edit is a silent no-op. On a PR, each modified (not added) copy gets a `::warning`
  saying so; the byte-mismatch FAIL tells the reader to ship a new migration when the version is
  already applied, and to merge the owner PR and re-copy only when it is not. It is a warning, not
  a failure, because fixing a copy that is merged but not applied yet is legitimate.
  The "not on main" message now also says the check can simply be re-run after the owner merge.

## Slice 2 (S237): schema dump workflow (N1) + safe migration runner (N5)

Data architecture review N1 + N5 (`AA-Ecosys/docs/audits/2026-10-14-S237-lane-backlog/data-architecture/README.md`
§5.3, §7) and data standards MIG-3, MIG-9, MIG-10, MIG-12, DM-3.1, DM-9.2.

Files: `db/run_migration.py` (runner), `db/check_migration_files.py` (lint + unique numbers),
`db/schema_dump.py` (read-only dump, runs in the ECS task), `db/gen_schema_reference.py` (Markdown),
`.github/workflows/db-schema-dump.yml` (new), `db-migrate.yml` and `migration-copy-guard.yml`
(changed), tests `db/tests/test_run_migration.py` + `test_schema_reference.py`.

### Decisions
- **Runner settings through the connection's `server_settings`** (`lock_timeout 5s`,
  `statement_timeout 15min`, `application_name db-migrate`), not `SET` statements: they cover
  every statement of the session, including the `schema_versions` reads, and a file's own
  `SET LOCAL` (the MIG-9 interim rule) still wins inside its transaction. Only the two timeouts can
  be overridden by a header; `application_name` stays fixed for attribution (standards C1.1a).
  Values must match `^[0-9]+(us|ms|s|min|h|d)?$`, so a header cannot inject anything.
- **Directive syntax** = data standards MIG-9/10/12: `-- migrate: <flag>` or `-- migrate: key=value`,
  one per line, only in the leading comment block (blank and `--` lines before the first
  statement). Unknown, malformed, duplicated-with-another-value or misplaced directives are errors
  (fail closed: a typo like `no-transation` must not silently run a CONCURRENTLY file in a
  transaction). A trailing `-- note` after a directive is allowed.
- **One lint, three places.** `lint()` lives in the self-contained runner (it is exec'd in the task,
  so it cannot import a sibling module); `check_migration_files.py` (CI) and the DB Migrate
  "Validate input" step (`--inspect`) import/call it. `asyncpg` is imported lazily so CI and the
  workflow runner need no install. Errors: CONCURRENTLY without no-transaction, `DROP TABLE` /
  `DROP SCHEMA` / `DROP MATERIALIZED VIEW` / `ALTER TABLE … DROP [COLUMN]` / `TRUNCATE` without
  destructive, BEGIN/COMMIT in a no-transaction file, a no-transaction file whose last statement is
  not the `shared.schema_versions` INSERT. `DELETE` is only a warning (small config-row deletes are
  legitimate, MIG-13). Statements are found with a small splitter that understands `--` and nested
  `/* */` comments, `'…'` with `''`, `E'…'` with backslashes, quoted identifiers and dollar quotes,
  so anything inside a `DO $$ … $$` body or a string is not linted.
- **no-transaction execution**: each statement is sent as its own simple-protocol message, so each
  autocommits (needed for CONCURRENTLY and VACUUM). Transactional files are still sent whole, as
  before (no behaviour change for any existing copy).
- **Destructive snapshot taken by the workflow, not the task.** The CI role
  (`aa-cis-infra-tf-apply`, AmazonRDSFullAccess) can create snapshots; the ECS task role has no
  RDS permissions and should not get them. The workflow creates `db-migrate-<version>-<run id>-<attempt>`,
  waits for `available`, passes the id as `MIGRATION_SNAPSHOT`; the runner refuses a destructive
  apply without it (exit 5), so a run outside the workflow cannot skip the snapshot.
- **"latest" per owner prefix**: the check output now shows the latest key of the same owner
  (`^[0-9]{3}$`, `^tp-[0-9]{3}$`, `^bk-[0-9]{3}$`) instead of `max(version)` over numeric keys only
  (review N5 "a latest query per prefix"). `007b` and other legacy keys are excluded.
- **Unique numbers** are checked on the Infra copies (the files DB Migrate can apply). The CIS
  legacy duplicates (007/008/019/007b) are not copied here, so no allowlist is needed.
- **Dump runs as a one-off ECS task like DB Migrate** (lesson "long ad-hoc scripts → one-off task",
  S234), not ECS exec. Uses the task's `DATABASE_URL` (no Secrets Manager read in the script) and
  the task role's existing `s3:PutObject` to write the JSON (no presigned PUT needed). Read-only by
  construction: `default_transaction_read_only=on`, one `REPEATABLE READ READ ONLY` transaction
  (consistent snapshot), `statement_timeout 60s`, `lock_timeout 10s`.
- **Catalog source = `pg_catalog`, not `information_schema`.** `information_schema` filters by the
  caller's privileges; `pg_attribute` + `format_type()` does not and gives exact types
  (`character varying(64)`, `vector(1024)`, `text[]`, schema-qualified enums). One-time diff in
  type spelling vs the S209 file (`_text` → `text[]`, bare udt names → qualified names).
  Extension-owned tables/functions are left out (pgvector functions would add hundreds of rows).
- **Root PR only on structural change.** The Markdown carries `schema-fingerprint` = sha256 of the
  dump without row estimates, sizes, scan/activity counters, sessions and timestamps. The workflow
  compares it with the fingerprint in the root repo's `master` copy; equal → no PR (manual
  `publish=true` forces one). Statistics in the file are therefore "as of the last structural
  change" — the Conventions section says so. The PR branch `bot/db-schema-reference` is
  force-pushed from master every time, so there is at most one open PR, updated in place.
- **Root PR token**: GITHUB_TOKEN cannot write to another repo. New secret `ROOT_REPO_DOCS_TOKEN`
  (fine-grained PAT or GitHub App token scoped to `AdventureAsia365-Ecosys/AA-Ecosys`,
  Contents + Pull requests read/write). If it is missing, the dump, S3 copy and artifact still
  succeed and the publish step fails with a clear error (loud, not silently skipped).
- **After-apply trigger** = a last DB Migrate step that dispatches `db-schema-dump.yml` with the
  job's `GITHUB_TOKEN` (`actions: write`); `workflow_dispatch` is one of the events a
  GITHUB_TOKEN may trigger. Chosen over `workflow_call` so a dump failure never turns a successful
  migration run red, and over `workflow_run` because that event cannot see the `mode` input.
- **Separate concurrency group** `db-schema-dump`: sharing `db-migrate` would let a queued dump
  cancel a pending migration run (GitHub keeps one pending run per group).
- **Published content is filtered**: role settings only from an allowlist (`statement_timeout`,
  `lock_timeout`, `idle_in_transaction_session_timeout`, `search_path`, `application_name`,
  `default_transaction_read_only`, `work_mem`), no function bodies, no query text from
  `pg_stat_activity` (only counts per application_name/role/state), no row data. The root repo is
  public (E10: no secrets in schema/RLS).

### Changed (vs the spec / review text)
- Spec: "move the scripts". The S209 scripts stay in root `.tmp-session/` (gitignored); the new
  files replace them. The root steering `.kiro/steering/db-schema.md` and `skill/aa-cis-schema`
  still describe the manual S209 procedure — update them in the next root PR (orchestrator).
- "Fails on unmanaged objects" (review §5.3, N1 drift) is **not** in this slice: that needs a DB
  built from all migrations to diff against. Each root PR shows the diff instead, and its body asks
  the reviewer to look for objects no migration explains.
- The ECS waiter in DB Migrate now retries up to 3 × 10 min: with `statement_timeout 15min` a
  legitimate migration could outlive the single 10-minute `aws ecs wait`.
- Squawk was not added (grep-style rules only; the review allows "squawk or grep rules").

### Tradeoffs
- **Snapshot on every destructive `apply` dispatch**, even if the version turns out to be applied
  already (the workflow does not know before the task runs). A wasted snapshot costs minutes and
  cents; a missing one is not recoverable.
- **The dump uses the DB Migrate CI role and `environment: prod`.** No new IAM, no bootstrap apply.
  The cost: a powerful role runs nightly, and a future required reviewer on `prod` would stall the
  nightly run. A dedicated read-only role/environment belongs to X1.
- **Statistics lag** between structural changes (fingerprint decision) — accepted to avoid a
  nightly PR that only moves row counts.
- `pg_total_relation_size` takes an ACCESS SHARE lock; with `lock_timeout 10s` a dump that meets a
  migration's exclusive lock fails instead of waiting; the next run succeeds.

- Local results (15/10/2026): 55 unit tests pass (`python3 -m unittest discover -s db/tests`);

  history flags exactly the real cases: CIS 002/003/120/121/122/146/208 (DROP TABLE/COLUMN/SCHEMA)
  and 205 (CREATE/DROP INDEX CONCURRENTLY + VACUUM, applied by hand at the time); DELETE warnings
  for 075/104/146/207. Against a local `postgres:15-alpine` with a seeded catalog (RLS + FORCE,
  policy, table/column grants, default ACLs, SECURITY DEFINER trigger function, multi-column FK,
  enum, matview, extension): `collect()` returned every section and a write inside the dump
  transaction raised `ReadOnlySQLTransactionError`; the runner applied a no-transaction file

  exit 6 and the lock hint.

### Review fixes (S237 adversarial review)
- Lint: `REFRESH MATERIALIZED VIEW CONCURRENTLY` no longer needs no-transaction (PostgreSQL allows
  it in a transaction block); `VACUUM` outside a no-transaction file is now a lint error instead of
  a runtime failure. Two tests added (57 total).
- DB Migrate: the snapshot id carries `run_attempt` (`db-migrate-<version>-<run_id>-<attempt>`), so
  "Re-run jobs" does not fail on `DBSnapshotAlreadyExists`; the after-apply dispatch of DB Schema
  Dump is `continue-on-error`, so a dispatch problem never turns a successful apply red (the nightly
  run catches up).
- Should know: `lock_timeout` also bounds the waits inside `CREATE INDEX CONCURRENTLY` (it waits
  for older transactions). On a busy table set `-- migrate: lock_timeout=…` in the file, or the
  build stops after 5 s and leaves an INVALID index to drop before the retry.
- Should know: the dump holds ACCESS SHARE on every table, TOAST table and index it sizes until
  its one transaction ends (seconds). That is ~1–2k lock-table entries for a few seconds, well under
  `max_locks_per_transaction × max_connections`, and DDL that meets it waits at most the dump's
  length (DB Migrate itself gives up after 5 s).
