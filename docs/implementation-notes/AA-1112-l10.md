# AA-1112 — retention rows for every owner, stale RLS allowlist entries fail (lane l10, S284)

Lane `l10-aa1112`, S284 (2026-11-18), Claude Code. Two AA-1112 Done-when items: "the CI rule (a new table needs its
DM-7.1 retention row) is green" and "the allowlist has no stale entries". The allowlist cleanup itself is in
AA-CIS-App (canonical `tests/integration/rls_catalogue_rules.py`); this PR carries its byte copy.

## Decisions

- **One check, in the Copy Guard.** Every owner migration reaches Dev through a copy here, so the existing
  `db/check_retention_rows.py` (AA-929, `crm` + the CIS `learn` schema) now covers all four owner dirs instead of
  four per-repo checks. `RETENTION_OWNERS` gains `booking` and `tripplanner`; `cis` was already there for `learn`.
- **Grandfathering by number.** DM-7.1 keeps the existing tables of CIS, Booking and TripPlanner without a row until
  their owner proposes a window. `RETENTION_FROM = {cis: 448, booking: 60, tripplanner: 35}`, the next free number of
  each owner on 18/11/2026: a table created or renamed in a file at or above it needs its row. 85 older tables have
  no row today (CIS 46, Booking 36, TripPlanner 3); they stay grandfathered. A unit test pins the three numbers, so
  raising one to turn the check green needs a visible test change.
- **A rename needs the new name's row** (DM-7.1 "creates, renames or splits"): the location reported is the RENAME
  statement, and from `RETENTION_FROM` on the new name must be in the registry.
- **Error text names what to edit:** `<file>:<line>: table <schema.table> has no row in the DM-7.1 retention
  registry. Add a row whose first cell is `<schema.table>` to the table of '## 7. Retention and archival' in
  AA-Ecosys docs/architecture/data-standards/02-data-management.md (root PR, merged to master first), then re-run`.
- **Stale RLS entries fail on the Dev dump** with `db/check_rls_allowlist.py` (stdlib, imports the rules copy): the
  latest successful DB Schema Dump artifact on main, downloaded the way Expand classify already does. Only Dev holds
  every owner's objects; the CIS replay checks the CIS-side entries (AA-CIS-App PR of this lane).
- **Same advisory job, renamed** "Retention rows and RLS allowlist" (was "Retention rows for new-app tables"): both
  steps compare a registry with what exists, and one job keeps the S271 one-billed-job budget. The job stays out of
  the ruleset (S271 review); it now has `actions: read` for the artifact download. The RLS step runs after a red
  retention step too (`!cancelled()`), and warns (passes) when no dump artifact exists (expired).

## Tradeoffs

- The DB Schema Dump workflow itself does not fail on a stale entry: a failed job makes its run not "success", and
  Migration Apply, Migration Sync and Expand classify read the latest successful run. The Copy Guard's nightly run
  (02:17 UTC) reads the previous night's dump, so an apply that leaves an entry stale shows red within a day.
- The retention check stays advisory (not required) as decided in S271; a red check is still a red check for
  `ship_merge.py`, which waits for every check.
