# AA-1165 — per-viewer rate rule on the CloudFront path (CRM hosts)

Tech-lead decision S286 D10: one WAF rate rule now (about 1 USD/month), a full CloudFront web ACL when prod starts.
Background and the reason for the rule: Linear AA-1165 (not repeated in this public repo).

## Decisions

- **Rule in the existing REGIONAL web ACL `aa-<env>-waf` (modules/waf), no new ACL.** The CRM distributions have no
  web ACL of their own; a CLOUDFRONT-scope ACL is ~5 USD/month fixed and the S272 decision (AA-1038) already put the
  TripPlanner edge rules in this ACL for the same reason. Rule `CloudFrontViewerRateLimit`, priority
  `local.rule_priorities.cloudfront_viewer_rate` = 5: after CommonRuleSet and the TripPlanner rules, before both allow
  rules (CloudFrontOriginAllow ends the evaluation of every CloudFront request; VpcLinkInternalAllow is passed too,
  same reasoning as AA-1038). The five later rules move up by one (in-place UpdateWebACL, relative order unchanged).
- **Key: `x-aa-viewer-ip` (FORWARDED_IP, fallback MATCH)**, written by a CloudFront viewer-request function from
  `event.viewer.ip` over any value the viewer sent. Not X-Forwarded-For (WAF reads its first address, which the viewer
  writes); not `CloudFront-Viewer-Address` (`ip:port`, not a valid key). Same header and same JS as the TripPlanner
  function (AA-1038). Agency and client distributions get a new function `aa-crm-<env>-viewer-ip` (same code file as
  the TripPlanner one); the partner distribution already has a viewer-request function (301 to the agency host) and a
  behaviour takes one, so that function writes the header on the `/crm` requests it lets through.
- **Scope: origin secret EXACTLY AND NOT TripPlanner AND NOT our NAT egress.** TripPlanner (both distributions carry
  the site header) has its own per-viewer rules (3000 / 5 min); counting it again at a lower limit would block the
  planner. The NAT egress is essential: the CRM web's server-side calls go to the API through the partner host
  (`CRM_API_ORIGIN`), so every agency user's BFF call reaches WAF with the NAT address as the viewer; counted together
  they would block the whole CRM. The egress IP set (AA-1092) is matched with `ip_set_forwarded_ip_config` on the same
  viewer header (position FIRST, absent = NO_MATCH, so a missing header is still counted).
- **Limit 5000 / 5 min per viewer** (`crm_edge_rate_limit`, default = the staff web rule's value): the CRM web is a
  Next.js app behind CachingDisabled, so a page with its chunks, RSC navigations and BFF calls is dozens of requests,
  like the staff web. Not scoped away from static paths: nothing in this ACL does that, and uncached chunks cost the
  task too. No health-check exclusion needed: ALB target health checks never pass the web ACL, and the NLB's do not
  carry the origin secret.
- **COUNT first, then BLOCK (the issue's scope).** `crm_edge_rate_count_only` defaults to `false` (the steady state);
  `terraform.tfvars` sets `true` for the count window. The flip is a one-line PR that removes the tfvars line.
- **Answer: 429 with the JSON body `rate_limited` and the AA-1111 security headers** (the TripPlanner rate rules'
  answer), not the 403 of RateLimit1000 that the issue's Done-when names: 429 is the meaning, and the CRM web can tell
  it from an auth 403.
- **Thresholds as settings (S279):** the limit and the mode are named Terraform variables published in the read-only
  root output `platform_limits` (the AA-1096 L6 rule for edge values: app roles never write WAF). No app-settings
  row: there is no admin-editable layer for WAF values by design.

## Tradeoffs

- One rate bucket per office NAT: several agency staff behind one address share 5000 / 5 min. Fine on Dev; the
  variable is the knob, and the CloudFront web ACL at prod sees the viewer natively.
- The rule only sees requests that reach the ALB (all CRM behaviours are uncached, so that is every request).
- No alarm: this ACL has no CloudWatch alarm today and a new
  standard alarm is 0.10 USD/month, so it is a follow-up for the tech lead rather than part of this change. The rule
  has its own metric (`CountedRequests` / `BlockedRequests`, Rule = CloudFrontViewerRateLimit) and the WAF log keeps
  every counted or blocked request.

  not expand them).
- WCU (est.): rate rule 2 + exact header match 2 + NOT site header 2 + NOT IP set 1, about 8; the ACL stays far under
  the 1500 included.
- **Cost (D-19):** one WAF rule 1 USD/month; requests are inspected by this ACL already (no new request fee); the
  CloudFront Function invocations stay inside the always-free 2M a month on Dev. About 1 USD/month in all.
- **Live proof (review fix):** `/crm/health` carries the CRM API's own per-viewer limiter (60 a minute), so a burst
  answers mostly 429 from the app with or without this rule. The burst in `docs/waf-count-review.md` therefore tallies
  the body key as well (`429 error` = WAF `{"error":"rate_limited"}`, `429 detail` = app `{"detail":"rate_limited"}`),
  runs 18000 requests at 20 in parallel (about 3 minutes, far past 5000, longer than the up-to-a-minute evaluation
  lag), and the required evidence is a non-zero `CountedRequests` / `BlockedRequests` sum for
  `Rule=CloudFrontViewerRateLimit`, not the status tally.
