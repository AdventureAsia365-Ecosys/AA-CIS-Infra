# AA-894 part 1: generated ERD from the nightly schema dump

Scope of this branch: Linear AA-894 scope 1 and Done-when line 1 only (generated ERD per schema + `erd.json`).
The admin live view (scope 2), the design ERD and drift check (scope 3), PRD as code (scope 4) and the
env-config register (scope 5) are later branches.

## Decisions

- **Sibling generator `db/gen_erd.py`**, not more code in `db/gen_schema_reference.py`. It imports `parse_tag`
  (DM-6.1 tags) from the reference generator and `SCHEMA_OWNERS` from `db/rls_catalogue_rules.py`, which the
  owner-registry test already keeps equal to `db/owners.yaml`; so no new mirror of the registry. Standard library
  only, like the reference generator (runs on the GitHub runner).
- **Primary keys come from the primary index**, not from `pg_constraint`: the dump query keeps only `c` and `f`
  constraints, and adding `p`/`u` would change the structural fingerprint of every dump and the reference
  rendering. The PK columns are parsed from the `is_primary` index definition (`USING btree (a, b)`); unique keys
  (`UK`) from single-column, non-partial, valid unique indexes. Expression and partial indexes give no key.
- **Pages:** one `docs/architecture/erd/<schema>.md` per schema that has relations, plus a generated
  `docs/architecture/erd/README.md` index (schemas, owner, counts, cross-schema FKs, empty schemas). Catalog ID
  `APP-04-erd` (index) and `APP-04-erd-<schema with - for _>` (pages), under APP-04 "DB schema reference + ERD".
- **What the diagram shows:** base tables (not partitions, not views), every FK as an edge labelled with the
  constraint name. A schema with no base tables (`catalog`: views only) shows its views instead, so every
  non-empty schema has a diagram. A schema's diagram draws **its own FKs** only; the parent of an FK into another
  schema is a quoted `"schema.table"` entity without attributes. FKs of other schemas that point into this one
  are listed under "Foreign keys in from other schemas", not drawn: with them `shared` drew 58 extra edges to
  `tenants` / `destinations` (first render on the 21/10 dump) and the diagram stopped being readable.
- **Index page:** cross-schema FKs as schema-pair counts, plus the full list of FKs between two owners (today:
  10 `tripplanner` -> `shared.destinations`), not all 74 cross-schema FKs.
- **Readable big schemas:** full columns when a schema has at most `MAX_FULL_TABLES` (20) tables and
  `MAX_FULL_COLUMNS` (150) columns; otherwise only key columns (PK, FK, UK). Every page also has a Markdown table
  (columns, PK, FKs out/in, DM-6.1 tagged columns) and points to `db-schema-reference.md` for the full column list.
- **Mermaid text rules:** types shortened to Mermaid-safe words (`character varying(64)` -> `varchar(64)`,
  `timestamp with time zone` -> `timestamptz`, `numeric(10,2)` -> `numeric(10_2)`, schema prefix of an enum
  dropped); the full type stays in `erd.json`. The DM-6.1 tag is the attribute comment (`"pii:contact"`).
  Cardinality: parent `||` when every FK column is NOT NULL, else `|o`; child `o|` when the FK columns are the
  child's PK or a unique key (one-to-one), else `o{`. A NOT VALID FK is drawn dashed (`..`).
- **No volatile content in the pages** (no row counts, sizes, timestamps of the dump): the pages change only
  when the structure does. `last_reviewed` is the date of the newest migration of the schema's owner, so it moves
  only with a migration of that owner.
- **`erd.json`** (format 1): schemas, owner app + owner role, tables (kind, columns with full type, NOT NULL, PK,
  FK, UK, DM-6.1 tag), PK, unique keys, FKs, and a flat sorted edge list; `fingerprint` = sha256 of the model
  without `generated_at`/`source`, for the admin "changed since the previous dump". No row data, no free-text
  comments, no grants/roles.

## Changed

- `db/gen_erd.py` (new), `db/tests/test_gen_erd.py` (new, 20 tests on a small fixture dump: index parsing, Mermaid
  words, keys and tags, no row data / comment text in `erd.json`, deterministic and volatile-free pages, an added
  FK changes exactly `booking.md` + `README.md` with the new relationship line, a dropped cross-schema FK changes
  the child page, the parent's incoming list and the index; front matter and the markdownlint rules a generator
  can break).
- `.github/workflows/db-schema-dump.yml`: render the ERD next to the reference, keep `erd/` + `erd.json` in the
  run artifact, optional S3 upload (repo variable `ERD_S3_UPLOAD`, default off), and the root PR now also carries
  `docs/architecture/erd/*.md`. Publish condition: reference fingerprint moved **or** an ERD page differs from
  master (`git status --porcelain --untracked-files=all`) **or** `publish=true`. The first run after merge opens
  a root PR (no ERD on master yet). The PR body lists the changed ERD pages.
- `db/gen_schema_reference.py`: one `**ERD:**` line linking `erd/README.md` (text only; the fingerprint is
  unchanged, so it reaches master with the first ERD PR, which carries the target of the link).
- `.github/workflows/migration-copy-guard.yml`: `db/gen_erd.py` in the path filter (its tests run on the PR).
- `db/README.md`, `CONTEXT.md`, `README.md`: one paragraph / line each.

## Tradeoffs

- **Separate publish trigger for the ERD** instead of folding the ERD into the reference fingerprint: the reference
  fingerprint already covers every input of the ERD (columns, types, NOT NULL, indexes, FKs, tags), so a
  structural change moves both. The extra "page differs from master" check only matters when the generator itself
  changes (this PR, or a later layout change), and it costs one `git status`.
- **Key columns only for big schemas** loses the non-key columns from the picture (`shared`, `booking`, `geo`,
  `acp_shared` today). A full-column diagram of `shared` (42 tables, 567 columns) does not render readably on
  GitHub; the reference has the full list and the scope-2 admin view will show columns on click.
- **`last_reviewed` = date of the owner's newest migration**, not the dump date: a dump date would change every page
  every night and open a PR nightly. Cost: a CIS migration touches the date line of the 8 CIS pages and the index.
- **`erd.json` is not committed to the root repo**: it carries `generated_at` (needed by the admin view) and would
  change every night. Scope 3 (drift check) can read it from the artifact/S3, or commit a stripped copy if needed.
- **Mermaid validated offline** with `mermaid@11.4.1` `mermaid.parse()` (jsdom) on all 11 pages of the 21/10 live
  dump and the fixture pages, not in CI: adding Node + mermaid to the dump job costs minutes for a check the unit
  tests approximate with line regexes. `numeric(10,2)` and multi-word types fail the parser, hence the type map.

## Should know

- Verified locally on the live dump of 21/10 (`db-schema-dump/latest.json`, catalog only): 11 schema pages +
  index, 186 FK edges; `markdownlint-cli2` 0.23.2 with the root `.markdownlint-cli2.jsonc`: 0 issues; root
  `frontmatter.schema.json`: 0 errors, IDs unique; Mermaid parse OK for every page.
- Cross-owner FKs on Dev today: 10, all `tripplanner.*` -> `shared.destinations` (listed on the index page).
- **Root docs/README.md catalog row APP-04** still says "ERD: AA-894": update it in the root PR that merges the
  first bot PR (or right after). The bot PR's Docs lint must be green before merge (root rule).
- **S3 / IAM for scope 2 (not in this PR):**
  - Writer: the dump job's CI role (`aa-cis-infra-tf-apply`) has `AmazonS3FullAccess`, so the optional upload needs
    no change. Turn it on with the repo variable `ERD_S3_UPLOAD=true`.
  - Reader: the CIS ECS task role's inline policy (`modules/ecs/main.tf` `ecs_task_policy`) allows `s3:GetObject`
    on `*`, so CIS can already read `db-schema-dump/erd/latest.json`. That same `*` also lets CIS read the full
    dumps (`db-schema-dump/<run>/schema.json`, `db-schema-dump/latest.json`: roles, grants, policies). The scope-2
    IAM PR (risky, needs review) should add an explicit `s3:GetObject` on exactly
    `<bronze>/db-schema-dump/erd/latest.json` and `previous.json`, and deny the task role the rest of
    `db-schema-dump/*` (or narrow the `*`).
  - The migrator task role may put `db-schema-dump/*` (`accounts/aa365/db_migrator.tf`), so a dump task could
    overwrite `erd/latest.json`; narrow it to `db-schema-dump/*/schema.json` in the same PR, or move the ERD key to
    its own prefix.
  - Cost: one ~650 KB object (+ one previous copy) and two PUTs a night when enabled: well under $0.01/month.

# AA-894 scope 3: design ERD drift check (+ review note 1 on the generator)

Branch `feat/erd-design-drift-check`, S247. The design page itself (`docs/architecture/erd/design/crm.md`) and the
PRD (scope 4) are in the root branch `docs/erd-design-prd-as-code`.

## Decisions

- **The checker lives here** (`db/check_erd_drift.py`), next to `gen_erd.py`: `erd.json` exists only inside the
  DB Schema Dump run (artifact, optional S3), and that run already checks out the root repo with
  `ROOT_REPO_DOCS_TOKEN`. No new secret, no new trigger.
- **What is compared:** table set (base tables and views, partitions excluded on both sides), primary keys where
  the design gives one, and FK edges as `(child, sorted FK columns, parent)` for tables present on both sides
  (a missing table is reported once, not again with every edge). Columns, types and unique keys are not compared:
  the design page shows keys only, and the generated page + reference already show every column.
- **Edge identity = FK columns, not the constraint name.** The design writes the child's FK column list as the
  relationship label; constraint names are chosen in the migration and would make every design edge a mismatch.
- **Implied tenant FK** through the marker (`implied-fk=tenant_id:tenant`): about 80 `tenant_id` lines would hide
  the diagram. A box whose `tenant_id` is marked `FK` without a drawn edge gets the implied edge.
- **Marker in an HTML comment**, not front matter: the shared front-matter schema (`additionalProperties: false`,
  copied in four repos) stays untouched for this, and the marker sits next to the diagrams it describes.
- **Fail policy:** exit 1 only when the schema is live (has relations in the dump) **and** the page says
  `enforce=true`, for drift or for a design-page problem (line that does not parse, a bare name without a box,
  an FK attribute without an edge, a label column that is not an FK attribute, file name != schema). Otherwise a
  report (`::notice` not live, `::warning` drift). `crm` is `enforce=false` until the first `crm-NNN` tables
  (AA-933 `crm-001` onwards) are applied; flipping it is a one-line root PR once the first dump is in sync.
- **Workflow step after the root PR step** (`if: always()` + root checkout and render succeeded): an enforced
  drift turns the run red but never holds back the regenerated reference PR.
- **Review note 1 (gen_erd):** Mermaid 11.4.1's ER lexer (`erDiagram.jison`, extracted from the npm tarball) reads
  `one`, `many`, `to`, `u`, `erDiagram` as keywords before names (case-insensitive; the multi-word cardinalities
  start with `one`/`zero`/`only`/`optionally`; later versions add `direction`, `style`, `classDef`, `class`,
  `title`, `accTitle`, `accDescr`). Such table names are now quoted. Inside an attribute block `\b(PK|FK|UK)\b`
  wins over a name, so a column `pk`/`fk`/`uk` (or `pk-...`) is written `pk_`; `check_erd_drift.py` maps `pk_`
  back. `erd.json` keeps the real names. No current page changes (no such names live).

## Changed

- `db/check_erd_drift.py` (new), `db/tests/test_check_erd_drift.py` (new, 15 tests: marker, keys, implied and
  cross-schema edges, design-page problems; a matching state in sync; a seeded mismatch (dropped FK, stray table,
  changed PK) reported, failing only when enforced; not-live passes when enforced; CLI exit codes and summary).
  The live side of the tests is built with `gen_erd.build_model`, so the two scripts cannot drift apart.
- `db/gen_erd.py`: `ENTITY_KEYWORDS`, `ATTRIBUTE_KEY_RE`; `entity()`, `mermaid_name()`, `mermaid_type()`.
  `db/tests/test_gen_erd.py`: 2 tests (names, and a rendered page with a table `many` and a column `pk`).
- `.github/workflows/db-schema-dump.yml`: id `root` on the root checkout, step "Design ERD drift (report)",
  header item 4. `.github/workflows/migration-copy-guard.yml`: path filter `db/check_erd_drift.py`.
- `db/README.md`, `CONTEXT.md`, `README.md`: one paragraph / line each.

## Tradeoffs

- A Mermaid-subset parser (regexes for the lines `gen_erd.py` and the design page use) instead of a real Mermaid
  parser in CI: no Node in the dump job. Anything outside the subset is a design-page problem, so it cannot pass
  silently. The real grammar was checked offline (Mermaid 11.4.1 `erDiagram.jison` run under Node on all 13
  diagrams of `design/crm.md`, the 11 generated pages and keyword fixtures).
- Unique keys and NOT NULL are not compared (the design shows only single-column `UK` and uses `|o` loosely);
  adding them later is a compare() change plus a test.

## Should know

- Done-when "drift check runs in CI (green on a matching state, red on a seeded mismatch)": the unit tests run in
  the Migration Copy Guard on this PR and in every DB Schema Dump run; the first dump after merge shows
  "`crm`: not live yet" in its summary.
- When `crm-001` (AA-933) applies the first `crm` tables, the dump reports drift for every table not yet migrated (expected,
  `enforce=false`). Set `enforce=true` once the migrated set matches the design for the waves done, or split the
  page per wave; decide in AA-933.

# AA-894 scope 2 (Infra half): S3 key + CIS read grant for the admin data-model view

Branch `feat/erd-cis-read-grant`. The CIS half (route + page) is AA-CIS-App `feat/admin-data-model-erd`.

## Decisions

- **Own prefix `data-model/erd/` in the bronze bucket** (no new bucket; bronze is private, AES256, TLS-only, and
  has no lifecycle rule on this prefix). Part 1 wrote `db-schema-dump/erd/`, but the part-1 notes above list two
  problems with that prefix: the migrator task role may put `db-schema-dump/*`, and denying CIS the full dumps
  under `db-schema-dump/*` would also deny the ERD. A sibling prefix solves both without touching the migrator
  role. The upload was off by default in part 1, so no reader depended on the old key.
- **`ReadErdModel`** (Allow `s3:GetObject` on exactly `data-model/erd/latest.json` and `previous.json`) on the CIS
  task role (`modules/ecs` `ecs_task_policy`, api + worker share it). Redundant today (the role's
  `s3:GetObject` on `*`), written so the view keeps working when that `*` is narrowed.
- **`DenySchemaDumpPrefix`** (Deny `s3:GetObject`/`s3:PutObject` on `db-schema-dump/*`): the full catalog dumps
  (roles, grants, policies, functions) are not for the CIS runtime. No CIS code names the prefix (grep of
  `api/ services/ shared/ worker/ scripts/` on 22/10/2026). The dump task runs with the migrator task role and the
  workflow's copies with the CI role, neither touched.
- **`DenyErdModelWrite`** (Deny `s3:PutObject`/`s3:DeleteObject` on `data-model/*`): CIS only reads the model.
- **Upload on by default**: `ERD_S3_UPLOAD` now means "off only when 'false'". Part 1 kept it off until a reader
  and its grant existed; this PR adds both, so no repo variable has to be set by hand.
- **previous.json semantics unchanged**: replaced only when the model fingerprint moves, so "changed since the
  previous dump" shows the last structural change until the next one (a nightly run with no change keeps the pair).

## Changed

- `modules/ecs/main.tf`: three statements appended to `ecs_task_policy` (above).
- `.github/workflows/db-schema-dump.yml`: `ERD_S3_PREFIX` `db-schema-dump/erd` -> `data-model/erd`, upload default on,
  header + step comments.
- `CONTEXT.md`: the DB Schema Dump paragraph names the S3 key, the reader and the grant.

## Tradeoffs

- **Deny on `db-schema-dump/*` instead of narrowing the role's `s3:*` on `*`**: narrowing the broad grant touches
  every S3 path CIS uses (uploads, photos, archive, batch, scripts) and needs its own audit; a targeted Deny closes
  the one sensitive prefix now with no risk to those paths.
- **Bucket name from `var.bronze_bucket_name`** in the ARNs (the module already receives it for the BRONZE_BUCKET
  env), not `module.s3` output wiring: the module has no bucket ARN variable and adding one is churn.

## Should know

- **Risky (IAM)**: plan shows one in-place update of `module.ecs.aws_iam_role_policy.ecs_task_policy`, nothing else.
  `terraform fmt -check` and `terraform validate` pass (local, `-backend=false`); plan/apply are the orchestrator's.
- IAM eventual consistency: the Deny can take ~5 to 8 minutes to settle (lesson S243); verify N/N after that.
- Old object: if the part-1 upload was ever switched on, `s3://<bronze>/db-schema-dump/erd/latest.json` (and
  `previous.json`) are orphans; delete them after the first run on the new prefix.
- Cost: unchanged from part 1 (two small objects, a few PUT/GET a night plus one GET per admin view per 5 min).

# AA-894 scope 5: env-config register (names only)

Branch `feat/aa894-env-config-register`, S247. Linear AA-894 scope 5 / Done-when 5: env var names (secrets by name,
no values) of the live ECS task definitions, Lambda configurations and Vercel projects, rendered to the root
`docs/generated/env-config.md` (catalog row APP-03) through the Infra docs pattern.

## Decisions

- **Same pipeline as the four Terraform pages** (`docs-gen.yml`, AA-893): same read-only plan role
  (`aa-cis-infra-tf-plan`, `ReadOnlyAccess` covers `ecs:Describe*`, `lambda:ListFunctions`,
  `secretsmanager:ListSecrets`), same `ROOT_REPO_DOCS_TOKEN`, same bot branch `bot/generated-infra-docs` and root PR.
  No second workflow, no new IAM, no Terraform change.
- **Sibling generator `tools/docs/gen_env_config.py`**, not more code in `gen_docs.py` (that one renders from a
  Terraform JSON only). It reuses `gen_docs` for the table helpers, `page()` (new optional `blurb`, default
  unchanged, so the four existing pages render byte for byte the same) and `changed` (new `EXTRA_PAGES`).
- **Live reads, not Terraform state:** CIS and Booking deploys register new task-definition revisions outside
  Terraform, so the state lags. ECS: every service of `aa-cis-dev-cluster` (`list_services`), the task definition
  of the PRIMARY deployment. Lambda: every function (`ListFunctions` already carries `Environment`). Discovery
  instead of a fixed list, so a new service or function (today `aa-crm-dev-spike`) appears without a code change;
  `render` still fails closed when one of the Done-when runtimes (3 ECS services, 2 TP Lambdas, 4 Vercel
  projects) is missing.
- **Values dropped at extraction**: `extract_task_def` / `extract_lambda` / `extract_vercel_api` /
  `parse_vercel_cli` return names, sources, secret NAMES, Vercel kind and targets only; the names-only JSON model
  is all `render` sees. Secret name = `ListSecrets` ARN -> Name map (metadata), fallback: strip the 6-character
  ARN suffix; JSON key (`:login::`) shown as "JSON key"; SSM parameters by name. No account, region or ARN on the
  page.
- **Vercel source:** no Vercel token exists in AA-CIS-Infra CI. The workflow uses the API when a repo secret
  `VERCEL_TOKEN` is added (optional repo variable `VERCEL_TEAM_ID`), else the checked-in names-only snapshot
  `tools/docs/env_config_vercel.json` (captured 22/10/2026 with the local CLI: `vercel-snapshot --cli`, which
  parses `vercel env ls` and keeps only the name, type and environments columns; the value column is dropped on
  read and an unknown type label raises without echoing the line). The page says which source it used and the
  capture date.
- **Vercel kind**: `sensitive` (write-only) vs `readable` (encrypted/plain: a member can read it). CLI 60 labels
  `Secret` / `Config`.
- **Notes column** reuses the AA-878 secret-shaped-name rule (copied, since `register_check.py` needs PyYAML):
  flags `SENTRY_AUTH_TOKEN`, `ADMIN2_PASSWORD` (aa-cis-frontend) and `TRIPPLANNER_API_KEY` (aa-tripplanner,
  development/preview) as readable today; `_ARN` names are labelled "an ARN (read at run time)".
- **No volatile content in the body** (no revision, image tag or capture time outside the Vercel source line), so
  the page changes only when a name/source/target changes; the catalog's "nightly + after deploy" is met by the
  nightly run (no cross-repo dispatch from app deploys).
- **Region default fixed to us-west-1**, not `AWS_REGION`: the local shell had `AWS_REGION=ap-southeast-1` and
  the first local run hit ClusterNotFound.

## Changed

- `tools/docs/gen_env_config.py` (new), `tools/docs/tests/test_gen_env_config.py` (new, 17 tests: planted
  `SUPERSECRETVALUE` + fake account in task defs, Lambda env, Vercel API and CLI output never reach the model or
  the page; ARN suffix / JSON key / SSM; ListSecrets denied fallback; primary-deployment revision; sections per
  app; fingerprint stable across date/sha; fail closed on a missing required runtime; checked-in snapshot is
  names-only), `tools/docs/env_config_vercel.json` (new, 33 names of 4 projects).
- `tools/docs/gen_docs.py`: `EXTRA_PAGES`, `page(..., blurb=None)`, `changed_pages(..., names=PAGES)`.
- `.github/workflows/docs-gen.yml`: boto3 install (before credentials), step "Env config register (names only)"
  (`continue-on-error`, fails the run at the end), commit/PR text `Refs AA-893, AA-894`, PR title + body.
- `CONTEXT.md`: tools/docs line and the Docs Gen paragraph.

## Tradeoffs

- **One workflow** instead of a separate env-config workflow: same role, token, bot branch and PR, no second
  nightly job; a collection failure is isolated (`continue-on-error` + final failing step).
- **boto3 instead of the AWS CLI in bash:** the CLI would have to write raw task definitions (with plain values)
  to disk before parsing; boto3 keeps them in memory and only the names-only model is written. Cost: a pinned
  `pip install boto3` (~5 s) per run.
- **Snapshot for Vercel** until a token exists: the Vercel part is only as fresh as the last
  `vercel-snapshot --cli` + PR. Adding `VERCEL_TOKEN` to Infra is a new secret (register row, AA-878) and a
  decision for Nghiệp.
