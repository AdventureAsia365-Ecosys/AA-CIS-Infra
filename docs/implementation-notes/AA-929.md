## Decisions

- **The class list has one home in Infra:** `gen_schema_reference.TAG_CLASSES`. `check_migration_files.py` imports
  it (both run on the GitHub runner with the standard library). `run_migration.py` is not touched: it ships alone
  to the DB Migrate task (presigned URL), so it cannot import the reference module, and a second copy of the list
  would need its own mirror test. The PR check is enough for "fails lint".
- **What fails, what warns.** Unknown class in any `pii:`/`conf:` tag of a `COMMENT ON COLUMN … IS '…'` → error.
  A comment that names a tag but does not start with one → warning (the schema reference already lists it as a
  finding; making it an error would be a new rule the standard does not state).
- **The lint runs on every copy**, old ones included. Checked: all 74 copies today use only known classes
  (`test_real_copies_carry_known_classes_only`), so nothing old turns red.
- **`crm` joins `PII_CANDIDATE_SCHEMAS`** now, so the partner CRM's untagged `email_enc` / `phone_bidx`-style columns
  appear in the reference's "Untagged candidates" from its first migration. No `crm` schema exists yet, so the
  fingerprint does not move (no spurious root PR); only the rendered sentence "in booking, crm, tripplanner"
  changes, and only on the next structural change.
- **Retention-row check scope:** only migration dirs in `check_retention_rows.RETENTION_OWNERS` (today `crm`). The
  cis/booking/tripplanner tables are grandfathered by DM-7.1 ("an existing table without a row keeps all its rows
  until its owner proposes a window"); scanning them would fail on day one for reasons this issue does not own.
- **Registry = the root file, not a copy.** DM-7.1 says Part B §7 *is* the registry (DM-1.2), so the check reads
  `docs/architecture/data-standards/02-data-management.md` from the root repo's `master`. A YAML twin in Infra
  would be a second registry that can drift.
- **What counts as a row:** a backticked `schema.table` in the first column of any table row under
  `## 7. Retention and archival`. A name cited in a rule's text (DM-7.1 row) or in another section does not count.
- **SQL read:** `CREATE [UNLOGGED] TABLE [IF NOT EXISTS]` (unqualified → the dir's schema), skipping `TEMP` and
  `PARTITION OF` children (covered by the parent's row); `DROP TABLE` and `ALTER TABLE … RENAME TO` in file
  order, so a dropped table needs no row and a renamed one needs its new name. Built on
  `run_migration.split_statements`, so comments, strings and dollar bodies cannot fake a CREATE.

## Tradeoffs

- **A secret in a PR workflow.** The retention-rows job reads one root file with `ROOT_REPO_DOCS_TOKEN` (the PAT
  DB Schema Dump and Docs Gen already use; Contents read/write on the root repo). It is passed only to the one
  `gh api` step, only when a `crm` copy exists, and the job has `contents: read` on this repo. Same exposure class
  as the other repo secrets on `pull_request` from same-repo branches (no forks on a private repo). Alternative
  without a secret: a YAML twin of the registry in Infra (rejected above). When U-25 replaces the PAT with a GitHub
  App token, give this job a read-only installation token.
- **Root master, not the root PR branch.** The check reads the merged registry, so the order is: root PR with the
  row merged → Infra copy PR. That matches D8 (the migration PR in the owner repo merges first anyway). A root PR
  still open gives a clear "add the row … merge it, then re-run".
- **Regex parsing, not a SQL parser.** Dynamic SQL (`EXECUTE 'CREATE TABLE …'`, `EXECUTE format('COMMENT …')`) is
  out of reach for both checks. Backstops: the schema reference's tag findings (live catalog) and review.
