# AA-908 — traveller sign-up on the EXTERNAL pool: WAF, callback hosts, e2e travellers (Infra slice S1)

ADR 0006 Phase 4. This slice turns on the shared Cognito web ACL. It also registers the second
TripPlanner host and adds two synthetic traveller mailboxes. Native email sign-up on the traveller
clients stays off (review round 1, see Decisions). The migration copies (tp-019, bk-024) ship as separate copy PRs after the owner PRs merge.

## Decisions

- `terraform.tfvars`: `identity_waf_enabled = true` only. `identity_external_native_signup_enabled`
  stays `false` (review round 1). The spike (Should know) found that managed-login `/signup` asks for a
  password. ADR 0006 decision 1 and 4 say travellers are not offered passwords (EXTERNAL allows
  EMAIL_OTP only), and the "PASSWORD stays in allowed_first_auth_factors" note in `identity.tf` holds only
  because nobody but break-glass has a usable password. Opening sign-up now would change an ADR decision
  quietly, before S4/S5 choose between (a) and (b). The flag flips in the S4/S5 PR, after Nghiep's choice
  (and, for (a), an ADR 0006 amendment in the root repo). The WAF goes first anyway, which is the order
  the EXTERNAL pool precondition asks for.
- **Managed-login form posts are rate limited too (new rule `ManagedLoginPostRatePerIp`).** The coded ACL
  only matched the public API (`x-amz-target` = SignUp / InitiateAuth / ResendConfirmationCode).
  Managed login v2 is a server-rendered app on the pool domain. Its forms post to `/login`,
  `/login/continue`, `/verifyCode`, `/signup`, `/signup/confirm/resend-code`, `/forgotPassword` and other
  paths, and never send `x-amz-target` (route list read from the managed-login manifest on
  auth.lumiguides.it.com, 24/10/2026). Without the new rule, the browser sign-up path that travellers
  use (and that sends SES mail) would sit under the 1000/5 min global cap only. That would not meet the
  Done-when "WAF is on for the sign-up path".
  - Scope: any `POST` whose path does not start with `/oauth2/`. `/oauth2/token` and `/oauth2/revoke` are
    called server-side by the app BFFs from shared Vercel egress addresses, need a code, a refresh token
    or a client secret, and send no mail, so they stay under the global cap only.
  - It is a rule of its own because the AWS provider rejects a `not_statement` inside an `and_statement`
    inside the existing `or_statement` scope-down (`terraform validate`: "Blocks of type
    not_statement are not expected here"). It shares `identity_waf_signup_rate_limit` (100 / 5 min / IP).
- **No CI allow-list. Instead, the limits are kept and an alarm is added (`identity_waf_blocked`).** SCHEDULE §5
  asked for an allow-list or higher limits so that GitHub-runner sign-ins are not throttled. The numbers:
  - Every CI sign-in (CIS `e2e-cognito.yml`, CIS `ui-smoke.yml` smoke-staff, Partner `e2e-dev.yml`) is a
    browser sign-in through managed login. None calls the public API.
  - Each sign-in makes about 3-4 scoped posts and fewer than 10 requests on the pool domain. The page
    assets come from Cognito's CloudFront hosts (`*.cloudfront.net`), which the web ACL never sees.
  - A run makes 1-2 sign-ins. One run at a time per concurrency group (`e2e-cognito`, `e2e-dev`). Each
    GitHub-hosted job has its own runner address.
  - So CI uses under 10 % of each limit.
  - An IP allow-list cannot target GitHub-hosted runners, which have no fixed addresses. A shared-secret
    bypass header would add a secret that skips the abuse limits, plus app changes in two other repos.
  - The alarm (`aa-identity-dev-waf-blocked`, `BlockedRequests`, Rule=ALL, >= 1 in 5 min, ALARM and OK
    mail) makes the first block visible. The fix is then one tfvars line.
  - The M2M pool (server-to-server client credentials over the shared NAT) is not associated with the
    ACL, so ECS/Lambda M2M token calls are unaffected.
- **Callback hosts:** the `tripplanner` client also allows `https://aa-tripplanner.vercel.app/auth/callback`
  and `https://aa-tripplanner.vercel.app/` (logout). Both hosts are production domains of the Vercel
  project. Both answered 200 with the same page title on 24/10/2026. The guest cookie
  `__Host-tp_guest` is host-only, so the callback must return to the host where sign-in started.
- **e2e mailbox:** three travellers, `e2e-test-traveller@`, `-2@` and `-3@e2e-mail.lumiguides.it.com` (`-3` added S252 for the fresh sign-up check).
  The plan's live check 7 needs a second account, which must see an empty list and get a 404. They are
  added to the existing receipt rule (the region's only active rule set). The AA-945 rule comes after this
  one (SCHEDULE §2).

## Tradeoffs

- **Cost:** a third rule costs $1/month more, so the ACL is about $8/month instead of the plan's $7, plus
  $0.60 per million requests and one CloudWatch alarm (about $0.10/month). Folding the post scope into the
  existing rule would save the $1, but the provider cannot express it.
- **One limit for both scoped rules:** each rule keeps its own per-IP counter, so a client can make 100 API
  calls and 100 form posts in the same 5 minutes. A legitimate person needs fewer than 10 of either.
- **Excluding `/oauth2/` from the post rule:** a credential-stuffing script against `/oauth2/token` would hit
  only the global cap. That endpoint takes no password: the grants are a code (PKCE), a refresh token or
  a client secret. Throttling it per IP would instead hit every user behind one Vercel egress address.

## S4/S5 Infra: traveller sign-up on, through the TripPlanner BFF (option b)

### Decisions

- **Option (b), passwordless through the BFF** (S250; ADR 0006 decisions 1 and 4 unchanged, so no ADR
  amendment). The TripPlanner BFF calls the Cognito public API from Vercel: `SignUp` with no password,
  `ConfirmSignUp`, `InitiateAuth` `USER_AUTH` with `PREFERRED_CHALLENGE=EMAIL_OTP`, `RespondToAuthChallenge`,
  `GetTokensFromRefreshToken` (rotation is on) and `RevokeToken`.
- **`identity_external_native_signup_enabled = true`** (tfvars). `SignUp` from the BFF is a native sign-up
  (`PreSignUp_SignUp`), which the EXTERNAL trigger refuses while `NATIVE_SIGNUP_ENABLED=false`. The trigger
  still allows it only on the traveller clients and still refuses a sign-up that sets `email_verified`.
- **WAF re-keying for the BFF (the S1 review warning).** Counted per egress IP, every traveller behind one
  Vercel address would share one counter of 100 per 5 minutes, and one script could lock all of them out.
  - The BFF sends `x-aa-traveller-bff: <secret>` and `X-AA-Traveller-IP: <the traveller's address>` (from
    Vercel's `x-forwarded-for`, set by Vercel's edge).
  - `SignUpAndCodeRatePerIp` and `ManagedLoginPostRatePerIp` now skip a request that carries the exact value.
  - New rule `BffRatePerTravellerIp` (priority 2): rate-based, `FORWARDED_IP` on `X-AA-Traveller-IP`, same
    limit (`identity_waf_signup_rate_limit`), scope-down = the exact header value. `GlobalRatePerIp` moves to
    priority 3 and still counts everything per IP.
  - The value is `random_password.identity_traveller_bff` (48 alphanumerics) in the Secrets Manager secret
    `tripplanner/<env>/cognito-bff-key`, the pattern of the TripPlanner edge key. The orchestrator pipes it
    into Vercel `TP_COGNITO_BFF_KEY`.
  - Why not a forwarded-IP key without a secret: anyone calling Cognito directly could then forge a new
    address per request and leave the per-person limit. Without the value, a caller stays on the per-IP rules.

### Changed

- `accounts/aa365/terraform.tfvars`: `identity_external_native_signup_enabled = true`, comments.
- `accounts/aa365/identity.tf`: locals `id_traveller_bff_header` / `id_traveller_ip_header`; the two
  scoped rules get a NOT on the BFF header; new rule `BffRatePerTravellerIp`; `GlobalRatePerIp` priority 3;
  `random_password` + secret + version `identity_traveller_bff`; the header comment (replaces the S1
  warning).
- `accounts/aa365/cicd_split.tf`: the new secret's ARN in `local.tf_plan_secret_arns`.
- `accounts/aa365/identity_variables.tf`: WAF cost ($9/month) and what the scoped limit counts.
- `CONTEXT.md`: the identity row.

### Tradeoffs

- **A secret that changes how the limits count.** The S1 notes rejected a bypass header for CI. This one
  is not a bypass: the BFF's calls are still limited, per traveller instead of per egress IP. If the value
  leaked, its holder could forge traveller addresses, but stays under the 1000 / 5 min global cap per real
  IP. Rotation is one `-replace` and one Vercel env update.
- **Global cap per egress IP stays.** All BFF traffic of one Vercel address shares 1000 / 5 min. A sign-in
  is about 3 calls and a session refresh about 1 per hour, so this is far from the limit at TripPlanner's
  size. Splitting it per traveller too would cost another rule ($1/month); the alarm shows when it bites.
- **Cost:** +$1/month (fourth rule) and +$0.40/month (secret). About $9.50/month in total.

### Review round (S250, independent reviewer)

- **Blocker fixed: pre-registration takeover.** With native sign-up on and nothing else, anyone could call the
  public `SignUp` API with `ClientId=tripplanner`, the victim's address and a `Password`. The user waits
  UNCONFIRMED. When the victim later enters the address on TripPlanner, the BFF's `start()` gets
  `UsernameExistsException`, then `UserNotConfirmedException`, and calls `ResendConfirmationCode`. The victim types
  the code, so `ConfirmSignUp` confirms the attacker's account, password included. The attacker then signs in with
  `USER_AUTH` + `PASSWORD` (offered to any user who has a password, `identity.tf` header) and holds the victim's
  `sub` with `email_verified=true`: My Trips, every trip, and hand-offs as the victim's verified customer.
  - **Fix: only the BFF may create a traveller.** The BFF signs each `SignUp` in `ValidationData`:
    `bff_ts` (unix seconds) and `bff_proof` = hex HMAC-SHA256(key, `"<normalised email>\n<bff_ts>"`).
    `external.pre_sign_up` checks it for every `PreSignUp_SignUp` on a traveller client: missing, malformed, more
    than 5 minutes off, for another email, or under another key = denied (constant-time compare). The BFF never
    sends a password, so every self-registered traveller is passwordless. The managed-login `/signup` page sends
    no proof, so it is closed too.
  - **Key:** a separate `random_password.identity_traveller_signup_proof` (48 alphanumerics) in
    `tripplanner/<env>/cognito-signup-proof-key`, not the WAF header value (that one is in the web ACL definition
    and in sampled requests). The trigger reads it by ARN (env `SIGNUP_PROOF_SECRET_ID`) and caches it for
    5 minutes per container. Its role gets `secretsmanager:GetSecretValue` on that one ARN
    (`identity_external_signup_proof_key`). The ARN joins `local.tf_plan_secret_arns`. All of it exists only while
    native sign-up is on (`local.id_ext_native_signup`).
  - **Atomic go-live:** the trigger code and `NATIVE_SIGNUP_ENABLED=true` ship in the same published Lambda
    version behind the `live` alias, so there is no window with sign-up on and the proof check off.
  - **No pre-existing hostile account:** native sign-up was refused until now. Read-only check on 25/10/2026:
    `list-users --filter 'cognito:user_status = "UNCONFIRMED"'` on `aa-external-dev` returns 0 (6 users in all).
    Repeat it right before the apply.
  - **Booking customers:** the proof is required on the `booking-customer` client too. Nothing signs up there
    today. A future Booking BFF needs the same key (or the trigger a per-client key map).
  - **Defence in depth on the BFF (`ResendConfirmationCode` only for accounts the BFF created):** the public API
    cannot tell the BFF who created an UNCONFIRMED user. The trigger is what guarantees it: with the proof, every
    UNCONFIRMED traveller was created by the BFF, without a password.
- **WAF headers (should-fix):** the BFF now sends `x-aa-traveller-bff` only together with `X-AA-Traveller-IP`.
  Without a traveller address, its call stays on the per-egress-IP rules instead of escaping every per-person
  limit. The `identity.tf` comment says so.
- **Global cap (nit), kept as is.** All BFF traffic from one Vercel egress address shares the 1000 / 5 min
  `GlobalRatePerIp` counter. Calls spread over 10+ client addresses (each under 100) could fill it and block
  sign-in and refresh for travellers behind that address until the window rolls. Not excluded from the global
  rule on purpose: it is the backstop if the BFF header value leaks (its holder could forge traveller addresses).
  Residual risk accepted on Dev. The follow-up, if it bites (the `waf-blocked` alarm shows it), is a Vercel
  Firewall rate-limit rule on `/api/auth/start` and `/api/auth/verify` (per client IP, no code change).
- **Tests:** `lambda_src/identity_triggers_tests/test_external.py`: no proof, malformed (6 shapes), wrong key,
  other email, stale and future timestamp, missing config, short key, Secrets Manager error = denied; a valid
  proof on both traveller clients = allowed; the key is cached and re-read after its TTL; federated and
  AdminCreateUser sign-ups need no proof; a fixed HMAC vector shared with the TripPlanner BFF test.
- **Extra apply steps:** the plan now also shows `+ random_password.identity_traveller_signup_proof[0]`, its
  secret and version, and `+ aws_iam_role_policy.identity_external_signup_proof_key[0]`; the Lambda env gains
  `SIGNUP_PROOF_SECRET_ID`. After apply, pipe the key into Vercel (never printed), from the TripPlanner
  `frontend/`:
  `aws secretsmanager get-secret-value --secret-id tripplanner/dev/cognito-signup-proof-key --query SecretString --output text --profile aa365-admin --region us-west-1 | tr -d '\n' | vercel env add TP_COGNITO_SIGNUP_PROOF_KEY production`
  (and again for `preview`).
- **Cost:** one more secret, +$0.40/month (about $9.90/month for the identity WAF and its two secrets).
