# AA-860 — X1 S19: Deny the CIS task role the master and other-app secrets

Branch `feat/x1-s19-task-role-deny`. **Staged: merge and apply LAST in the session** (after S18 is verified
and after every lane's ECS-exec script that reads `aa-cis/dev/rds` has run: AA-816 S0 readiness, AA-878

## Decisions
- `modules/ecs/main.tf` `aws_iam_role_policy.ecs_task_policy` (the api + worker task role
  `aa-cis-dev-ecs-task-role`) gets a statement `Sid = DenyMasterAndOtherAppSecrets`, `Effect = Deny`,
  `secretsmanager:GetSecretValue` on:
  - `…:secret:${project}/${environment}/rds-??????` — exactly 6 characters after `rds-`, i.e. the master
    `aa-cis/dev/rds-7K4JX3`; `rds-app-user-…` and `rds-cis-app-…` have more and stay readable;
  - `…:secret:${project}/${environment}/db-migrator-??????`;
  - `…:secret:booking/*`, `…:secret:tripplanner/*`.
  The broad `GetSecretValue` on `*` above it is unchanged (narrowing it is AA-878 D4's follow-up); an explicit
  Deny wins over it.
- Checked against the real secret ARNs (list-secrets metadata, no value read) with IAM wildcard semantics:
  denied `aa-cis/dev/rds-7K4JX3`, `aa-cis/dev/db-migrator-77RviC`, `booking/dev/database-url-…`,
  `tripplanner/dev/{database-url, api-key, mapbox-geocoding-token}-…`; allowed `aa-cis/dev/rds-app-user-…`,
  `aa-cis/dev/rds-cis-app-…`, `aa-cis/dev/gdrive-photo-reader-…`, `aa-cis/dev/booking-jwt-signing-key-…`.
  (The IAM policy simulator is not callable from a builder session; the main session may run it.)
- What the CIS code reads (grep of api/, services/, shared/ on 19/10/2026, plus the open AA-884 / AA-885
  worktrees): `aa-cis/dev/{rds-app-user, booking-jwt-signing-key, e2e-tenant/*, gdrive-photo-reader,
  geoapify, jwt-secret, sentry-dsn-api, typesafe}`, the DataForSEO ARN, `acp/{cms,social}/*`. None denied.
  The only code naming the master is `services/acp_produce/sweeper_lambda.py`, a Lambda handler that is not
  deployed (list-functions) and not imported by the api or worker.

## Changed (vs the lane plan)
- Pattern prefixes use `${var.project}/${var.environment}` (the module's variables) instead of a literal
  `aa-cis/dev`, so a future environment gets the same Deny.

## Tradeoffs
- `DATABASE_URL` is injected by the execution role, which this Deny does not touch; after S18 that is the
  cis_app DSN. Before S18 it is still the master DSN in the container's environment: S19 closes the
  "read any secret" path, not the env var. So S19 after S18 (plan order).
- Any S3-mediated ECS-exec script that fetches `aa-cis/dev/rds` stops working; master-level work goes
  through DB Migrate `mode=run-script` (`db/scripts/README.md`). Root branch `docs/x1-s19-ecs-exec` updates the
  `aa-cis-schema` skill accordingly.
