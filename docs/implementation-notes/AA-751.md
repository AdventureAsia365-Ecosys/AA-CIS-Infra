# AA-751 — X6 job table template, guards and alarms (Infra part)

Plan: `AA-Ecosys/docs/audits/2026-10-16-S240-aa751/aa751_plan.md` (§2 I1, §4). ADR 0003a decision 5:
DB Migrate `apply` waits until **all** owner job tables are idle (data standards C6.3b).

## Slice I1 (S240): DB Migrate idle check

### Decisions
- **Tables come from the catalog**, not a list: every `<schema>.job` (relkind r/p) with a `status`
  column. A future `tripplanner.job` is covered with no change here. `shared.job` and
  `booking.job` (the keys of `IDLE_EXEMPT_KINDS`) are *expected*: if one is missing the run logs a
  WARNING and goes on (plan: "a missing table is a WARNING"). Missing `shared.rerun_wave` is the
  same.
- **Fail closed on a read error.** A table the runner cannot read (permission, missing column) is
  logged as `busy: <table> unreadable (<error>), counted as busy` and blocks apply like a busy
  table. The runner connects as `aa_cis_admin`, which owns every `booking.*` object (bk-001 header)
  and `shared.*`, so this should not happen on Dev; refusing is safer than applying blind. The
  override still works.
- **Wait semantics:** the always-on report is the first check. apply then waits up to 3 times,
  20 s apart, re-checking after each wait (4 checks, at most ~60 s). An idle first check costs no
  extra query and no wait. Re-checks that are still busy log only the busy lines, so the job
  summary does not repeat every idle line 4 times.
- **Order in apply:** `skip: already applied` first (an applied file never waits), then the idle
  check, then the destructive snapshot check. So a busy destructive apply exits 7, not 5.
- **Override:** with `MIGRATION_IDLE_OVERRIDE` set and something busy, the run logs
  `MIGRATE WARNING: idle check OVERRIDDEN (<reason>), busy: <list>` and applies at once (no waits:
  the person already decided). Set but idle: one `note:` line. In check mode: one `note:` line
  ("only applies to mode=apply").
- **Workflow input `override_busy_jobs`:** passed through a job-level env var (never `${{ }}` inside
  the script, no shell injection), validated in "Validate input" (one line, at most 200 chars),
  echoed as a `::warning::` and into the job summary, then sent to the task as
  `MIGRATION_IDLE_OVERRIDE` in the `jq` container overrides. Exit 7 gets its own `::error::` text
  in "Task log + result".
- **Exempt kinds** exactly as the plan: `shared` → `ops_rds_role_connections`, `booking` →
  `bk_inquiry_pull`, per owner (a CIS-exempt name in another owner's table is not exempt).

### Changed (vs. the plan text)
- `wait_until_idle(conn, first=None, attempts=3, interval_s=20, sleep=asyncio.sleep)` takes the
  report already logged as `first`; `run_task` gains a `sleep` parameter for tests.
- Extra log lines not in §4: `MIGRATE idle: shared.rerun_wave open=0`, `MIGRATE waiting 20s …
  (re-check i/3), busy: …`, the WARNING lines for missing tables and the `unreadable` line. The four
  lines §4 specifies are byte-for-byte as written there (unit tests assert them).
- Multiple kinds in `kinds=[…]` are joined with `, ` (§4 shows one kind only).
- **Not done here:** the plan's optional fold-in "`schema_dump.py` adds `c.reloptions`". It is not in
  the I1 task text, it changes the dump fingerprint (one extra root PR), and Migration Copy Guard does
  not run on `schema_dump.py`. Left for a follow-up or the dump PR before R1.

### Tradeoffs
- The exempt list duplicates the CIS registry and Booking `DEPLOY_GATE_EXEMPT` until X1
  (`owners.yaml`). Accepted in the plan (§4 "Known costs").
- A destructive apply takes its RDS snapshot in an earlier workflow step, before the task runs the
  idle check, so a refusal wastes one snapshot. Moving the check ahead of the snapshot would need a
  second ECS task per run; the README says run `check` first instead.
- Retrying an `unreadable` table 3 times is pointless (a permission error does not go away in 60 s)
  but harmless and keeps one code path.
- Check-then-apply race: a job claimed between the last idle check and the ALTER is still caught by
  `lock_timeout 5s` (exit 6 with the existing hint).

### Should know
- Exit code 7 is new: the workflow fails the job with "apply refused: a job table is busy …".
- The task now issues `SELECT … FROM <schema>.job` (aggregate, no row values) and
  `to_regclass('shared.rerun_wave')` on every run, check included. Under the session defaults
  (`lock_timeout 5s`, `statement_timeout 15min`).
- Verified locally against a throwaway PostgreSQL 16 with the real CIS 174 + 217 and Booking
  bk-001 + bk-002 files: idle, exempt-only, check busy, apply busy (exit 7 after waits 20/20/20),
  both tables busy, override, idle after the first wait, open wave, and a role without access to
  `booking` (unreadable → exit 7). Live evidence on Dev comes from window A (two seeded refusals).
