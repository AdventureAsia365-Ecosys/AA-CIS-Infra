# AA-751 — X6 job table template, guards and alarms (Infra part)

Plan: `AA-Ecosys/docs/audits/2026-10-16-S240-aa751/aa751_plan.md` (§2 I1, §4). ADR 0003a decision 5:
DB Migrate `apply` waits until **all** owner job tables are idle (data standards C6.3b).

## Slice I1 (S240): DB Migrate idle check

### Decisions
- **Tables come from the catalog**, not a list: every `<schema>.job` (relkind r/p) with a `status`
  column. A future `tripplanner.job` is covered with no change here. `shared.job` and
  `booking.job` (the keys of `IDLE_EXEMPT_KINDS`) are *expected*: if one is missing the run logs a
  WARNING and goes on (plan: "a missing table is a WARNING"). Missing `shared.rerun_wave` is the
  same.
- **Fail closed on a read error.** A table the runner cannot read (permission, missing column) is
  logged as `busy: <table> unreadable (<error>), counted as busy` and blocks apply like a busy
  table. The runner connects as `aa_cis_admin`, which owns every `booking.*` object (bk-001 header)
  and `shared.*`, so this should not happen on Dev; refusing is safer than applying blind. The
  override still works.
- **Wait semantics:** the always-on report is the first check. apply then waits up to 3 times,
  20 s apart, re-checking after each wait (4 checks, at most ~60 s). An idle first check costs no
  extra query and no wait. Re-checks that are still busy log only the busy lines, so the job
  summary does not repeat every idle line 4 times.
- **Order in apply:** `skip: already applied` first (an applied file never waits), then the idle
  check, then the destructive snapshot check. So a busy destructive apply exits 7, not 5.
- **Override:** with `MIGRATION_IDLE_OVERRIDE` set and something busy, the run logs
  `MIGRATE WARNING: idle check OVERRIDDEN (<reason>), busy: <list>` and applies at once (no waits:
  the person already decided). Set but idle: one `note:` line. In check mode: one `note:` line
  ("only applies to mode=apply").
- **Workflow input `override_busy_jobs`:** passed through a job-level env var (never `${{ }}` inside
  the script, no shell injection), validated in "Validate input" (one line, at most 200 chars),
  echoed as a `::warning::` and into the job summary, then sent to the task as
  `MIGRATION_IDLE_OVERRIDE` in the `jq` container overrides. Exit 7 gets its own `::error::` text
  in "Task log + result".
- **Exempt kinds** exactly as the plan: `shared` → `ops_rds_role_connections`, `booking` →
  `bk_inquiry_pull`, per owner (a CIS-exempt name in another owner's table is not exempt).

### Changed (vs. the plan text)
- `wait_until_idle(conn, first=None, attempts=3, interval_s=20, sleep=asyncio.sleep)` takes the
  report already logged as `first`; `run_task` gains a `sleep` parameter for tests.
- Extra log lines not in §4: `MIGRATE idle: shared.rerun_wave open=0`, `MIGRATE waiting 20s …
  (re-check i/3), busy: …`, the WARNING lines for missing tables and the `unreadable` line. The four
  lines §4 specifies are byte-for-byte as written there (unit tests assert them).
- Multiple kinds in `kinds=[…]` are joined with `, ` (§4 shows one kind only).
- **Not done here:** the plan's optional fold-in "`schema_dump.py` adds `c.reloptions`". It is not in
  the I1 task text, it changes the dump fingerprint (one extra root PR), and Migration Copy Guard does
  not run on `schema_dump.py`. Left for a follow-up or the dump PR before R1.

### Tradeoffs
- The exempt list duplicates the CIS registry `deploy_gate_exempt` and, for Booking,
  `intake.RECURRING` (`bk_inquiry_pull`, every 60 s) until X1 (`owners.yaml`). Booking has no
  `DEPLOY_GATE_EXEMPT` registry yet (it arrives with B4; point the comment at it then). Accepted in
  the plan (§4 "Known costs").
- A destructive apply takes its RDS snapshot in an earlier workflow step, before the task runs the
  idle check, so a refusal wastes one snapshot. Moving the check ahead of the snapshot would need a
  second ECS task per run; the README says run `check` first instead.
- Retrying an `unreadable` table 3 times is pointless (a permission error does not go away in 60 s)
  but harmless and keeps one code path.
- Check-then-apply race: a job claimed between the last idle check and the ALTER is still caught by
  `lock_timeout 5s` (exit 6 with the existing hint).

### Should know
- Exit code 7 is new: the workflow fails the job with "apply refused: a job table is busy …".
- The task now issues `SELECT … FROM <schema>.job` (aggregate, no row values) and
  `to_regclass('shared.rerun_wave')` on every run, check included. Under the session defaults
  (`lock_timeout 5s`, `statement_timeout 15min`).
- Verified locally against a throwaway PostgreSQL 16 with the real CIS 174 + 217 and Booking
  bk-001 + bk-002 files: idle, exempt-only, check busy, apply busy (exit 7 after waits 20/20/20),
  both tables busy, override, idle after the first wait, open wave, and a role without access to
  `booking` (unreadable → exit 7). Live evidence on Dev comes from window A (two seeded refusals).

### Review fixes (i1 review, S240)
- `FakeConn.fetch` filters rows in Python, so it now asserts the query it gets is exactly
  `JOB_BUSY_SQL` for the quoted table and records the exempt list per owner. A new test pins the
  predicates (`status IN ('queued', 'running')`, `NOT (kind = ANY($1::text[]))`, no `run_after` in
  the WHERE clause, the catalog filter in `JOB_TABLES_SQL`, `status = 'open'` for waves); another
  asserts the exempt list sent per owner (`shared` → `['ops_rds_role_connections']`, `booking` →
  `['bk_inquiry_pull']`, `tripplanner` → `[]`). Removing `'queued'` now fails CI.
- "Validate input" trims `override_busy_jobs` like the runner's `.strip()`; a value of only
  whitespace is rejected with `::error::` instead of being reported as an override the task then
  ignores. Length/newline checks, the warning and the summary use the trimmed value (the raw value
  still goes to the task, which strips it to the same text).

## Slice I3 (S240): in-process sampling, job backlog alarms, ALARM-only e-mail

Shared contract approved by Nghiệp in S240 (about US$1.75/month of CloudWatch in total). The
AA-832 chain "Scheduler every 5 min -> ops-probe Lambda -> POST
/admin/job-runner/rds-role-connections/schedule -> shared.job -> CIS worker -> PutMetricData" is
replaced by an asyncio sampler in the CIS api (`api/core/ops_metrics_sampler.py`, AA-CIS-App) and
a `JobMetricsSampler` in AA-Booking; both also publish job backlog metrics. This slice is the
Infra side.

### Decisions
- **ALARM-only notifications everywhere on the topic.** `ok_actions` removed from every
  `aws_cloudwatch_metric_alarm` in `observability.tf` and `observability_ecosys.tf` (contract), and
  also from `ses.tf` (2 SES reputation alarms) and `modules/eventbridge` (`acp_dlq_depth`): Nghiệp's
  approved direction was "no OK e-mail on any alarm", and those three publish to the same
  `aws_sns_topic.alerts`. The rule is written once at the top of `observability_ecosys.tf` (and a
  one-line pointer in the other files).
- **Job backlog alarms** in `observability_ecosys.tf`, `for_each` over `local.job_backlog_owners`
  (`cis` -> `AA/Jobs/CIS`, prefix `local.name_prefix`; `booking` -> `AA/Jobs/Booking`, prefix
  `local.bk_name_prefix`): `jobs_queue_age` (Maximum, 300 s, 2/1, > 900, notBreaching),
  `jobs_overdue_running` (Maximum, 300 s, 2/1, > 0, notBreaching), `jobs_sampling_stopped`
  (SampleCount of OldestQueuedAgeSeconds, 900 s x 3, < 1, breaching). No dimensions, matching the
  publishers. Tags `local.ecosys_tags` + `App` (file convention).
- **IAM:** `cis_ecs_task_put_metric_aa_rds` keeps its address and policy name (an in-place update,
  no replace) and its condition becomes `cloudwatch:namespace` in `["AA/RDS", "AA/Jobs/CIS"]`; the
  Sid changes. New `booking_ecs_task_put_metric_jobs` on `aws_iam_role.booking_ecs_task`, namespace
  `AA/Jobs/Booking` only, placed next to the CIS grant (not in `booking.tf`, whose task-role comment
  now points to it). The workload permissions boundary allows `*`, so the grant is effective.
- **Schedule removed:** `aws_scheduler_schedule.rds_role_connections` and
  `var.rds_role_connections_schedule_expression` (`dfs_balance.tf`); the path left the handler's
  `_ALLOWED_PATHS`, so an old event naming it is logged `path_refused` and skipped.
- **`__pycache__` never zipped:** `data.archive_file.dfs_balance` gets
  `excludes = ["__pycache__", "__pycache__/**", "**/*.pyc"]` (S240 lesson on the AA-832 apply).
  Verified with archive 2.8.1 in a scratch root: a source dir with `__pycache__/x.pyc` and a stray
  `.pyc` zips to `['handler.py']` only, and its hash equals the clean directory's hash.

### Changed (vs. the contract text)
- `ok_actions` also removed in `ses.tf` and `modules/eventbridge/main.tf` (see Decisions).
- `db/run_migration.py` `IDLE_EXEMPT_KINDS["shared"]` is now empty (was
  `{ops_rds_role_connections}`), with `db/README.md` and the tests: the list mirrors the CIS registry
  `deploy_gate_exempt`, which no longer has an exempt kind. The exemption mechanism stays covered by
  a test-only kind (`mock.patch.dict`), and a new test pins that a leftover
  `ops_rds_role_connections` row now counts as busy.

### Tradeoffs
- **Sampling-stopped alarm for Booking** stays in ALARM while Booking is at `desired_count = 0`
  (its normal Dev state) or `WORKER_ENABLED` is off. With ALARM-only e-mail that is one e-mail per
  scale-down, not a pair per flip; accepted per contract, documented in the alarm description and
  the section comment.
- The Lambda re-zips once (handler text changed: path removed). F21 had avoided a re-zip; the
  contract removes the path, so the re-zip is intended. The `excludes` line itself does not change
  the hash of a clean checkout.
- The cost block counts custom metrics against the 10-metric free tier (7 before, 11 after, 1
  billable) instead of AA-832's "no free tier" basis; alarms are all billable (42 on acc2).

### Should know
- **Order (split apply, from merged `main`; addresses are relative to `accounts/aa365`):**
  1. **Step 0, before the CIS and Booking deploys, IAM only (additive):**
     `-target=aws_iam_role_policy.cis_ecs_task_put_metric_aa_rds` (in-place: namespace condition
     widened to `AA/RDS` + `AA/Jobs/CIS`) and
     `-target=aws_iam_role_policy.booking_ecs_task_put_metric_jobs` (create). Safe early: the old
     CIS worker job only writes `AA/RDS`, which stays allowed. Without this step every 5-min tick of
     the new samplers gets `AccessDenied` on `AA/Jobs/CIS` / `AA/Jobs/Booking` (logged, never
     raised) until Infra applies, and there is no clean evidence that they publish.
  2. **Deploy CIS (C2), then Booking (B5).** Check `ops_metrics_sampled` log lines and that
     `aws cloudwatch list-metrics --namespace AA/Jobs/CIS` / `AA/Jobs/Booking` show data.
     Between the CIS deploy and step 3 the old schedule still POSTs the removed endpoint: the
     handler logs `http_error` (404) and returns 502 in its body, no Lambda error and no retry storm.
  3. **Step 2, the rest except the sampling-stopped job alarms:**
     `-target=aws_scheduler_schedule.rds_role_connections` (destroy),
     `-target=aws_lambda_function.dfs_balance_check` (re-zip, path dropped from the allowlist),
     `-target=module.eventbridge.aws_cloudwatch_metric_alarm.acp_dlq_depth` and every alarm in
     `observability.tf`, `observability_ecosys.tf` and `ses.tf` whose `ok_actions` went
     (in-place), plus `-target=aws_cloudwatch_metric_alarm.jobs_queue_age` and
     `-target=aws_cloudwatch_metric_alarm.jobs_overdue_running` (create, 2 each). Then a full
     `terraform plan` should show only the 2 `jobs_sampling_stopped` creates.
  4. **Step 3, once both samplers have at least one datapoint:**
     `-target=aws_cloudwatch_metric_alarm.jobs_sampling_stopped` (create, `cis` + `booking`), or
     they fire on creation (as AA-832 did). Booking's goes to ALARM whenever Booking is scaled to 0
     or its worker is off; that is expected.
  If the whole plan applied before the CIS deploy, the per-role alarms would go blind (schedule
  gone, old CIS still waits for the POST) and `rds-role-connections-sampling-stopped` fires after
  45 min; the split above avoids it.
- **Leftover rows:** after the CIS deploy, any `ops_rds_role_connections` row still queued is an
  unregistered kind: the CIS sampler counts it as starved (queue-age alarm) and DB Migrate counts it
  as busy. Cancel leftovers once after the CIS deploy (see the rollout in the report).
- The 2 `jobs_sampling_stopped` alarms are created last (step 3 above), after the samplers publish.
