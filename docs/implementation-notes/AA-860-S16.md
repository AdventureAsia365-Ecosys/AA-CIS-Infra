## Decisions
- **New cell `rls.force_parity.cis_app`** (group `rls`). For each table of `RLS_PARITY_TABLES` (the 8 FORCE RLS
  tables + `gold_aa_internal.tenant_tour_versions`) the probe counts `count(*)` through **cis_app's own DSN**
  (`aa-cis/dev/rds-cis-app`), once without a tenant GUC and once under a forged uuid, and compares both with
  the catalog login's reference counts. The reference is taken before and after the role logins (same
  bracket as the existing `tenant_tour_versions` reference), so a row inserted in between does not fail it.
  Keyed on `244` + `cis_app_secret_ready` + `cis_app_password_set`: pending until S17's set-password, then
  expected. It catches the S243 plan bug directly (a FORCE table without the parity policy reads 0 rows as
  cis_app).
- **owners.yaml `cis.rls_parity_tables`** (new optional key, sorted) with the reason in a comment; mirrored by
  `RLS_PARITY_TABLES` in the probe and checked by `test_owners_registry` (equal, sorted, every table in a CIS
  runtime schema).
- Counts only, through savepoints in the probe's READ ONLY transaction (set_config undone with the savepoint);
  no row value, no tenant id printed.

## Changed (vs the lane plan)
- The plan's "note on cis.rls" became a registry key, so the probe constant has a source to be checked
  against instead of a comment.
- DRAFT_244 in `db/tests/test_run_migration.py` is unchanged: the real 244 passes the role lint
  (`run_migration.py --inspect` on the copy → no errors).

## Tradeoffs
- After S22 the catalog login is `db_migrator`, a member of `cis_app`: its reference counts then also go
  through the parity policies. Still a fair reference (it is what the runtime reads), but no longer an
  independent one; the 244 apply-time guard (master measured before the policies) remains the independent
  check.
- 9 tables × 4 small counts per run; the tables are < 2k rows on Dev.
