# AA-828 — Per-app budgets on the `App` cost allocation tag (S238)

Repo/files: `accounts/aa365/observability.tf`, `accounts/aa365/variables.tf`

## Decisions

- One `aws_budgets_budget.per_app_monthly` with `for_each` over
  `var.per_app_monthly_budgets` (map of App tag value -> USD). Budget names:
  `aa-cis-dev-monthly-app-<app>` (same `local.name_prefix` as the existing
  `aa-cis-dev-monthly-total`).
- Filter: `cost_filter { name = "TagKeyValue", values = ["user:App$<app>"] }`.
  Built with `format("user:App$%s", each.key)` — in an HCL string `$${` is an
  escape, so `"user:App$${each.key}"` would produce the literal text
  `user:App${each.key}`.
- Tag values come from the code, not assumed: `local.bk_tags` (`booking`),
  `local.tp_tags` (`tripplanner`), `local.ecosys_tags` overrides (`cis`,
  `shared`, `booking`, `tripplanner`). Provider `default_tags` (versions.tf)
  carry no `App` key.
- Notifications: 80 % ACTUAL + 100 % FORECASTED, e-mail to `var.alert_email`
  (same subscriber as the total budget). The total budget keeps its own
  80 %/100 % ACTUAL pair unchanged.
- Default amounts (variable comment explains them): cis 150, tripplanner 25,
  booking 25 = 200 of the 250 total, leaving ~50 for shared/untagged spend.
- Validation on the variable: keys must be one of the DM-10.1 App values
  (`cis`, `tripplanner`, `booking`, `crm`, `shared`), amounts > 0.
- Budgets themselves are tagged `ecosys_tags + App + Issue` (CI role already has
  `budgets:TagResource`, AA-287).

## Changed

- Scope addition from the S238 comment: replaced the stale AA-360 "Bedrock
  daily cost" note with the actual decision (ledger in `shared/cost_guard.py` +
  `shared.spend_budget`, alerts to `shared.notifications`, Cost Operations UI,
  reconciled under AA-804, no rollup Lambda; satellite accounts not covered by
  acc2 tags). Removed both `AA-364` week_run blocks. The AA-287 "no
  cost-allocation tags" note now points at the per-App budgets.
- Not done here (issue scope bullet 1): adding `App` tags to RDS, snapshots,
  the S3 archive bucket, the CIS log groups, and flipping `default_tags`.
  Re-tagging everything built from `local.common_tags` hits the CI role's
  restricted `iam:TagRole` (see observability_ecosys.tf header) and needs its
  own targeted plan.

## Tradeoffs

- The `cis` budget reads close to $0 until CIS resources carry `App = "cis"`
  (today only the REST API execution log group does). Built anyway because the
  tag is now active and the budget starts working the day tagging lands; the
  comment says so, so nobody trusts a $0.
- No "shared"/untagged budget: shared infra is not tagged `App = "shared"` yet
  (RDS lives in `modules/rds` with `common_tags`). A `shared` key is a one-line
  addition once it is. An untagged budget (`user:App$` with an empty value)
  was considered but not built: the semantics should be checked in the console
  first.
- FORECASTED alerts need some spend history; for a tag activated today AWS may
  not forecast for the first weeks. The 80 % ACTUAL alert still works.

## Should know

- A targeted plan should show exactly 3 creates:
  `aws_budgets_budget.per_app_monthly["cis"]`, `["tripplanner"]`, `["booking"]`
  (plus the existing `time_sleep.wait_for_iam_propagation` dependency, no change).
  No change to `aws_budgets_budget.total_monthly`.
- Fargate cost is attributed by task tags. `aws_ecs_service.booking` has no
  `propagate_tags`, so Booking task cost will not show under `App = booking`
  once it runs (desired_count 0 today). Follow-up: `propagate_tags = "SERVICE"`
  (+ `enable_ecs_managed_tags = true`), same for the CIS services in
  `modules/ecs` once they carry `App = "cis"`.
- AWS Budgets pricing: check whether extra non-action budgets are billed on this
  payer (historically first two free, then about $0.02/day each).

# AA-828 part 2 — `App` tag coverage + Fargate propagation (S238)

Repo/files: `accounts/aa365/{main,observability,diagnostics,booking,variables}.tf`,
`modules/{vpc,rds,alb,ecs,elasticache,efs,secrets,api_gateway}`.

## Decisions

- **Module/locals tag maps, not provider `default_tags`.** `default_tags.App` would (1) put every
  future resource that forgets its own App under `cis`, TripPlanner/Booking included, and (2) re-tag
  every resource in the root at once, including the bootstrap IAM roles (`cicd.tf`,
  `cicd_split.tf`, `agent_session.tf`) that only a human MFA apply may change. Resource tags win
  over `default_tags` for the same key, so the existing `bk_tags` / `tp_tags` / `ecosys_tags`
  overrides would have survived, but the silent default was the reason to avoid it.
- `local.common_tags` gains `App = "cis"` (everything built from it is CIS: S3 medallion buckets,
  EventBridge/ACP schedules, REST API + stage + domain, DFS balance Lambda, ACP alarms).
- `local.shared_tags = merge(common_tags, { App = "shared" })` for the WAF, the alert SNS topic
  (every app's alarms publish to it), the RDS CPU alarm, CloudTrail (bucket + trail) and all of
  `diagnostics.tf` (VPC flow logs, ALB access-log bucket, account-level API Gateway logging role).
- Modules that had no `tags` input get a new `variable "tags"` (default `{}`) merged into every
  taggable resource. The root passes only `{ App = ... }` (`local.cis_app_tags` /
  `local.shared_app_tags`) so the Project/ManagedBy values those resources already carry from
  `default_tags` do not change (passing the full `common_tags` would rewrite `Project = AA-CIS` to
  `aa-cis` and `ManagedBy = Terraform` to `terraform` on ~40 resources for no gain).
  - `shared`: `modules/vpc` (VPC, IGW, 6 subnets, NAT instance + root volume + EIP + role, route
    tables, DB subnet group, SGs), `modules/rds` (instance, parameter group, log group),
    `modules/alb` (ALB, CIS target group, listeners, VPC-link NLB + its SG/TG/listener, VPC link —
    Booking routes through the same ALB and VPC link).
  - `cis`: `modules/ecs` (services, task definitions, ECR repo, `/ecs/aa-cis-dev` log group,
    execution + task roles), `modules/elasticache` (only the CIS api reads `REDIS_HOST`),
    `modules/efs` (legacy ChromaDB/LangGraph volume), `modules/secrets`.
  - ECS cluster: `cluster_tags = { App = "shared" }` (Booking's service runs in it). A cluster has
    no cost line; tasks are attributed by their own tags.
- **`propagate_tags = "SERVICE"`** on `aws_ecs_service.booking` and the CIS api/worker services.
  Not `TASK_DEFINITION`: both deploy workflows (`AA-CIS-App` and `AA-Booking` `deploy-dev.yml`)
  build each new revision from `aws ecs describe-task-definition` output without `--include TAGS`
  and `register-task-definition` without `--tags`, so the revisions that actually run carry no
  tags. The service tags are Terraform-owned and stable. Task definitions are tagged too (DM-10.1),
  but only the Terraform-tracked revision gets them.
- API Gateway REST: cost allocation uses the **stage** tags, so `aws_api_gateway_stage.dev` now
  gets `var.tags` (the Booking stage already had `bk_tags`).
- NAT instance: `volume_tags` added so the root EBS volume (separate cost line) is tagged.
- `var.per_app_monthly_budgets` gains `shared = 50` → one new budget
  `aa-cis-dev-monthly-app-shared` (filter `user:App$shared`).

## Changed

- Issue bullet "S3 archive bucket" is covered by the CIS S3 module (all six medallion buckets get
  `App = cis`); the RDS snapshots get `App = shared` through `copy_tags_to_snapshot = true` from the
  first snapshot after apply (existing snapshots keep their old tags).
- Not tagged on purpose (all $0 resources): bootstrap IAM roles/policies/OIDC provider
  (`cicd.tf`, `cicd_split.tf`, `agent_session.tf` — need a human MFA apply, see header of
  `cicd_split.tf`), the NAT instance profile (`iam:TagInstanceProfile` is a separate grant), API
  Gateway usage plans, Application Auto Scaling targets, the CloudWatch dashboard (no tag support).

## Tradeoffs

- Explicit tags per module mean a new resource must remember its tags (DM-10.1 review rule). The
  alternative (a default) mis-attributes silently, which is worse for a budget.
- Fargate tags reach tasks only when ECS starts them: running tasks keep empty tags until the next
  deploy (CIS) or scale-up (Booking). No forced redeploy is added here.

## Should know

- Replacement check (offline, provider hashicorp/aws 5.100.0, fake credentials, `-refresh=false`
  against a synthetic state): changing `tags` is in-place for every resource type touched here, and
  `propagate_tags` / `volume_tags` are in-place too (no `# forces replacement` on those paths).
- `aws_db_instance` tag-only change = `AddTagsToResource`, no `ModifyDBInstance`, no reboot. The
  targeted plan for `module.rds.aws_db_instance.main` must show only `tags` / `tags_all`; anything
  else (e.g. a pending AA-824 class change) is a separate diff — stop and review.
- CI permissions gaps (both `aa-cis-dev-role` and `aa-cis-infra-tf-apply` share
  `cicd_inline_statements`): no `elasticfilesystem:TagResource`, `ecr:TagResource` only on
  `aa-booking-*` repos, and the legacy role's `iam:TagRole` covers only the scheduler/TripPlanner/
  agent/Booking names (not `aa-cis-dev-ecs-*`, `aa-cis-dev-diag-*`, `aa-cis-dev-dfs-*`,
  `aa-cis-nat-instance-role`). `aa-cis-infra-tf-apply` has `iam:TagRole` on `aa-*-dev-*` + the
  NAT role. Apply locally with the MFA admin profile (targeted), not through CI.

## S238 add-on — CIS operator e-mail env (spend budget alerts)

App side: AA-CIS-App branch `feat/aa-828-llm-spend-email` (job `ops_alert_email`, SES helper).

### Decisions
- `modules/ecs` gets three optional inputs (`ops_alert_email`, `ses_from_address`,
  `ses_configuration_set`, default `""`) rendered as `ALERT_EMAIL_TO`, `SES_FROM_ADDRESS`,
  `SES_CONFIGURATION_SET` on BOTH the api and worker task definitions (one local,
  `local.ops_alert_mail_env`). The worker sends; the api gets the same env so a job handler run in
  the api process (JOB_WORKER_IN_API) behaves the same.
- Recipient is a new root var `cis_ops_alert_email` (ses_variables.tf, tfvars
  `nghieppham@adventure.asia`), not `var.alert_email`: that one is a personal Gmail used for SNS and
  AWS Budgets, and in the SES sandbox only verified recipients receive mail.
- From / configuration set reuse `var.ses_from_address` and
  `aws_sesv2_configuration_set.stream["transactional"]` — exactly what
  `aws_iam_role_policy.cis_ecs_task_ses_send` (ses.tf, Infra #113) already allows on the CIS task
  role (`ses:SendEmail` on `identity/*` + the transactional set, condition `ses:FromAddress`). No IAM
  change needed.

### Should know
- Targeted plan: `-target=module.ecs.aws_ecs_task_definition.api
  -target=module.ecs.aws_ecs_task_definition.worker` → 2 to add, 0 to change, 2 to destroy
  (task definitions are replaced = new revisions; the old revision is deregistered). The services
  ignore `task_definition`, so nothing rolls until the CIS Deploy Dev copies the family's latest
  revision. Apply this BEFORE merging the CIS PR.
- Terraform's container definitions carry image `:latest`; the CIS deploy swaps in the SHA image.
  Before apply, compare the plan's env list with the live latest revision
  (`aws ecs describe-task-definition --task-definition aa-cis-dev-worker`) to be sure nothing set
  outside Terraform would be dropped.
