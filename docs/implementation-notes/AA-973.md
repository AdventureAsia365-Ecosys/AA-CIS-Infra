## B2B seed script for the live check (S248, `db/scripts/aa973_b2b_seed.py`)

Dev had no sellable trip plan with components and no published contract with rates, so the booking.b2b.v1 flow
(products → quote → hold → confirm → B2B trip case) could not be verified past `GET /products`. The script writes the
smallest synthetic set that makes it verifiable, through DB Migrate `mode=run-script`.

### Decisions

- **run-script, not a migration**: Dev-only synthetic data that must never replay in CI or another environment.
- **Writes as `bk_owner`** (`SET LOCAL ROLE`, the master is a member, rl-001) in one transaction under
  `pg_advisory_xact_lock`; `catalog.v_tour` is read as the first of `booking`, `tripplanner` the master may switch to
  (the catalog views grant SELECT to those, not to `bk_owner`; aa847's probe showed the master can switch to
  `tripplanner` on Dev). No role can read the catalog → `SCRIPT refuse what=catalog_read`, exit 13, nothing written.
- **Two inactive seed staff rows** (`seed-s248-aa973-maker` / `-checker`, role `contracting`, `active = false`): a
  published contract needs a maker and a different checker (bk-008), and every `created_by` is an FK to
  `booking.staff_users`. Inactive rows are refused by Booking's staff auth (`staff_inactive`), and their ids cannot
  match a Cognito or CIS identity. Real staff are never written as the authors of synthetic terms.
- **Tour choice**: the seed's own plan if its tour is still in `catalog.v_tour`; else the first `catalog.v_tour` row by
  `source_id` with no `booking.trip_plans` row. A real commercial row is never touched.
- **Departures are written by the seed** (capacity 2, `auto_confirm`, 14 and 21 days ahead or the next free 7-day
  offsets): the partner API only reads departures and the staff `POST …/departures` needs a Cognito staff token.
- **USD contract, USD quote**: no FX row needed. Net amounts are synthetic constants and are never printed.
- **DRY RUN by default** (`READ_ONLY = True` as merged); apply and cleanup are one-line follow-up PRs
  (`READ_ONLY = False`, then `ACTION = "cleanup"`), like aa680 / aa816: run-script takes no arguments.
- **Cleanup retires** rather than deletes where the domain forbids deletes: published contracts become `expired`
  (bk-008 allows only that; their rates stay fixed, bk-010), suppliers / hotels / room types / services become
  `inactive`, departures that a quote or hold line points at become `cancelled` and keep the plan (`sellable = false`).
  Components, unreferenced departures and an unreferenced plan are deleted. The staff rows stay (FK targets).

### Should know

- Checked locally on a throwaway PostgreSQL 16 with the AA-Booking `main` migrations (bk-001 … bk-020, the CI role
  shape) and the real Booking app (ASGI client, local M2M issuer): dry run in a read-only session writes nothing;
  apply → second apply `steps=0`; products lists the plan; quote 2 adults on a departure → 201 `available`; hold 201,
  same Idempotency-Key → same hold; a 1-adult proposal on the same departure → quote `sold_out`, hold 422 `sold_out`;
  confirm → 201 `TC-…`; hold + DELETE on the second departure → 204; cleanup → second cleanup `steps=0`; seed again →
  reactivated supply, new contract, new departure dates; cleanup again.
- The run-script runner's idle check applies to the apply and the cleanup (they write); the dry run only reports.
