## Decisions

- **`removed { lifecycle { destroy = false } }`, never a plain delete.** `modules/secrets` and
  `tripplanner.tf` set `recovery_window_in_days = 0` in dev, so deleting the resource blocks would
  have deleted the secrets at once with no recovery. Terraform now forgets them; the secrets stay in
  AWS until the main session deletes them by CLI with a 30-day recovery window (AA-878 M2, DRY RUN
  first). Nothing is deleted by this PR.
- **The removed blocks sit in the module that declared the resource** (`modules/secrets/main.tf` for
  the two ACP secrets, `tripplanner.tf` for Mapbox). Same-module `removed` is valid on every
  Terraform version that has `removed` (1.7+, CI pins 1.7.5); a root block pointing into a child
  module was avoided. Checked locally on 1.15.5 with a hand-made state: both forms plan
  "will no longer be managed by Terraform, but will not be destroyed", `0 to destroy`, and a
  `-target` on a removed address works.
- **`tf_plan_secret_arns` shrinks in the same PR (5 → 2)**, as the critic required: the
  `aws_secretsmanager_secret.tripplanner_mapbox.arn` and `module.secrets.acp_*_arn` references
  cannot survive the removal. Consequence: `aws_iam_role_policy.tf_plan` changes, and that policy
  sits on a bootstrap role the CI apply role may not write (DenyRoleWritesOutsideStack), so a local
  MFA targeted apply is required (runbook below).
- **Both Lambdas share one role policy** (`tripplanner_lambda_permissions`): `ReadMapboxSecret` is
  replaced by `ReadApiKeySecret` on `aws_secretsmanager_secret.tripplanner_api_key.arn`. No new
  env var: the app derives the secret name from the existing `ENVIRONMENT`.
- **`random_password.tripplanner_api_key` + its secret stay**: the secret is the source of truth;
  the Vercel `TRIPPLANNER_API_KEY` holds the same value (set by hand).
- **`aa-cis/dev/api-keys` is not Terraform-managed**: only its stale `terraform.tfvars` comment
  changes (orphan, M2 deletes it).
- **I3 rides with I2** (same PR, separate commit): `tools/secrets/register_check.py` follows the
  `tools/identity` layout (tests in `tools/secrets/tests`, own workflow), stdlib + PyYAML (already
  pinned 6.0.2 in three Infra workflows). The optional scheduled drift workflow + OIDC role is
  **not built**: it needs a new role in `tf_managed_role_arns` and another MFA bootstrap apply;
  deferred as the plan allowed.

## Tradeoffs

- **Two-step apply** (bootstrap local, then CI) instead of one local apply of everything: the IAM
  grant for the api-key secret lands and propagates before the env key disappears, so there is no
  window where the Lambdas fail closed with AccessDenied (503). The cost is one extra dispatch.
- The checker trusts the inventories it is given (no AWS calls of its own). That keeps it
  value-free and testable; collecting fresh inventories is a documented step in the register.
- Vercel and Lambda env inventories are filtered to secret-looking names, so a secret with an
  innocent name would slip through; GitHub and Secrets Manager are compared in full.
