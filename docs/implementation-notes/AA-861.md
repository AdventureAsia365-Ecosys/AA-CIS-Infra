# AA-861 — Infra half: tp-021 copy, tripplanner.job in the registry, the TripPlanner jobs Lambda

TripPlanner outbox payloads keep traveller contact data forever; DM-6.6 / DM-7.2 want it redacted after 90 days by an
owner-run TTL kind in the owner's own job table. TripPlanner had neither a job table nor a worker. App half:
AA-TripPlanner-Web `docs/implementation-notes/AA-861.md` (migration tp-021, `backend/jobs/`).

## Decisions

- **A third Lambda, not a branch of assembly.** ADR 0003a d4 asks for a scheduled Lambda that claims from
  `tripplanner.job`. Reusing the assembly function (like the old `extraction` direct-invoke branch) would have run the
  worker with the assembly role (Bedrock invoke, satellite assume, SES, edge key). The jobs function has its own role:
  the DB DSN and Sentry DSN secrets by ARN, VPC ENIs, its own log group. Same zip as browse / assembly (the app
  packages `jobs.zip`, handler `backend.jobs.handler.handler`), same no-ingress security group (the RDS SG already
  admits it), no API Gateway route.
- **The scheduler only wakes.** One daily rule (19:30 UTC) sends `{"op": "tick"}`; the Lambda queues the day's runs
  itself with an idempotency key per kind and UTC day, then runs due jobs. Async invoke, `maximum_retry_attempts = 0`
  (a run that redacted rows and then failed must not run twice the same day; the job itself has `max_attempts = 1`).
- **Alarms:** errors >= 1 in 5 min (a tick raises when a job failed or a retention run was HELD over 2x the last live
  run), and not-run (no invocation for 2 daily periods, missing = breaching). Not in `local.tp_functions` of
  `observability_ecosys.tf`: that map's errors alarm needs 3 errors and its throttles alarm is for HTTP bursts.
- **Reserved concurrency 1** with a validation (one runner); connection budget pool `tp-jobs` 1 x 1 (tripplanner 21 /
  30, total 121 / 135).
- **Live override closed by default.** `RETENTION_OVERRIDE_ENABLED` = `var.tripplanner_jobs_retention_override_enabled`
  (default `"false"`). A DRY RUN override (counts with a small `older_than_days`) needs no flag in the app; a LIVE
  override does (plus ENVIRONMENT dev, `older_than_days >= 7`, `max_rows <= 1000`). Booking sets its flag on Dev
  permanently; here it is opened only for an approved proof run.
- **Registry:** `owners.yaml` `tripplanner.job_table = tripplanner.job`, `run_migration.IDLE_EXEMPT_KINDS["tripplanner"]`
  = empty (the daily kind is never always-queued). The DB Migrate idle check already discovered job tables from the
  catalog (`JOB_TABLES_SQL`); a registered table missing from the catalog is a WARNING, not busy, so this can merge
  before tp-021 is applied. `tripplanner.job` is not added to `expand_hot_tables`: the TripPlanner code names every
  column (no `SELECT *` / `RETURNING *`).
- **Schema reference:** `tripplanner.job.payload` joins `PII_ALLOWLIST` (token "payload", carries flags and counts
  only). Until tp-021 is applied the entry is reported as stale (informational).

## Tradeoffs

- A separate function costs one more deploy target in the app workflow and the post-deploy verify row, for a role
  with no LLM or mail rights. Accepted: the worker will grow (job retention, erasure kinds) and should not inherit
  assembly's grants.
- Daily cadence only. A retry of a failed job (backoff) waits for the next tick unless an operator invokes `run`.
  Enough for a daily TTL kind; a kind that needs minutes-level latency would add a second schedule.
