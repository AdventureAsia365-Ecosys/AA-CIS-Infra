# AA-871 — Sentry wiring for Booking and TripPlanner + Booking uptime probe (Terraform part)

App code is already on main: AA-Booking `backend/app/observability/sentry.py` (env `SENTRY_DSN`, `SENTRY_REQUIRED`),
AA-TripPlanner-Web `backend/shared/observability.py` (both Lambdas) and `frontend/lib/sentryLite.ts` (Vercel env
`SENTRY_DSN`, server-only). This branch adds the AWS side.

## Decisions

- **Secret shells only** (`aws_secretsmanager_secret`, no `aws_secretsmanager_secret_version`), names per the repo's
  `<app>/<env>/<name>` rule: `booking/dev/sentry-dsn` (tags `bk_tags` + `Issue = AA-871`, so `App = booking`) and
  `tripplanner/dev/sentry-dsn` (`tp_tags` + `Issue`, `App = tripplanner`). `recovery_window_in_days` 0 in dev like the
  sibling secrets. Terraform never holds the DSN, so the plan role reads nothing new (`tf_plan_secret_arns` unchanged)
  and the AA-846 plan guard (secret versions) is not tripped.
- **Booking: container `secrets` block, gated by `var.booking_sentry_enabled` (default false).** ECS refuses to start
  a task whose secret has no AWSCURRENT value, and the Booking deploy copies the family's LATEST revision. Mapping it
  unconditionally would break every Booking deploy (other agents merge Booking PRs in parallel) between the apply and
  the `put-secret-value`. So: apply 1 creates the shell + the execution-role grant (task definition unchanged, no new
  revision); the DSN is put; a one-line tfvars flip (`booking_sentry_enabled = true`) adds `SENTRY_DSN` (secret) and
  `SENTRY_REQUIRED=true` (the app's missing-DSN guard, "Infra turns it on together with the secret",
  `backend/app/settings.py`); the next Booking deploy carries the revision. The execution-role grant on the one ARN is
  always on (harmless without the mapping).
- **TripPlanner Lambdas: read by name at cold start, not a Terraform-fed env value.** TripPlanner already resolves
  secrets at run time: the edge key by name `tripplanner/<ENVIRONMENT>/api-key` (`backend/shared/auth.py`, AA-878)
  and the DB DSN by ARN (`backend/shared/db.py`). Reused: the Lambdas read `tripplanner/<ENVIRONMENT>/sentry-dsn`;
  this branch only adds the grant `ReadSentryDsnSecret` (one ARN). No Lambda env change, so this apply does not
  update either TripPlanner function. The reader is a small companion change in AA-TripPlanner-Web (branch
  `feat/aa871-sentry-dsn-from-secret`): `observability.py` today reads only the env. Rejected: a data source
  `aws_secretsmanager_secret_version` -> `SENTRY_DSN` env, because (1) plan/apply fail while the secret has no value,
  so shell + reader cannot ship together and "off until a DSN exists" breaks; (2) the DSN would be in state and in
  the Lambda configuration, against the AA-878 rule in this file's CONTEXT ("no secret value in the Lambda env");
  (3) the plan role would need GetSecretValue on it, a bootstrap change to `cicd_split.tf` applied locally; (4) every
  rotation would need an apply.
- **Uptime probe on the existing ops-probe Lambda** (`dfs_balance.tf`), no new function/role/group: schedule
  `aa-cis-dev-booking-uptime` in group `aa-cis-dev-acp` (CI scheduler grants are scoped there), `rate(5 minutes)`,
  flexible window OFF, event `{"health": "booking"}`. The handler GETs the URL from env `BOOKING_HEALTH_URL`
  (`var.booking_health_url`, default `https://api-booking.lumiguides.it.com/booking/health`); targets are an
  allowlist (`_HEALTH_TARGETS`), so an invoke cannot aim it at an arbitrary URL; https only; no secret read. Healthy =
  200 + JSON `status == "ok"` (the live body today: `{"status":"ok","service":"aa-booking-api","git_sha":...}`);
  anything else is logged `ops_probe health_failed` and raised -> AWS/Lambda `Errors`.
- **Alarm `aa-booking-dev-uptime`**: function `Errors` Sum >= 1 in 2 of 2 five-minute periods (~10 minutes of failed
  probes), missing = notBreaching, ALARM + OK actions (D-20), runbook `api_5xx`, tags `App = booking`. The other
  schedules on the function never raise (they return a status body), so the metric counts failed probes plus real
  crashes of the function, both worth an e-mail.
- Empty `booking_health_url` = no schedule and no alarm (count 0).

## Changed (vs. the task)

- The TripPlanner reader needed an app change (one small PR in AA-TripPlanner-Web), not Infra only. Both orders are
  safe: without the grant or the value the read fails and Sentry stays off.
- Booking mapping behind a flag + second tiny apply instead of mapping at once (see above).
- Alarm name uses the Booking prefix (`aa-booking-dev-uptime`, like the other Booking alarms); the schedule keeps the
  `aa-cis-dev-` prefix because it lives in the CIS schedule group.

## Tradeoffs

- Lambda async invoke retries a raised probe up to 2 more times (~1 and ~3 minutes later); with the 2-period alarm a
  single blip does not page, a sustained outage does. Scheduler `retry_policy` is 0 (delivery retries only).
- The probe also fires while Booking is scaled to 0 on purpose (same as `aa-booking-dev-jobs-sampling-stopped`).
  Remove the alarm noise then by setting `booking_health_url = ""`.
- No alarm on "probe stopped running" (missing data = notBreaching); the Lambda's Invocations metric shows it.
- Cost: ~8.7k invocations/month at 128 MB (~0.01-0.02 USD, inside the free tier), Scheduler ~0.01 USD, one standard
  alarm 0.10 USD, a few MB of logs: ~0.15 USD/month. Secrets: 2 x 0.40 USD/month once they hold a value.
