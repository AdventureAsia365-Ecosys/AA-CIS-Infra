# AA-935 — CRM-07 AA-Partner CRM web on Dev (lane aa-935, S249)

Source: root `docs/audits/2026-10-21-S246-crm-design-v3/design-v3.md` §6.3 card CRM-07 and §2.1 (hosts, Fix C10);
`final/crm-design-final.md` §1.4 and §4.4; root ADR 0010 decision 2. App side: AA-Partner `web/`, `CONTEXT.md` and
`docs/implementation-notes/AA-935.md` (branch `feat/aa-935-web-skeleton`).

## Decisions

- **`accounts/aa365/crm_web.tf`, the `crm_app.tf` pattern**: ECR `aa-crm-dev-web` (IMMUTABLE), task definition,
  target group (`/healthz`), service at desired 0, two alarms. The partner host's default rule `crm_partner_default`
  (priority 10, below `crm_api`) changes from the fixed 404 JSON to a forward to the web target group, modified in
  place (same priority and ARN); `alb_rule_order.py` keeps the order (`crm_api` 5 < default 10 < deny 20).
- **Own roles for the web, not the API's.** The web never touches the database or the KMS keys: its execution role
  reads only `crm/dev/web` (never `crm/dev/database-url`), its task role holds ECS Exec only. The API's task role name
  stays the one the KMS key policies trust; nothing in `crm_data.tf` changes.
- **The deploy role is shared** (`aa-crm-dev-app-deploy`, `crm_app.tf`): its statements now list both repos, both
  families and both services; a separate `EcsUpdateCrmWebService` statement lets the web service take only a web
  revision. The OIDC trust (AA-Partner `environment:dev`) is unchanged.
- **Secret shell without a version** (`crm/dev/web`, JSON `{cognito_client_secret, session_secret}`), filled by
  `tools/identity/crm_dev_identity.py web-secret`. A Terraform `aws_secretsmanager_secret_version` would have needed
  a plan-role grant (`tf_plan_secret_arns`, bootstrap local apply) and `allow_guarded`, and would put the session key
  in the state; the Sentry DSN shell is the precedent.
- **FARGATE_SPOT only** for the web: stateless pages, no worker; a Spot interruption is a few seconds of 503 on Dev.
- **The web calls the API through the public partner host** (`CRM_API_ORIGIN = https://partner-dev.…`, egress via the
  NAT instance), never the internal ALB: the `/crm/*` rule needs the CloudFront origin secret, which the web would
  then have to hold.
- **Sign-in with the EXTERNAL `cis-portal` client** until AA-939 (card: "same `cis-portal` client as the portal"):
  its callback / sign-out URLs gain `https://partner-dev.lumiguides.it.com/auth/callback` and `/signed-out` (and
  localhost:3005 for local development). AA-939 swaps `COGNITO_*` to the partner pool's web client.
- **e2e users of the synthetic agencies in the EXTERNAL pool**, e-mail `e2e-test-crm-<agency>-<role>@e2e-mail.<zone>`,
  one list `tools/identity/crm_e2e_users.json` read by `e2e_mailbox.tf` (receipt-rule recipients) and the tool. They
  sign in with the e-mail code (no password, `MessageAction=SUPPRESS`); the codes land in the existing e2e mailbox
  bucket under the same prefix. The rule widens from one recipient to seven fixed addresses (still no catch-all).
- **`CONTENT_STUDIO_URL = https://portal.<zone>`**: the cross-link target of the CRM sidebar (Fix C10).

## Tradeoffs

- The CIS e2e mail reader role can also read the CRM e2e codes (same bucket and prefix). Accepted for synthetic Dev
  agency users; a separate prefix would need a second rule ARN in the bucket policy and a second reader.
- With the web at desired 0 the partner host answers 503 on every non-`/crm` path instead of the old 404 JSON.

## Follow-up (S249): managed login branding for every EXTERNAL client

- **Found live (24/10/2026, read-only):** `describe-managed-login-branding-by-client` answered "does not exist" for
  all three EXTERNAL clients (`cis-portal`, `booking-customer`, `tripplanner`). With managed login version 2 a client
  without a style gets `/login` -> 403 "Login pages unavailable", on both EXTERNAL domains (the style is per client,
  not per domain), so the partner host sign-in this card ships could not work. AA-816 (S242) had parked the EXTERNAL
  style as a follow-up ("needs its own header SVG without Staff").
- **Decision: same look as WORKFORCE, page header off.** `aws_cognito_managed_login_branding.external`, `for_each`
  over `aws_cognito_user_pool_client.external` (a new key gets its style in the same apply). Settings reuse
  `local.id_branding_settings_workforce` (colours, card, buttons, light mode) with `pageHeader` disabled and its
  component removed; assets are the form logo PNG (mark + "Adventure Asia", no "Staff") and the favicon SVG. The
  WORKFORCE header SVG reads "Staff sign-in" and Cognito has no title setting, so it is left out instead of drawing a
  new outlined-text SVG now. `use_cognito_provided_values` (AWS look) was not chosen: ADR 0006a A5 wants the branded
  look because the unbranded Cognito page got the domain flagged by Safe Browsing.
- **Create only, no WORKFORCE change:** the WORKFORCE resource and its settings local are untouched (no replace of
  the staff styles). A payload Cognito rejects leaves the EXTERNAL clients as they are today (still 403).
- **Output:** `identity_managed_login_base_urls.external` now follows `identity_custom_domains_enabled` like
  WORKFORCE (`https://auth.lumiguides.it.com` on Dev); `crm_web.tf` already used that host. New output
  `identity_external_branding_ids`.
- **Guard:** `tools/terraform/managed_login_branding.py` (+ tests, workflow `managed-login-branding.yml`, offline)
  fails when an interactive client (`code`/`implicit` flow) of a pool with a managed-login-v2 domain has no branding
  resource covering it (`for_each` over the whole client map, or `client_id = <client>.id`), or the branding names
  another pool. Machine clients (`client_credentials`, the M2M pool) are skipped. On `origin/main` before this change
  it reports the EXTERNAL gap (B1); it will catch the AA-939 partner pool clients too.
- **Plan (local, read-only, `-lock=false`, 24/10/2026):** `Plan: 3 to add, 0 to change, 0 to destroy` — the three
  `aws_cognito_managed_login_branding.external[...]`; outputs: `+ identity_external_branding_ids`,
  `identity_managed_login_base_urls.external` prefix URL -> `https://auth.lumiguides.it.com`.
- **Cost:** $0 (managed login branding is included in the Essentials tier the pools already use; no new resource
  with a price).
- **Verify after apply:** `curl -s -o /dev/null -w '%{http_code}' 'https://auth.lumiguides.it.com/login?client_id=<cis-portal client id>&response_type=code&scope=openid&redirect_uri=https://partner-dev.lumiguides.it.com/auth/callback'`
  returns 200 (was 403); same for the `tripplanner` and `booking-customer` client ids with one of their registered
  callback URLs; `describe-managed-login-branding-by-client` returns a style for each.
