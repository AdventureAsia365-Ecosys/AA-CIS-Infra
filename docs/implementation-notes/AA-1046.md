# AA-1046 R4b part 1: isolation probe off the Booking B2C objects (S271)

Root plan: AA-Ecosys `docs/audits/2026-11-05-S270-aa1037-b2c-drop-dryrun/README.md` section 4. Booking bk-045
(destructive) drops `booking.customers` and the view `booking.v_ops_inquiry_inbox` (bk-035).

## Decisions

- **Cross-app cells read `booking.trip_cases`** instead of `booking.customers`: a read of a missing table raises
  42P01, not 42501, so every cross-app cell on `booking.customers` would FAIL right after the drop. `trip_cases` is
  kept, holds traveller data of the kept b2c cases, and is granted to role `booking` only (schema reference), so the
  same five roles (`tripplanner`, `aa_app_user`, `cis_app`, CIS runtime, `crm_app`) still get 42501.
- **Consumer grant cell `bk-035` removed** (probe + `owners.yaml`): after the drop the view is absent while bk-035 is
  registered, which the probe reports as a missing contract grant. Removing the cell before the drop is safe: the
  probe checks expected grants only, it does not flag an extra one.

- **Owner-only relations (review fix).** bk-045 creates `booking.retired_b2c_record` and revokes everything from
  role `booking` (the archive is owner-only). Without an exemption `runtime_grants.booking` would ask SELECT on it
  and go red on the bk-045 apply and every night after. `owners.yaml` `runtime_privileges.booking`
  gets `owner_only_relations: [booking.retired_b2c_record]` (mirrored in `RuntimePrivileges.owner_only`, kept in
  sync by `test_owners_registry.py`): the baseline SQL leaves those relations out (`$6`), and a new cell
  `owner_only.booking` asserts the role holds NO table privilege on them (`OWNER_ONLY_HELD_SQL`; an absent relation
  holds nothing, so the cell passes before bk-045 too). Tested on PostgreSQL 16: the exempt relation drops out of
  the missing list, any other relation without SELECT stays in it, a later GRANT shows up as held.
- **DM-6.5 consent script (review fix).** `db/scripts/dm65_consent_capture.py` read `booking.customers` in all four
  queries. It now checks `tripplanner.customers` and its hand-off (`booking.inbox_events`, `inquiry.submitted`,
  unredacted rows only, joined on `payload.customer.customer_id`); same text as root
  `docs/legal/consent-capture-query.md`. Ran on a local PostgreSQL 16 in a read-only session (writes refused 25006).

## Changed

- `db/README.md` cell list; `db/tests/test_isolation_probe.py` (cell names, key tuple, a guard that no cross-app
  cell names `booking.customers`).
- Not changed: `db/rls_catalogue_rules.py` keeps `booking.v_ops_inquiry_inbox:cis_app` (byte copy of the CIS file;
  a stale allowlist entry is reported, not fatal). Remove it in both repos after the drop.
- Not changed: the old one-off `db/scripts/aa682_*_live_check.py` name the dropped tables; they are history (run
  once, never scheduled) and would fail cleanly on a missing table. `dm65_consent_capture.py` is not one-off (the
  KPI K-PRIV-CONSENT cites its query), so it moved (above).

## Tradeoffs

- Moving the cell target rather than deleting the cells keeps the X1 S2 isolation guarantee for every role.
