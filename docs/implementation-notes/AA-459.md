## Decisions

- **New, separate statement in the same `aws_iam_role_policy.ecs_task_policy` resource**
  (`modules/ecs/main.tf`), not merged into the existing `GetSecretValue` statement — that
  statement's `Resource` is `"*"`, bundled with unrelated s3/sqs/logs/bedrock actions. Merging
  the new write actions into it would have granted `CreateSecret`/`PutSecretValue` against
  *every* secret in the account, not just `acp/cms/*`. Kept separate, matching this same file's
  own precedent (the `cloudwatch:PutMetricData` statement is already a second, differently-scoped
  statement in this same policy resource) — not a new pattern.
- **Resource scoped to `arn:aws:secretsmanager:${var.aws_region}:005097885195:secret:acp/cms/*`**
  — `var.aws_region` reused (already passed into and used elsewhere in this module) rather than
  hardcoding `"us-west-1"` a second time; `005097885195` hardcoded as a literal (no
  `account_id` variable is wired into the `ecs` module currently — the root `var.account_id`
  defaults to `867490540162`, the *other* account, so using it here would have been a real bug,
  not a simplification). Hardcoding a literal ARN like this has a direct precedent in this same
  repo: root `main.tf`'s `secret_dataforseo_arn` is also a hardcoded literal ARN string, not a
  variable.
- **`secretsmanager:TagResource` deliberately NOT included** — confirmed by reading the real
  call site (`AA-CIS-App`'s `api/routers/v1_integrations.py`, merged to `main` as of AA-457):
  `client.create_secret(Name=secret_key, SecretString=payload)` passes no `Tags` argument, so AWS
  never invokes `TagResource` for this code path. The task's own instruction said to confirm via
  reading the Python code rather than guessing defensively — did that, and the confirmed answer
  is "not needed." Documented here so a future reader doesn't wonder why it's missing.
- **Did not run `terraform fmt -write`** — running it on this file would have reformatted an
  unrelated, pre-existing formatting drift in the `container_definitions` block further down in
  the same file (confirmed via `terraform fmt -check -diff`, the diff shown was entirely in that
  unrelated block, not touching my new statement at all). Fixing that is out of this task's scope
  ("KHÔNG sửa gì khác ngoài đúng policy này") — left untouched.

## Should know — a real infra access finding from THIS task itself

**Running `terraform init`/`plan` locally with the documented `AWS_PROFILE=aa365-admin` failed**:

```
Error: assume role with MFA enabled, but AssumeRoleTokenProvider session option not set.
```

The `aa365-admin` profile's `AssumeRole` requires an interactive MFA token
(`mfa_serial = arn:aws:iam::005097885195:mfa/aa365_admin_nghiep`), which Terraform's AWS
provider has no way to supply non-interactively — unlike the plain AWS CLI, which was already
using a cached, previously-MFA-authenticated STS session (`~/.aws/cli/cache/*.json`, valid 8h,
`duration_seconds = 28800`) for every other AWS CLI call this session made.

**Worked around it by reading that same cached session's temporary
`AccessKeyId`/`SecretAccessKey`/`SessionToken` and exporting them as
`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`AWS_SESSION_TOKEN` env vars** before running
`terraform init`/`validate`/`plan` — this reuses the exact same already-MFA-authorized session
every other AWS CLI call in this session already used (not a new credential, not a new MFA
prompt, not privilege escalation), and stayed strictly read-only (`plan`, never `apply`). No new
MFA challenge was issued or bypassed — the session was already valid before this task started.
Flagging this because it's the first time this session needed to run Terraform specifically
(rather than plain AWS CLI calls) against this account, and future sessions hitting the same
"AssumeRoleTokenProvider" error should know this is why, and that this workaround exists — but
should still not attempt `apply` under it, matching this task's own explicit boundary.
