# X2 RLS catalogue guard (Infra side), S245

The CIS side (rules, CI guard, seeded violations) is in AA-CIS-App
`docs/implementation-notes/AA-848-s245.md`. This repo runs the same rules on the nightly Dev dump.

## Decisions

- **Byte copy, not a second implementation.** `db/rls_catalogue_rules.py` is a byte copy of AA-CIS-App
  `tests/integration/rls_catalogue_rules.py`. `db/check_migration_copies.py` gained `CODE_COPIES`: the same byte
  compare against the owner's main as the migration copies, with no registration check. `--all` (nightly and
  manual) includes it, and a PR that changes the copy checks it. As with migrations, the CIS PR merges first and
  then the copy PR.
- **The input is the existing dump.** `db/schema_dump.py` already has every field the rules read (relations,
  columns, policies, FK constraints with the parent schema, table, column and schema grants with PUBLIC spelled
  `PUBLIC`). No new catalog query, and no change to the ECS task.
- **Findings go in the rendered file.** `db/gen_schema_reference.py` adds `## RLS catalogue guard (X2)` after the
  soft-key section. It shows the violation count per rule, the violation list (expected "none"), every allowlist
  entry in use with its count and reason, and stale entries. The Totals line also gives the violation count.
- **The guard outcome is part of the fingerprint.** `fingerprint()` now hashes the structural view plus the guard
  outcome (violations, allowlisted findings with reasons, stale entries). A rules or allowlist change opens the
  root PR on the next run. The first run after this merges opens one too, which is what lands the section in
  `db-schema-reference.md`.
- **Not fatal in the workflow.** Like soft-key orphans, the dump must still publish. `--rls-guard` prints one
  summary line for the step summary and a `::warning::` per violation. Blocking happens in CIS CI, where a
  migration that breaks a rule cannot merge.
- **Owner maps are mirrored and tested.** `rls_catalogue_rules.SCHEMA_OWNERS` and `ROLE_OWNERS` are checked
  against `db/owners.yaml` in `db/tests/test_owners_registry.py`: schemas per owner, and the owner role, runtime
  roles and view owner roles per owner. The master and db_migrator are never app roles.

## Changed

- `db/rls_catalogue_rules.py` (new, copy), `db/gen_schema_reference.py`, `db/check_migration_copies.py`,
  `.github/workflows/db-schema-dump.yml` (annotation lines),
  `.github/workflows/migration-copy-guard.yml` (path filter + the copy in the PR diff), tests.
- `db/owners.yaml` is not touched. AA-826 is editing it, and rule f stays out of scope.

## Tradeoffs

- Hashing the guard outcome into the fingerprint changes every fingerprint once. That costs one root PR, and
  that PR is wanted anyway.
- Rule g's allowlist lives in the rules module until the owners.yaml grant registry (rule f) replaces it. Its
  entries restate `consumer_grants` / `owner_grants` by hand.
