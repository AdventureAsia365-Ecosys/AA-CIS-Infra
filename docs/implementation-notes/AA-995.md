# AA-995 (Infra part) — TripPlanner place-read probe (S257)

The app-side notes are in AA-TripPlanner-Web `docs/implementation-notes/AA-995.md` (section S257).

## Decisions

- **A DB Migrate run-script, not an ECS-exec script.** `cis_app` (the CIS container login) has no SELECT on
  `catalog.v_tour_place`, and the measurement must run as `tripplanner` (the Lambda's role, `SET LOCAL ROLE`), which
  only the master can switch to. Read-only (`READ_ONLY = True`), so it runs during a wave.
- **The candidate view is measured inline, as the master.** `catalog._live_tour` / `_tour_day_text` are
  catalog_owner's and granted to nobody, so the master inlines them (CIS 273 / 289 statements verbatim); `old_inline`
  (CIS 256's body, inlined the same way) calibrates master-inline timings against the real view as `tripplanner`.
- **Literals, not bind parameters, in EXECUTE.** `EXPLAIN … EXECUTE stmt(<uuid[] literal>)`; every id comes from
  `catalog.v_tour` and is re-validated with `uuid.UUID` before it is inlined.

## Changed

## Tradeoffs

- Wall timings include the round trip from the migrator task; EXPLAIN times are server-side. Both are printed.
- A data change between the `tripplanner` read and the master read of a set would show as a parity diff; the window
  is seconds and parity is re-run per set.

## Should know

- Verified locally against a stand-in schema (PostgreSQL 16, the real view bodies over stand-in tables): all parity
  lines PASS, ~20 s. On the stand-in, the view with JIT took ~91 ms per call and ~26 ms with jit off.
- Read the output from the DB Migrate job log: lines starting with `SCRIPT `.
