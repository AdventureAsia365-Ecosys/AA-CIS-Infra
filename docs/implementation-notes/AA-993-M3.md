# AA-993 Phase E, slice M3 — `migration-sync` + `migration-apply` (expand auto-apply)

Design: root `docs/audits/2026-10-26-S252-aa993-delivery-pipeline/design.md` §1 D2.2 / D2.5, §2 M3; critic points 1,
2, 4, 11; root ADR 0017 decisions 2, 5, 6, 8 (Proposed) and ADR 0011a (Proposed). Builds on I1 (#477: role
`aa-cis-infra-db-auto-apply`, environment `dev-db-auto`, ruleset), M1 (schema-dump auto-merge), M2a (#478: expand
header, lint, lock risk, CIC validity, apply lock) and M2b (#485: runtime post-check exit 14, `--classify`).

## Decisions

- **Where each half runs.** The narrow role has no Secrets Manager and no RDS API, and the database is VPC-private,
  so everything that needs `shared.schema_versions` runs in the migrator task: a new runner mode
  `MIGRATION_MODE=apply-pending` (`run_apply_pending` in `db/run_migration.py`). Everything that needs the internet
  (owner repos' `main`, the dump artifact, a scratch PostgreSQL for classify) runs on the GitHub runner in
  `db/apply_pending.py`, with no AWS. The two halves share one pure planner, `run_migration.plan_pending`, so the
  runner's forecast and dry run follow exactly the task's rule.
- **One task per run, a bundle as its input.** The runner uploads one JSON bundle (every copy of the four owner dirs
  above the legacy floor: path, sha256, SQL, the runner's verdict) through the existing `MIGRATION_URL` /
  `MIGRATION_SHA256` variables; `MIGRATION_FILE` / `MIGRATION_VERSION` are empty. No new variable name reaches the
  task (`test_runner_modes` guards this, `migration-apply` is now in its workflow list). The task re-checks the bundle
  digest and every file's sha256, and re-lints each file itself.
- **The runner's verdict = bytes AND classify.** `ok` only when the copy is byte-identical to a fresh clone of the
  owner's `main` (never the copy PR's merge or label, ADR 0017 d5) AND `db/expand_check.py --classify` (run in this
  workflow on a replay of Dev) gives class `expand`. No dump artifact or no classify result = "no classify evidence"
  = the task stops at that file. Nothing is applied on a header alone.
- **Strict prefix with three stop kinds.** Per owner, number order, unregistered files above the floor: stop at the
  first file that is (a) below the owner's highest registered key (`out-of-order`), (b) not expand by header / lint
  (contract), or (c) refused by the runner. Owners are independent.
- **Legacy floor.** CIS has unregistered copies 232, 252, 263 (hand-applied before self-registration; AA-CIS-App
  readiness `LEGACY_CIS_BASELINE = 263`). Without a floor the strict prefix would stop CIS forever at 232, so
  `AUTO_APPLY_FLOOR = {"cis": 263}`: unregistered copies at or below it are counted as legacy and ignored. The other
  owners have no gap (dump of 2026-10-29: every Booking / TripPlanner / CRM copy registered).
- **Lock.** The task takes the apply lock (advisory 993/1) on its own session for the whole run, reads the keys
  under it, and applies each file on its own connection (each file has its own `lock_timeout` / `statement_timeout`
  server settings). `apply_file(..., lock_held=True)` skips the per-file lock (the session holding it is a different
  one, so taking it again would wait 25 min and fail).
- **`run_task` split.** The per-file body of `run_task` moved unchanged into `apply_file()`; `run_task` (DB Migrate)
  calls it. `execute_file` gained an optional `info` dict that receives the SQLSTATE (for the 55P03 retry).
- **Busy rules (ADR 0017 d5, Q5).** Expand files skip the job-table idle wait (as M2a); a file naming a hot table
  waits for an open rerun wave (3 × 20 s) and then is **deferred** (status `deferred`, exit 0 for the run, the owner
  stops, the next run retries) rather than a red run. Never an idle override, never a snapshot (the task env drops
  `MIGRATION_IDLE_OVERRIDE` / `MIGRATION_SNAPSHOT`; an expand file cannot be destructive by lint).
- **55P03 retry**: two more tries after 30 s and 90 s (`AUTO_LOCK_RETRY_S`), only for a lock timeout.
- **A failed file** stops its owner; other owners still run; the task exit is the first failure's code.
- **Blocking probe = reusable `db-isolation-probe.yml`** with inputs `environment` (default `prod`) and `s3_root`
  (default `db-isolation-probe`). migration-apply calls it with `dev-db-auto` / `db-auto-apply/probe`, so the probe
  runs under the narrow role too (it only needs the migrator family, `DescribeTaskDefinition` and the S3 prefix, all
  in `cicd_db_auto_apply.tf`). Its concurrency group became `${{ github.workflow }}-isolation-probe` (in a reusable run
  `github.workflow` is the caller's name), so a called probe is never cancelled as a pending run by a nightly one.
  Its S3 prefix gained `-<run_attempt>` (re-runs no longer share a prefix).
- **Gate (ADR 0017 d8).** Apply only when `vars.DB_AUTO_APPLY == 'true'` AND the repo is public AND
  `GET /rules/branches/main` shows `pull_request` + `required_status_checks`. Anything else = list only. The same
  public + ruleset gate controls the sync's merge pass (ADR 0011a d6).
- **Sync uses the GitHub API, not git push.** Branch from `main`'s SHA (`POST /git/refs`), file via
  `PUT /contents` with the owner's raw bytes, PR via `POST /pulls`, all with the ci-bot token (its PR events start
  the required checks; a `GITHUB_TOKEN` PR would not). Labels and label creation use the job's `GITHUB_TOKEN`
  (`issues: write`, `pull-requests: write`), so the App token stays Contents + Pull requests only.
- **Sync floor.** The set difference ignores owner files numbered below the owner's lowest copy here (CIS 001-214,
  TripPlanner 001-006 predate the copy flow and were never copied). A late lower-numbered file above that floor is
  found (critic 2).
- **Out-of-order label** uses the dump's registered keys; without an artifact, the highest copy here (a label only:
  the apply recomputes from the database).
- **Merge pass conditions** (`merge-check`): open, non-draft, same-repo branch `bot/migration-copy/<owner>-<NNN>`,
  author type Bot, exactly one changed file with status `added` matching owner and number, head bytes = owner main,
  every required context of `tools/github/infra-main-ruleset.json` completed with success / skipped / neutral, no
  failed check run; merge pinned with `--match-head-commit`. A bot PR whose file reached `main` another way is closed.
- **Schedules.** Sync every 10 min (design); apply hourly at :37 as a backstop (push on a merged copy is the main
  trigger). A scheduled apply in list-only mode skips the classify (no evidence is needed when nothing is applied).
- **Paths.** New scripts live in `db/` (not `tools/migration_sync.py` as the design names it): they import
  `check_migration_copies` / `run_migration`, and their tests run with the rest of `db/tests` in the Copy Guard job.
  `db/migration_guard_scope.py` and `scripts/pre-push.sh` list the new files.

## Changed (vs the design / ADR text)

- The design's "DB Migrate apply step moved into a shared script that both workflows use" is **not** done in this
  PR: `db-migrate.yml` is unchanged. The shared part is the runner itself (`apply_file`) plus
  `.github/scripts/migrator-task.sh`; the log fetch / exit mapping in `migration-apply.yml` is a copy of DB Migrate's
  (exit texts in `db/apply_pending.py EXPLAIN`). Moving DB Migrate onto a shared script touches the manual path that
  every contract file needs; better in a follow-up after migration-apply has a green live run.
- Exit 7 (hot table + open wave) is a deferral, not a failure (ADR: "waits for an open wave to close").
- The copy-PR comment "manual DB Migrate apply needed" is posted by migration-apply's `summary` job once per PR
  (marker `<!-- aa993-manual-apply -->`), and the sync also writes it in the PR body for contract / destructive files.
- `db-auto-apply-role-check.yml` is kept (its header says M3 may delete it after a green migration-apply run).

## Tradeoffs

- **Classify in the apply workflow** costs a replay (minutes) whenever an expand file is next in line; it is skipped
  when nothing can be applied, and on scheduled list-only runs. The authoritative check is still the runtime
  post-check inside the task (exit 14); the classify is the "re-classify, never trust the merge" layer the ADR asks for.
- **Forecast from a possibly stale dump**: if the dump is older than the last apply, the forecast may stop at a file
  that is already applied and skip this run; the next dump (every apply dispatches one, plus nightly) fixes it. The
  forecast can never make the task apply something: the task re-reads the keys under the lock.
- **Bundle of every copy above the floor** (~120 files, ~1.5 MB) rather than only the expected pending ones: the
  task decides from the database, so a stale forecast cannot hide the real next file.

## Should know

- **DB_AUTO_APPLY stays unset** (list only) until the orchestrator / tech lead switches it on. ADR 0011a's open point
  (code-owner review on every path outside `db/migrations/<owner>/` before `DB_AUTO_APPLY=true`, because a leaked
  ci-bot key could merge a green PR that changes the runner) is still open and is the tech lead's decision.
- The **merge pass is live as soon as this merges** (repo public, ruleset in force): ci-bot will open and merge copy
  PRs every 10 min. The App secret / variable already exist (DB Schema Dump uses them). Test it first with
  `workflow_dispatch` `dry_run=true`.
- The classify step executes owner SQL as a superuser in a scratch container on the runner; that job has only
  `contents: read` + `actions: read` and no AWS. The apply job consumes only the bundle artifact of the same run.
- The task-side tests use the fakes of `test_run_migration` (no database); the classify / replay itself is covered by
  the M2b PostgreSQL tests in the Copy Guard job.
- Live proof (design §2 M3): (1) a sync dispatch with nothing new does nothing; (2) the M2b probe file is copied,
  merged, applied, registered, probe-green, dump PR auto-merged; (3) a manual DB Migrate `check` of an expand file
  during an auto-apply waits on the advisory lock and neither run is cancelled.
