# AA-1158 (Infra) — alarms on the Booking supplier bank account KMS key (S294)

The key itself landed in S289 (`modules/environment/booking_supplier_bank.tf`). This slice adds the two alarm rules
the S289 notes left as a follow-up, with the same pattern as the CRM keys (`crm_data.tf` `crm_kms_key_admin` /
`crm_kms_foreign_use`).

## Decisions

- **Same two rules as CRM, for the Booking key:** `aa-sec-<env>-booking-kms-key-admin` (administration events on this
  key or its alias) and `aa-sec-<env>-booking-kms-foreign-use` (a crypto call, allowed or denied, by any principal
  other than the Booking task role or an AWS service). Event name lists are copied unchanged from the CRM rules.
- **Name prefix `aa-sec-<env>-booking` (orchestrator decision, option B):** the CI apply role's `SecEventRuleManage`
  (`accounts/aa365/cicd_sec.tf`) and both topic policies (alerts: `identity_alerts.tf`
  `AllowSecurityEventBridgeRules`; page: `alert_severity.tf` `AllowPageEventBridgeRules`) already admit
  `rule/aa-sec-*`. So a CI apply creates the rules with no IAM, topic policy or bootstrap change. The first draft
  used `aa-booking-<env>-kms-*`, which needed a new page policy prefix, a new alerts topic statement and a new CI
  grant (a bootstrap object); dropped.
- **App = booking tag** (`local.bk_tags`) stays: the CIS alerts catalogue (`api/services/alerts_catalogue.py`) and the
  generated alarms page (`tools/docs/gen_docs.py`) take the `App` tag first and use the name prefix only as a
  fallback, so the rules list under Booking, not under the shared `aa-sec-*` bucket.
- **Matching:** one key, so `resources[].ARN` is the key ARN and `requestParameters.keyId` is matched exactly against
  the four forms a caller can pass (key id, key ARN, alias name, alias ARN); `aliasName` matches the one alias. The CRM
  rules use prefixes because they cover an alias folder of three keys.
- **Severity:** page, locked (`var.alert_tags.page_locked`), component `security`, like the CRM KMS rules (AA-1171
  D5). Each rule has an alerts-topic target and a page-topic target with the same e-mail text (`booking_kms_page`).
- **Runbook:** `incident` (there is no Booking key runbook; `alarm_runbooks.tf` rule: no specific playbook ->
  incident). A Booking key runbook page in the root repo is a follow-up.

## Changed

- `modules/environment/booking_supplier_bank.tf`: header (alarms section, why the aa-sec prefix, cost), locals
  `bk_kms_rule_prefix` / `bk_supplier_bank_key_match` / `bk_kms_alert_input_paths`, two rules, two alerts targets,
  one page target map.
- Tests: `test_aa1158_booking_bank_kms.py` (`AlarmTest`: names, prefix admitted by the existing grant and both topic
  policies, App tag, targets, and the patterns evaluated offline against sample CloudTrail events with the matcher of
  `test_crm_kms_alarm_check.py`); `test_aa1171_alert_severity.py` (Booking page target).
- No change to `accounts/aa365` (topic policies, CI grants).

## Tradeoffs

- `aa-sec-*` reads as "account security" while the rules belong to Booking. Accepted: the App tag carries ownership
  for the catalogue and cost views, the name still says `booking`, and the alternative was a bootstrap apply of new
  grants for two rules.
- The foreign-use rule keeps the CRM exemption for `AWSService` callers, though no AWS service uses this key today;
  the key policy denies every other account principal anyway, so the alarm reports attempts.
- No live check tool like `crm_kms_alarm_check.py` for Booking: the offline test covers the pattern; the live step
  after the apply lists the rules and their targets.
