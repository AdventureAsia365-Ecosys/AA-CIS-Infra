# AA-990 — DB Migrate idle check: a queued row far ahead does not block apply

Paired with the AA-CIS-App branch `fix/aa-990-geocode-credit-requeue` (place_geocode queues its next run for the
Geoapify credit reset, next 00:00 UTC + 10 min). Merge this before that CIS change deploys.

## Decisions

- `JOB_BUSY_SQL` counts a queued row only when `run_after <= now() + BUSY_HORIZON_S` (3600 s, = CIS
  `queue.DEPLOY_GATE_HORIZON_S`); running rows always count; no lower bound (overdue rows count). Rows beyond the
  horizon come back as a new `later` column, shown as `later=<n>` on the idle / busy line, never busy.
- The horizon applies to every owner job table, not only `shared.job`: a row due more than an hour ahead is not
  touched by a migration that takes minutes, whichever app queued it.

## Changed

- Review of the CIS branch found that without this, the credit-reset row made `apply` wait and refuse from each day's
  credit stop until 00:10 UTC for several days while ~4,600 names drain at 2,500 credits a day.

## Tradeoffs

- One shared constant per side (CIS and Infra) instead of a cross-repo import: the runner ships only this file and the
  SQL to the task. The unit test pins the value to 3600 with a comment naming the CIS constant.

## Should know

- `kinds=[…]` lists only groups with rows inside the horizon; `later` is the total per table.
- Tests: `db/tests/test_run_migration.py` (FakeConn rows take `later=True`; two new idle-check tests).
