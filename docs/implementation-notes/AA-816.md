# AA-816 — CIS staff directory: task role may manage WORKFORCE staff (plan step I3)

Session S242 (18/10/2026), Claude Code. Branch `feat/aa816-cis-task-role-cognito` from `origin/main`
at `dec2b1f` (#180). Plan: root `docs/audits/2026-10-18-S242-cognito-phase1/plan.md` step I3.
ADR: root `docs/adr/0006-ecosystem-identity.md` (IAM for the directory writer).

## Decisions
- **New file `accounts/aa365/identity_iam.tf`, root-level policy on `module.ecs.task_role_name`.**
  Same pattern as `ses.tf` `cis_ecs_task_ses_send` and `observability_ecosys.tf`
  `cis_ecs_task_put_metric_aa_rds`; `modules/ecs` is not touched, so the Booking and migrator roles
  cannot pick it up by accident.
- **Exactly the 8 ADR actions** (`AdminCreateUser`, `AdminAddUserToGroup`, `AdminRemoveUserFromGroup`,
  `AdminDisableUser`, `AdminEnableUser`, `AdminUserGlobalSignOut`, `ListUsers`, `ListUsersInGroup`),
  one Allow statement, resource = `aws_cognito_user_pool.workforce.arn` only.
- **No `AdminGetUser`** (counts as MAU, ADR 0006 "Costs"); no `AdminSetUserPassword`,
  `AdminUpdateUserAttributes`, `AdminLinkProviderForUser`, `AdminInitiateAuth`,
  `AdminRespondToAuthChallenge`, `AdminDeleteUser` (account-takeover risk, ADR 0006).
- **No EXTERNAL pool grant.** Tenant invitations are a later, separate step.
- **Allow-list plus an explicit Deny (review fix, S242).** First commit was allow-only. Review
  finding 2 accepted: a second statement `DenyStaffTakeoverActions` denies `AdminSetUserPassword`,
  `AdminUpdateUserAttributes`, `AdminLinkProviderForUser`, `AdminInitiateAuth`,
  `AdminRespondToAuthChallenge`, `AdminDeleteUser`, `AdminSetUserMFAPreference` on both the
  WORKFORCE and EXTERNAL pool ARNs. It widens nothing; it only stops a later broad grant on the
  role from undoing the ADR exclusions. A Deny on the CIS task role does not affect break-glass or
  any human/ops principal, so it cannot block an ops exception. No other policy on the role grants
  `cognito-idp` today (checked: `modules/ecs/main.tf` `ecs_task_policy`,
  `ecs_task_infra_status_readonly`, the Cost Explorer / Bedrock assume and PutMetricData policies,
  `ses.tf` — none lists `cognito-idp` or `*` actions).

## Tradeoffs
- Explicit Deny vs. ADR-literal allow-only: chose the Deny (fail-closed). Cost: one more statement
  than the ADR list; a future need for one of these actions on this role would have to remove the
  Deny on purpose, which is the intent.
- The `AdminCreateUser` + `TemporaryPassword` gap (see Should know) cannot be closed in IAM (no
  Cognito condition key for `MessageAction` / `TemporaryPassword`); dropping `AdminCreateUser` would
  break the staff directory, so the grant stays and the risk is documented for detective controls.

## Should know
- **Worker uses the same role.** `modules/ecs/main.tf` `aws_ecs_task_definition.api` (line ~373) and
  `.worker` (line ~574) both set `task_role_arn = aws_iam_role.ecs_task.arn`, so the reconcile job on
  `aa-cis-dev-worker` gets the grant with no task-def change. Takes effect within seconds of apply
  (IAM policies are evaluated per request, after brief eventual consistency); no redeploy or
  credential refresh needed, so the probe can run right after apply.
- **Boundary:** the role carries `aa-workload-boundary` (AA-806), which allows all actions except IAM
  writes and account/organizations, so `cognito-idp` is not blocked.
- **CI apply:** `aws_iam_role_policy` on this role is already managed by CI (ses.tf, observability),
  so the apply role can put it; no bootstrap grant needed.
- **terraform plan (local, read-only, 18/10/2026, acc2):** `Plan: 1 to add, 0 to change, 0 to destroy`
  — only `aws_iam_role_policy.cis_ecs_task_workforce_directory`, resource
  `arn:aws:cognito-idp:us-west-1:005097885195:userpool/us-west-1_bCcFvbSOS`.
- **After apply, probe once from inside the container** (LES:14) via S3-mediated ECS exec with the
  output written back to S3 (LES:51): `list_users(UserPoolId=..., Limit=1)` succeeds;
  `admin_set_user_password` on a dummy username returns `AccessDeniedException`.
- Plan risk 5: do not stack this apply with the X1 task-def/SG PRs; apply one after the other.
- **Residual risk — `AdminCreateUser` is still a takeover path (review finding 1, S242).**
  `AdminCreateUser` takes `TemporaryPassword`; IAM cannot force `MessageAction=SUPPRESS` or forbid a
  password. With PASSWORD a pool-wide first factor and a pre-token trigger that checks only domain /
  `email_verified` / groups, a compromised CIS task role can (1) create `ghost@adventure.asia` with
  `email_verified=true`, its own password and SUPPRESS, add it to `booking-admin`/`cis-admin`, sign
  in and answer `NEW_PASSWORD_REQUIRED` — staff tokens with no mailbox; (2) per the AdminCreateUser
  API reference, `MessageAction=RESEND` "reset[s] the temporary-password duration with a new
  temporary password", so RESEND with its own `TemporaryPassword` on a real staff user still in
  `FORCE_CHANGE_PASSWORD` (all admin-created users while `identity_ses_enabled = false`) takes that
  account over. Not verified live (no Cognito Admin calls in this step); the doc wording is the
  evidence. This makes ADR 0006's accepted-risk line ("not usable without that mailbox or Google
  account") too strong. Mitigations need an orchestrator decision before staff accounts exist in the
  pool or Booking honours `booking-admin`: (a) CloudTrail/EventBridge alarm on WORKFORCE
  `AdminCreateUser` with a password or `RESEND`, and on `NEW_PASSWORD_REQUIRED` responses for anyone
  but break-glass; (b) the reconcile job flags WORKFORCE users missing from the directory and any
  non-break-glass user with a password set / `FORCE_CHANGE_PASSWORD`; (c) amend ADR 0006
  consequences (root repo, not this worktree).
