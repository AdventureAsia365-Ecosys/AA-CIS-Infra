# AA-806 — Split the CIS CI role + permissions boundary; TripPlanner API throttling (from AA-805)

## Decisions

- **Three roles, not two.** The issue names `aa-cis-dev-app-deploy` and `aa-cis-infra-tf`; the plan
  and apply jobs need different rights, so the Infra side is `aa-cis-infra-tf-plan` (PR, read only)
  and `aa-cis-infra-tf-apply` (prod environment, boundary).
- **Trust contexts.** App deploy: only `environment:dev` (all three App jobs that assume a role run
  in `dev`). Plan: only `pull_request`. Apply: only `environment:prod` (terraform-apply +
  db-migrate). `StringEquals` on the exact immutable subject, like #99 for TripPlanner. A GitHub sub
  carries the environment *or* the ref, so "main only" relies on the environments'
  deployment-branch rules.
- **eval-regression.yml on the app deploy role.** It shares the App's `AWS_ROLE_ARN` secret in the
  `dev` environment, so the role also gets `ecs:ListTasks` / `ecs:ExecuteCommand` on the CIS cluster.
  Same blast radius as deploying an image.
- **DB Migrate on the apply role.** It runs in `prod` and needs ECS RunTask + PassRole + S3 + logs,
  which the apply role has. A dedicated migrate role is possible later; not needed now.
- **Apply role = parity with aa-cis-dev-role** (same 10 managed policies, same inline statements via
  a shared `local.cicd_inline_statements`) so the cut-over is a drop-in. Only differences:
  `IAMRoleManage` (Resource `*`) and the four per-name TagRole statements are replaced by one
  statement scoped to `role/aa-*-dev-*` (+ `aa-cis-nat-instance-role`), plus `apigateway:SetWebACL`.
  No `ReadOnlyAccess` on the apply role: it would be an 11th managed policy (default quota 10).
- **Two boundaries.** `aa-workload-boundary` (no IAM writes, no account/org) is what roles created by
  the apply role must carry; `aa-cis-infra-tf-apply-boundary` caps the apply role (role writes only
  on stack names, CreateRole only with the workload boundary, no boundary removal/edit, no users /
  keys / org, no `sts:AssumeRole`).
- **Review fix: bootstrap carve-outs inside the name pattern.** `role/aa-*-dev-*` also matches the
  legacy `aa-cis-dev-role` (no boundary, IAM on `*`), the new `aa-cis-dev-app-deploy` and
  `aa-cis-dev-agent-session`. The apply boundary now denies every role write + PassRole on the app
  deploy and agent session roles, and on the legacy role everything except `DeleteRole` /
  `DetachRolePolicy` / `DeleteRolePolicy` (so step 3 can still run through CI). Kept the spec's
  name `aa-cis-dev-app-deploy` (explicit deny) instead of renaming it out of the pattern.
- **Review fix: OIDC provider is bootstrap.** The apply role's `OIDCProviderManage` is replaced by a
  read-only `OIDCProviderRead`, and the boundary denies all OIDC/SAML provider writes.
- **Review fix: plan role secrets narrowed** to exactly the secrets Terraform refreshes
  (`local.tf_plan_secret_arns`: 3 TripPlanner secret versions, 2 ACP secrets, the admin secret).
  `booking/dev/*`, the RDS DSN, JWT and OpenAI secrets are no longer readable from a PR run.
- **Bootstrap applied by a human.** The new roles/policies are outside what the apply role may touch
  (by design) and the old role lacks `iam:CreatePolicy` and TagRole for the new names, so this PR is
  applied locally with the MFA admin profile. That also avoids the "grant + use in one apply"
  propagation trap (lessons: S225 AA-750).
- **Review fix (blocker): generous stage default, tight limits only on LLM-cost routes.** The first
  cut put 20 rps / burst 40 on every route via `default_route_settings`. AA-TripPlanner-Web
  `frontend/components/MapView.tsx` fetches one `/browse/tiles/{id}` per 1-degree cell with
  `Promise.all` on every moveend / filter change, so one viewport is a burst of dozens of requests on
  the same `ANY /browse/{proxy+}` bucket and normal panning would get 429s. The default is now
  500 rps / burst 1000 (variables, Dev placeholders). Tight limits stay only where a request costs
  money: narrate (2 / 5) and a new dedicated `GET /browse/search` route (10 / 20) on the same browse
  integration (`backend/browse/search.py` makes one Cohere embedding call per query; the frontend
  debounces typing in `FilterChips.tsx`). Path checked end to end: `lib/api.ts` `search()` ->
  BFF `app/api/browse/route.ts` (`resource=search` -> `GET /browse/search?q=...`) ->
  `backend/browse/handler.py` `_SEARCH_RE = ^/browse/search$`. Narrate: `lib/api.ts` `narrate()` ->
  BFF `app/api/trip/route.ts` `op: narrate` -> `POST /trip/{id}/narrate` -> `_NARRATE_RE`.
  The existing Lambda permission (`source_arn .../*/*`) already covers the new route.
- **Narrate throttle via a dedicated route.** `POST /trip/{trip_id}/narrate` → same assembly
  integration. The handler routes on `requestContext.http.path`
  (AA-TripPlanner-Web `backend/assembly/handler.py`), so the route key does not change behaviour.

## Changed

- `cicd.tf`: inline statements moved into `local.cicd_inline_statements` (rendered policy identical)
  + new `IAMPolicyRead` statement so the old role can refresh the new customer-managed policies
  during the transition.
- New `cicd_split.tf` (roles, policies, boundaries, outputs).
- `tripplanner.tf`: narrate route and `GET /browse/search` route; `default_route_settings` +
  two `route_settings` on the `$default` stage. `tripplanner_variables.tf`: six throttle variables
  (default 500/1000, narrate 2/5, search 10/20 — all Dev placeholders).
- `variables.tf`: `tf_apply_require_boundary_on_role_policy_writes` (phase-3 switch, default false).
- Docs: `docs/ci-role-split.md` (cut-over plan), `docs/waf-count-review.md` (CountedRequests review
  runbook), CONTEXT.md.
- Not changed: `aa-cis-dev-role` trust/managed policies, workflow files, `waf_common_rules_count_only`.

## Tradeoffs

- Requiring the workload boundary on *policy writes* to existing roles would block every role change
  today (no existing role has a boundary), so phase 1 only requires it on CreateRole; the stronger
  rule is a variable flipped after step 4. **Until then the apply role can escalate**: rewrite the
  policy or trust of an unbounded `aa-*-dev-*` workload role (e.g. the ECS task role), PassRole it
  to a task/Lambda it can start, and run code with rights the boundary denies the apply role. The
  `sts:AssumeRole` deny does not stop this (no AssumeRole call). Only steps 3 + 4 + phase 3 close
  it; until then the guard is procedural (prod environment = reviewed main). Phase 3 cannot cover
  `UpdateAssumeRolePolicy` / `PassRole` (AWS does not set `iam:PermissionsBoundary` for them), but
  with every role bounded those only ever yield workload-boundary rights.
- Narrowing the plan role's secrets means a new `aws_secretsmanager_secret_version` must be added to
  `local.tf_plan_secret_arns` (local apply) or plan fails on refresh. Accepted: new secret versions
  are rare, and the alternative exposes every dev secret to any PR branch.
- Plan role uses `ReadOnlyAccess` (broad read, including S3 object reads) instead of a hand-made
  read list: a narrow list breaks plan whenever a new resource type is added. Secret values: limited
  to the stack's name prefixes; they are in the state file the role reads anyway.
- Throttle numbers are Dev placeholders, not capacity numbers (open question for Nghiệp): default
  500 rps / burst 1000 **per route** (was 20 / 40, which broke the map tile fan-out) (stage `default_route_settings` applies to each route without its own
  `route_settings` separately — `ANY /browse/{proxy+}` and `ANY /trip/{proxy+}` each get a bucket;
  it is not one stage-wide cap), narrate 2 rps / burst 5, search 10 rps / burst 20. The generous
  default means the non-LLM routes are effectively capped only by Lambda concurrency and the account
  limit; acceptable for Dev because they only hit the DB, while every LLM-cost route has its own
  tight bucket. A new LLM-backed path must get its own route + `route_settings`, or it inherits
  the generous default. Limits are shared by all callers; HTTP
  APIs have no usage plans / per-client limits.

## Should know

- Expected step-1 plan (local admin apply): creates in `cicd_split.tf`, create of the narrate and
  search routes,
  in-place update of `aws_iam_role_policy.cicd_inline` and `aws_apigatewayv2_stage.tripplanner`,
  replacement of `time_sleep.wait_for_iam_propagation` (trigger hashes `cicd_inline.policy`).
- Bootstrap (local apply only): the three new roles, both boundaries, the OIDC provider,
  `aa-cis-dev-agent-session`, `aa-cis-dev-role` and `local.cicd_inline_statements` (feeds both the
  legacy and the apply role), `local.tf_plan_secret_arns`.

- After step 1, a new `aws_iam_role` in any later PR must set
  `permissions_boundary = aws_iam_policy.workload_boundary.arn` once CI applies with the new role.
- `local.tf_managed_role_arns` is the list of role names the apply role may manage. A role named
  outside `aa-*-dev-*` (other than the NAT role) cannot be managed by CI apply.
- Validated locally, in `accounts/aa365` only: `terraform fmt -check` and `terraform validate`
  (init `-backend=false`). `terraform fmt -check -recursive` from the repo root fails on
  pre-existing files outside this diff (acc1-bedrock/main.tf, acc3-bedrock/batch.tf,
  envs/dev/terraform.tfvars, modules/monitoring/main.tf) — not touched here. No plan against real
  state. Apply boundary policy size estimated offline at ~3.2 KB (managed policy limit 6,144). Rendered inline policy size measured offline:
  old role ~6.7 KB minified, apply base ~5.7 KB (+ three statements), under the 10,240-char limit.
- Policy semantics (boundary conditions, `ecs:task-definition` condition) are not unit-testable
  offline; the real check is the first plan/apply and the step-2 smoke runs.
