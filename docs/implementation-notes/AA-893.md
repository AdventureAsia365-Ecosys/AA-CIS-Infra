# AA-893 — Alarm catalog with runbook links and core Terraform outputs (generated docs)

Step 1 part A (runbook URL in every metric alarm description) shipped in S243 (Infra #213, applied).
This change finishes step 1 (generated alarm catalog + runbook link check) and does step 2 (root
outputs + docs-gen workflow with a bot PR into the root repo).

Branches: Infra `chore/generated-alarm-catalog`, root `docs/generated-alarm-catalog`.

## Decisions

- **One generator, state JSON as the source.** `tools/docs/gen_docs.py render` reads
  `terraform show -json` (state) or `terraform show -json tfplan` (plan; same `root_module` shape under
  `planned_values`). The state already holds every alarm (for_each expanded, interpolations resolved)
  and the outputs, so `terraform output -json` is not read separately. Parsing HCL was rejected: the
  descriptions are built from locals and `for_each`, which only Terraform evaluates.
- **Pages live in the root repo, `docs/generated/`.** The issue says "bot PR into root"; the doc
  catalog said `INF docs/generated/...`. Root wins: the runbooks are in root, so the relative links are
  checked by root's docs lint (lychee + the new check); root has no required CI, so a bot PR can be
  merged by hand, while a bot PR into Infra (branch protection, PRs opened with `GITHUB_TOKEN` trigger no
  CI) could never go green. Catalog rows OPS-07, ARCH-02/03/04 updated in the same root PR (same model
  as APP-03: "G in INF, PR into root").
- **Read-only role.** docs-gen.yml has no environment, so its OIDC sub is `ref:refs/heads/main`. The
  plan role `aa-cis-infra-tf-plan` (ReadOnlyAccess) now trusts that subject too; the repo-level
  `AWS_ROLE_ARN` secret already names the plan role (terraform-plan.yml). The job also fails closed if
  the assumed role is anything but `aa-cis-infra-tf-plan`. A new dedicated role was rejected: same
  rights, one more bootstrap object.
- **Runbook marker also on EventBridge alarm rules.** The three identity rules that e-mail the alerts
  topic carry `${local.runbook_suffix.*}` in the rule description (read by the generator) and in the
  target input_template (the e-mail). Mapping: break-glass secret access → `break_glass`; denied
  secret read and WORKFORCE AdminCreateUser → `incident`.
- **Missed alarm fixed:** `cis_app_too_many_connections` (X1 S18, added after step 1) had no runbook;
  now `database`.
- **Guard in three places:** `check-source` (offline, PR CI in Infra `docs-gen-test.yml`): every
  `aws_cloudwatch_metric_alarm` and every SNS-targeting event rule + its input_template has a runbook
  suffix. `render --root-dir root` in docs-gen.yml: the URL is under root `docs/` and the file exists.
  Root `tools/docs/check_alarm_runbooks.py` in docs-lint: every row links to an existing file (catches
  a runbook renamed or deleted in root later).
- **Publish rule:** a page goes into the bot PR when its body fingerprint (`<!-- docs-fingerprint -->`,
  sha256 of the body, excluding front-matter date, sha and source line) differs from root master, when
  it is missing there, or when master's copy is older than 30 days (`review_every_days: 45`, so the
  freshness report stays quiet). Nightly runs with no change open nothing.
- **Inventory scope:** every managed resource, grouped by the `App` tag; configuration sub-resources
  (API GW methods, bucket configs, policy attachments, records, ...) are counted, not listed.

## Tradeoffs

- The plan role may now be assumed by any workflow on `main` that asks for it (sub `ref:refs/heads/main`).
  That is narrower than today (any PR branch can already assume it through `pull_request`) and the role
  stays read-only (ReadOnlyAccess + lockfile + two TripPlanner secret values it already reads for plans).
- The state JSON holds secret values in clear text on the runner: kept in `RUNNER_TEMP` with umask 077,
  deleted by a trap, never uploaded; the generator reads whitelisted attributes and skips sensitive
  outputs (unit test asserts a planted secret never reaches a page). Only the rendered pages go to the
  artifact and the root PR. The pages hold IDs, ARNs and client IDs: fine in the private root repo (the
  resource-id lint exempts generated pages), never copy them into an app repo.
- The first root pages were rendered locally from the plan JSON of this branch (admin MFA session,
  read-only plan) so the root PR shows real content and its lint proves every link resolves. After the
  apply, docs-gen renders the same body from the state; the fingerprints should match, so the first bot
  run opens a PR only if something drifted.
- Budgets and the Cost Anomaly subscription also notify the alerts topic but are not alarms (no
  description to carry a runbook); they are in the inventory, not in the alarm catalog.
- acc1 / acc3 roots (Bedrock and Cost Explorer satellite roles) are not covered: no state read for them.
