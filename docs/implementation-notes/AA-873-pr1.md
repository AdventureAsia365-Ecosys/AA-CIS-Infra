# AA-873 PR 1 (S255) — account security baseline, free items + bootstrap grants

Session S255 (28/10/2026), Claude Code Infra lane. Branch `feat/aa-873-security-baseline-free`.
Source: root audit `docs/audits/2026-10-28-S255-finops-security/` §7 (decision D3 step 1) and its draft
`tf/acc2_security_baseline.tf`. PR 2 (`feat/aa-873-cloudtrail-kms`, notes `AA-873-pr2.md`) and PR 3
(`feat/aa-873-guardduty-gated`, notes `AA-873-pr3.md`) build on the grants of this PR.

## Decisions

- **Split as the audit proposed**: (1) free items here, (2) CloudTrail/KMS/bucket, (3) GuardDuty behind a flag.
- **All AA-873 apply-role grants ship here, in one bootstrap policy** (`cicd_sec.tf`, `aa-cis-infra-tf-apply-sec`),
  so one local MFA apply covers the three PRs. Measured with `terraform console` on a local-backend copy of main
  82400b9: the apply role's inline policy renders to **8,963 / 10,240** characters; the same grants inline made it
  **10,156** (84 left). So they go in a customer managed policy like `cicd_crm.tf`. The role already has 10 managed
  attachments (default quota), so **AmazonSQSFullAccess moves into the new policy unchanged** (`sqs:*` on `*`, Sid
  `SqsManage`) and frees its slot. Net permissions for SQS: identical.
- **Boundary**: the new policy ARN joins `DenyBoundaryPolicyEdits` (CI cannot edit or tag it), like the CRM policy.
- **KMS scope = keys tagged `App = shared`** (the trail key carries `local.shared_tags`): create only with the tag,
  refresh/rotation/alias/cancel-deletion only on such keys, untag anything but `App`. No `PutKeyPolicy`,
  `ScheduleKeyDeletion`, `DisableKey`, grants or crypto: those stay local MFA, as for the CRM keys.
- **Expected-change principals = only `aa-cis-infra-tf-apply`.** The draft also listed `aa-cis-infra-tf-apply-crm`,
  which is a policy, not a role. Local MFA applies by the admin role DO alert; that is intended (planned change, the
  e-mail says so).
- **Alerts topic policy**: new statement `AllowSecurityEventBridgeRules` for `rule/aa-sec-<env>-*`. The draft missed
  it: the topic only lets EventBridge publish from `aa-identity-*` and `aa-crm-*` rules, so without it every
  `[aa-sec]` e-mail would have been dropped silently.
- **Forwarder role** carries the workload boundary (CLAUDE.md rule; the draft had none) and is named
  `aa-sec-dev-events-forwarder` (inside `aa-*-dev-*`, so `IAMRoleManageStack` covers create + PassRole).
- **Forward only IAM write calls** (`readOnly = false`) plus every root event: Terraform plan/drift jobs make
  thousands of IAM reads a day, which the draft would have forwarded for nothing.
- **Access Analyzer e-mail uses scalar fields only** (`id`, `resource`, `resourceType`, `isPublic`): the draft put
  `$.detail.principal` (an object) into a quoted template, which would break the JSON string.
- **Runbook** = `incident` (incident-response.md); `gen_docs.py check-source` passes. A dedicated security-alert
  runbook in the root repo is a follow-up, not needed for the guard.

## Tradeoffs

- One bootstrap for three PRs means PR 1 grants KMS/GuardDuty rights before they are used; they are scoped and
  harmless until then, and it saves two more MFA windows.
- IAM/root alerts depend on CloudTrail delivering us-east-1 events to EventBridge there. With today's single-region
  trail that is not guaranteed, so the IAM/root half is proven only after PR 2 makes the trail multi-region.
- SG/IAM changes by the CI apply role are not alerted (otherwise every apply mails). A compromised CI role is covered
  by the trail-tamper rule, GuardDuty (PR 3) and CloudTrail itself, not by these two rules.
