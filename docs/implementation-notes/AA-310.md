# AA-310 — ECS `stopTimeout` for graceful shutdown drain (AA-295 Direction 3)

Session S196 (24/09/2026, Claude Code). Branch `fix/aa-310-ecs-stop-timeout`.

## Evidence gathered before choosing the number (read-only, 24/09/2026)

- **Job durations** (`shared.pipeline_jobs`, all time, 148 `run_tour` jobs, 17–21/09):
  p50 759s (~13 min), p90 1460s, p99 2256s, max 2297s (~38 min). 0 jobs in `interrupted`.
- **Shutdowns in the last 14 days** (CloudWatch `/ecs/aa-cis-dev`, retention 14d): 20 task
  shutdowns, each `Shutting down → Application shutdown complete` in ~0.1s. **Zero**
  `shutdown_draining_background_tasks` / `run_tour_job_cancelled` events → no deploy or Spot stop
  happened while a background job was running inside the retention window.
- ECS service events: normal rolling deploys (start new → stop old → deregister target), no Spot
  interruption events in the last 40 events.
- Service uses `FARGATE` base 1 + `FARGATE_SPOT` weight 3.

## Decisions

- **`stopTimeout = 90`** (container definition, `modules/ecs/main.tf`).
  Shutdown budget: uvicorn in-flight HTTP requests (LLM-backed endpoints 15–30s) + lifespan drain
  (`asyncio.wait(..., timeout=25)`) + pool/redis close + `CancelledError` → `mark_interrupted()`
  (own asyncpg connection) on still-pending jobs. ≈60s worst case; 90s gives margin.
- Not 120: 120 is the Fargate hard cap and equals the Spot 2-minute notice exactly — no margin for
  ECS's own stop handling on Spot. 90 stays safely inside both.
- Not bigger than needed on purpose: a longer timeout only matters when shutdown hangs; normal
  shutdowns take 0.1s, so there is no deploy-speed cost either way.

## Changed vs. the issue

- The issue asked to first observe one real rolling deploy during a running job. That never
  happened in the 14-day log window (jobs ran only 17–21/09, no deploy overlapped). Reproducing it
  would require a paid LLM job + a forced deploy. Proceeded without it because the issue's concern
  ("don't change App + Infra at the same time") no longer applies — the App drain code is
  unchanged since July (PR #72), so this PR is the only variable.
- Measured job length shows the issue's framing needs a correction: no `stopTimeout` (max 120s)
  can let a `run_tour` job finish. The value of this change is only that pending jobs get marked
  `interrupted` cleanly (and pools close) instead of being SIGKILLed mid-write. The boot-time
  `sweep_interrupted()` (AA-223) remains the backstop if SIGKILL still wins.

## Tradeoffs

- Task definitions are immutable → `terraform plan` shows `aws_ecs_task_definition.api` replaced
  (new revision). The service has `lifecycle.ignore_changes = [task_definition]`, so **apply does
  not roll the service by itself**.

## Should know

- Activation path: after `terraform apply` registers the new revision, the **next App
  "Deploy Dev"** copies the latest revision of the family (`describe-task-definition` → jq swaps
  only the image → `register-task-definition`), so `stopTimeout: 90` carries into every later
  revision. Until an App deploy happens, the running task keeps the 30s default.
- Verify after activation: `aws ecs describe-task-definition --task-definition aa-cis-dev-api
  --query 'taskDefinition.containerDefinitions[0].stopTimeout'` → `90`.
- Apply is human-only + MFA (ADR-2026-023); then `terraform plan` again must show no drift.
