# AA-993 Phase E, slice I1 — narrow auto-apply role, environment and ruleset on main

Design: root `docs/audits/2026-10-26-S252-aa993-delivery-pipeline/design.md` §2 I1, critic point 1; root ADR 0017
decisions 6 and 8 (Proposed); root ADR 0011a (Proposed, same session) for the ci-bot rights this enables later.
Nothing in this slice applies SQL or runs a task: M3 (`migration-apply.yml`) is the first user of the role.

## Decisions

- **Role in its own file** (`accounts/aa365/cicd_db_auto_apply.tf`), not in `cicd_split.tf`: another lane (AA-873)
  edits `cicd_split.tf` this session, and the role is a separate job type. Same trust shape as
  `aa-cis-dev-app-deploy`: `sub = <infra prefix>:environment:dev-db-auto` AND `ref = refs/heads/main`.
- **Bootstrap object.** The name `aa-cis-infra-db-auto-apply` is outside `aa-*-dev-*`, so the CI apply role cannot
  create, change or pass it (`DenyRoleWritesOutsideStack`). That is the point (a merged PR cannot widen it through a
  CI apply), and it means a human applies it locally with MFA. Boundary: `aa-workload-boundary` (no IAM writes).
- **Grants = what `migrator-task.sh` + the run step of `db-migrate.yml` call**, nothing more: list/describe task
  definitions (unscoped by AWS), describe the CIS api service, register/run the migrator family only (run limited
  to the CIS cluster), describe tasks of the cluster, PassRole on the two migrator roles only (to ECS tasks),
  `ec2:DescribeSubnets/SecurityGroups`, S3 put/get/delete on `aa-cis-bronze-…/db-auto-apply/*` (+ ListBucket on that
  prefix), `logs:GetLogEvents` on `migrate/migrate/*` streams. No RDS snapshot (auto-apply never runs destructive
  files), no secret read (the task role reads the DSN), no service update.
- **`ecs:DeregisterTaskDefinition` on `*`**: the ECS service authorization reference lists no resource type for it.
  The script refuses ARNs outside the family; worst misuse = a deregistered revision (running tasks keep running).
  Proof step 3 below confirms with `simulate-principal-policy`.
- **New S3 prefix `db-auto-apply/`** instead of DB Migrate's `db-migrate/`, so the two flows never touch each
  other's uploads. M3 must use it.
- **Ruleset (tools/github/infra-main-ruleset.json)**: target `~DEFAULT_BRANCH`; rules deletion, non_fast_forward,
  pull_request (0 approvals in the dev phase, squash only), required checks `Terraform Plan (dev)`, `gitleaks`,
  `Copies match owner main`, `Migration lint and unique numbers`, each pinned to the GitHub Actions app
  (`integration_id` 15368) so no other App can post a passing status with the same name. Not strict (no
  "up to date" requirement: Infra has no merge queue and the squash-from-stale-branch lesson is covered by
  `git diff --stat origin/main...HEAD` before merge). Bypass: `OrganizationAdmin` with `bypass_mode: pull_request`,
  i.e. Nghiệp can merge a PR without the checks but nobody, Nghiệp included, can push to `main` directly. The
  agent's App and the ci-bot App are not bypass actors.
- **GitHub settings by script, not Terraform**: there is no GitHub provider in this repo and the Apps have no
  Administration permission (ADR 0011 d1). `tools/github/db_auto_apply_gate.sh` runs with Nghiệp's `gh` login.
- **The environment's secret `AWS_ROLE_ARN`** holds the role ARN (repo is public: ARNs are secrets, lesson S249).
  The script reads the ARN with the admin profile and pipes it to `gh secret set`; it is never printed.
- **Proof workflow `db-auto-apply-role-check.yml`** (manual, read calls only) gives live proof 4 now, before M3
  exists. M3 may delete it.

## Changed vs the design

- **Migration Copy Guard runs on every PR** (no `paths` filter), with a new `scope` job that skips the other jobs
  when the PR touches none of the old filter's paths (`db/migration_guard_scope.py`; a skipped job satisfies a
  required check). The design named the guard as a required check but every guard job was path-filtered, and a
  required check whose workflow never starts blocks every unrelated PR. `Terraform Plan (dev)` and `gitleaks`
  already run on every PR. `scripts/pre-push.sh` keeps the same list; a unit test keeps both lists equal and checks
  that every required check is a job of a workflow with no PR path filter.
- **`classify` is not a required check yet**: it does not exist until M2b. M2b adds it to the JSON and re-runs
  `db_auto_apply_gate.sh ruleset`.

## Tradeoffs

- 0 required approvals: the dev-phase rule (DM-11.5) has the agent merge after green CI; the ruleset's job here is
  "no direct push + green checks", which is what critic point 1 asked for. From the first prod, raise
  `required_approving_review_count` and turn on code-owner review (AA-880).
- A required `Terraform Plan (dev)` fails on S3 state-lock contention when two Infra PRs plan at once (lesson S243):
  re-run the plan; that was already the merge discipline.
- The `scope` job costs ~10 s on PRs that used to start nothing; free while the repo is public.

## Should know

- **Order:** merge → local MFA apply of the two role resources → `db_auto_apply_gate.sh env` → `secret` →
  `ruleset` (after merge: open Infra PRs created before it need one new push or a close/reopen so the guard's
  `scope` job reports) → proofs.
- **Live proofs:** (1) `db_auto_apply_gate.sh show` lists the ruleset; (2) a direct push of a no-op commit to
  `main` with an App token is refused (`GH013`); (3) `aws iam simulate-principal-policy` on the role: PassRole of
  `aa-cis-dev-ecs-task-role` denied, PassRole of the migrator task role allowed, RunTask of `aa-cis-dev-api` family
  denied; (4) dispatch `DB auto-apply role check` from `main` = green, from a branch = refused by the environment.
- **Rollback (exact):** `tools/github/db_auto_apply_gate.sh rollback` (deletes the ruleset and the environment with
  its secret); `terraform destroy -target=aws_iam_role_policy.db_auto_apply -target=aws_iam_role.db_auto_apply` from
  `accounts/aa365` with MFA (nothing uses the role before M3); revert the PR to restore the guard's path filter. Each
  step is independent: the ruleset can be deleted alone if it blocks a merge unexpectedly.
- When AA-CIS-Infra goes private (ADR 0014), the ruleset and the environment branch rule stop being enforced on
  GitHub Free: set `DB_AUTO_APPLY=false` that day (ADR 0017 d8).
