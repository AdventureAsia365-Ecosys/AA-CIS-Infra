# AA-284 — SNS alerting + CloudWatch alarms (S102 Phase 3a)

Repo/file: `accounts/aa365/observability.tf`

## Decisions

- Re-created `aa-cis-dev-acp-alerts` as a fresh SNS topic on account 2
  (005097885195). The AA-61 original (account 1, 867490540162) is gone with
  the account decommission — this is a new build, not an import.
- DLQ-depth alarm: created one per queue (all 6 in `module.sqs`), not just
  one. AA-61's original scope covered a single DLQ, but since the account-1
  definition no longer exists there was nothing to confirm which queue it
  was — covering all 6 is the safer default given the low cost of a CloudWatch
  alarm.
- Alarm evaluation: `threshold = 0`, `comparison_operator =
  GreaterThanThreshold`, `period = 300` — matches the task's exact spec ("DLQ
  depth > 0, period 300s").
- Added `dlq_names` output to `modules/sqs_sns` (previously only `dlq_arns`
  existed) — needed a queue-name dimension for the CloudWatch alarm, ARNs
  don't work as the `QueueName` dimension value.

## Changed vs. original ask

- Proposed additions from the task (RDS CPU > 80%, ECS RunningTaskCount <
  DesiredCount) were implemented, not just proposed in prose — but flagged
  clearly in code comments and the PR description as open for Nghiep to
  drop.

## Tradeoffs

- ECS `RunningTaskCount` alarm depends on Container Insights being enabled on
  `aa-cis-dev-cluster`. It is not currently known whether Container Insights
  is enabled — enabling it would touch `modules/ecs`, out of scope for this
  PR. If it's off, the alarm will sit in `INSUFFICIENT_DATA` and never
  fire — `treat_missing_data = "notBreaching"` prevents it from falsely
  alarming in that case, but it also means it's silently inert. Follow-up
  needed if Nghiep wants this alarm to actually work.
- SNS topic subscription (email) cannot be auto-confirmed by Terraform —
  stays `PendingConfirmation` until Nghiep clicks the email link.

## Should know

- All new alarms point at the same `aws_sns_topic.alerts` — one topic, no
  severity routing/separate channels.
- No CloudWatch Logs / Container Insights changes were made anywhere in this
  PR — purely additive alarm resources.
