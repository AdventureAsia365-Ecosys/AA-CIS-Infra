# AA-931 — CRM-03 Infra bootstrap + CloudFront VPC-origin spike

Source: root `docs/audits/2026-10-21-S246-crm-design-v3/design-v3.md` §6.3 card CRM-03, §4.1 (keys and buckets),
§6.5 (who applies what), lane `delivery-plan.md` CRM-03 (T1, V3, N3 b) and `final/crm-design-final.md` §4.

## Decisions

- **Reuse the existing internal NLB** (`aa-cis-dev-nlb`, the API Gateway VPC-link NLB) as the CloudFront VPC origin.
  It is already internal, in the private subnets, has a security group (a VPC-origin requirement) and a plain TCP :80
  listener (VPC origins refuse an NLB with TLS listeners). A second NLB would cost ~$18/month plus LCU for no gain.
  Both private subnets are in usw1-az1 / usw1-az3 (checked 22/10/2026); VPC origins do not support usw1-az2.
- **Source IP problem, handled both ways.** The AWS guide lets the origin admit CloudFront either by the
  `com.amazonaws.global.cloudfront.origin-facing` prefix list or by the service SG, so VPC-origin traffic most likely
  arrives with a CloudFront origin-facing (public) source IP, and an NLB with an `alb` target type always preserves
  the client IP to the ALB. So:
  - NLB SG: extra ingress :80 from that prefix list (the NLB is internal: only VPC-origin traffic can carry those IPs);
  - ALB: a second SG `aa-cis-dev-sg-alb-from-nlb` that admits :80 from the NLB SG (AWS's recommended rule for targets
    of an NLB with a SG). The ALB SG itself is NOT opened to the prefix list: the ALB is still internet-facing, and a
    prefix-list rule there would let any third-party CloudFront distribution reach the ALB and skip API Gateway.
  - If the spike shows the source is NATed to a VPC IP instead, the old VPC-CIDR rules already admit it and the two
    new rules are inert. The spike's `/whoami` answers which case is real (X-Forwarded-For as the ALB saw it).
- **Secret origin header `X-AA-Origin`** (random_password, 48 alphanumerics) added by CloudFront to every origin
  request. ALB HTTP listener rules (priorities in one map, `accounts/aa365/alb_rules.tf`):
  - 10 `crm_spike_partner`: Host = `partner-dev.lumiguides.it.com` AND `X-AA-Origin` = secret → spike target group;
  - 20 `crm_origin_deny`: any `X-AA-Origin` → fixed 403;
  - 100 `booking` (unchanged); default → CIS api (unchanged).
  So anything that came through CloudFront (raw `*.cloudfront.net` name, any other Host) gets 403 and can never reach
  CIS or Booking; an API Gateway caller cannot reach the partner rule (API Gateway rewrites Host to the NLB name, and a
  guessed header without the secret falls into the 403 rule).
- **WAF (shared REGIONAL ACL on the ALB): new rule `CloudFrontOriginAllow`** (priority 3, after CommonRuleSet and
  VpcLinkInternalAllow; RateLimit1000 4, GeoBlockNonAllowed 5, were 3 and 4). With a preserved CloudFront source IP the
  geo rule would judge the *edge's* country and the rate rule would count a whole edge as one client, so a viewer
  outside the 10-country list could be blocked (the "E" case). Requests carrying the exact secret are allowed after
  the content rules. `x-aa-origin` is added to the WAF log redaction list.
- **CloudFront**: VPC origin `http-only` :80, origin read timeout 60 s (the max without a quota increase; the default
  30 s would cut a 30 s SSR response), keepalive 60 s, managed `CachingDisabled` + `AllViewerAndCloudFrontHeaders-2022-06`
  (forwards the viewer Host the ALB rule needs, plus `CloudFront-Viewer-Address` for the later app rate limits),
  `compress = false` (no buffering of streamed SSR), PriceClass_200 (Asia edges), no WAF (W8), no logs.
- **Hello container without an image build**: `public.ecr.aws/docker/library/python:3.12-slim` (ARM64) running
  `accounts/aa365/assets/crm_spike/server.py` passed as `python3 -c`. Endpoints: `/` (HTML, flushed in two chunks),
  `/stream?seconds=N` (one chunk per second, N ≤ 60), `/slow?seconds=N` (first byte after N s, N ≤ 55), `/whoami`
  (Host, X-Forwarded-For, CloudFront-Viewer-* and whether `X-AA-Origin` was present, never its value), `/health`.
  No task role, ECS exec off, FARGATE_SPOT only, `desired_count = 0` + `ignore_changes` (scaled by hand for the check).
- **Apply-role grants as a customer managed policy** `aa-cis-infra-tf-apply-crm`, not inline: the role's inline
  policies share one 10,240-character limit that earlier PRs already had to trim (AA-846). The role already had the
  default quota of 10 managed policies, so `AWSStepFunctionsFullAccess` is detached in the same apply: no Step
  Functions resource exists in any root since AA-750 (`grep aws_sfn` = 0) and its only other useful action,
  `iam:ListRoles`, is also in `AWSLambda_FullAccess`. No quota request needed.
- **Grants content** (`cicd_crm.tf`):
  - CloudFront VPC origins, origin request policies, functions (the P2b `/trip/*` 301 may use one), plus
    `iam:CreateServiceLinkedRole` only for `vpcorigin.cloudfront.amazonaws.com`;
  - `elasticloadbalancing:SetSecurityGroups` on the CIS ALB / NLB only (the second ALB SG);
  - ECR create/configure on `aa-crm-<env>-*` (like Booking);
  - KMS: `CreateKey` + `TagResource` only with request tag `App=crm`; aliases only under `alias/crm-*`; describe /
    rotation / description / tag reads on keys tagged `App=crm`; untag of any key except the `App` key. **Not granted:**
    `PutKeyPolicy`, `ScheduleKeyDeletion`, `DisableKey`, `CreateGrant` and every crypto verb;
  - EventBridge rules `aa-crm-*` (CRM-04 key alarms, SES bounce events), SES contact lists (one-click unsubscribe).
  - Already covered, nothing added: S3 Object Lock (AmazonS3FullAccess), Cognito pools/clients/resource servers/
    domains (CognitoUserPoolManage), SES identities, configuration sets and receipt rules, ACM, Route 53, budgets,
    roles named `aa-crm-dev-*` (IAMRoleManageStack, workload boundary required).
- **Boundary denies** (`aa-cis-infra-tf-apply-boundary`), so a later key-policy or bucket-policy edit cannot widen the
  CI role: on keys tagged `App=crm` deny Decrypt/Encrypt/GenerateDataKey*/ReEncrypt*/Sign/CreateGrant/PutKeyPolicy/
  ScheduleKeyDeletion/DisableKey; on `aa-crm-*-audit-*` buckets deny `BypassGovernanceRetention`,
  `PutObjectLegalHold`, `PutObjectRetention` and object deletes. The new managed policy joins `DenyBoundaryPolicyEdits`.

## Tradeoffs

- Prefix-list ingress on the NLB SG (option 1) instead of the service-managed SG (option 2): option 2 is tighter but
  the SG only exists after the VPC origin is created (two applies or a fragile data source). The NLB is internal, so
  option 1 admits nothing extra in practice; CRM-04 may switch to option 2.
- The origin secret sits in state, in the ALB rule, the WAF rule and the distribution config (readable by the
  ReadOnlyAccess plan role). It is defence in depth on top of the network path (internal NLB, ALB SG) and the Host
  rule, not the only control. Rotation = `terraform apply -replace=random_password.crm_origin_verify` (guarded type).
- `AllViewerAndCloudFrontHeaders` forwards every viewer header to the origin; fine for an SSR app that needs cookies.
- Spot only for the hello task: an interruption just means re-running the check.
- The web ACL is shared with the REST API stages once `waf_protect_rest_api_stages` is turned on (false today). A
  caller who knows the secret could then skip rate + geo on those stages too. Accepted: the secret is readable
  only by principals that can already read the whole config; rotate it if it leaks.
- CloudFront → NLB is plain HTTP inside the VPC origin. Fine for Dev; Go-real (W8) can switch to TCP :443 on the
  NLB passing through to the ALB HTTPS listener if end-to-end TLS is required.
