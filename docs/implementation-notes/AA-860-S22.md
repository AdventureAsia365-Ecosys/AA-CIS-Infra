## Decisions
- **Master DSN read in the task, by code, only for the three master uses** (`roles/` files, `set-password`,
  `run-script`): `connect_master()` connects with `DATABASE_URL` first and keeps that session when it is already the
  master (before the Terraform switch, or after a rollback of it), else closes it, reads `MASTER_SECRET =
  "aa-cis/dev/rds"` with boto3 (migrator **task** role) and connects with `ssl="require"`. Each run logs
  `master login: …` (where the DSN came from, never the DSN). The existing `session_user` checks stay after it, so an
  in-task DSN of anyone else still exits 8. Keyed on the live login, not on parsing the DSN, so the same runner works
  on both sides of the Terraform apply and needs no ordering between merge and apply.
- **`run-script` keeps the master** (S242 amendment and S19: master-level ECS-exec scripts moved there), although
  the S22 step text names only `roles/`, set-password and extensions. Extensions live in `roles/`, so they are covered.
- **Exit 8 for a missing master** (secret unreadable / empty / login failed): same class as "not the master"; the
  messages carry the AWS error code or the SQLSTATE only (`_redact` also covers both DSNs in run-script errors).
- **Owner-dir files never read the master secret**: check/apply of `cis/`, `booking/`, `tripplanner/` keep the
  `DATABASE_URL` login and the XD8 switch unchanged. Verified, not changed: with `db_migrator` as login every dir is
  switched (`cis_owner`, `bk_owner`, `tp_owner`), and a dir whose anchor schema is still the master's is refused
  (`db_migrator` is not a member of the master) — new tests pin both.
- **Terraform:** task definition secret → `aws_secretsmanager_secret.db_migrator.arn` (H6, the one underscore line,
  edited by the agent with Nghiệp's OK this session); execution role `InjectMigratorDsn` → that secret only; task role
  list unchanged (master for the in-task reads, `db-migrator` for `set-password role=db_migrator`, the runtime DSNs for
  the probe). `migrator-task.sh check-base` already accepts the `db-migrator` secret (S12).
- **Schema dump / probe need no code change for the login**: both read `DATABASE_URL` (now `db_migrator`), and
  `db_migrator` inherits every owner role + `pg_read_all_stats`. The probe already keys `sessions.master_break_glass_only`
  on `catalog_login_not_master`; its isolation cells already use each runtime role's own DSN. Added only a
  `DUMP login=<role>` line to the dump (verify evidence, not in the JSON).
- **`owners.yaml`:** new `master_secret` (mirrored by `MASTER_SECRET`, registry test) and `migrator_secret`; cis
  `owner_role_today: cis_owner` (245 is applied); text of `master_role` / `migrator_role` says who logs in now.
- **XD9 wording:** the runner's catalog-recipe message no longer says "frozen until S22"; it names the recipe, "never
  RESET ROLE" and the login requirement (the reach check still refuses the recipe under a master login).

## Tradeoffs
- One extra short `db_migrator` session per `roles/` / set-password / run-script run (to learn the login) before the
  master session; within `CONNECTION LIMIT 5` and simpler than parsing the DSN user.
- The task role can still read the master for every run of the family (IAM cannot tell modes apart). The runner is
  the boundary: only the three modes call `connect_master`; the runner itself comes from `main` (reviewed) via a
  presigned URL. Narrowing further would need a second task definition just for master work: not worth it on Dev.
- Pre-existing `terraform fmt` drift in `accounts/acc1-bedrock/main.tf`, `accounts/acc3-bedrock/batch.tf`,
  `modules/monitoring/main.tf` (not touched, no CI fmt gate); `accounts/aa365` is fmt-clean.
