# AA-830 — bk-011 copy + DM-4.2 soft-key orphan check in the nightly dump (S238)

Infra half of AA-830 (data standards X3). Booking adds the catalog tour key to `booking.trip_case_legs` (bk-011,
AA-Booking branches `feat/aa-830-bk-011` then `feat/aa-830-trip-case-leg-key`); TripPlanner sends
`inquiry.submitted` v1.2 (`feat/aa-830-leg-catalog-key`); the root repo carries the contract and registry
(`feat/aa-830-inquiry-v1-2`).

## Decisions

- **`db/migrations/booking/011_trip_case_leg_tour_key.sql`** is a byte copy of the Booking file (flow D8: the
  Booking migration-only PR merges first, then the Copy Guard passes here).
- **The DM-4.2 orphan query lives in `db/schema_dump.py`** (the nightly run DM-4.2 names), as `SOFT_KEY_CHECKS`: one
  entry per cross-app soft key, first `booking.trip_case_legs (source_system, source_id) -> catalog.v_tour`. It
  returns counts only (rows, rows without a key, orphans); the dump stays "no row values".
- **A check never aborts the dump.** The dump runs every query in one read-only transaction, where any error would
  abort the rest. So each check first asks the catalog whether its table, target and columns exist and are readable
  (`SOFT_KEY_READY_SQL`) and reports `not_applicable` (bk-011 not applied yet) or `no_privilege` instead of running.
  The dump role is the CIS task's `aa_cis_admin`, which reads `catalog.v_tour` (S238 check: 892 rows, no GUC needed)
  and owns `booking.*`.
- **Orphan rate = orphans / rows with a key.** Rows without a key are counted separately (they are the back-fill's
  job, not orphans).
- **Reported, not fatal.** The workflow step summary lists every soft key; orphans > 0 add a `::warning::`
  annotation. The reference Markdown gets a *Soft-key orphans (DM-4.2)* section. The counts are volatile: they are
  dropped from the structural fingerprint (like `est_rows`), so they alone never open a root PR; a status change
  (`not_applicable` → `ok`) does.
