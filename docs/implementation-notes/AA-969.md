# AA-969 — CRM SLO alarms and the load-test identity (Infra part)

## Decisions

- Only free AWS metrics become alarms: the CRM API target group's `RequestCount`, `HTTPCode_Target_5XX_Count` and
  `TargetResponseTime` (`modules/environment/crm_slo.tf`). No custom metric and no metric filter: the S263 alert diet
  removed them (`observability_ecosys.tf`), and a metric filter would be a billed custom metric.
- Two alarms: the 5xx rate (metric math, at least 20 requests in the window, above 2 % in 2 of 3 five-minute windows)
  and the p95 latency (above 1.5 s in 2 of 3 windows). The crm.job lag alarm stays the in-app `jobs_starved` check of
  AA-Partner (> 900 s), not a CloudWatch alarm.
- Per-route-group latency, status classes, crm.job lag and fair-share refusals are saved Logs Insights queries
  (`aws_cloudwatch_query_definition`): free to keep, billed only per GB scanned when run.
- The bounded load test signs in as one new e2e user, `e2e-test-crm-lt-agent` (`tools/identity/crm_e2e_users.json`),
  a member of the 50 load-test agencies only, so the existing e2e agency picker does not change.

## Changed

- `modules/environment/crm_slo.tf` (new): 2 alarms, 4 saved queries, all counted by `crm_edge_on`/the log group.
- `tools/identity/crm_e2e_users.json`: one entry `lt` / `agent` (also a recipient of the e2e mailbox receipt rule).

## Tradeoffs

- ALB latency is per target group, not per route: the alarm is the all-routes p95 (1.5 s, the slowest group's
  target); each group's own target is checked by the load test thresholds and the saved query.
- Cost: 3 alarm metrics x 0.10 USD = 0.30 USD per month. The receipt-rule recipient and the queries cost nothing.

- Apply with the normal Terraform Apply Dev; the plan should show 2 alarms + 4 query definitions created and the
  e2e mailbox receipt rule updated in place (one recipient more), nothing destroyed.
