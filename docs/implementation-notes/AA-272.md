# AA-272 — VPC Link V1 + NLB (account 2 only)

## Decisions
- NLB, its SG, target group, attachment, listener, and the `aws_api_gateway_vpc_link`
  all live in `modules/alb/vpc_link.tf` (new file, same module as the ALB) — per
  spec, since the module already owns `aws_lb.main` and the VPC Link's only job
  is to front that same ALB.
- Target group attachment (`target_id`) references `aws_lb.main.arn` directly
  instead of the literal ALB ARN string given in the ticket — same module, so
  the resource reference is authoritative and avoids drift if the ALB is ever
  recreated. Verified it resolves to the same ARN
  (`arn:aws:elasticloadbalancing:us-west-1:005097885195:loadbalancer/app/aa-cis-dev-alb/736e3d6857cade37`).
- NLB subnets wired via `var.private_subnet_ids` (new module input, sourced from
  `module.vpc.private_subnet_ids` in `accounts/aa365/main.tf`) rather than the
  two hardcoded subnet IDs in the ticket — those IDs are exactly what that
  output already returns, and using the output avoids a second hardcoded copy.
- New SG ingress CIDR wired via `var.vpc_cidr_block` (new module input, sourced
  from the existing root `var.vpc_cidr`, default `10.2.0.0/16`) instead of a
  hardcoded literal — same reasoning.
- `alb_dns_name` variable in `modules/api_gateway` is kept (not deleted) even
  though after this change no `aws_api_gateway_integration.uri` in that module
  references it anymore — `accounts/aa365/main.tf` still assigns it in the
  `module "api_gateway"` call and grep showed no reason to break that wiring.
  Per explicit instruction: don't delete if still referenced elsewhere.

## Changed
- `modules/alb/variables.tf`: +`private_subnet_ids`, +`vpc_cidr_block`.
- `modules/alb/vpc_link.tf` (new): `aws_security_group.nlb` (ingress tcp/80 from
  `var.vpc_cidr_block`, egress all), `aws_lb.vpc_link_nlb` (internal network LB,
  `var.private_subnet_ids`), `aws_lb_target_group.vpc_link_nlb` (target_type=alb,
  TCP/80, TCP health check), `aws_lb_target_group_attachment.vpc_link_nlb_to_alb`
  (target_id = `aws_lb.main.arn`, port 80), `aws_lb_listener.vpc_link_nlb`
  (TCP/80 → the above TG), `aws_api_gateway_vpc_link.this` (target_arns =
  [`aws_lb.vpc_link_nlb.arn`]).
- `modules/alb/outputs.tf`: +`nlb_dns_name`, +`vpc_link_id`.
- `modules/api_gateway/variables.tf`: +`nlb_dns_name`, +`vpc_link_id` (both
  required, no default — every environment wiring this module must supply them).
- `modules/api_gateway/main.tf`: all 8 `aws_api_gateway_integration` resources
  (`root`, `health`, `auth`, `admin`, `content`, `docs`, `openapi`, `v1`) gained
  `connection_type = "VPC_LINK"` + `connection_id = var.vpc_link_id`, and their
  `uri` domain changed from `var.alb_dns_name` to `var.nlb_dns_name` (path/proxy
  suffix unchanged). This covers every route, not just `/v1/*`.
- `accounts/aa365/main.tf`: `module "alb"` call gained `private_subnet_ids =
  module.vpc.private_subnet_ids`, `vpc_cidr_block = var.vpc_cidr`. `module
  "api_gateway"` call gained `nlb_dns_name = module.alb.nlb_dns_name`,
  `vpc_link_id = module.alb.vpc_link_id`; existing `alb_dns_name` assignment
  left untouched.

## Tradeoffs
- Ran `terraform fmt -recursive` once, which reformatted whitespace across the
  whole repo — including account-1's root `main.tf`, `envs/dev/terraform.tfvars`,
  and unrelated modules (`ecs`, `lambda`, `monitoring`, `rds`, `step_functions`,
  `waf`, `eventbridge`). Caught via `git status` before validate/plan and
  reverted everything outside the AA-272 file set with `git checkout --`.
  Lesson: use `terraform fmt -diff <explicit file list>` for scoped changes in
  this repo, not `-recursive`, since account 1 and account 2 share top-level
  `modules/`.
- Did not add a `vpc_id` input to the NLB target group separately — reused the
  module's existing `var.vpc_id` (same VPC the ALB is already in), no new
  variable needed there.

## Follow-up fix (feature/aa-272-fix-apply-errors)
First real `terraform apply` (run locally under `aa365-admin` admin creds, not
CI) failed partway through, after creating the NLB and its SG but before the
target group. Root-caused via read-only recon (live traffic unaffected —
root integration was still `connectionType=INTERNET`; NLB left `tainted` in
state; target group never existed in AWS or state):

1. `aws_lb_target_group.vpc_link_nlb` health check used `protocol = "TCP"`
   with `target_type = "alb"` — AWS rejects this combination; ALB-type targets
   require an HTTP/HTTPS health check. Fixed: `protocol = "HTTP"`,
   `path = "/health"` (the ALB already serves `/health`, confirmed in
   `modules/alb/main.tf`'s own target group health check).
2. `aa-cis-dev-role`'s inline policy only had `elasticloadbalancing:Describe*`/
   `Get*` (Sid `ELBDescribe`) — no create/modify/delete on ELB. Added a new
   Sid `ELBManageVpcLinkNLB` in `accounts/aa365/cicd.tf` (not touching
   `ELBDescribe`) covering NLB/target-group/listener/tag lifecycle actions.
   Didn't actually block the failed apply (that ran under `aa365-admin` admin
   creds, not this CI role) but needed fixing regardless so a future CI-driven
   apply doesn't hit it as error #3.

Second real `terraform plan` after both fixes: NLB shows tainted → `+/-`
replace (expected, zero dependents yet), target group → clean `+ create`
with the HTTP health check, `cicd_inline` policy → `~ update in-place` (not
replace). 6 add / 10 change / 2 destroy, fully reconciled — no unexpected
resource in the diff.

## Incident + rollback (feature/aa-272-revert-state-drift)
`terraform-apply.yml` ran clean (`4 added, 9 changed, 1 destroyed`, matching
plan exactly) after the NLB untaint. But live verification across all 8
routes showed most returning 500, and the NLB's target health showed the ALB
as `unhealthy` (`Target.FailedHealthChecks`). Root cause, found via WAF logs
(`aws-waf-logs-aa-cis-dev`): the ALB's WAF Web ACL has a `GeoBlockNonAllowed`
rule (priority 2, blocks any country not in a 10-country allow-list). Traffic
through the NLB uses private VPC IPs (e.g. `10.2.11.27`, the NLB's own ENI)
which WAF can't geolocate — labeled country `XX` — and `XX` isn't on the
allow-list, so the rule blocks it. This blocked the NLB's own health checks
(`User-Agent: ELB-HealthChecker/2.0`, `uri: /health`) as well as all real
traffic proxied through that path. Previously (connectionType=INTERNET),
traffic reached the ALB with a public source IP that resolved to an allowed
country, so this gap was invisible until the VPC Link cutover.

Emergency response: patched all 8 `aws_api_gateway_integration` resources
directly via `aws apigateway update-integration` (bypassing Terraform,
given live impact) back to `connectionType=INTERNET` + the ALB's public DNS,
then `aws apigateway create-deployment` to activate. Confirmed `/health`,
`/openapi.json`, `/docs`, `/admin/tenants` all back to 200 within ~1min
(brief lingering 500s were propagation lag, not a persistent issue).

This PR closes the resulting Terraform/live drift: reverted all 8
integrations in `modules/api_gateway/main.tf` back to `alb_dns_name`, no
`connection_type`/`connection_id` — matching the manual rollback exactly.
`modules/alb/vpc_link.tf` (NLB, its SG, target group, attachment, listener,
VPC Link) and the `nlb_dns_name`/`vpc_link_id` variables are all kept as-is,
untouched in both code and AWS — ready for a retry once the WAF gap is
fixed. That WAF fix (new `aws_wafv2_ip_set` for the VPC CIDR + a priority-0
allow rule in `modules/waf`) is out of scope here — separate PR, not urgent
since live traffic no longer depends on it.
