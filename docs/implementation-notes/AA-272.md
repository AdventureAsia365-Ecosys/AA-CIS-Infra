# AA-272 — VPC Link V1 + NLB (account 2 only)

## Decisions
- NLB, its SG, target group, attachment, listener, and the `aws_api_gateway_vpc_link`
  all live in `modules/alb/vpc_link.tf` (new file, same module as the ALB) — per
  spec, since the module already owns `aws_lb.main` and the VPC Link's only job
  is to front that same ALB.
- Target group attachment (`target_id`) references `aws_lb.main.arn` directly
  instead of the literal ALB ARN string given in the ticket — same module, so
  the resource reference is authoritative and avoids drift if the ALB is ever
  recreated. Verified it resolves to the same ARN
  (`arn:aws:elasticloadbalancing:us-west-1:005097885195:loadbalancer/app/aa-cis-dev-alb/736e3d6857cade37`).
- NLB subnets wired via `var.private_subnet_ids` (new module input, sourced from
  `module.vpc.private_subnet_ids` in `accounts/aa365/main.tf`) rather than the
  two hardcoded subnet IDs in the ticket — those IDs are exactly what that
  output already returns, and using the output avoids a second hardcoded copy.
- New SG ingress CIDR wired via `var.vpc_cidr_block` (new module input, sourced
  from the existing root `var.vpc_cidr`, default `10.2.0.0/16`) instead of a
  hardcoded literal — same reasoning.
- `alb_dns_name` variable in `modules/api_gateway` is kept (not deleted) even
  though after this change no `aws_api_gateway_integration.uri` in that module
  references it anymore — `accounts/aa365/main.tf` still assigns it in the
  `module "api_gateway"` call and grep showed no reason to break that wiring.
  Per explicit instruction: don't delete if still referenced elsewhere.

## Changed
- `modules/alb/variables.tf`: +`private_subnet_ids`, +`vpc_cidr_block`.
- `modules/alb/vpc_link.tf` (new): `aws_security_group.nlb` (ingress tcp/80 from
  `var.vpc_cidr_block`, egress all), `aws_lb.vpc_link_nlb` (internal network LB,
  `var.private_subnet_ids`), `aws_lb_target_group.vpc_link_nlb` (target_type=alb,
  TCP/80, TCP health check), `aws_lb_target_group_attachment.vpc_link_nlb_to_alb`
  (target_id = `aws_lb.main.arn`, port 80), `aws_lb_listener.vpc_link_nlb`
  (TCP/80 → the above TG), `aws_api_gateway_vpc_link.this` (target_arns =
  [`aws_lb.vpc_link_nlb.arn`]).
- `modules/alb/outputs.tf`: +`nlb_dns_name`, +`vpc_link_id`.
- `modules/api_gateway/variables.tf`: +`nlb_dns_name`, +`vpc_link_id` (both
  required, no default — every environment wiring this module must supply them).
- `modules/api_gateway/main.tf`: all 8 `aws_api_gateway_integration` resources
  (`root`, `health`, `auth`, `admin`, `content`, `docs`, `openapi`, `v1`) gained
  `connection_type = "VPC_LINK"` + `connection_id = var.vpc_link_id`, and their
  `uri` domain changed from `var.alb_dns_name` to `var.nlb_dns_name` (path/proxy
  suffix unchanged). This covers every route, not just `/v1/*`.
- `accounts/aa365/main.tf`: `module "alb"` call gained `private_subnet_ids =
  module.vpc.private_subnet_ids`, `vpc_cidr_block = var.vpc_cidr`. `module
  "api_gateway"` call gained `nlb_dns_name = module.alb.nlb_dns_name`,
  `vpc_link_id = module.alb.vpc_link_id`; existing `alb_dns_name` assignment

## Tradeoffs
- Ran `terraform fmt -recursive` once, which reformatted whitespace across the
  whole repo — including account-1's root `main.tf`, `envs/dev/terraform.tfvars`,
  and unrelated modules (`ecs`, `lambda`, `monitoring`, `rds`, `step_functions`,
  `waf`, `eventbridge`). Caught via `git status` before validate/plan and
  reverted everything outside the AA-272 file set with `git checkout --`.
  Lesson: use `terraform fmt -diff <explicit file list>` for scoped changes in
  this repo, not `-recursive`, since account 1 and account 2 share top-level
  `modules/`.
- Did not add a `vpc_id` input to the NLB target group separately — reused the
  module's existing `var.vpc_id` (same VPC the ALB is already in), no new

## Follow-up fix (feature/aa-272-fix-apply-errors)
First real `terraform apply` (run locally under `aa365-admin` admin creds, not
CI) failed partway through, after creating the NLB and its SG but before the
target group. Root-caused via read-only recon (live traffic unaffected —

   Sid `ELBManageVpcLinkNLB` in `accounts/aa365/cicd.tf` (not touching
   `ELBDescribe`) covering NLB/target-group/listener/tag lifecycle actions.
   Didn't actually block the failed apply (that ran under `aa365-admin` admin
   creds, not this CI role) but needed fixing regardless so a future CI-driven
   apply doesn't hit it as error #3.

Second real `terraform plan` after both fixes: NLB shows tainted → `+/-`
replace (expected, zero dependents yet), target group → clean `+ create`
with the HTTP health check, `cicd_inline` policy → `~ update in-place` (not

## Incident + rollback (feature/aa-272-revert-state-drift)
`terraform-apply.yml` ran clean (`4 added, 9 changed, 1 destroyed`, matching
plan exactly) after the NLB untaint. But live verification across all 8
routes showed most returning 500, and the NLB's target health showed the ALB
as `unhealthy` (`Target.FailedHealthChecks`). Root cause, found via WAF logs
(`aws-waf-logs-aa-cis-dev`): the ALB's WAF Web ACL has a `GeoBlockNonAllowed`
rule (priority 2, blocks any country not in a 10-country allow-list). Traffic
through the NLB uses private VPC IPs (e.g. `10.2.11.27`, the NLB's own ENI)
which WAF can't geolocate — labeled country `XX` — and `XX` isn't on the
allow-list, so the rule blocks it. This blocked the NLB's own health checks
(`User-Agent: ELB-HealthChecker/2.0`, `uri: /health`) as well as all real
traffic proxied through that path. Previously (connectionType=INTERNET),
traffic reached the ALB with a public source IP that resolved to an allowed
country, so this gap was invisible until the VPC Link cutover.

Emergency response: patched all 8 `aws_api_gateway_integration` resources
directly via `aws apigateway update-integration` (bypassing Terraform,
given live impact) back to `connectionType=INTERNET` + the ALB's public DNS,
then `aws apigateway create-deployment` to activate. Confirmed `/health`,
`/openapi.json`, `/docs`, `/admin/tenants` all back to 200 within ~1min
(brief lingering 500s were propagation lag, not a persistent issue).

This PR closes the resulting Terraform/live drift: reverted all 8
integrations in `modules/api_gateway/main.tf` back to `alb_dns_name`, no
`connection_type`/`connection_id` — matching the manual rollback exactly.
`modules/alb/vpc_link.tf` (NLB, its SG, target group, attachment, listener,
VPC Link) and the `nlb_dns_name`/`vpc_link_id` variables are all kept as-is,
untouched in both code and AWS — ready for a retry once the WAF gap is
fixed. That WAF fix (new `aws_wafv2_ip_set` for the VPC CIDR + a priority-0
allow rule in `modules/waf`) is out of scope here — separate PR, not urgent
since live traffic no longer depends on it.

## Việc #1 — WAF allow rule for internal VPC Link traffic (branch feature/aa-272-waf-vpc-allow)

Closes the WAF gap flagged in the "Incident + rollback" section above — this
is the deferred fix that let `GeoBlockNonAllowed` block the NLB's own health
checks (private VPC IP → country `XX` → not on allow-list).

### Decisions
- `modules/waf` is a shared module — account-1 root `main.tf` (867490540162,
  decommissioned per AA-271) still calls it. Rather than hardcode the new
  rule, added `var.vpc_allow_cidr` (`string`, default `null`) — same
  parameterization pattern as `rate_limit`/`geo_allowed_countries`. The new
  `aws_wafv2_ip_set.vpc_allow` and the priority-0 `rule` block are both
  count/for_each-gated on `var.vpc_allow_cidr != null`, so the account-1 root
  (which doesn't pass this var) gets `count = 0` / an empty `dynamic "rule"`
  — no new resource, no rule, automatically. Avoids ever auto-creating an
  ip_set scoped to account-2's VPC CIDR if anyone accidentally re-runs
  plan/apply against the decommissioned account-1 state.
- `accounts/aa365/main.tf`'s `module "waf"` call passes
  `vpc_allow_cidr = var.vpc_cidr` (reusing the existing `10.2.0.0/16` root
  variable, not a repeated literal).
- New rule uses a `dynamic "rule"` block (not a static one) since it needs
  to be conditionally emitted — the other 3 rules stay as static blocks,
  matching the existing style exactly rather than converting everything to
  dynamic blocks.
- New rule's `visibility_config.metric_name = "VpcLinkInternalAllow"` — own
  metric name, doesn't reuse any existing rule's CloudWatch metric.

### Plan-diff caveat verified before apply
`aws_wafv2_web_acl.main`'s `rule` attribute is schema-typed as a set of
nested blocks, not an ordered list — adding one new rule caused Terraform's
plan renderer to show `AWSManagedRulesCommonRuleSet` (priority 3) as
`- rule` / `+ rule` with byte-identical content (removed-then-re-added).
Confirmed this is a rendering artifact, not a real destroy: WAFv2's
`UpdateWebACL` API always submits the complete `Rules` array in one call
(no per-rule patch endpoint), so this "update in-place" is one atomic API
call carrying all 4 rules — `RateLimit1000` and `GeoBlockNonAllowed` (the
two rules actively gating production traffic) didn't even appear in the
diff (unchanged, hidden). Top-level plan: `1 to add, 1 to change, 0 to
destroy` — no destroy anywhere.

### Two AWS CLI mechanics bugs hit during execution (not root cause, but slowed
the response and worth remembering for next time)
1. `aws apigateway update-integration --patch-operations op=...,value=<uri
   with {proxy} in it>` — the CLI's shorthand parser treats `{`/`}` in a
   plain string value as JSON-shorthand syntax and throws
   `ParamValidation: Expected ',', received '}'`. Hit on all 4 proxy routes
   (`auth`, `admin`, `content`, `v1` — anything with a `{..._proxy}` path
   segment) on both the forward cutover and the rollback. Fix: write the
   patch document to a JSON file and pass `--patch-operations file://...`
   instead of inline shorthand — bypasses the shorthand parser entirely.
2. `op=remove,path=/connectionId` — rejected by the API itself with
   `BadRequestException: Invalid patch path /connectionId` (not a CLI
   parsing issue this time, a real API constraint: `connectionId` can't be
   *removed* via patch, even though it was fine to *add* via `replace`
   during the forward cutover). Fix: `op=replace,path=/connectionId,value=""`
   instead of `remove`. This means the emergency rollback command block
   written in the STEP-0 prep message (using `op=remove`) would **not**
   have worked as written — worth fixing in any future prep for this same
   operation.

## Root-cause investigation of the HTTP 000 hang (read-only, no resources changed)

### What was checked, live (not Terraform code, not memory)
1. **NLB/ALB access logs + VPC Flow Logs**: all disabled.
   `access_logs.s3.enabled=false` on both NLB and ALB,
   `connection_logs.s3.enabled=false` on ALB, `aws ec2 describe-flow-logs`
   returned `[]` (no VPC Flow Logs configured anywhere in the VPC). No
   traffic-level log exists to inspect this hop directly.
2. **API Gateway execution logs (stage `dev`)**: disabled —
   `get-stage` shows `methodSettings: {}`, and no
   `API-Gateway-Execution-Logs*` log group exists. No visibility from the
   API Gateway side into what happened on the backend call.
3. **Integration timeout**: all 8 routes use the default `timeoutInMillis
   = 29000`, unchanged. Own test gap: verification curls used
   `--max-time 10`, shorter than the 29s integration timeout, so it's
   unknown whether API Gateway would have eventually returned its own
   `504` at 29s or hung indefinitely — the `curl: (28) Operation timed
   out ... 0 bytes received` only proves curl gave up at 10s, not what
   API Gateway itself does past that point.
4. **NLB/ALB protocol config**: NLB listener `TCP/80` → NLB target group
   `TCP/80` (health check `HTTP /health`) → ALB listener `HTTP/80` +
   `HTTPS/443`, integration URIs use `http://` (port 80) — protocol chain
   consistent end to end. **`proxy_protocol_v2.enabled = false`** on the
   NLB target group — the leading suspect (PROXY protocol header sent by
   NLB but not understood by ALB) is **ruled out**: it's off, so no PROXY
   protocol wrapper is sent at all. `preserve_client_ip.enabled = true` —
   confirmed via `grep` that this was never set in
   `modules/alb/vpc_link.tf` (AWS's own default for `target_type = alb`,
   not something this session configured) — noted as a difference in
   connection-handling semantics but not confirmed as causal from CLI
   evidence alone.
5. **Security groups, live**: NLB SG (`sg-019193b854e9be1c3`) — ingress
   `10.2.0.0/16` on TCP/80, egress all. ALB SG (`sg-05b3f6475701b468d`) —
   ingress `0.0.0.0/0` on 80/443 (matches known tech debt, "Should know"
   in the VPC Link section above), egress all. No SG rule blocks
   NLB→ALB in either direction. AZ coverage: NLB and ALB both span
   `us-west-1a`/`us-west-1c` — `load_balancing.cross_zone.enabled=false`
   at the NLB level doesn't create an AZ gap since both LBs are present
   in both AZs (target registered as `AvailabilityZone: all`, `healthy`).

### Key finding (not one of the 5 requested checks, but decisive): WAF logs
during the actual incident window
Queried `aws-waf-logs-aa-cis-dev` for the exact cutover→rollback window
(11:50–11:55, covering deploy `7o8akt` at 11:50:48 through rollback deploy
`ipv4f0` at 11:54:04), not the pre-cutover gate-check window used earlier.
Found only the routine NLB health-check `ALLOW` traffic (10.2.10.131 /
10.2.11.27, 30 each) plus a handful of public-IP `ALLOW` entries for
`/openapi.json`, `/docs`, `/admin/tenants`, `/health` — but those all
correspond to the **post-rollback** verification curls (their source IPs
are AWS-public-range, matching `connectionType=INTERNET` behavior, and
their timing matches the 200/200/403 recovery already logged above). **Zero
log entries — ALLOW or BLOCK — exist for the actual outage sub-window**
while `connectionType=VPC_LINK` was live and the timeout curls were
running. This means those requests never reached the ALB/WAF evaluation
stage at all — the hang is localized to the API Gateway (VPC Link ENI) →
NLB hop, or within the NLB itself, before traffic would reach the ALB.
This rules out WAF, ALB routing, and the backend ECS/target as the cause
of *this* hang (separate from incident #1's WAF block, which did show up

### Synthesis
| Hypothesis | Verdict |
|---|---|
| `proxy_protocol_v2` mismatch (NLB sends, ALB can't parse) | **Ruled out** — disabled on the NLB target group, no PROXY protocol header sent |
| TCP vs TLS protocol mismatch | **Ruled out** — TCP/80 end to end, matches ALB's HTTP:80 listener |
| Security group blocking NLB→ALB | **Ruled out** — both directions permissive, no deny rule |
| Cross-AZ mismatch (NLB `cross_zone.enabled=false`) | **Unlikely** — both LBs present in both AZs |
| Integration timeout too short | **Not the cause of the symptom, but a gap in the verification test** — never confirmed what happens past 10s up to the 29s integration timeout |
| Hang localized to API Gateway VPC-Link-ENI ↔ NLB hop | **Strongest evidence-backed finding** (zero WAF log entries during the outage sub-window) — but the specific root cause *within* that hop is still unknown; no log source currently covers it |
| `preserve_client_ip=true` (AWS default for `target_type=alb`) | **Inconclusive** — real config difference worth understanding, not confirmed causal |

### Step 7: root cause (full, unhurried log analysis post-stabilization)
Downloaded and grepped the actual ALB access logs (S3, not just CW Logs
Insights) covering the full incident window
(08:18:54Z-08:27:16Z): **zero entries for any of the 6 failing test
requests** — only the NLB's own recurring `/health` checks
(`ELB-HealthChecker/2.0`) appear, 73 of them, all `200` in ~5ms. The actual
client requests never reached the ALB at all.

Traced further upstream via VPC Flow Logs on the NLB's subnets, widening
the filter to catch any source hitting the NLB's two ENI IPs
(`10.2.10.131`, `10.2.11.27`) on port 80 — not just `10.2.*` sources.
Found 39 matching flows in the incident window, **100% `REJECT`**, **100%
sourced from `172.16.0.0/x`** addresses (e.g. `172.16.102.113`,
`172.16.103.128`, ~36 distinct IPs) — a completely different range from
the project's own VPC CIDR (`10.2.0.0/16`). These are API Gateway's own
VPC Link connection source IPs (AWS-managed address space for the
VPC Link → NLB path, not part of the customer VPC).

**Root cause**: `aws_security_group.nlb` (`sg-019193b854e9be1c3`,
`modules/alb/vpc_link.tf`) has exactly one ingress rule — tcp/80 from
`var.vpc_cidr_block` (`10.2.0.0/16`) only. That CIDR is correct for the
NLB's *own* health-check traffic to the ALB (source `10.2.x.x`, which is
why target health stayed "healthy" the entire incident — health checks
were never blocked) but **does not cover the actual VPC Link → NLB client
path**, whose source IPs come from AWS's API-Gateway-managed range
(`172.16.0.0/x`), outside the customer VPC entirely. Every real proxied
request was silently dropped at the NLB's security group before ever
reaching WAF or the ALB — a different, previously-undiscovered gap from
the `GeoBlockNonAllowed`/WAF issue fixed in việc #1 (that fix was
necessary but not sufficient; this SG rule sits one hop earlier in the
same path and was never exercised by a full 8/8 cutover until now).

Open question this doesn't answer: why did the very first single-route
probe (`/health` via deployment `hwerw8`) succeed at 08:15:37Z through
this same SG? Leading hypothesis: security-group association on NLBs is
eventually consistent, and that first request landed inside a brief
propagation window before enforcement caught up — unconfirmed, would need
an AWS support case or a second isolated single-route test with tighter
instrumentation to verify. Not investigated further here since the
customer-facing question (why did the full cutover fail) is answered with
direct log evidence and doesn't depend on resolving this side question.
