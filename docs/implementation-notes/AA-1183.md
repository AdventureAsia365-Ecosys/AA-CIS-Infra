# AA-1183 — ACM certificate expiry alert (part 1, S296)

The register v2 half of part 1 is in the root repo (`docs/implementation-notes/AA-1183.md` there). Part 2 (S297): the
weekly rotation check and its read-only metadata permission.

## Decisions

- **EventBridge ACM events, not the `DaysToExpiry` CloudWatch metric.** Both are free, but an alarm per certificate
  needs one alarm per ARN (10 today, 0.10 USD each per month) and a new one for every certificate; the event rule
  covers every current and future certificate of the region at 0 USD.
- **Alert on chosen days, not daily.** ACM sends "Approaching Expiration" every day from 45 days before expiry by default
  (account setting DaysBeforeExpiry). The rule matches only `var.acm_expiry_alert_days` (default 30, 14, 7, 3, 1); "Renewal Action
  Required" and "Expired" always alert.
- **us-east-1 is forwarded, not alerted there.** The alerts topic lives in us-west-1 and SNS is not a cross-region
  EventBridge target. The existing `aa-sec-<env>-events-forwarder` role already allows PutEvents on the us-west-1
  default bus, so the forward rule adds no IAM. One local rule alerts for both regions.
- **`aa-sec-*` names** so the CI apply grant (rules in every region) and the alerts topic policy already admit them:
  no bootstrap apply.
- **Severity ticket** (AA-1171): a month of lead time, handled in working hours.
- **Runbook** `docs/ops/runbooks/certificate-expiry.md` (root, new; key `cert_expiry` in `alarm_runbooks.tf`).

## Tradeoffs

- The alert days are a Terraform variable, not an admin-page setting (the S279 rule for app thresholds): Infra has no
  admin settings store; moving it to one is a follow-up.
- No end-to-end e-mail test before a real event: `aws.acm` is a reserved source a caller cannot put. Proof is
  `test-event-pattern` on both live rules (sec_alert_check.py) plus `list-targets-by-rule`.
