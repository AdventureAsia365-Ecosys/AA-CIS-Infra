# AA-805 (S245): read-only DB evidence script for TripPlanner AI Phase 0

Script: `db/scripts/aa805_ai_guards_read.py`, run by DB Migrate `mode=run-script`. Test:
`db/tests/test_aa805_ai_guards_read.py`. Evidence it feeds: root repo
`docs/audits/2026-10-20-S245-tp-ai-phase0/`.

## Decisions

- **DB Migrate run-script, not ECS exec.** Since X1 S18/S19 the CIS container runs as `cis_app`, which cannot read
  `tripplanner.*`. The master reads it through its `tp_owner` membership (rl-001). `READ_ONLY = True`, so the idle check
  only reports and the run does not wait for job tables.
- **The AA tenant is named in the SQL, not only through `app.tenant_id`.** The master is a member of `cis_owner`, and
  `published_tours` has a `cis_owner` policy `USING true` (CIS 245). Under the master, `set_config('app.tenant_id')`
  alone would show every tenant's tours, which is not what the TripPlanner Lambda (role `tripplanner`, policy
  `tenant_isolation` only) sees. Every `published_tours` read therefore has `pt.tenant_id = $1` and still sets
  `app.tenant_id` in one transaction, like `x1_photo_itinerary_parity.py`. A unit test checks the filter is in all four
  queries.
- **The returned destination ids are hard-coded** (725 distinct ids from the S245 live run of the 30-query set). A
  script cannot read the root repo or S3. The script prints a 16-character sha256 of the sorted set, and the test pins
  it, so the run's output can be tied to `aa805_search_results.json`.
- **The rule checked equals TripPlanner `search.py` ACTIVE_TOUR_SQL** (`pt.tour_id::text = c.source_tour_id`,
  `master_status = 'active'`, `deleted_at IS NULL`), plus `c.embedding IS NOT NULL`, because the semantic path only ranks
  embedded components. All 30 live queries came back `ranking: semantic`, so the keyword fallback (which does not
  require an embedding) is not in play.
- **Negative control:** destinations whose embedded components all belong to tours that are not active (inactive,
  trashed, soft-deleted, another tenant, or no `published_tours` row). The check is only meaningful when that count is
  above 0 and none of them was returned.
- **Cache-test candidates added (section 4).** In S245 the live `/narrate` came back `source: master` on every trip
  tried (4 trips, 12 components, 6 countries). Master text is never cached (`CACHEABLE_SOURCES = (llm, mixed)`), so the
  live cache-hit proof needs a component whose tour day has no AA master text. The script lists up to 5 ids for each of
  two kinds: `no_structured_text` (`aa_itineraries` NULL or without any `Day N` header, so `parse_days` returns {}) and
  `own_day_missing` (no header for the component's own day, and the tour text does not contain the component name, so
  `resolve_days` cannot redirect). The second kind approximates TripPlanner's `_mentions` (exact substring on
  lower case, no accent or punctuation folding). Treat it as a candidate list, not a guarantee.

## Changed

- New `db/scripts/aa805_ai_guards_read.py`, new `db/tests/test_aa805_ai_guards_read.py`, and a paragraph in
  `db/scripts/README.md`. No migration, workflow, Terraform or IAM change.

## Tradeoffs

- Hard-coding 725 UUIDs makes the file long (about 240 lines of ids). The alternative, passing them as a workflow
  input, would need a change to the DB Migrate workflow. That is a riskier change than a long, reviewable constant.
- The day-header regex mirrors `master_content._DAY_HEADER` in a PostgreSQL ARE
  (`(^|\n)[[:space:]]*day[[:space:]]*0?N[[:space:]]*[:–—-]`, case-insensitive). Python's `\s` and PostgreSQL's
  `[[:space:]]` differ only on exotic whitespace. That gap is acceptable for a candidate list.

## Should know

- The SQL was run against a throwaway local PostgreSQL 16 loaded with stub tables (the column names come from
  `docs/architecture/db-schema-reference.md`, verified 19/10) in a `default_transaction_read_only` session. Expected
  results matched. The clean set gave PASS. A set with one inactive-only destination and one not-embedded destination
  gave FAIL and named both. "Day 13" did not match day 3, "Day 01 -" matched day 1, and NULL or unstructured text was
  classed `no_structured_text`.
- The output is aggregates, catalog ids and statuses only: no narration text, customer data or DSN.
- A successful run-script also dispatches DB Schema Dump and the DB Isolation Probe (workflow behaviour). Neither
  writes anything for a read-only script.
