# AA-1054 — pilot-day E2E identity tool (S297 slice, lane l9-pilot-fence)

## Decisions

- `tools/identity/e2e_identity_fence.py`, beside the WORKFORCE bootstrap tool, reusing its Dev facts (profile, region,
  expected account, pool id) and its output redactor.
- The address list is the trigger's own `E2E_*_EMAIL` constants (`workforce.py`, read with `ast`: no import, no copy
  to keep in step). `CODES` maps each constant to its root ADR 0006a code; an unmapped constant stops the tool (exit 2)
  and fails the test.
- The pool is read with ListUsers (`email ^= "e2e"`, then an exact domain check), like the bootstrap tool, so a DRY RUN
  counts no monthly active user. Pool users of the E2E domain that the trigger does not name are listed as `unmapped`
  and disabled by `--apply` too (the CIS and Booking pilot fence refuses the whole domain as well).
- DRY RUN by default; `--apply` disables and signs out (refresh tokens revoked), then reads back; exit 0 only when no
  E2E user is left enabled. It never deletes a user (undo = AdminEnableUser).
- Output names codes and masked labels only; every address and username is registered with the redactor, so an AWS
  error message cannot print one either.

## Changed

- New tool, its tests (`tools/identity/tests/test_e2e_identity_fence.py`, botocore Stubber) and a README section. No
  Terraform, no IAM, no resource.

## Tradeoffs

- The lane brief said 11 identities; the trigger names 12 addresses (A10, A10a, A10b, A10c, A10d, A10e x3, A10e-2,
  A10f, A10g, A10h). The tool lists what the trigger holds.

## Should know

- Run on the pilot day only, after the CIS setting `cis.platform.pilot_e2e_fence` is on (root runbook
  `docs/ops/runbooks/pilot-agency-onboarding.md`, "Pilot day"). Never run in a lane.
